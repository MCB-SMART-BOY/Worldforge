# 《万构界·驭器卷》设定细化

## 一、卷定位

《驭器卷》负责把系列拉回文明深处，回答一个更沉重的问题：

**文明如何继续驭使古老重器，而不沦为少数人的私有记忆。**

这卷不能写成“新道替旧道”的简单优越叙事。
它真正要写的是：

- 为什么重器值得敬畏
- 为什么传奇会成为结构性风险
- 为什么“只有我会修”既是功勋也是病根

### 卷级真正难题
《驭器卷》不是去证明“旧道落后”，而是去证明：
**如果古器永远只能靠传奇维护，那么文明越敬畏它，就越把未来锁进少数人的记忆里。**

---

## 二、时代与宿域

### 1. 时间位置
同样发生在第七时代，但视角更靠近古史沉积之处。

### 2. 主要宿域
主场在**原生重器宿域**，并向**守制平台宿域**与**协阵扩域宿域**外溢。

### 3. 时代压力
- 古器还在支撑新世界
- 维护者代际更替开始断层
- 构建、调试、发布依赖大量口传与经验
- 外部系统越来越多地经由桥梁调用重器

---

## 三、核心器、阵、门

### 1. 核心项目：玄枢
定位为：
**一套长期承担高性能计算、设备控制或关键运行职责的重器内核。**

它不是一次性程序，而是被无数后来系统包裹、调用、适配、迁移过的古器母核。

### 2. 玄枢的结构形态
- `xuanshu-core`：重器核心
- `xuanshu-adapter`：外接适配层
- `xuanshu-probe`：观象与剖解工具
- `xuanshu-shell`：守门者使用的运维与诊断入口

### 3. 主对象层级推进
- 起卷主对象：器
- 中段主对象：阵
- 卷尾主对象：门

### 4. 卷内真正的产物
不是把玄枢整体推翻重写，而是：
- 把真正危险的边界写清
- 把口传秘义转成可传的说明
- 建立能让后来者逐步接近核心的梯子
- 证明“接火”可以是一条阶梯，而不必永远是宗匠私授

---

## 四、主道与辅道

### 1. 主道
**驭器之道**

### 2. 辅道
- 明契之道：逼迫旧核边界显形
- 守序之道：提供组织化维护秩序
- 简阵之道：让重器面对新式系统协作压力

### 3. 主相与次相
- 主相：式、流
- 次相：史、契

### 4. 典型共构关系
- 驭器—明契
- 驭器—简阵

## 五、角色阵型

### 1. 主角位
古器门下学徒或长期跟着重器打交道的年轻驭器者。
他尊重力量，也容易把掌握核心误认为终极价值。

### 2. 镜像者位
传奇宗匠。
救过整个时代，人人敬畏，却始终没有把火真正传下去。

### 3. 守门者位
现任核心维护者。
他背着太多旧史与现实代价，以至于很难再相信别人接得住。

### 4. 同门者位
来自明契或守序之道的协作者。
他不断追问：哪些经验必须写明，哪些边界必须立住。

### 5. 使用者位
真正依赖玄枢活下去的一线系统、设备操作者或平台调用方。
他们最怕重器停火，却也最常被迫接受“你们别问为什么”。

### 6. 继承者位
刚刚进入古器院的新构师。
他不是不聪明，而是根本没有进入知识阶梯的入口。

### 7. 观象者位
最懂 crash、dump、profile、trace 的人。
他能从碎裂现象里看见古器真实的流。

### 8. 渡桥人位
负责 wrapper、adapter、兼容桥与边界隔离的人。
他既怕动太少，也怕动太猛。

### 9. 失传者位
可能是一位已经故去或彻底离场的旧驭器者，只留下残缺石录、危险注记和未竟桥梁。
他的空位本身就是本卷最直接的警告：古器之火已经不是“能不能更强”，而是“会不会断在这一代”。

### 10. 诱惑者位
强调“重器不能停、谁都别乱碰”的权力代表。
他不断把维护风险锁回少数人手里。

## 六、主要矛盾与病理

### 1. 表层冲突
- 构建流程只靠旧人记忆
- ABI / 生命周期 / 手工资源管理充满陷阱
- 一次意外就可能牵动大片系统
- 任何人想改旧器都像触犯禁律

### 2. 中层冲突
- 重器依赖英雄式维护
- 门内把“能掌握秘义”当作身份资本
- 外部系统不断叠桥，重器却没有同步写清边界

### 3. 深层冲突
主角越成功地驭使重器，就越可能成为那个“只有他知道怎么修”的新宗匠。

### 4. 主病理
- 乱流
- 断史
- 黑箱化
- 解释权垄断
- 古器系缚

### 5. 主角最容易犯的错
- 崇拜控制感
- 用经验代替明文
- 把“别人不懂”当成自己价值的一部分

### 6. 古道与新道的四种冲突机制
- 古器系缚：玄枢早已深嵌进大量新阵，谁都知道危险，却谁都不敢让它停
- 门众惯性：现有维护流程、教材、口传与身份秩序都围着旧驭器法沉积
- 宿域制力：工具链、平台、兼容负担与外部系统共同把重器锁在既有边界里
- 时代病灶错位：旧道仍强，但它最擅长解决的已不是这个时代的主病

### 7. 卷级大悬念
真正的问题不是“主角能不能驭使玄枢”，而是：
**玄枢能不能第一次出现一条不依赖传奇宗匠也可继续运转的接火路径。**

## 七、叙事推进

### 第一段：断火
一次重器事故或险些断火的危机，让主角真正看见古器不只是强大，也极度脆弱。

### 第二段：入骨
主角获得进入更深层核心的机会，看到过去为何留下这些奇异结构、危险习惯与古老门径。

### 第三段：追史
通过石录、冷史、旧版桥梁与事故复盘，主角理解很多”看似糟糕”的设计其实来自真实代价。

### 并行弧线：六维工具链从无到有

驭器卷作为第一卷，承担”文明从蛮荒走向秩序”的起源叙事。C++ 世界的工具链不是一开始就有的——**每一步都是被痛苦逼出来的。** 这段演化不是单一线索，而是**六条维度并行推进**：

**1. 构建系统**：手写命令 → Makefile → autotools（奠基范式）→ CMake → CMake presets+CPack
**2. 版本管理**：文件夹备份 → 手写石录 → RCS → CVS → SVN → Git（石录制度化）
**3. 静态分析**：编译器警告 → lint（最早的静态检查）→ cppcheck → clang-tidy → clangd/LSP（机器理解代码）
**4. 调试诊断**：printf → gdb → valgrind → sanitizer家族 → perf/VTune → 观测制度化
**5. 测试**：无 → “跑一下看看” → 自写脚本 → CppUnit → GoogleTest → CI集成 → 测试文化
**6. 文档**：口传 → README → Doxygen → 文档即代码 → 文档制度

每个维度的”→”都不是技术演进——是一个具体的痛苦逼出了下一步。

### 被时代抛弃但奠基未来的工具（驭器卷独有叙事资源）

这些工具在故事发生时可能已是”遗迹”，但它们的遗产活在每一行现代代码中：

| 工具 | 年代 | 解决了什么 | 为什么被替代 | 在驭器卷中的叙事角色 |
|---|---|---|---|---|
| autotools (autoconf/automake/libtool) | 1990s | 第一次系统解决”在不同Unix上构建同一份代码” | M4宏晦涩、Windows不兼容 | 玄枢早期版本的构建层——考古对象。纪承钧发现三年前的configure脚本，没人知道那些M4宏是什么意思 |
| RCS | 1980s | 发明了”版本”和”diff”的概念 | 只能锁单个文件，不能多人协作 | 玄枢最古的石录残片——“最早的版本。每文件一个。每次只能一个人改。” |
| CVS | 1990s | 发明了”多人协作”和”仓库” | 提交不原子、目录操作弱 | 玄枢第二代石录——迁移到SVN时丢了一部分历史，迁移到Git时又丢了一部分。丢失的历史里藏着秘密 |
| SVN | 2000s | 原子提交、目录版本化 | 集中式——离线不能提交 | 玄枢第三代石录——仍在运行，”因为迁移太危险” |
| `lint` | 1979 | 第一个静态检查工具——比C++本身还老 | 功能被现代工具覆盖 | 考古发现——玄枢建立之初就有人跑过lint，”他们没有坚持下去” |
| ctags/cscope | 1980s-90s | 最早的代码导航——“跳转到定义”的史前形态 | 被LSP取代 | 陆踏痕在旧机器上发现一份ctags索引——“原来前人也在试图让代码可导航” |
| CppUnit | 2000s | 把JUnit的单元测试范式带入C++ | 宏注册机制笨重，被GoogleTest取代 | 玄枢最早的测试尝试——“但只写了三个测试类。因为第四个需要mock，而CppUnit没有mock。” |
| Purify/Insure++ | 1990s | 最早的内存错误检测——商业工具 | 被valgrind/ASAN（开源+编译器集成）取代 | 卫千枢的时代用过Purify——“但他买不起许可证。所以只在最关键的模块上跑过。” |

> **核心写作原则**：这些工具不是”落后技术”，而是”考古层”。它们证明了文明每前进一步都踩在前人的尸体上。在驭器卷中，纪承钧和陆踏痕会不断在玄枢深处发现这些旧工具的痕迹——它们曾经是某人最好的解决方案，现在变成了需要被理解的遗产。**工具可以被替代，但它定义的范式永存。** autotools定义了`configure→make→make install`，CMake做了同样的事但做得更好——但如果没有autotools先定义这个问题，CMake甚至不知道要解决什么。

> **写作铁律（不变）**：工具链的每一次进化都必须由一个具体的事故或痛苦触发。永远不写”有人发明了好办法”——只写”有人被旧办法伤得太深”。

### 第四段：立界
开始做真正困难的事：
- 切出安全边界
- 给危险区写明责任
- 用工具、runbook、适配层与观象替代部分口传
- 把“谁能动哪里、为什么能动、出了事谁负责”第一次写成公共秩序

### 第五段：传火
卷尾不是“主角彻底掌控重器”，而是：
- 重器第一次出现不用传奇也能继续运转的可能
- 主角第一次接受：真正的胜利不是自己成为新宗匠，而是让别人不必再把全部希望押在下一位宗匠身上

## 九、卷尾产物

卷尾最理想的收束应包括：

- 一份可被后来者理解的重器边界说明
- 一组最关键的观象与诊断手段
- 若干安全包裹层与适配层
- 一条不再依赖单一宗匠的接火路径

## 十、跨卷接口

### 1. 与化形卷（直接后继）
驭器卷首先让读者看见”没有工具链的文明如何构建重器”；化形卷作为第二卷，展现”速度文化如何回应蛮荒时代的重量”——Python 的包管理演化史（pip→conda→poetry→uv）本身就是对 C++ “没有包管理”的直接回答。

### 2. 与简阵卷
简阵卷把 C++ 的古器边界问题升级到平台规模——“古器边界是否清楚”从门内问题变成公共问题。Go 的简洁哲学是对 C++ 复杂性的反向回答。

### 3. 与明契卷（终卷回声）
明契卷作为终卷，Rust 的工具链（Cargo）和所有权系统是 C++ 蛮荒时代所有痛苦的最高回答。沈见微的契约被纪承钧的玄枢炸了——不是敌对，是”你在古代世界留下的伤痕，在最终世界成为回声”。

## 主线锚点

### 纪承钧的发现
在整理玄枢旧石录时，纪承钧在玄枢内核最深处发现了一段不属于任何已知语言的残码声明：
`[RESERVED FOR INHERITANCE COVENANT — PENDING RATIFICATION]`
钟守玄说这是从玄枢建立之初就有的。没有人知道它是什么意思。没有人敢删。
纪承钧把它抄进了 runbook 的第一页。旁边标注："待查。可能与玄枢断火的深层原因有关。"

### 钟守玄的沉默
钟守玄知道比他说出来的更多。他见过第一个修补者。不是传说——是很多年前，当他还是年轻的守门者时。那个人来过玄枢。他试图修复一段旧核里的隐式依赖。修到一半，他停下来了。他告诉钟守玄："我修的越多，后来者越不知道这里曾经坏过。他们不知道这里坏过，就永远不会问——它为什么坏。而那个'为什么'，比我修的任何东西都重要。"
钟守玄一直没有把这段话告诉纪承钧。不是因为藏私。是因为他知道这个道理不能被告知——必须被自己发现。

## 深层主线：纪承钧的放弃弧线

### 信念建立
纪承钧在驭器卷中建立了核心信念：有些东西写不清楚——你必须先活过。runbook 是幸存者的地图。他在15章中证明了这个信念的有效性——玄枢从断火到传火。

### 入侵点（卷外——化形卷Ch09-10）
纪承钧带着善意去息壤，写了详尽的迁移 runbook。runbook 在息壤炸了——因为它假设的前提（依赖关系已知）在息壤不成立。

周栖野说："你的 runbook 之所以能工作——不是因为你的方法正确。是因为你所在的世界，信息是可得的。"

### 信念动摇
纪承钧意识到：runbook 需要考古前提。他把玄枢的考古工作当成了理所当然——忘了那是他和钟守玄花了无数年才做到的。把需要前提的方法扔进没有前提的世界，是陷阱。

### 卷内锚点
- Ch07：在玄枢内核中发现残码声明 `[RESERVED FOR INHERITANCE COVENANT]`。钟守玄说从开天辟地就有。
- Ch14-15：钟守玄对纪承钧说："他（修补者）不是不想写完——是他发现了，写完之后，后来者会停止自己思考。"

### 放弃时刻（终局——简阵卷Ch14-15）
在修补者的旧屋，纪承钧写下：
"我放弃'runbook 是完整地图'。我承认——地图不是疆域。我选择留下：一份 runbook，第一页写着——'此 runbook 画于特定时间、特定基座、有限已知范围内。你所在的地方可能不在地图上。如果不在——你来画。'"
