# Harness Engineering System

> 万构界项目的工程化工作流编排系统。不是另一套规则——是让所有已有规则**能被系统地执行**的脚手架。

## 什么是 Harness

在软件工程中，harness 是运行测试、管理状态、编排流程的基础设施。在万构界项目中，harness 承担同样的角色：

- **不是新规则**——canon 已有全部写作铁律
- **不是新工具**——skills 已有全部执行能力
- **是连接器**——把 canon、skills、workspace、supplements 连接成**一条可执行的流水线**
- **是状态机**——追踪每一章从章纲到成稿的完整生命周期
- **是质量系统**——在每个阶段设置检查门，不通过不能进入下一阶段

## 为什么需要 Harness

当前 `.claude/` 体系的每个组件都是**优秀的独立工具**，但存在三个系统性问题：

| 问题 | 表现 | Harness 如何解决 |
|------|------|-----------------|
| **碎片化** | 9个skills各自独立，没有统一的调用入口 | 命令中心（04_命令中心）——一个入口，路由到正确的工具链 |
| **无状态** | 不知道哪章写了、哪章审了、哪章卡住了 | 状态机（02_状态机）+ 进度面板（07_进度面板）——480章每章的状态可查 |
| **无质量门** | 写完就提交，没有系统化的检查流程 | 质量门（03_质量门）——每个阶段有明确的通过标准 |

## 快速开始

### 场景一：我要写新的一章

1. 查 `07_进度面板.md` → 确定下一章是哪个
2. 查 `02_状态机.md` → 确认该章当前状态
3. 执行 `01_流水线.md` 定义的流程 → 章纲读取 → 设计 → 场景 → 正文
4. 过 `03_质量门.md` 的 prose gate → 自查
5. 提交

### 场景二：我要审阅已写章节

1. 查 `04_命令中心.md` → 确定该用 `/review-chapter` 还是 `/audit-volume`
2. 执行审阅 → 对照 `03_质量门.md` 的 review gate
3. 记录结果 → 更新 `07_进度面板.md`

### 场景三：我隔了一段时间回来，不知道从哪继续

1. 读 `06_会话协议.md` 的"恢复会话"流程
2. 查 `07_进度面板.md` → 看哪些章在"草稿"状态
3. 从最早的未完成章节继续

## 设计原则

1. **工程优先**：harness 是工程工具，不是文学工具。它追踪状态、执行检查、路由任务——不评判文学质量。
2. **不重复规则**：所有写作规则都在 canon 中。harness 只定义**何时**检查**哪些**规则。
3. **可扩展**：新卷、新skill、新检查类型——都应能插入现有流程而不破坏已有流水线。
4. **状态透明**：任何时候都能回答"现在做到哪了"和"下一步做什么"。
5. **会话可恢复**：每次会话结束时，下一个会话应该能在 2 分钟内恢复到工作状态。

## 与现有体系的关系

- **canon/** → harness 的质量门引用 canon 的规则作为检查标准
- **skills/** → harness 的命令中心路由到 skills，流水线编排 skills 的调用顺序
- **workspace/** → harness 的状态机追踪 workspace 中所有产出物的状态
- **supplements/** → harness 的模板注册表覆盖 supplements 的模板
- **CLAUDE.md** → harness 的会话协议指导 CLAUDE.md 的上下文加载策略
