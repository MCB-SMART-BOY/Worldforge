# 06 · 会话协议

> Claude Code 会话的标准启动、继续和结束流程。目标：**任何会话都能在 2 分钟内恢复到工作状态。**

## 一、核心原则

1. **最小上下文加载**：每次会话只加载当前任务必需的文件——不是越多越好
2. **状态驱动**：先读进度面板，再决定加载什么——不是凭记忆
3. **显式结束**：每次会话结束时，留下明确的"下次从哪继续"——不依赖大脑记忆

---

## 二、首次会话

### 启动流程

```
1. 读 CLAUDE.md（项目指令）
2. 读 .claude/harness/07_进度面板.md（全局进度）
3. 确定目标卷和章段
4. 读目标卷的 00_卷索引.md
5. 读目标卷对应的 canon 卷设定（canon/09-12）
6. 加载目标章段的章纲文件（workspace/XX_卷/章纲/）
7. 开始工作
```

### 首次会话的上下文清单

| 文件 | 用途 | 必需/按需 |
|------|------|----------|
| `CLAUDE.md` | 项目指令、命名、铁律摘要 | 必需 |
| `.claude/harness/07_进度面板.md` | 全局进度 | 必需 |
| `workspace/XX_卷/00_卷索引.md` | 卷级进度、人物表、章节目录 | 必需 |
| `canon/09-12` 对应卷 | 卷级设定 | 必需 |
| `workspace/XX_卷/章纲/` 目标 Section | 目标章的章纲 | 必需 |
| `canon/15` 写作铁律 | 全文（首次会话必读） | 必需 |
| `canon/24` 术语对照 | 按需查询 | 按需 |
| `canon/23` 120章蓝图 | 按需查询（了解全卷结构） | 按需 |
| `skills/` 相关 skill | 按调用的 skill 加载 | 按需 |

## 三、恢复会话（高频）

### 识别：这是个恢复会话吗？

以下任一情况 → 按恢复会话处理：
- 用户说"继续"、"继续推进"、"接着写"
- 用户说"从上次的地方继续"
- 会话在完成一批章之后结束，现在回来继续

### 恢复流程

```
1. 读 .claude/harness/07_进度面板.md
   → 定位第一个状态为 "待写" 或 "草稿" 或 "自查" 的章

2. 确认恢复点：
   ├── 有待写的章 → 从该章的 Phase 1 开始
   ├── 有草稿的章 → 从该章的 Phase 3 继续（先读已有正文）
   ├── 有自查的章 → 处理审校报告的 ❌ 项
   └── 全部完成 → 恭喜！规划下一步

3. 读目标章的章纲（如 Phase 1 未做）

4. 读目标卷的 00_卷索引.md（如涉及跨 Section）

5. 开始工作
```

### 恢复会话的最简上下文

如果用户只是说"继续"——且之前的会话是同一个任务链：

```
必需加载：
├── 07_进度面板.md
├── 目标卷 00_卷索引.md（卷级进度表部分）
└── 目标章的章纲（workspace/XX_卷/章纲/对应Section文件）

如果章已部分写作：
└── 已有正文文件（读最后 30 行确认叙事连续性）
```

### 恢复会话检查清单

| # | 检查 | 为什么 |
|---|------|--------|
| 1 | 上次写到哪一章了？ | 避免跳过或重复 |
| 2 | 那章现在什么状态？ | 决定从哪个 Phase 开始 |
| 3 | 上次提交了吗？ | 未提交的更改需要先处理 |
| 4 | 前后章写了吗？ | 叙事需要连续性 |
| 5 | 用的哪个卷？ | 加载正确的卷设定 |

## 四、结束会话

### 正常结束

每完成一批章后，在会话结束前：

```
1. ✅ 确认已提交的章
   → git log --oneline -5 确认最新 commit

2. ✅ 更新进度面板
   → 07_进度面板.md + 对应卷 00_卷索引.md 的进度状态表

3. ✅ 写"下次从哪继续"标记
   → 在进度面板顶部或专门的 Continue 区：
      "下一批：驭器卷 Ch56-60（卷六「旧桥」Section 后半）"
      "下一章状态：章纲 ✅，待进入 Phase 1"

4. ✅ 记录待解决问题（如有）
   → "待解决：Ch54 的跨卷引用需要确认化形卷 Ch26 的残码内容"
```

### 中断结束

如果会话被中断（上下文窗口快满、需要 compact）：

```
1. 快速总结当前进度：
   ├── 已完成的章：Ch X-Y
   ├── 当前章状态：Ch Z — 正文已写一半
   └── 下一个动作：继续 Ch Z 的第三拍

2. 这些信息会在 compact 后的 summary 中保留
```

### 不要做的事

- ❌ 结束时不说"下次从哪继续"——下次会话需要重新探索
- ❌ 不更新进度面板——进度面板失准，恢复时走错路
- ❌ 未提交的更改留在工作区——下次会话不知道这些更改的意图

## 五、上下文管理策略

### 5.1 分批加载

不是一次性加载所有可能用到的文件。按阶段加载：

```
Phase 1 (准备) → 加载章纲 + 卷设定 + 前后章纲
Phase 2 (设计) → 加载 canon 补充（按主题）+ skill 文件
Phase 3 (写作) → 加载已有正文（前后章）+ 术语对照（按需）
Phase 4 (审阅) → 加载 skill 文件 + canon 规则
```

### 5.2 按需加载

以下文件不在首次加载，用到时才读：
- canon/07 (术语索引) — 查询时读
- canon/24 (术语对照) — 写作 Phase 3 时读
- canon/22 (共享事件) — 涉及跨卷章时读
- workspace/XX_卷/资料/ — 需要具体资料时读

### 5.3 大型文件策略

- **章纲 Section 文件**（可能 200+ 行）：只读目标章附近（前后 3 章的章纲）
- **卷索引**：先读人物表和进度状态表，章节目录按需展开
- **canon/23**（120章蓝图）：只读目标卷的 Section，不读全文件

## 六、会话间的记忆传递

### 6.1 通过进度面板传递

进度面板是会话间的主要状态传递机制。包含：
- 每章的当前状态
- 最后更新时间
- 阻塞问题标记

### 6.2 通过 git commit 传递

每次提交的 commit message 应包含足够的上下文：
```
feat: 驭器卷 Ch51-55 卷六「旧桥」——顾迁舟到来与桥的分类学

本批：Ch51-55。从化形卷到来的顾迁舟带来桥账，桥的分类学
（data bridge / control bridge / legacy bridge），valgrind诊断，
SVN→Git迁移的张力。

下一批：Ch56-60（卷六后半——旧桥之后）
```

### 6.3 通过 memory 传递

对于跨越多会话的重要决策，使用 `.claude/memory/` 记录（详见 `CLAUDE.md` memory section）。适用于：
- 用户反馈的模式（如"好的 继续推进" = 继续写下一批5章）
- 写作决策（如"留白哲学"的写作模式）
- 项目级决策（如卷推进顺序）

## 七、常见会话模式

### 模式 A：持续推进

```
用户: "继续"
→ 恢复会话流程 → 写下一批 → 提交 → 更新进度 → 结束（标记下次）
```

### 模式 B：审阅中断

```
用户: "审一下刚写的那批"
→ 读进度面板 → 找到 "草稿" 章 → /review-chapter → 修改 → /audit-volume
```

### 模式 C：跳到别卷

```
用户: "先写化形卷的..."
→ 读进度面板 → 确认新目标卷 → 加载新卷设定 → 恢复正常流水线
```

### 模式 D：大规模重构

```
用户: "把 .claude/ 体系重新整理"
→ 先做架构设计 → 写方案 → 批准 → 实施 → 更新所有相关文件
```

## 八、会话协议反模式

| 反模式 | 为什么错 | 正确做法 |
|--------|---------|---------|
| 每次加载全部 canon | 浪费上下文，大部分用不到 | 按 Phase 分批加载 |
| 恢复时凭记忆写 | 记忆不可靠，可能写重或写漏 | 先读进度面板 |
| 结束时不说"下次从哪继续" | 下次会话=冷启动 | 显式标记下一个任务 |
| 中途改卷不更新上下文 | 带着驭器卷的上下文写化形卷 | 切换卷时重新加载卷设定 |
| 同一会话写太多章（>10）不暂停 | 后期章缺乏前期的质量反馈 | 每5章停一次做 Section 审阅 |
