## 二、数据流

### 2.1 主要数据流：写一章的全路径

```
章纲(workspace) ──→ 章节设计(design-chapter) ──→ 场景构思(craft-scene)
                                                       │
                                                       ▼
                                                正文写作(正文/)
                                                       │
                                                       ▼
                                              自查(review-chapter)
                                                       │
                                                       ▼
                                              审阅(audit-volume/check-canon)
                                                       │
                                                       ▼
                                              git commit
```

每一步的输入和输出：

| 步骤 | 输入 | 工具 | 输出 | 质量门 |
|------|------|------|------|--------|
| 1. 读取章纲 | workspace章纲文件 | Read | 章纲内容 | — |
| 2. 章节设计 | 章纲 + canon卷设定 | `/design-chapter` | 设计蓝图 | Design Gate |
| 3. 场景构思 | 设计蓝图 | `/craft-scene` | 场景大纲 | — |
| 4. 正文写作 | 场景大纲 + 设计蓝图 | — | 正文初稿 | — |
| 5. 自查 | 正文初稿 | `/review-chapter` | 审校报告 | Prose Gate |
| 6. 审阅 | 正文 + 审校报告 | `/audit-volume` 或 `/check-canon` | 审阅意见 | Review Gate |
| 7. 提交 | 正文终稿 | git | commit | Commit Gate |

### 2.2 跨卷数据流

```
驭器卷事件 ──→ canon/22_共享事件表 ──→ 化形卷章纲 ──→ 化形卷正文
    │                                        │
    └──→ 简阵卷章纲 ──→ 简阵卷正文           │
    │                                        │
    └──→ 明契卷章纲 ──→ 明契卷正文 ←─────────┘
```

跨卷锚点通过 `canon/22_第一阶段四卷共享事件表.md` 和 `canon/23_四卷120章总蓝图.md` 的 Section 7 记录。

### 2.3 质量反馈流

```
质量门不通过 ──→ 回到上一阶段 ──→ 修复 ──→ 重新过门
```

不跳级。不跳过。质量门是串行的——前一扇门必须通过才能进入下一阶段。

```
新会话启动
    │
    ├── 首次会话 → 会话协议 §首次会话
    │               ├── 加载 canon 01-05 (世界底层)
```

## 五、扩展接口

### 5.1 新增一卷

1. `workspace/05_XX卷/` — 按五层结构创建
2. `supplements/05_XX卷/` — 按三件套创建
3. `canon/` — 新增卷级设定文件
4. Harness 更新：
   - `02_状态机.md` — 新增卷的状态追踪
   - `07_进度面板.md` — 新增卷的进度行
   - `04_命令中心.md` — 确认路由覆盖新卷

### 5.2 新增一个 Skill

1. `skills/new-skill.md` — 按现有 skill 格式创建
2. Harness 更新：
   - `04_命令中心.md` — 添加路由规则
   - `01_流水线.md` — 确认流水线阶段是否需要调整
   - `05_模板注册表.md` — 如果skill产出新类型模板则注册

### 5.3 新增一个质量检查

1. `03_质量门.md` — 在对应阶段添加检查项
2. `09_集成验证.md` — 如果是跨卷检查则添加
3. 确认自动化（`08_自动化.md`）能够执行新检查

## 六、关键设计决策

### 决策 1：Harness 不包含规则，只编排规则

**理由**：规则的一站式真理源是 canon。Harness 如果也包含规则，会出现"以哪个为准"的问题。Harness 只定义：在什么阶段、检查什么规则、用什么工具。

### 决策 2：状态机追踪产出物，不追踪过程

**理由**：追踪"纪承钧的人物弧线写到第几阶段"太细粒度，维护成本高于收益。状态机追踪的是可验证的产出物状态：章纲有没有、正文有没有、审阅过没过。

### 决策 3：质量门是串行的

**理由**：跳级检查（比如正文还没写就做跨卷验证）没有意义。串行门确保每一层的质量基础存在，上层检查才有意义。

### 决策 4：会话协议是最小上下文策略

**理由**：Claude Code 的上下文窗口有限。每次会话只加载必要的文件，通过进度面板和状态机定位到具体任务，而不是每次都把整个 canon 和 workspace 加载进来。
