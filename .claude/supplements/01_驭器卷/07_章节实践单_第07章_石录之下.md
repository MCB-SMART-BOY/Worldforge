# 《驭器卷》章节实践单：第07章《石录之下》

## 一、文档头
- 所属卷：驭器卷
- 对应章节：第07章 石录之下
- 实践单状态：已可用

## 二、本章工程问题
- 翻出旧版本文档和代码遗迹时，如何从中提取被遗忘的修正理由——以及卫千枢为什么在石录里写下"后来的人，对不起"

## 三、本章要立起的判断尺
- 版本历史不是垃圾堆，是唯一能告诉你"为什么当初这么做"的东西。删掉注释只留代码的行为，等于删掉了唯一能挡在"重蹈覆辙"前面的护栏

## 四、故事映照
- 本章事件：纪承钧翻出石录——旧版本文档中记录了三年前一次关键修正的遗迹，但修正的理由和执行过程只有卫千枢的简略批注，且多处标注"后来的人，对不起"
- 代价承担：钟守玄承认"那次修正的细节我也说不全——卫千枢做了大部分，我当时觉得以后再看也来得及"。三年来没人翻过石录的这一页
- 为什么用这个工程动作照剧情：石录不是代码——它是修正理由的时间胶囊。当修正理由只存在于某一个人的脑子里时，每一次沉默的修正都是一颗定时炸弹。"对不起"不是为自己道歉，是为"我没时间写清楚而我明知这会给后来者制造麻烦"道歉

## 五、本章最小实践

### 核心概念
- 版本考古（version archaeology）
- 修正理由（fix rationale）
- 代码遗迹（code fossil）
- 时间胶囊式文档（time-capsule documentation）

### 最小项目动作
- 用 `git log -S` 或 `git blame` 找一条至少一年前的关键修改。查看当时的 commit message 和关联的 issue/PR 讨论——那条修改的"为什么"是否在代码里能读到？如果不能，补写一条注释，至少包含：触发条件、当时的决策依据、已知的替代方案（即使被否决）

### 必做练习
- 练习目标：体验石录考古——把一条"不知道为什么当时这样改"的修改追溯到它的决策现场
- 输入：项目中一条你或他人做过的关键修改（commit、配置变更、架构调整）
- 输出：一条包含"触发条件 → 决策依据 → 排除方案 → 已知风险"的修正理由记录，直接写入代码注释或项目文档
- 完成标准：另一个工程师看到这条修改后，不需要翻聊天记录或考古就能理解"为什么是这样而不是那样"

## 六、自检清单
- 我能找到项目中至少三条"改了但不知道为什么改"的关键修改
- 我能解释为什么卫千枢写"后来的人，对不起"——以及我是否也有该写但没写的修正理由
- 我知道 git blame 能看到谁改的，但看不到为什么改——而这个"为什么"才是石录真正的价值
- 我能分辨"这条注释三年后还有用"和"这条注释三个月后就过时了"

## 七、常见误区
- 误区：代码就是最好的文档——读代码就能理解为什么这样做
- 为什么不：代码能告诉你"做了什么"，不能告诉你"为什么不那样做"。所有被否决的替代方案、所有触发这次修改的外部约束、所有"这个选择在当时是错的但现在是对的"的历史判断——这些信息代码里没有，只存在于做决定那一刻的上下文里。石录保存的就是这个上下文
