## 二、本单定位

### 1. 本章工程问题

- 怎样让项目从“几个人互相传代码”转成“别人能沿公开入口提问、讨论和修改”

### 2. 本章要立起的判断尺

- 没有远端共同入口，协作就仍然是私下关系，不是公共秩序

### 3. 本单不负责的内容

- 不依赖真实线上仓库
- 不讲完整组织治理
- 不把 issue / PR 形式化到失去问题本身

## 四、故事映照

- 本章对应的主要事件：使用者第一次沿公共入口提出问题，项目不能再只靠面对面解释
- 本章是谁在承担代价：主角失去部分解释权，使用者获得第一次公共发问权
- 这一章为什么必须用这个工程动作来照出剧情：门外之问一旦出现，青炉就不再只是门内私器

## 五、本章最小实践

### 1. 核心概念

- remote
- issue
- pull request

### 2. 最小项目动作

- 为 `qinglu` 写出最小协作入口：问题单模板、改动提交流程、PR 检查单

### 3. 推荐工具 / 命令 / 观察点

- 工具：Markdown 模板文件
- 命令：`git remote -v`
- 观察点：别人第一次提问时，是否知道该去哪、带哪些信息

### 4. 必做练习

- 练习目标：把“协作入口”从口头默契改成公开路径
- 输入：当前 `qinglu` 项目
- 输出：`docs/collab/issue-template.md`、`docs/collab/pr-checklist.md`
- 完成标准：模板里至少说明“问题描述、复现信息、预期行为、改动范围”，并且 PR 检查单能逼改动者补上文档和错误说明

### 5. 可选延伸

- 如果你有真实远端仓库，再把这些模板迁进去；如果没有，就用本地文档模拟一次提问到改动的流程

## 七、常见误区

- 误区一：
  - 表现：觉得只要有群聊和口头沟通，issue 模板就可以省
  - 为什么不对：这样问题仍然不会进入公共史
- 误区二：
  - 表现：把 PR 当成纯形式，实际改动理由仍然不写
  - 为什么不对：没有理由链，后来者仍然接不到这段火
