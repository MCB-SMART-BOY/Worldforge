## 二、本单定位

### 1. 本章工程问题

- 怎样避免把一种工具或语言写成万能信仰，同时又不把它的真正价值抹平

### 2. 本章要立起的判断尺

- 成熟不是“什么都用 Rust”，而是“知道哪一层必须重，哪一层可以轻”

### 3. 本单不负责的内容

- 不做语言大战排行
- 不写抽象哲学辩论
- 不把“快原型”与“长寿命核心”混成同一类问题

## 五、本章最小实践

### 1. 核心概念

- 工程适配
- 核心层 / 外壳层 / 试法层
- 语言边界
- 判断矩阵

### 2. 最小项目动作

- 为一个真实项目画一张“哪层适合 Rust、哪层不一定适合 Rust”的分层判断表

### 3. 推荐工具 / 命令 / 观察点

- 工具：架构图、模块边界说明
- 命令：无硬性命令，以书面判断为主
- 观察点：你是否能把“高故障代价”“高协作负担”“高不确定试法”区分开来

### 4. 必做练习

- 练习目标：从信仰或反感里退出来，回到问题本身
- 输入：一个包含核心逻辑、实验脚本、交付壳层和运维脚本的项目
- 输出：分层判断矩阵
- 完成标准：至少写清
  - 哪层最值得用 Rust
  - 哪层不必强推 Rust
  - 每一层的判断依据是什么

### 5. 可选延伸

- 对其中一层写一句反例：如果硬把它 Rust 化，最可能多付什么代价

## 七、常见误区

- 误区一：
  - 表现：把所有性能敏感问题都自动归给 Rust
  - 为什么不对：性能、边界、协作寿命和迁移成本不是同一件事
- 误区二：
  - 表现：因为某层不适合 Rust，就反过来否定 Rust 在核心层的价值
  - 为什么不对：成熟判断从来不是全盘接受或全盘否定
