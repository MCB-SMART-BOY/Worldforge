## 四、故事映照

- 本章对应的主要事件：青炉第一次真正面向门外用户，使用者开始反向塑形项目路线
- 本章是谁在承担代价：使用者承担安装和入门成本，继承者承担第一批门外问题，主角承担放弃“把一切都对外暴露”这种虚荣的代价
- 这一章为什么必须用这个工程动作来照出剧情：若用户入口仍然依赖熟人说明，前面的门规和发布都只写给自己看

## 五、本章最小实践

### 1. 核心概念

- crate 发布
- 二进制交付
- 快速开始
- 帮助信息

### 2. 最小项目动作

- 明确 `qinglu` 的首个公开交付面，并补一套最小安装与上手入口

### 3. 推荐工具 / 命令 / 观察点

- 工具：`cargo`
- 命令：`cargo publish --dry-run`
- 命令：`cargo install --path .`
- 观察点：用户第一次遇见项目时，能不能只靠公共入口完成安装、看懂帮助、跑通最小命令

### 4. 必做练习

- 练习目标：让“第一次上手”不再要求维护者在旁边解释
- 输入：当前 `qinglu` 项目
- 输出：安装说明 + 快速开始 + `--help` / `--version` 约定
- 完成标准：必须至少说清
  - 推荐的交付方式
  - 用户第一次应该先运行什么
  - 失败时先看哪里

### 5. 可选延伸

- 让一个没参与项目设计的人只按文档完成一次最小上手，记录卡住的位置

## 七、常见误区

- 误区一：
  - 表现：为了显得专业，把半熟 API 一起公开
  - 为什么不对：用户一旦依赖它，你就开始欠债
- 误区二：
  - 表现：安装文档默认用户拥有维护者同款环境
  - 为什么不对：这样等于把门外问题重新推回熟人帮助链
