# /craft-scene — 场景工艺

为一个具体场景做戏剧构造。**场景是小说的最小完整单元——一个场景如果同时没有工程推进和情感推进，它就不该存在。**

## 核心信念

> 万构界最好的场景，是让读者同时感受到两件事：
> 1. "原来这个工程概念是这样运作的"（认知收获）
> 2. "这个人的处境让我心里一沉"（情感共鸣）
>
> 只做到第一件 → 教科书。只做到第二件 → 与世界观脱节。两件都做到 → 这就是万构界。

## 参数

- `scene_context` — 场景在章节中的位置（前情 + 当前需要推进什么）
- `characters` — 场景中的人物
- `engineering_point` — 这个场景要传达的工程概念/方法/教训
- `emotional_point` — 这个场景要触发的情感变化（困惑→明了？恐惧→勇气？信任→怀疑？希望→绝望？）
- `tension_target` — 这个场景的张力强度（1-5：背景铺垫 / 轻度紧张 / 中度对峙 / 高度危机 / 全章高潮）

## 场景设计流程

### 第一步：确定场景功能

每个场景只能主推一件事。选择主功能：

| 主功能 | 描述 | 本场景占的比例 |
|--------|------|--------------|
| 推进工程认知 | 读者学到了一个新工程概念或看见了一个工程病 | 60%+ |
| 推进人物弧线 | 人物做了一個选择，暴露了信念/盲点/成长 | 60%+ |
| 推进情节 | 发生了不可逆的事件，改变了后续行动方向 | 60%+ |
| 建立氛围 | 让读者感受世界/卷/项目的独特质感 | 60%+ |

标注主功能 + 辅助功能。一个场景不能平分两个功能（平分 = 两个都没做好）。

### 第二步：确定张力形态

选择这个场景的张力来源：

| 张力来源 | 读者在想什么 | 万构界里的典型场景 |
|---------|------------|-----------------|
| **认知张力** | "这个系统到底是怎么运作的？" | 追踪一个 bug、排查一个依赖链 |
| **人际张力** | "这两人的分歧会在哪一刻爆发？" | 代码审查对峙、师徒对修复方案的分歧 |
| **时间张力** | "还来得及吗？" | 开窗前夜、回滚倒计时、临时方案的有效期 |
| **代价张力** | "这个决定会伤到谁？" | 选择快速修复（累积债务）还是重构（延误工期） |
| **揭示张力** | "真相到底是什么？" | 找到一段三年前的代码，发现注释和实现矛盾 |
| **制度张力** | "规矩和现实哪个赢？" | 流程说必须先评审，但外面已经在等了 |

### 第三步：设计场景节奏

每个场景内部有三段式微型节奏：

```
开场 → 建立此刻的状态（谁在，在哪，什么压在心上）
转折 → 一个信息/事件/选择改变了局面
收束 → 新的状态确立，为下一个场景留下引力
```

标注每一段的预期字数比例（如 30% / 50% / 20%）。

转折的强度必须匹配 tension_target：
- 张力 1-2：转折可以是一个认知上的小发现
- 张力 3：转折必须是一个令人不安的信息或一个被迫的选择
- 张力 4-5：转折必须是一个不可逆的事件——做了就不能回头

### 第四步：设计场景内的信息释放

场景中读者和角色的信息差：

| 在这个场景中 | 读者知道 | 角色知道 |
|------------|---------|---------|
| 工程事实 | [列出] | [列出] |
| 人物情感/动机 | [列出] | [列出] |
| 即将发生的危险 | [列出] | [列出] |

选择至少一种信息差作为本场景的戏剧引擎：
- **读者知道，角色不知道** → 读者替角色捏汗（"别点那个！"）
- **角色知道，读者不知道** → 读者追问"你到底看到了什么？"
- **读者和角色都不知道** → 一起探索，一起撞墙（适合事故/调试场景）
- **读者和角色都知道** → 看着事情不可避免地向悲剧滑去（最沉重）

### 第五步：场景结尾的引力

每个场景结尾必须有"引力"——让读者不能不读下一段的理由。选择至少一种：

- **未答问题**："他看到了什么？"
- **代价预告**："这个选择会在天亮前找上门"
- **情感余震**：一个意象、一个动作、一句沉默
- **因果钩子**："因为刚才做了X，现在已经来不及做Y了"
- **视角切换预告**："同一时刻，在另一扇门后……"

### 第六步：工程概念的场景化

将工程概念嵌入场景的具体动作中：

- ❌ 错误做法：角色A对角色B解释 trait 是什么（课堂教学式）
- ✅ 正确做法：角色B写了一个 trait 但忘了实现某个方法，编译器不通过，角色A指着报错说"它不认你，因为你答应的事没做"（冲突中学习）

工程概念必须作为**解决场景冲突的工具或制造场景冲突的原因**出现，而非作为"教学内容"出现。

### 第七步：情感锚点确认

- [ ] 这个场景里有没有至少一个人物的情感状态是读者能感同身受的？
- [ ] 这个情感是否通过具体行动/身体反应/对话变化表现出来（而非直接告知"他很担心"）？
- [ ] 场景的情感温度是否有变化（开始冷 → 中间热 → 结尾温）？

```markdown
- **情感点**：[这个场景让读者的情感从____变成____]

### 张力设计

- **张力强度**：[1-5]

### 信息差引擎
- 读者知道/角色不知：[具体是什么]
- 角色知道/读者不知：[具体是什么]
- 选择的戏剧模式：[选一]

### 开场
> [第一段 —— 谁在，在哪，什么压在心上]

### 转折
> [核心事件/信息/选择 —— 改变了什么]

### 收束
> [新状态确立 + 引力 —— 下一段为什么必须读]

### 工程嵌入
- **工程概念**：[真实术语]
- **出场方式**：[作为冲突的工具/作为冲突的原因 —— 具体怎么出现]
- **角色是否懂**：[懂 → 展示专业 / 半懂 → 展示盲点 / 不懂 → 展示学习]

### 情感锚点
- **谁的情感在变化**：[角色名]
- **何种变化**：[从___到___]
- **如何表现**：[一个具体的行动/身体反应/对话选择]

### 三问
1. 🩻 这个场景结算哪种四蚀？[失式/乱流/背契/断史]
2. 😣 这个场景的代价可被看见了吗？[谁/失去什么/在哪一刻]
3. 🛤️ 这个场景让后来者的路发生了什么变化？[更清晰了/更模糊了/暂时无变化但有伏笔]
```

## 场景序列设计（多场景组合时使用）

若一次设计多个连续场景，必须标出场景之间的张力度变化：

```
场景1（张力2）→ 场景2（张力3）→ 场景3（张力1·呼吸点）→ 场景4（张力4·小高潮）
```

规则：
- 连续两个场景不能同为高强度（4-5）
- 每三个场景至少有一个呼吸点（张力 1-2）
- 全章最高张力的场景永远不在第一章的第一个场景（要给读者进入状态的时间）

## Gotchas（常见场景设计错误）

- **课堂式场景**：角色围坐一圈，轮流解释概念。这是万构界最常见的病——因为工程概念需要解释，最方便的方式就是让角色张嘴说。解法：把解释变成冲突。不是"我来教你 trait"，而是"你写的 trait 过不了审契者的校验，因为他认为你的抽象层级错了"。
- **无冲突场景**：场景中所有角色都同意彼此，只是分工不同。没有分歧的场景 = 没有张力的场景。即使师徒授业，也要有"徒弟的理解和师傅的意图有偏差"。
- **情感标注式**：写"他感到沮丧"而不是展示沮丧（他把刚写的代码全删了，盯着空屏，手指悬在键盘上方三秒没动）。
- **信息均匀释放**：从头到尾信息以同一密度释放 = 读起来像说明书。关键信息必须在某个具体时刻、因某个具体原因、以某种具体方式砸在角色（和读者）脸上。
- **场景没引力**：场景结尾是一个自然的"段落结束"感。正确：场景结尾应该让读者不舒服——有个东西没解决、没回答、没放下。
