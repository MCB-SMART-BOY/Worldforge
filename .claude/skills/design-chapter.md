# /design-chapter — 章节设计

按《万构界》六步设计工作流，为一章生成完整蓝图。
**蓝图包含两条并行的骨架：工程教学骨架 + 剧情张力骨架。两条骨架必须在同一场景中同时承重。**

## 参数

- `volume` — 卷名（明契卷/驭器卷/化形卷/简阵卷）
- `chapter_number` — 章号
- `topic` — 本章要覆盖的工程主题（如 Cargo、所有权、Git、tracing、runbook）
- `context`（可选）— 该章在卷中的位置和前情提要

## 设计流程

### 第一步：确定核心对象层

该章主要写哪一层？为什么选这一层？

可选层：念 → 约 → 图 → 文 → 骨 → 器 → 阵 → 门 → 史

每章应聚焦一层，其他层作背景。

### 第二步：确定核心相与失守形态

该章主要处理哪一相？对抗哪种失守？

可选：式 / 流 / 契 / 史
失守：失式 / 乱流 / 背契 / 断史

### 第三步：确定工程主题

该章的现实工程内容是什么？列出：
- 核心工程概念（用真实术语）
- 这个概念的常见坑/梗/报错
- 这个概念在程序员日常中怎么痛

### 第四步：世界观切入句

写一句能把工程和世界观接起来的话。

格式：「在万构界，[工程概念]不只是[技术定义]，更是[文明命题]。」

### 第五步：落回真实术语

列出本章必须出现的真实工程术语清单（至少 5 个）。确保它们以自然方式出现在对话、师徒传授、代码审查、事故复盘等场景中。

**⚠️ 铁律四之补充：中文专有名词每次出现必须注英文原名。** 正文中凡使用中文表达的CS/数学/软件工程专有名词，每次出现时必须以括号注出其标准英文原名。格式："所有权（ownership）"、"健康检查（health check）"。参考：`.claude/canon/24_世界术语-现实工程对照表.md`。

**⚠️ 文学表达标注工程原型**：正文中首次使用世界观文学表达（如"玄枢""石录""火""桥""传火"等）时，必须通过场景或括号标注其工程原型（如：玄枢=大型C++遗留系统、石录=版本控制/commit历史、火=服务运行状态）。参考：`.claude/workspace/01_驭器卷/章纲/00_章纲索引.md` 第六节「文学表达-工程原型对照表」。

### 第六步：设计张力曲线（⚠️ 新增）

本章必须有一条可辨识的张力曲线。选择一种曲线形态：

| 曲线形态 | 描述 | 适用场景 |
|---------|------|---------|
| **攀升型** | 从平静逐步升到章末高点 | 引入新概念，逐步暴露其复杂性 |
| **倒钩型** | 开头即危机，中间回溯原因，章末再掀一波 | 事故复盘、追根溯源 |
| **双峰型** | 两个张力高点 + 中间低谷反思 | 概念对比（正确做法 vs 错误做法） |
| **悬疑型** | 张力来自"不知道真相"，章末揭示但留下新问题 | 系统缺陷追踪、技术债溯源 |
| **崩塌型** | 开头稳定，逐步坍塌，章末最低点（为下一章蓄力） | "所有补救都失败"的章节 |

确定本章的张力曲线形态：[选一种]

标出：
- **张力起点**：读者在第几段开始感到"有什么事不对"？
- **第一个张力峰**：本章最紧张的时刻在哪？
- **呼吸点**：在哪给读者半页消化？（必须至少一处）
- **章末钩子**：读者翻到下一章的动力是什么？（悬念/未答问题/代价预告/情感余震）

### 第七步：设计揭示节奏（⚠️ 新增）

信息不是均匀释放的。设计本章的揭示节奏：

| 时机 | 读者知道什么 | 角色知道什么 | 张力类型 |
|------|------------|------------|---------|
| 开场 | ... | ... | 同步/反讽/悬念 |
| 中段 | ... | ... | ... |
| 章末 | ... | ... | ... |

三种基本张力模式：
- **同步**：读者和角色同时发现 → 适合事故/探索
- **戏剧反讽**：读者知道但角色不知道 → 读者替角色捏汗
- **悬念**：角色知道（或发现）但读者还不知 → 读者追问"到底是什么"

## 不同卷的设计偏好

> **阅读/写作顺序**：驭器（C++）→ 化形（Python）→ 简阵（Go）→ 明契（Rust）。每卷120章（12卷×10章）。详见 `.claude/canon/23_四卷120章总蓝图.md`。

### 驭器卷（C++·玄枢）— 第一卷："从零建立"
- 偏「史」和「式」
- 冲突：古器 vs 新桥，口传 vs 文档，秘义 vs 公共知识，工具链蛮荒 vs 制度建立
- 项目落地：玄枢（古器核心维护与接火）
- 张力引擎：**"知道的人正在老去"** — 知识的不可传性与时间的不可逆性
- 典型曲线：崩塌型（古器稳定→逐层暴露脆弱→最低点）
- **独有叙事维度**：六维工具链从无到有（构建系统/版本管理/静态分析/调试诊断/测试/文档）+"考古层"工具遗迹
- **跨卷锚点**：残码发现(Ch47-48)、被青炉诊断报告炸(Ch75-78)、runbook炸息壤(Ch94-97)、修补者揭示(Ch104-105)

- **跨卷锚点**：三段残码同一行原因(Ch26-28)、被runbook炸(Ch55-59)、入侵驿河(Ch85-88)、傅↔周对话(Ch95-98)、放弃"速度自足"(Ch107)

### 化形卷（Python·息壤）— 第二卷："从乱到治"
- 偏「流」和「史」
- 冲突：速度 vs 沼泽，试法 vs 复现，个人 vs 团队
- 项目落地：息壤（脚本群治理与分层）
- 张力引擎：**"快乐留下的账单"** — 每次"快速搞定"都在积累未来的债务
- 典型曲线：双峰型（快的价值 vs 乱的代价）
- **独有叙事维度**：包管理从乱到治（pip→venv→requirements.txt→poetry→uv）+类型系统渐进演化
- **跨卷锚点**：三段残码同一行原因(Ch26-28)、被runbook炸(Ch55-59)、入侵驿河(Ch85-88)、傅↔周对话(Ch95-98)、放弃"速度自足"(Ch107)

### 简阵卷（Go·驿河）— 第三卷："从简到繁再归简"
- 偏「契」和「流」
- 冲突：扩域 vs 可知，简单 vs 隐藏复杂度，个人值班 vs 制度
- 项目落地：驿河（多服务平台的共同维护）
- 张力引擎：**"表面绿色，底下在烧"** — 简单接口掩盖的复杂现实
- 典型曲线：攀升型（从一次小故障→逐层暴露系统性缺陷）
- **独有叙事维度**：平台工程的简洁哲学与复杂度管理+Java（守序之道）前传伏笔
- **跨卷锚点**：远古告警(Ch25-26)、被化形模块OOM(Ch65-68)、温故来512MB(Ch69/74)、成阵(Ch102-110)

### 明契卷（Rust·青炉）— 第四卷："集大成者"
- 偏「式」和「契」
- 冲突：显式 vs 隐式，边界 vs 模糊，承诺 vs 侥幸，工具链完备 vs "然后呢？"
- 项目落地：青炉（工具链起炉过程）
- 张力引擎：**"写下来的东西不够用"** — 纸面承诺 vs 真实复杂度的差距。终极悖论：拥有所有正确工具≠拥有所有正确答案
- 典型曲线：倒钩型（事故→回溯→制度回应）
- **独有叙事维度**：现代工程集大成——Cargo/所有权/形式化验证三维弧线+终极悖论
- **跨卷锚点**：旧注释(Ch35-36)、诊断报告入侵物(Ch77-78)、炸了玄枢(Ch105-108)、梁故川遗产(Ch95-98)、放弃"写清楚就是一切"(Ch109)

## Gotchas（常见设计错误）

- **六拍平铺**：把六拍当成六段叙事，每段同等长度 → 节奏死板。正确做法：六拍是结构性检查点，不是等分段。有些拍可以压缩到半段，有些需要展开三页。
- **张力虚高**：用玄幻词汇（"惊天动地""前所未有"）渲染紧张，但工程内容并未真正升级。张力必须来自工程后果的具体化（"如果不修，凌晨三点谁接传讯牌"比"后果不堪设想"紧一百倍）。
- **入门暴力**：第一章就塞进 8 个世界术语 + 5 个工程概念。读者不是来考试的。每章最多引入 3 个新世界观术语 + 1 个核心工程概念。其他都是深化。
- **揭示过载**：一段话同时解释概念定义 + 历史背景 + 与其他概念的关系。正确做法：一次只给一个层面的信息，让同一个概念在不同场景中逐层丰满。
- **术语缺英文**：中文CS/工程术语出现时未标注英文原名 → 违反铁律四之补充。每次出现必须注："构建系统（build system）"、"回滚（rollback）"。
- **文学表达无根**：使用"玄枢""石录""火""桥"等世界术语但未建立工程原型的对应关系 → 读者看不懂这些词在说什么。首次出现时必须通过场景暗示或括号标注其工程含义。
