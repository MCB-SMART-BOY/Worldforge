# 卷一「凡火」Ch 1-10：错版夜发事故全貌

## Section 总览

- **章段**：Ch 1-10
- **叙事主题**：错版夜发——命令成功不等于秩序成立。青炉前身——旧工具链群（一堆脚本、手工流程、口传知识、没有文档的维护）——在凌晨炸了。从救火到追问——"为什么每次都靠人来补？"裴照川出场止火。梁故川的灰印首次浮现。
- **核心冲突**：旧工具链不是"坏了"——是"从来就没有过秩序"。每一代维护者都在补——但没人写下"为什么这样补"。"命令成功"让人以为"秩序成立"——但命令成功只是按了回车——不等于后来者知道为什么按。
- **工具链阶段**：rustup/toolchain入门（卷尾Ch10选道——为什么是Rust）
- **对象层**：念→约（从"先修再说"的念——到"我们需要约"的觉醒）
- **主相→蚀**：史 → 断史 + 契 → 背契（旧工具链的维护知识全在人的脑子里——口传。梁故川离开——知识断了。）
- **主角状态**：沈见微——旧工具链的救火者。他不是负责人——负责人已经走了——他是唯一还在凌晨接传讯牌的人。
- **卷尾落点**：火灭了——裴照川止住了——但沈见微知道"这火还会再烧——因为烧火的不是代码——是没有人知道为什么火会烧。"

### 第01章：凡火未明

- **核心对象层**：念→念（错版夜发——凌晨——发布系统跑了一个"和昨天一样的命令"——但"昨天"之后——有人手动改过一个配置——发布不知道——命令成功——产物上线——炸了。命令成功——不等于秩序成立。）
- **核心相与失守**：史 → 断史（发布命令成功了——但发布命令不知道有人手动改过配置——因为手动修改没有被记录在任何地方。成功是盲目的——它只告诉你"我做了"——不告诉你"世界在你不知道的地方变了"。）
- **工程锚点**：发布（deployment）与配置管理（configuration management）——不是"能发布就行"——是"发布时的世界状态——和上一次发布时——有没有被记录下来的差异"。CI/CD的前提不是自动化——是"自动化知道自己不知道什么"。
- **张力曲线**：崩塌型（凌晨——发布系统报"成功"——但产物上线后——三十分钟——用户开始报错——错误蔓延——沈见微被传讯牌叫醒——"什么情况？""发布了。""谁的发布？""自动的——和昨天一样。""昨天之后——有人改过配置吗？""......不知道。"）
- **六拍骨架**：
  1. 问题先出：凌晨自动发布——命令成功——产物上线——炸了
  2. 为什么痛：发布系统只知道"我做了"——不知道"有人在我不知道的地方改了东西"
  3. 引出方法：发布不是自动化就够了——是"发布时的世界状态——被记录——被比对——差异被公开"
  4. 项目落地：沈见微天亮后查——发现有人在三天前手动改过一个配置——没有记录——因为"只是小事——不用写文档"
  5. 多方复盘："不是发布错了——是发布不知道有人在它背后改东西。自动化——不等于知道自己在做什么。"
  6. 高层收束：命令成功——不等于秩序成立。秩序——需要记录——需要"谁改了什么——为什么改——什么时候改的"。

### 第02章：谁在值守

- **核心对象层**：人→人（事故爆发前的最后一夜——旧工具链的值班——其实是"谁醒着谁倒霉"。没有轮值——没有on-call——没有"这是你的服务"——有的只是"谁离传讯牌最近——谁去"。）
- **核心相与失守**：契 → 背契（没有值班制度——不等于是自由的——等于是"没有人承诺过会接"。每个人都在睡——但每个人都被传讯牌叫醒——然后每个人心里都在想——"为什么是我？"）
- **工程锚点**：on-call轮值与ownership——与简阵卷Ch31-40形成跨卷对照。明契卷的旧工具链——和驿河的51个服务——同一种病在不同的阶段。"没有人认领的服务——在凌晨——是所有人的噩梦——但没有一个人的责任。"
- **张力曲线**：弥漫型（事故爆发前夜——展示旧工具链的"值守"——沈见微在睡——韩砺年在睡——贺时进在睡——传讯牌响——沈见微接了——因为"他知道别人不会接"。）
- **六拍骨架**：
  1. 问题先出：展示旧工具链的值班现状——"谁醒着谁倒霉"——没有轮值——没有owner
  2. 为什么痛：每个人都在"等别人接"——等——传讯牌响得更久——事故更大——最后接的人付的代价最大
  3. 引出方法：on-call不是"让人不睡觉"——是"让人知道——今晚——就是我——没有别人——我不接——没人接"
  4. 项目落地：（此章不解决——只暴露。"这是旧工具链的现状——沈见微接了——不是因为制度——是因为他是唯一还在接的人。")
  5. 多方复盘："没有制度——是最累的。制度不是束缚——是让你知道——'今晚不是我——我可以睡'。"
  6. 高层收束：值守——不是技术问题——是"谁负责"——没有owner的系统——在凌晨——是所有人的噩梦——但没有人负责。

### 第03章：脚本成墙

- **核心对象层**：器→器（旧脚本群——几百个脚本——bash、Python、Perl——各种语言——各自写了各自的部分——拼在一起——"能跑"——但没有人知道全部脚本之间的关系。脚本不是工具——是墙——每一道墙后面是一个人的"我知道怎么跑"——但墙之间——是隐式的依赖——没有人画过图。）
- **核心相与失守**：式 → 失式（脚本群没有结构——不是设计出来的——是"加加加"出来的。每一个脚本是合理的——但脚本之间的关系——没有人设计——所以结构不可见——"脚本成墙"——墙内的人知道自己在做什么——墙外的人——只能爬过去。）
- **工程锚点**：脚本依赖管理——不是"脚本不好"——是"脚本之间的依赖——应该被记录、被版本化、被测试"。脚本=代码——代码之间的关系——是契约——不是"我调你——你调我——就这样"。Rust的module系统和Cargo的依赖声明——是这面墙的反面。
- **张力曲线**：考古型（沈见微在事故后追查根因——穿过几十个脚本——每一个脚本调下一个——下一个调下一个——"这个脚本是谁写的？""三年前——那个人已经走了。""这个脚本改过吗？""去年——加过一个参数——在脚本的第437行——没有版本——没有记录——只有'当时能跑'。"）
- **六拍骨架**：
  1. 问题先出：追查事故根因——穿过几十个脚本——依赖关系不可见
  2. 为什么痛：每一个脚本都是"当时能跑"——但没有人画过它们之间的关系——关系是隐式的——在人的脑子里——人走了——关系丢了
  3. 引出方法：脚本不是墙——但没有记录的脚本——是墙。"代码之间的关系——是契约——不是'能跑就行'。"
  4. 项目落地：沈见微花了两天画出旧脚本群的依赖图——图上有几十条线——很多是循环的——"这个图——就是旧工具链的病。"
  5. 多方复盘："脚本没问题——是'脚本为什么被写出来——谁依赖它——它可以被删吗'——这些答案——在离开的人的脑子里——不在代码里。"
  6. 高层收束：脚本成就了墙——因为每一个脚本都是"快速解决问题"的产物——快速——但没留下路。后来者——面对墙——不知道从哪里爬。

### 第04章：口传之链

- **核心对象层**：文→史（维护知识靠口传——"问韩砺年"——韩砺年是旧工具链的守门人——他知道每一个脚本为什么存在——每一个配置为什么这样设——每一个"注意"在哪里。但韩砺年不会永远在——而他的知识——不在文档里——在他的脑子里。）
- **核心相与失守**：史 → 断史（口传——是"我知道——我告诉你"。但"我告诉你"的前提是"我还在"。知识在脑子里——不在记录里——等于"知识是人的延伸"——人走——知识断。）
- **工程锚点**：知识管理（knowledge management）——不是写文档——是"让'为什么'离开人的脑子——进入后来者能查到的记录"。文档不是"写一遍"——是"每当有人问'为什么'——答案被记录下来——下次别人不需要再找人问。"
- **张力曲线**：焦虑型（沈见微——"韩师——这个配置为什么设成300？""因为三年前——有个事故——当时的峰值到了280——设300是留20余量。""文档里没写。""嗯——我知道——但我没写下来——因为觉得三年前的事——很远——不需要——""但如果有一天你不在了——后来者看到300——不知道是'事故后的余量'——他改成100——三年前的事故——重演。"）
- **六拍骨架**：
  1. 问题先出：沈见微排查事故时——反复"问韩砺年"——因为文档里只写了"做什么"——没写"为什么"
  2. 为什么痛：韩砺年是唯一知道"为什么"的人——如果他不在了——"为什么"就永远丢了
  3. 引出方法：口传必须变成文档——不是"写说明"——是"写为什么这样设计"——每次有人问——答案被记录——变成后来者的"不需要问"
  4. 项目落地：（此章是暴露——韩砺年知道一切——但他没写——因为"觉得不需要"。沈见微意识到——"这不是韩师的错——是没有'写为什么'的文化。")
  5. 多方复盘："韩砺年不是不写——是他以为'大家都知道'——但其实只有他一个人知道。"
  6. 高层收束：口传之链——是最脆弱的链——因为它是一对一的——人走——链断——知识灭。文档——是一对多的——人走——文档在——后来者查得到。

### 第05章：灰印

- **核心对象层**：史→史（**史约锚点首次出现**。沈见微在追查旧代码时——发现一条旧注释——"此处逻辑不应被文档化。"——注释没有署名——没有日期——只有这九个字。这九个字——是梁故川留下的——他是上一任维护者——已经离开了——这九个字——是他的"灰印"——不是写下来的——是留下的——"不文档化"——是一种"写清楚"的反面——"故意不写清楚"。）
- **核心相与失守**：史 → 断史（"不文档化"不是"忘了写"——是"主动选择不写"。为什么？梁故川留下了九个字——但没有留下"为什么不"。灰印——是一个人的决定——但决定的原因——没有被传递——后来者只能猜测。）
- **工程锚点**：（这不是工程——是文明叙事。灰印是明契卷的"史约锚点"——与驭器卷Ch47-48的"残码"、化形卷的"桥账"、简阵卷的"远古告警"——形成四卷的史约线索网。灰印=一个人主动选择"不让后来者知道"——这个选择——指向明契卷最深的问题——"写清楚"的边界在哪里。）
- **张力曲线**：悬疑引入型（沈见微看到旧注释——"此处逻辑不应被文档化。"——"谁写的？""不知道——没有署名——没有日期。""为什么不文档化？""......不知道。"——"这是故意留下的——不是遗漏——是决定。但决定的原因——丢了。"）
- **六拍骨架**：
  1. 问题先出：沈见微在代码深处发现旧注释——"此处逻辑不应被文档化"
  2. 为什么痛：不是"忘了文档化"——是"主动选择不文档化"——但没有写"为什么不"
  3. 引出方法：（悬疑——不解答——这条旧注释将在卷四Ch35-36、卷十Ch95-98、卷十二Ch115-116反复出现——每次揭示更多——最终指向梁故川的完整故事。）
  4. 项目落地：沈见微抄下旧注释——在旁边写——"待查。为什么？"
  5. 多方复盘："最可怕的不是没有文档。是有人故意不文档化——但没有告诉后来者'为什么不'。后来者——不知道是陷阱——还是设计。"
  6. 高层收束：灰印——是"故意留下的空白"——这个空白比错误更大——因为它让后来者不知道——"这里——是路——还是墙。"

- **史约锚点**：灰印=明契卷的"史约第一线索"——与驭器卷的残码`[RESERVED FOR INHERITANCE COVENANT]`并行——但明契卷的线索不是"留下的东西"——是"故意不留下的东西"——"此处逻辑不应被文档化"——是"史约"的反面——"不约"。

### 第06章：止火者

- **核心对象层**：人→人（**裴照川出场**——传奇修补者。旧工具链群的事故蔓延——沈见微一个人堵不住——传讯牌响——但没有人能接——此时——裴照川来了。他不是青炉团队的人——他是"整个世界的止火者"——哪里有火——他去哪里——灭了——然后离开。他是镜像者——他的存在——让沈见微看到了"另一种可能"——"一个人——可以走遍世界——扑灭所有的火。"）
- **核心相与失守**：（裴照川=沈见微的镜像——"如果他可以一个人止住所有火——那我为什么不能一个人写清楚所有东西？"——这是沈见微弧线的起点——也是"写清楚就是一切"的源头——"因为裴照川——一个人修了所有——所以沈见微觉得——一个人写清楚所有——是可能的。"）
- **工程锚点**：事故止火（incident response）——裴照川的止火方法——"不是修根因——是让火不蔓延——先止损——再追根。"这是SRE的核心理念——但裴照川是"一个人版本"的SRE——他走了——没有留下体系——只留下"传奇"。
- **张力曲线**：登场型（裴照川出现——无声——走到最关键的脚本——看——改——部署——火灭——整个过程——十五分钟——没有问任何人——因为他看过所有类似的火——他知道根因在哪——"这不是青炉的火——这是和玄枢一样的火——断火。"）
- **六拍骨架**：
  1. 问题先出：事故蔓延——沈见微独力难支——裴照川出现——止火
  2. 为什么痛：裴照川是"一个人的免疫系统"——他在——火灭——但他在——不等于系统有了免疫——因为免疫在他身上——不在系统里
  3. 引出方法：传奇修补者是双刃剑——"他止住了火——但没有人学到——因为他是'传奇'——没有人问他'你怎么知道的'"
  4. 项目落地：裴照川止火后——没有留下记录——"这是断火——你应该认识。"——然后离开。"你不留下来？""火灭了——我走了。还有别的火。"
  5. 多方复盘："裴照川是旧时代的最高形态——一个人——能止住所有的火。但他的方法——不在任何文档里——在他几十年的经验里——而经验——不可传递。"
  6. 高层收束：最伟大的修补者——也是最大的隐患——因为他的能力——不在系统里——在他一个人身上。他走了——世界失去了免疫。

- **跨卷锚点**：裴照川是明契卷的镜像者——他的"一个人能止所有火"——与沈见微的"一个人能写清楚一切"——形成镜像。裴照川的方法——最终在卷七Ch67-68揭示"另一面"——他的方法本身就是问题的一部分。

### 第07章：不是第一次

- **核心对象层**：史→史（同类事故的历史——"三年前也炸过——五年前也炸过——十年前也炸过。"每一次——有人来止火——火灭了——然后——三年后——再炸。不是因为没有修——是因为"修的——是症状——不是根因"。）
- **核心相与失守**：史 → 断史（事故重演——因为"上一次事故的教训——没有被留下来"。每一次事故——有人写报告——但报告写了——没有人看——因为"这一次和上一次不一样"——但其实根因是一样的——都是"没有人知道为什么"。）
- **工程锚点**：事故分析（incident analysis / postmortem）——不是写报告——是留下"后来者能学到什么"。postmortem的核心是——"不只是修这个bug——是修'这个bug为什么会存在'——和'为什么没有人发现'——和'下一次——怎样在炸之前发现'。"
- **张力曲线**：重复型（沈见微翻旧记录——发现三年前的事故报告——和这次几乎一样——"三年前——结论是'加强测试'——但三年后——测试加强了——事故还是炸了——因为事故不是测试的问题——是'没有人知道为什么测试哪些'。"）
- **六拍骨架**：
  1. 问题先出：沈见微翻出三年前的事故报告——和这次几乎一样
  2. 为什么痛：事故重演——不是因为没有修——是因为没有修根因——"上次修的是症状——不是病"
  3. 引出方法：从"修bug"到"修'bug为什么存在'"——每一次事故——修三层——修bug → 修'为什么没被发现' → 修'怎样让下一次——在炸之前——知道'
  4. 项目落地：沈见微把三年前的事故报告贴在记录板上——旁边是这次的报告——"两次——同样的根因——'没有人知道为什么'。"
  5. 多方复盘："事故不重演——不是因为人变聪明了——是因为'事故的教训——被写下来——被读——被理解——被编进下一次的决策'。"
  6. 高层收束：历史的教训——如果没被写下来——等于没有发生。事故——不是"修好了"——是"后来者知道——同样的坑——这里——注意"。

### 第08章：见病

- **核心对象层**：念→念（从救火到追问——"为什么每次都靠人来补？"沈见微的转向——不是"怎么做更好的救火者"——是"怎样让火不再需要人来补"。这是沈见微从"修补者"到"立约者"的转折——裴照川是"最好的修补者"——但沈见微不想成为他——因为"修补——是在火之后。火不应该有。"）
- **核心相与失守**：（沈见微的第一次觉醒——"靠人来补——是断史。人不在——火就烧。需要的是——让人不在——火也不烧——因为秩序在——不在人的脑子里——在系统里——在'写清楚'里。"）
- **工程锚点**：（哲学转向——从"incident response"到"incident prevention"——不是"更快地修"——是"让火不必被修"——"不是做更好的裴照川——是让裴照川不必存在。"）
- **张力曲线**：觉醒型（沈见微独白——"裴照川走了——下一次火——谁来止？没有人——因为裴照川是唯一的——而我不想成为唯一——我想让'火'——不再需要'止火者'。"）
- **六拍骨架**：
  1. 问题先出：裴照川止火离开后——沈见微看着记录板——"下一次——谁来？"
  2. 为什么痛：不是"我需要变成裴照川"——是"我需要让裴照川不再被需要"
  3. 引出方法：从修补到立约——不是更快地修——是让火——从一开始就不该烧
  4. 项目落地：沈见微在记录板上写——"不是做更好的修补者——是做不需要修补的秩序。"
  5. 多方复盘："裴照川是最伟大的修补者——但修补——意味着东西已经坏了。最好的文明——不需要最伟大的修补者——因为修补——在'坏'之前——就被阻止了。"
  6. 高层收束：见病——不是"看到火"——是看到"火为什么烧"——然后问——"怎样——火不再烧？"

---

### 第09章：立炉之前

- **核心对象层**：约→约（边界先行——不是先做，是先说清不做什么。沈见微在开始建青炉之前——先写scope——"这个项目——要解决什么——不解决什么"。这是"写清楚"的第一步——不是代码——是承诺。）
- **核心相与失守**：（正向——约的雏形。"写下来——不是'我决定了'——是'我承诺——这是边界——边界之内——我负责——边界之外——我不负责——但如果你的需求在边界之外——告诉我——我们可以重新谈边界。'"）
- **工程锚点**：scope definition（项目范围定义）——不是"做什么"——是"不做什么"。"不做什么"比"做什么"更重要——因为"做什么"会膨胀——"不做什么"是边界——保护项目不被膨胀压垮。
- **张力曲线**：建设型（沈见微写第一份scope——"青炉——不是替代旧工具链——是让工具链可以被理解、被测试、被传递。"贺时进——"为什么不先做——让大家先用上？""因为不说清楚——'让大家先用上'——就是'让旧工具链继续膨胀'——不先写边界——永远是救火。")
- **六拍骨架**：
  1. 问题先出：沈见微决定建新工具链之前——先写scope
  2. 为什么痛：旧工具链的问题——就是"没有边界"——什么都能加——加到谁都看不懂
  3. 引出方法：scope不是"做什么"——是"不做什么"——"不做什么"保护项目不被膨胀压垮
  4. 项目落地：沈见微写了第一份scope——"青炉——管理构建、测试、发布——不做运行时监控——不做数据分析——不替代运维系统。"
  5. 多方复盘："边界——不是拒绝使用者——是告诉使用者——'这是我的范围——你的需求如果不在范围内——告诉我——我帮你找对的人。'"
  6. 高层收束：立炉之前——不是先做——是先写——"写——不是束缚——是指南。"

### 第10章：选道而行

- **核心对象层**：念→念（为什么是Rust——不是因为它最强——是因为它的"道"——是"写清楚"。"Rust的编译器——不像C++——它不让你'先做了再说'。它让你——在编译期——说清楚——这个数据属于谁——这个借用什么时候还——这个错误你打算怎么处理。Rust——是'写清楚就是一切'的化身。"——这是沈见微选择Rust的原因——也是他将在卷十一放弃"写清楚就是一切"的起点。）
- **核心相与失守**：（正向——选道。"Rust不是最好的语言——但它的'道'——最接近青炉需要的：让承诺在编译期被验证——不是靠人的记忆——是靠编译器。"）
- **工程锚点**：Rust的设计哲学——ownership（所有权）、borrowing（借用）、lifetime（生命周期）、Result/Option（错误即值）、Send/Sync（并发安全在类型层）。"这些——不是语法——是'在编译期让承诺被验证'的机制。C++能做到——但靠人的纪律——Rust靠编译器——编译器不让你忘。"
- **张力曲线**：决断型（沈见微——"为什么Rust？因为它的'道'——就是青炉需要的：写清楚。但——"他停顿了——"写清楚——够吗？我不知道。但至少——Rust让'不清楚'在编译期就被发现——而不是在生产环境——凌晨——炸。"）
- **六拍骨架**：
  1. 问题先出：沈见微决定选道——为什么是Rust
  2. 为什么痛：旧工具链用多种语言——互相不理解——没有编译器在中间做保障
  3. 引出方法：Rust的设计哲学——"让承诺在编译期被验证"——不是靠人——是靠编译器
  4. 项目落地：沈见微写下选道声明——"青炉——Rust——不是因为Rust最强——是因为它的道——最接近'写清楚'。"
  5. 多方复盘：（伏笔）——"但沈见微现在还不知道——'写清楚'本身——会变成新的黑箱——'清楚'——在不同语境——意思是不同的。那是卷十一——放弃的时候——他才会理解。"
  6. 高层收束：选道——不是"选最好的工具"——是"选最契合'承诺'的工具"——然后——走——走到尽头——发现——工具是对的——但工具不够。
