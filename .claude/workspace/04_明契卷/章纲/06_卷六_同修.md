# 卷六「同修」Ch 51-60：Git·review·门规

## Section 总览

- **章段**：Ch 51-60
- **叙事主题**：从一个人到一群人——Git哲学（commit=因果秩序）、分支策略、merge conflict、review文化、闻衡打回PR、苏野平登场（化形之道同门者）、"先跑通"vs"先写清"的道统碰撞。
- **核心冲突**：同修——不是"大家一起写代码"——是"每个人的'写清楚'——在不同的层面上——有不同的标准"。苏野平的"先跑通"——是化形之道——"temporary is permanent"——与沈见微的"先写清"——正面碰撞。
- **工具链阶段**：Git / branch / merge / remote / review / PR规范
- **对象层**：门→门（从个人机制——到团队机制——到协作文化）
- **主相→蚀**：契 → 背契（merge conflict=两个人都做了对的事——但没有互相告诉）
- **主角状态**：沈见微从"我的写清楚"——到"团队的写清楚"——到"别的道——也有它的写清楚——只是写的方式不同"

---

### 第51章：留影为史

- **核心对象层**：史→史（Git不只是备份——commit是因果秩序。"每一次commit——是'我在这个时间——基于这些原因——做了这个变更'。——commit message——不是'修了bug'——是'修了什么bug——为什么存在——修了之后——如何验证'。——commit——是写下来的历史——后来者——在git log里——看到历史——不是看到'一堆代码改了'——是看到'为什么改'。"）
- **工程锚点**：Git——版本控制系统——commit=不可篡改的历史记录——commit message=变更的理由——"好的commit message——让后来者知道——这个变更——当时是为了什么——什么条件下做的——如果条件变了——这个变更可能需要重新审视。"
- **六拍骨架**：沈见微写青炉的第一个commit——"Initial commit: 青炉——从旧工具链群的事故中诞生。此commit——不完整——只包含scope和Cargo.toml。——后来者：接下来——每一行——都会写'为什么'。——不是代码的'为什么'——是决策的'为什么'。"

---

### 第52章：分支之上

- **核心对象层**：史→史（branch/merge——并行与汇合的艺术。"分支——不是'分开做'——是'各自在自己的轨道上——不互相阻碍——然后——汇合——在汇合时——检查——两条路——有没有撞'。branch——是文明的并行——每个人在各自的方向——走——然后——在merge时——对话。"）
- **工程锚点**：Git分支策略——feature branch → PR → review → merge——"不是'主干是真理'——是'每条branch是一个假说——在merge时——验证假说是否和主干不冲突'。"
- **六拍骨架**：沈见微建青炉的main分支——"每一条feature——在自己branch上——开发——测试——闻衡审契——通过——merge。——不是效率低——是让每个人——在自己的节奏上——不被别人打断。"

---

### 第53章：千里传书

- **核心对象层**：门→门（远端仓库与协作秩序——remote/协作。"不是'代码在GitHub上'——是'代码的权威版本——在远端——每个人从远端拉——推到远端——经过review——远端是唯一的真相来源'。——旧工具链——代码散落在各自机器上——'谁的机器上的是最新版'——不知道。远端——是'真相只有一个'。"）
- **工程锚点**：Git remote——origin/main=权威版本——pull/push/fetch——"不是'把代码放网上'——是'让分布式协作——有一个共同的权威版本'。"
- **六拍骨架**：沈见微设青炉的远端——"不是备份——是'真相'——真相——在远端——每个人从它开始——向它提交——经过验证——才成为新的真相。"

---

### 第54章：第一次冲突

- **核心对象层**：契 → 背契（merge conflict——两个人都改了对的事——"你改了配置文件——加了参数——我也改了——删了一个旧的——但我们改的是同一行——Git不知道——谁对——因为它不知道'你们两个——在改之前——聊过吗'。"——merge conflict——是"没有互相告诉——各自做了正确的判断——但判断——相互冲突"——这是背契——因为"契约——不只是代码——是'我做之前——告诉你会影响你'。"）
- **六拍骨架**：第一次merge conflict——沈见微和季循——各自改了同一段逻辑——各自都对——但合在一起——不兼容。"我们没有聊——因为我们觉得——'我们做的——是分开的事'——但代码——不是分开的——它在同一行——我们撞了。——不是Git的错——是我们的——没有在改之前——告诉对方。"

---

### 第55章：门规初成

- **核心对象层**：门→门（提交规范、评审文化与新人接引。"不是'怎么写commit'——是'写——让后来者知道——发生了什么事'。"Conventional Commits——`feat:`/`fix:`/`docs:`/`refactor:`/`test:`/`chore:`——"不是形式——是信号——让后来者——扫一遍log——就知道——这个版本——主要做了什么。")
- **工程锚点**：Conventional Commits + PR template + review checklist——"每一条——都是'写清楚'的具体实践——在commit层面——在PR层面——在review层面。"
- **六拍骨架**：闻衡写PR template——"PR标题——简短描述做了什么。PR描述——为什么做——什么场景需要——怎么验证——影响了谁。——不是'写得多'——是'让reviewer不需要猜'。"

---

### 第56章：闻衡不通过

- **核心对象层**：契→契（一个PR被闻衡打回——不是因为错——是因为没写清。"你的代码——是好的——但你的描述——'修了一个bug'——我不接受。修了什么bug——谁报告的——在什么场景下出现——为什么之前的测试没抓到——修了之后——怎么确保这个bug不会再出现。——我需要的——不是'你修了'——是'后来者——读你的PR——知道这个bug的完整故事'。")
- **六拍骨架**：闻衡——"我不是在找bug——我在找'没写清楚的地方'。因为代码的bug——编译器能找到——但文档的bug——只有人能找——而文档的bug——在生产环境——代码不会告诉你——只有凌晨接传讯牌的人——能找到。"

---

### 第57章：苏野平的脚本

- **核心对象层**：人→人（**跨卷人物深度**——苏野平——化形之道的同门者——"我那边有个脚本能帮上"——他从息壤过来——带着Python的生态——pip——脚本的快——"不需要写清楚——先跑通——再迭代"。——他是"先跑通"的化身——不是坏——是另一种"道"。）
- **六拍骨架**：苏野平——"沈见微——我写了个脚本——能在青炉构建之前——自动检查依赖的兼容性——Python写的——用了pip-audit——很快——我放你workspace里。""你的脚本——文档在哪？""呃——看代码——很简单的——三百行——不需要文档。""三百行——不需要文档——但后来者——看到py文件——不知道它做什么——什么时候该跑——什么时候不该。——'简单'——不等于——'清楚'。"

---

### 第58章：快与对的张力

- **核心对象层**：念→念（苏野平的"先跑通"与沈见微的"先写清"——两个"道"的正式碰撞。"你写的scope——写了三天——我等不了三天——我的用户等不了——他们需要'能用'——不是'完美'。——你的'先跑通'——让用户现在能用——但三个月后——脚本成墙——他们在凌晨撞墙——那时候——你在哪？"——这不是对错之争——是两种文明的选择——"快——代价是墙。慢——代价是等。——没有最优——只有'在什么场景下——选哪条路'。"）
- **六拍骨架**：苏野平——"不是所有东西都需要'写清楚'。有些东西——临时的——用完就扔——写文档是浪费。""你怎么知道——什么时候扔？如果'临时'的——被团队复制——被依赖——变成了'基础组件'——然后——没有人知道它是'临时'的——它不是被你'扔'的——是'永远留下来了——但没有人知道为什么'。"

---

### 第59章：团队成形

- **核心对象层**：人→阵（从一个人到一群人——同修者的秩序。"沈见微——写scope。闻衡——审契。顾迁衡——搭桥。季循——第一个使用者+继承者。苏野平——提供速度——在需要'快'的时候。程知序——使用者——验证'清楚'是否真的清楚。——每个人——在自己的位上——不是沈见微的'下属'——是青炉的共建者。"）
- **六拍骨架**：记录板上——团队名单——不是"沈见微"一个人——是"青炉同修者"——每个人有自己的专长——自己的"道"——在青炉这个workspace里——并行。

---

### 第60章：同修之后

- **核心对象层**：念→念（有了团队——但团队意味着更多需要写清的承诺。"一个人——我可以自言自语——在心里——不写。一群人——每个人——以为别人知道——但其实——只有你知道。——团队——不是因为人多——更清楚——是因为人多——更需要写清楚——因为你的'以为'——不在别人的脑子里。"）
- **六拍骨架**：卷尾——"同修——是好的——但同修需要更多的'约'——不是更少。因为我不能假设——别人知道我在想什么。——我必须写——写清楚——不只为我——为团队——为后来加入的人——为不在场的人。"

> 📝 卷尾。Git哲学建立——review文化建立——苏野平碰撞——团队成形。向卷七（守界——内存安全·并发·unsafe——裴照川的另一面）过渡。
