# 《万构界·明契卷》正式章纲：卷四到卷六

## 一、章纲定位

本章纲用于把《明契卷》中段最关键的卷四到卷六，从“十卷三十章母蓝图”继续压成可直接开写的正式章纲。

本轮只处理：

1. 卷四：筑基立制
2. 卷五：结丹成阵
3. 卷六：同门共修

选择先压这三卷，是因为它们负责解决《明契卷》当前中段最容易松掉的三处逻辑风险：

- 青炉会不会刚做出最小入口，就重新滑回“只在我机器能跑”
- 青炉会不会因为过早抽象、过快拆骨，再造一套新的内部黑箱
- 青炉会不会一直停留在“主角项目”，无法真正变成门内公共秩序

---

## 二、中段裁定

卷四到卷六统一承担《明契卷》的“中段真相”：

**真正危险的不只是旧工具烂，而是新工具也很容易在成长中复制旧病。**

这意味着：

1. 卷四必须把“只在我机器能跑”的病写成具体场景，而不是抽象口号
2. 卷五必须把“优雅抽象”与“可继承”之间的冲突写成项目内部共同体之争
3. 卷六必须让青炉第一次面对真正的协作、评审、门规与新人接引压力

---

## 三、卷四：筑基立制

使命：让青炉从“可用”进入“可维护”。这一卷必须让读者看见，项目的第二层病不是做不出来，而是做出来之后是否还能被别人稳定接住。

### 第十章：骨架初定，目录结构与核心抽离

- 青炉第一版虽然可用，但关键逻辑仍然大量缠在入口层
- 季循尝试给 `check` 增补一条新校验，结果发现参数解析、配置读取、校验规则与输出文案还纠缠在一起
- 韩砺年提醒主角：若现在就大拆，极可能把现实窗口再度打断
- 程知序则从使用侧反逼：若继续所有逻辑都挂在入口壳上，别人永远不知道哪一段是真正的骨
- 沈见微决定不先拆成大工程，而是先把“最核心的那根骨”从入口壳里抽出
- 本章必须落成三个可见动作：
  - `main.rs` 退回入口协调层
  - 最小核心能力被抽成独立模块
  - 模块地图第一次写进项目记忆
- 本章结尾要让季循第一次能沿结构而不是沿口传进入项目

教学点：

- 目录结构
- 核心抽离
- 模块地图
- 为什么“留位置”本身就是对后来者的责任

角色压力落点：

- 继承者：暴露“可用”和“可读”不是一回事
- 使用者：要求结构调整不能毁掉当下可信入口
- 守门者：提醒重构也会制造断流风险

### 第十一章：炉候可调，配置、环境与命令行参数

- 青炉在主角机器与季循机器上第一次出现“同命令不同结果”的新症状
- 追查后发现，问题不再来自旧脚本本身，而来自：
  - 一个没写进说明的环境变量优先级
  - 一条默认路径假设
  - 一处仍沿用旧桥位置的本地缓存
- 苏野平主张保留环境暗门，因为这能继续帮现场救火
- 闻衡则明确指出：如果新器继续靠暗门维持便利，那只是把旧病换了个壳
- 沈见微必须在这章里正式写出配置边界：
  - 什么属于 CLI 显式参数
  - 什么属于配置文件
  - 什么可以作为环境补充
  - 什么绝不能再藏在个人机器里
- 本章结尾必须落在一句更重的话上：
  - 若默认值不能解释，它就不是默认值，而是未来的事故埋点

教学点：

- config
- env
- CLI 参数优先级
- 默认值与行为一致性

角色压力落点：

- 同门者：为快路与暗门辩护
- 审契者：逼配置前提必须外显
- 主角：第一次承认新器也会复制旧病

### 第十二章：经卷留痕，文档、注释与项目记忆

- 结构与配置刚被立住，团队内部立刻出现另一种失真：
  - 代码开始变清楚
  - 但项目为什么这样长成，仍然只在几个人嘴里
- 程知序想知道：哪些输出现在可以真正当成对外承诺
- 季循想知道：哪些目录、字段与规则是暂定，哪些已经可依赖
- 韩砺年最抗拒写文，因为他知道一旦写下，就要对变化负责
- 闻衡则逼众人承认：若 README、设计说明、注释和变更理由仍然不分层，新史只会比旧史更快失真
- 沈见微在这章必须写下三层项目记忆：
  - README：给第一次进入者看
  - 设计说明：解释为何如此分骨
  - 注释：只留代码读者真正需要的局部理由
- 本章结尾必须让读者看见：
  - 青炉第一次不只存在于代码里
  - 它开始拥有公共记忆

教学点：

- README
- 设计说明
- 注释边界
- 项目记忆分层

角色压力落点：

- 守门者：代表“变化太快，写了也没用”的惯性
- 审契者：代表“若不写清，变化只会更糟”
- 继承者：代表真正依赖这些文档的人

---

## 四、卷五：结丹成阵

使命：让青炉从单体器胚进入多骨同炉。这一卷必须把“内部共同体”第一次真正写出来。

### 第十三章：契口分层，CLI 不等于万能入口

- 随着 `check` 以外的新入口开始被要求接入，`main.rs` 再次变厚
- 贺时进希望趁现实窗口一次把常用辅助动作都塞进 CLI
- 苏野平则建议先保留一个厚壳，把所有新东西挂进去再说
- 沈见微拒绝让 CLI 再次成为万能壳，决定把“别人真正会复用的部分”和“对人类说话的部分”拆开
- 这一章必须形成三个清楚动作：
  - 核心能力退到 `qinglu-core`
  - 命令入口留在 `qinglu-cli`
  - 配置解析开始从入口里剥离
- 季循第一次真正接手一段清楚的边界，而不是接手一锅混合逻辑
- 本章结尾必须让读者意识到：
  - 分骨不是为了好看
  - 分骨是为了不把未来协作再压成一人脑中的整团直觉

教学点：

- core 与 shell 分离
- 公共 API
- 能力复用与入口分层

角色压力落点：

- 诱惑者：推动“先都塞进去再说”
- 继承者：证明边界清楚后才能真正接手
- 主角：承受“拆骨会拖慢窗口”的压力

### 第十四章：宗门初立，workspace 与多 crate 协同

- 青炉完成第一轮分骨后，新的问题马上出现：
  - 各骨开始互相依赖
  - 版本与路径关系开始复杂化
  - 多人改动第一次真正发生冲撞
- 季循和程知序分别从不同入口提交改动，结果因为项目边界与依赖关系仍不统一，再次产生“你以为我知道”的断口
- 韩砺年开始第一次松口，因为 workspace 让他看见“这不是又一套私人壳”，而是一条能把多人拉进同一炉的路
- 沈见微必须在这章里正式立起：
  - workspace
  - 共用依赖策略
  - 多骨协同的最小共约
- 本章结尾必须让“项目内小共同体”第一次成形：
  - 人开始按骨分工
  - 但仍能沿同一套史与约协作

教学点：

- workspace
- 多 crate 协同
- 共约与共史

角色压力落点：

- 使用者：反向逼项目不要因为内部拆骨失去入口稳定
- 守门者：开始从“怕断”转向“愿意交一点火”
- 主角：第一次处理“不是一个人写”的项目形态

### 第十五章：阵法有门，trait、泛型与抽象的节制

- 青炉进入多骨协同后，最危险的诱惑不再是旧脚本，而是“过早抽象”
- 季循与苏野平都被某个漂亮的大接口吸引，觉得只要先做一个覆盖一切的 trait，未来所有规则和插件都能优雅接上
- 闻衡立刻指出：若此刻把还没成熟的责任关系一起抽成共门，新器就会长出新的假统一
- 沈见微在这章必须做出一次真正困难的拒绝：
  - 放弃一个形式上很优雅的大抽象
  - 保留几个更笨、更小、但语义清楚的接口
- 本章必须把《明契卷》中段真相真正说透：
  - 不是所有“看起来更高级”的结构都更有路
  - 有些抽象只是把今天的不确定，提前冻结成明天更难拆的壳
- 章尾要落在一种更成熟的判断上：
  - 优雅要服从可继承

教学点：

- trait
- 泛型
- 抽象边界
- 什么时候该停手

角色压力落点：

- 同门者：代表速度、灵感与漂亮结构的真实诱惑
- 审契者：代表对“抽象也必须立约”的强压
- 主角：第一次主动放弃技术上很诱人的短期最优

---

## 五、卷六：同门共修

使命：让青炉从个人项目变成真正的门内公共秩序。这一卷必须把“史”“门规”“共修”第一次写成能运转的现实。

### 第十六章：留影为史，Git 不只是备份

- 青炉开始进入多人修改阶段后，旧世界遗留的本地补丁与口头说明再次暴露问题
- 韩砺年手上有一段过去救过命的临时改动，但它只存在于一份未公开留痕的旧副本里
- 季循第一次意识到：若历史只存在于“谁还记得”，那青炉迟早会步旧工具链后尘
- 沈见微在这章必须把 Git 从“备份工具”改写成“项目内史”：
  - commit 不只是存档
  - branch 不只是分叉
  - tag 不只是打点
- 本章结尾要让历史第一次被认真地写进公共路径，而不是只存在于老手机器里

教学点：

- commit
- branch
- tag
- log
- Git 作为内史

角色压力落点：

- 守门者：代表“我做过，但没留痕”的旧式责任
- 继承者：代表真正需要沿历史回查的人
- 主角：把个人记忆转成交给共同体的史

### 第十七章：千里传书，远端仓库与协作秩序

- 当青炉的修改不再局限于身边几人时，问题从“怎么改”转成“怎样共同改”
- 程知序第一次不再只当使用者，而是从使用侧提出清楚的问题单
- 季循第一次把自己的改动整理成能被别人读的提交链
- 贺时进强烈要求直接合入，因为现实窗口不等人
- 闻衡坚持：若没有远端共同入口、issue 与 PR，所谓协作仍然只是“把代码传来传去”
- 沈见微必须在这章里正式立起：
  - 远端仓库
  - issue / PR
  - 讨论与修改的公共入口
- 本章结尾必须让青炉第一次面对“门外之问”：
  - 别人能提问题
  - 别人能沿公开入口参与
  - 主角不能再独占解释权

教学点：

- remote
- issue
- pull request
- 远端协作秩序

角色压力落点：

- 使用者：第一次反向塑形项目秩序
- 诱惑者：代表“直接合进来最省事”的短期压力
- 审契者：代表公共入口必须清楚

### 第十八章：门规初成，提交规范、评审文化与新人接引

- 远端协作刚立起，团队立刻遇见更难的一关：
  - 谁来评
  - 评什么
  - 新人怎样第一次不靠人情进门
- 季循提交第一份几乎能独立成立的 PR，却在 review 中暴露出：
  - 提交历史仍不够清楚
  - 错误说明仍有含糊
  - 文档更新仍未跟上
- 苏野平认为评审太慢，现实里根本不会给这么多礼貌空间
- 闻衡则逼众人承认：如果 review 只在关系好时才认真，那门规就还没有真正存在
- 沈见微在这章必须把青炉的初代门规写下来：
  - 提交规范
  - review 规则
  - 贡献指南
  - 新人接引入口
- 本章结尾不能只是“制度写完了”，而必须出现一次真正的门规验证：
  - 一个不是主角的人，按规则提改动
  - 一个不是主角的人，按规则完成评审
  - 青炉第一次显出“公共之门”的轮廓

教学点：

- review
- CI
- 贡献指南
- 新人接引
- 门规

角色压力落点：

- 继承者：代表新人是否真能进门
- 审契者：代表门规不能只写给熟人看
- 主角：第一次把解释权真正交出去一部分

## 六、卷四到卷六已固定的三个锚点

### 1. 中段真相

已固定为：

**青炉真正的危险不是做不出来，而是做出来之后随时可能复制旧病。**

### 2. 项目内共同体成形

已固定为：

**从卷五开始，青炉必须不再只是主角项目，而是多骨协同的小共同体。**

### 3. 初代门规验证

已固定为：

**卷六结尾必须出现一次不靠主角独占解释权的 review 与接引验证。**

## 七、本轮修掉的不足

本文件主要修掉了下面四处旧缺口：

1. 卷四“只在我机器能跑”的病灶，已经进入具体场景
2. 卷五“项目内共同体形成”的冲突，已经压进正式章纲
3. 卷六“评审文化与新人接引”的戏剧节点，已经固定
4. 《明契卷》中段真相不再只是抽象命题，而是具体到结构、配置、抽象与门规的多重复制风险
