# 卷二「绿色谎言」Ch 11-20：值班制度缺失

## Section 总览

- **章段**：Ch 11-20
- **叙事主题**：凌晨对账事故全面爆发——43条传讯牌的历史，"刚好醒着"不是制度。乔落登场——三个月的新人，凌晨两点接了传讯牌。
- **核心冲突**：健康检查骗了所有人。模板全绿不等于能安全过夜。而当事故真的发生——没有on-call制度——只有一个刚好醒着的人。
- **工具链阶段**：日志觉醒 / 传讯牌历史 / on-call缺失 / 模板困境
- **对象层**：器→阵（从单个服务的故障到"整个平台的运维危机"）
- **主相→蚀**：流 → 乱流 + 契 → 背契（运行时失控+值班责任的真空）
- **主角状态**：从"接手者"到"被叫醒的人"。傅远洲的凌晨不再是他自己的——因为他是唯一一个"刚好醒着"的人。
- **张力引擎**：凌晨事故是最诚实的——因为它暴露了所有"看起来正常"的东西在深夜的真相。没有值班制度——每个凌晨的事故最后都是同一个人在处理。
- **卷尾落点**：健康检查骗了所有人——下一步不只是让人看得见——是让"看"有责任人。

### 第11章：绿色不意味着活着

- **核心对象层**：流→流（凌晨对账事故——30%卡住，监控全绿。全章事故展开。）
- **核心相与失守**：流 → 乱流（事故的本质——监控看不到"进展"——只能看到"活着"。活着不等于在工作。）
- **工程锚点**：事故的不可见性（invisible incident）——健康检查不监测业务指标（business metrics / SLI）。处理中的业务是否在进展——不在任何监控面板上。对账服务本身完全正常——它调用的下游服务返回了空数据。
- **张力曲线**：崩塌型（凌晨两点→对账卡在30%→无告警→傅远洲被传讯牌叫醒→追查→发现四个服务都"活着"但它们之间的数据流断了→"不是任何一个服务的错。是他们之间的空白里出了问题。"）
- **角色焦点**：傅远洲（全章POV——凌晨被叫醒。追查事故。不是第一次被叫醒——但这一次他决定不再"修好了就回去睡"。）
- **六拍骨架**：
  1. 问题先出：凌晨——对账任务卡在30%。监控全绿——没有告警。
  2. 为什么痛：追查——A服务在正常运行，B服务也在正常运行——但A传给B的数据是空的。B没有告警——因为它成功处理了"空数据"。"这不是故障。这是更危险的东西——一个系统在稳定地做错误的事。"
  3. 引出方法：事故链的分析——五个服务串成一条流水线。第三个服务——`data-aggregator`——因为上游格式变更抛了一个未知异常——异常被catch了——返回了默认的空数据集。下游的所有服务都正常处理了空数据——没有报错。
  4. 项目落地：事故恢复后——傅远洲在记录板上画了事故链——五个服务，一个沉默的异常，30%的对账卡了三个时辰。"这不是一次事故。这是49次——同一个服务的同一个异常在过去六个月里发生了49次——每次都被catch——每次都没人知道——直到它参与了一条足够长的链——对账卡住了。"
  5. 多方复盘：秦望秋（即将在Ch23登场）："如果观测不只看'是否活着'——而看'是否在进展'——这个异常不会被沉默六个月。"这是从外部被提到的秦望秋——观测体系的引入。
  6. 高层收束：绿色是谎言——不是因为有人撒谎——是因为"绿色"的定义太窄了。一个系统可以全绿——并且在稳定地生产错误。
- **入门检查**：前置：Ch06-07 / 新术语：业务指标（business metrics / SLI）、事故链（incident chain）、沉默异常（silent exception）（≤3）
- **三问预检**：🩻乱流（五个服务的沉默异常——六个月无人知晓） 😣依赖对账结果的所有下游团队——他们对账的数据是错的 🛤️开始——观测需要看到"进展"——不只是"活着"
- **并发/观测/简洁/部署**：goroutine/日志觉醒/绿色谎言崩塌/手动→部署未知

> 📝 **路标章**：对应旧Ch02。保留凌晨对账事故的核心场景。新增：事故链分析+沉默异常六个月无人知晓的发现。

### 第12章：谁在值班

- **核心对象层**：阵→阵（43条凌晨传讯牌——"刚好醒着"不是制度。on-call缺失的完整暴露。）
- **核心相与失守**：契 → 背契（平台承诺"有人值守"——但实际上只是"刚好有人醒着"。承诺是假的——不是在内容上——在结构上。）
- **工程锚点**：on-call（值班）制度的设计——不是"指定谁在值班"——是建立"责任->响应"的完整链。缺少on-call的系统——所有事故都变成"刚好醒着的人的事"。那个人——通常是平台负责人。
- **张力曲线**：倒钩型（事故后——傅远洲拉出驿河的传讯牌历史→过去三个月——43条凌晨传讯牌→其中32条是他回复的→剩下11条——"没人回复"。)
- **角色焦点**：傅远洲（看着传讯牌历史——"我不是在值班。我只是刚好醒着。"）；团队（面对数据——每个人都被沉默击中了。）
- **六拍骨架**：
  1. 问题先出：傅远洲拉出传讯牌历史——"让我看看——到底是谁在值班。"
  2. 为什么痛：三个月——43条凌晨告警。32条——傅远洲回复。6条——三个不同的人各回复两次。"刚好醒了"。5条——没有人回复。告警发了——没有人看到——服务自己恢复了——或者没有恢复——但没有人知道。
  3. 引出方法：on-call的三要素——(a) 谁：每个时段明确的人 (b) 如何：升级路径——如果第一个人没回复，第二个人是谁 (c) 知道什么：runbook——接牌后该做什么。"驿河——三项都没有。"
  4. 项目落地：傅远洲在传讯牌数据表旁边贴了一行："我睡了五个月——不是完整觉。是我的问题——不是因为我没有设定on-call——是因为我不肯承认——'刚好醒着'不是制度。它是侥幸。侥幸不是系统——是系统的缺失。"
  5. 多方复盘："所以我们没有一个平台。我们只是23个人——各自在51个服务上——祈祷凌晨不会出问题。"
  6. 高层收束：值班不是美德——是制度。不建立制度——最负责任的人——承担最多的凌晨。这不是公平——这是惩罚。

- **入门检查**：前置：Ch11 / 新术语：on-call（值班）、传讯牌（pager / alerting）、升级路径（escalation path）、runbook（≤4）
- **三问预检**：🩻背契（平台的"有人值守"承诺——在结构上是空的） 😣傅远洲——"刚好醒着"让他承担了所有凌晨 🛤️开始——数据让"侥幸"变成可见的——下一步是制度
- **并发/观测/简洁/部署**：goroutine/日志觉醒/值班缺失/scp

> 📝 **路标章**：对应旧Ch03。保留43条传讯牌+傅远洲数据发现的核心场景。

### 第13章：乔落登场

- **核心对象层**：人→人（继承者建立——乔落，三个月的新人。凌晨两点接了传讯牌——不知道为什么是自己。）
- **核心相与失守**：（人物建立章——乔落的定位：后来者的具象化。他不是主角——但他代表驿河的未来。他能不能接住——将检验这个平台是否"可继"。）
- **工程锚点**：新人的on-call体验——在缺少runbook和ownership的制度中——接传讯牌 = 被胁迫。"你不知道这是不是你的责任——但你知道如果没人接——事情会更糟。这不是on-call——这是道德绑架。"
- **张力曲线**：人物建立型（凌晨→传讯牌响→乔落被惊醒→看着牌子——他不知道上面写的服务是什么——但他接了。因为他听到了传讯牌——"没有人接——我不能假装没听到。"）
- **角色焦点**：乔落（全章POV——新人凌晨接传讯牌的全过程。不是英雄主义——是无知+责任心被有缺陷的制度利用。）
- **六拍骨架**：
  1. 问题先出：凌晨两点——乔落被传讯牌叫醒。三个月前入职——这是他第一次看到传讯牌。
  2. 为什么痛：他不懂那个服务——他打开runbook——是空的。"runbook: TODO"。
  3. 引出方法：新人的on-call困境——他用最原始的方法排查：看日志→找错误→看不懂→Grep代码→找到一个超时设置→手动延长→重启→对账开始推进。不是英雄——是撞上了正确的方向。
  4. 项目落地：对账恢复了。乔落花了两个半时辰。一个老手可能只需二十分钟。"我修好了——但我不知道我修的是症状还是病根。"他在runbook上写了一行："问题——下游服务超时。临时方案——延长超时。需确认——根因是否为下游数据格式问题。"
  5. 多方复盘：第二天——傅远洲问谁处理了对账事故。一个声音："是我。"三个月的新人。傅远洲看着他——"你不知道你在修什么。""我知道。我宁愿不知道——但我不能假装没听到。"
  6. 高层收束：乔落——继承者的登场。不是在舒适中建立——而是在凌晨被推进一个制度缺失的黑洞——靠自己爬了出来。这是驿河未来的缩影——后来者需要能在黑暗中找路。

- **入门检查**：前置：Ch12 / 新术语：on-call困境（on-call dilemma）、排错（troubleshooting）、临时方案（workaround）（≤3）
- **三问预检**：🩻背契（制度缺失——让新人为整个平台的缺陷买单） 😣乔落——他的凌晨被消耗在了前人的沉默里 🛤️开始——乔落的runbook注解——是第一块"后来者给后来者"的砖
- **并发/观测/简洁/部署**：goroutine/日志/新人vs缺失制度/scp→Docker意识

### 第14章：传讯牌的历史

- **核心对象层**：史→史（传讯牌的考古——从4条到43条，没有一条被认领。传讯牌不是突然变多的——是一点一点被接受的。）
- **核心相与失守**：史 → 断史（传讯牌的历史——反映了平台运维责任从"无人负责"到"任何人都可以负责——但实际上没有人负责"的渐变。）
- **工程锚点**：告警的语义退化（alert fatigue / alarm desensitization）——当一个系统有43条告警而大多数都是误报或无人认领——告警不再意味着"出事了"。它意味着"又有一条——也许重要也许不重要"。
- **张力曲线**：考古型（秦望秋尚未登场——但傅远洲和团队考古了43条传讯牌的历史。第一条——三年前："deploy成功——但服务无响应"。回复——"重启解决。"第二条——"同上。"第三条——"同上。"十条之后——没有人再回复了。它们变成了背景噪音。）
- **角色焦点**：傅远洲（考古者——不是追责，是理解。"这些传讯牌不是在怪任何人。它们是在说——这个平台太复杂了——一个人管不了。")
- **六拍骨架**：
  1. 问题先出：傅远洲翻看传讯牌记录——从第一条开始
  2. 为什么痛：第一条到第三条——有人回复。第四到第十——有人回复，但越来越敷衍。第十一到第四十三条——基本无人回复。告警在跑——但没有人看。
  3. 引出方法：告警疲劳的阶梯——(a) 告警有意义→认真回复 (b) 告警太多→选择性回复 (c) 告警有太多假阳性→不信任→不再看 (d) 告警变成背景噪音→真正的告警被淹没
  4. 项目落地：傅远洲标记了43条告警中的28条为"假阳性或已自动恢复"——意味着三分之二的告警在浪费所有人的注意力。"这不是告警系统。这是注意力粉碎机。真正需要关注的告警——被假的盖住了。"
  5. 多方复盘："我们需要告警设计——不是每件事都值得叫醒一个人。什么是凌晨三点值得叫醒一个人的事？数据丢失。对账停滞超过半个时辰。关键下游连续失败。不是'某个服务的CPU超过80%了'——除非那个80%已经持续了一个时辰。"
  6. 高层收束：告警不是免费的。每一条告警都在消耗一个人的注意力。43条=43次注意力消耗。当注意力被消耗殆尽——真正的告警就没人看了。

- **入门检查**：前置：Ch12-13 / 新术语：告警疲劳（alert fatigue / alarm desensitization）、假阳性（false positive）、注意力消耗（attention cost）（≤3）
- **三问预检**：🩻断史（告警的历史是责任逐渐漂移的历史——无人认领→无人回复→无人看） 😣真正需要帮助的人——他们的告警被淹没在假阳性里 🛤️开始——告警审计
- **并发/观测/简洁/部署**：goroutine/日志进化/告警语义退化/scp

### 第15章：刚好醒着

- **核心对象层**：人→念（"我刚好醒着"——傅远洲的凌晨成了默认值班。隐性on-call的代价：不是一个人在值班——是平台在靠一个人的睡眠运营。）
- **核心相与失守**：契 → 背契（隐性on-call——没有被正式承认但被所有人习惯——"傅远洲会接"。这不是信任——是依赖。）
- **工程锚点**：隐性on-call（implicit on-call）的工程人类学——当一个系统中最能干的人总是接传讯牌——其他人不再觉得需要接。"他会处理的"——这句话让平台从"共同责任"变成"一个人的责任"——而没有经过任何人的同意。
- **张力曲线**：情感复合型（傅远洲凌晨三点——看着传讯牌——犹豫。接——他是三十二次中的又又一次。不接——没有人接。）
- **角色焦点**：傅远洲（全章独白——"刚好醒着"不是美德。是教训——制度不能靠一个人的睡眠。）
- **六拍骨架**：
  1. 问题先出：凌晨三点——传讯牌又响了。傅远洲醒了——没有立刻接。
  2. 为什么痛：他数了一下——这是这个月的第八次。"我在今天早上三点不是一个平台负责人。我是一个刚好醒着的人。我的刚好醒着——变成了这个平台的唯一保底。没有我——凌晨对账卡住了——明天所有人都要加班。不是因为别人不能处理——是因为没有人觉得这是自己的责任。"
  3. 引出方法：隐性on-call的病理——(a) 隐性on-call的人不被承认——但被依赖 (b) 隐性on-call的依赖者不知道自己在依赖 (c) 隐性on-call让正式的on-call制度被推迟——"反正有人在接"
  4. 项目落地：傅远洲接了——处理了。第二天——他在公共记录板上写："昨晚的事故——在传讯牌记录中是我处理的——但实际上不是我。是'刚好醒着'的我。'刚好醒着'不是制度——它是侥幸的反面：侥幸每天都在重复——但总有一天会不重复。那一天——没有人醒着。"
  5. 多方复盘：团队中有一个人说："我以为你自愿的。""我是。但我自愿——不等于这个制度是对的。我自愿——意味着你们不需要面对'没有我怎么办'。这对你们——不公平。"
  6. 高层收束：隐性on-call——是工程组织最危险的寄生关系。寄生者不是恶意——是被制度缺失喂大的习惯。

- **入门检查**：前置：Ch12, Ch14 / 新术语：隐性on-call（implicit on-call）、责任寄生（responsibility parasitism）（≤2）
- **三问预检**：🩻背契（平台的"有人在守"——实际上只建立在一个人自愿的睡眠碎片化上） 😣傅远洲——他和他的睡眠 🛤️开始——公开承认"刚好醒着"不是制度
- **并发/观测/简洁/部署**：goroutine/日志/隐性依赖/scp→Docker

### 第16章：乔落的第一次

- **核心对象层**：人→人（乔落第一次接传讯牌之后——面对的不只是事故——是"我不知道我做的对不对"的虚无感。继承者的核心困境。）
- **核心相与失守**：式 → 失式（没有runbook——没有标准——新人的"判断"缺乏任何验证。他做了——但没有人告诉他他对了没有。）
- **工程锚点**：新人的on-call后体验（post-on-call）——不是接的时候最难。是接完之后——"我做的对吗？"没有人验证。runbook是空的——没有前辈的经验可以对照——新人自己变成了"前辈"——他写的第一行runbook将被以后的人依赖。"这行可能错——但没有人会知道——直到下一次事故。"
- **张力曲线**：情感复合型（乔落第二天拿着他写的runbook注解找傅远洲——"我写了这个。我不知道对不对。"）
- **角色焦点**：乔落（全章POV——继承者的自我怀疑。不是能力不够——是没有参考系。）；傅远洲（看了跑注——"你不是对的。但你是诚实。诚实的错——比沉默的对——更有用。因为诚实会让人纠正。沉默不会。")
- **六拍骨架**：
  1. 问题先出：第二天——乔落找到傅远洲，手里拿着他凌晨写的runbook注解
  2. 为什么痛："我不知道对不对。我猜了。猜了一个方向——然后它刚好能跑了。但我不知道我修的是根因还是症状。"
  3. 引出方法：新手排错的本质——在没有runbook的情况下——排错=猜+试+碰。运气成分大于技能。这不是新人的问题——是系统没有给新人"参考已知错误"的途径
  4. 项目落地：傅远洲看了乔落的注解——"你的临时方案——是对的。但根因不在这里——在下游的数据格式变更——你延长超时只是让它在'有时间就成功'和'没时间就超时'之间摇摆。但你写的这一段——分析过程——是非常好的。它告诉我你怎么想的——让我可以告诉你——哪里对了、哪里需要一个不同的角度。"
  5. 多方复盘：乔落："所以runbook——不只是写'怎么做'——还要写'为什么做'和'我猜了什么'？""是的。这样后来的人——不只是重复你的做法——是能看到你的想法。好的想法会被保留——错的会被发现——因为它是可见的。"
  6. 高层收束：runbook不是完美答案的集合——是一个线索链。每个值班的人在上面加一环——后来的值班者就少一环需要自己猜。

- **入门检查**：前置：Ch13, Ch15 / 新术语：排错（troubleshooting）、线索链（clue chain）、根因vs症状（root cause vs symptom）（≤3）
- **三问预检**：🩻失式（runbook的空白让新人的判断缺乏任何验证——他不知道自己对了没有） 😣乔落——他的自我怀疑不是性格缺陷——是制度缺失 🛤️开始——乔落写的runbook是第一环
- **并发/观测/简洁/部署**：goroutine/日志/新人runbook/scp→Docker

### 第17章：不只是值班

- **核心对象层**：阵→阵（值班只是症状——真问题是"谁对这个服务负责"。ownership的缺失让on-call不可能建立。）
- **核心相与失守**：契 → 背契（on-call不是独立的——它建立在ownership之上。如果一个服务没有owner——没有人该被它的告警叫醒。）
- **工程锚点**：ownership与on-call的关系——(a) ownership = "我承诺维护这个服务" (b) on-call = "当这个服务出问题——我会被通知——并且我知道该做什么"。没有ownership的on-call——是空洞的——"我不知道这服务怎么回事——但我被它叫醒了。"
- **张力曲线**：认知型（傅远洲画ownership矩阵→"在建立on-call之前——我们需要先知道——谁该被叫醒。"→"之前不是没人值班。是没人知道自己该不该值班。"
- **角色焦点**：傅远洲（系统性认识——值班不是终点。ownership才是。）
- **六拍骨架**：
  1. 问题先出：傅远洲试图建立on-call轮值——发现无法建立——因为不知道应该通知谁
  2. 为什么痛：on-call是"谁在值班"——但更深的问题是"谁对哪个服务负责"。如果没有人对服务负责——那服务就不该有on-call——因为它不该在跑
  3. 引出方法：ownership→on-call→runbook 三层关系：(a) owner说"我管这个服务" (b) on-call说"出问题叫醒我（或我的轮值者）" (c) runbook说"被叫醒后——我知道该做什么"
  4. 项目落地：傅远洲在记录板上画了三层——箭头从ownership指向on-call指向runbook。"之前我们只有第三层的一小部分（乔落写的注解）。前两层是空的。"
  5. 多方复盘：团队——"所以我们需要先认领服务。""是的。认领不只是写名字——是承诺——凌晨这个服务如果告警——你会知道。"
  6. 高层收束：值班是最后一步——第一步是ownership。没有owner——值班是空中楼阁。

- **入门检查**：前置：Ch08, Ch16 / 新术语：ownership→on-call→runbook 三层、服务认领（service adoption）（≤3）
- **三问预检**：🩻背契（on-call建立在ownership缺失的基础上——值班不可能成功） 😣傅远洲——试图在废墟上建房子 🛤️开始——三层模型揭示了结构性的缺失
- **并发/观测/简洁/部署**：goroutine/日志/ownership哲学/scp

### 第18章：冯知远的半年

- **核心对象层**：人→人（使用者——默默维护了一个临时函数半年。没有人知道——因为没有人问过。隐性维护（implicit maintenance）。）
- **核心相与失守**：史 → 断史（冯知远的半年维护——没有任何记录。他不是owner——但他比任何owner都更了解那个函数。当ownership制度缺失时——隐性维护会填补空缺——但填补的人不会被承认。）
- **工程锚点**：隐性维护（shadow maintenance）——当正式ownership缺失——最有责任心的人会自动填补。他们不被承认、不被补偿、不被替代——但他们在凌晨修复了没人知道的事情。这种隐性维护是组织最脆弱的资产——因为它完全是单个人驱动的。
- **张力曲线**：情感复合型（冯知远在团队会上说："`data-normalizer`——我知道那个函数——我修了它半年。"所有人看着他。他不是owner。他是使用者。"我以为你们知道。""我们不知道你在修它。""我也不知道你们不知道。"）
- **角色焦点**：冯知远（全章POV——使用者的隐性维护。他是驿河的"叶藏拙"——在最暗的角落默默补缝。）；傅远洲（"你修了半年——为什么不说？""因为没人问过。我的报表用这个函数——它坏了就是我的报表坏——我修它——是因为我比任何人都更怕它坏。"）
- **六拍骨架**：
  1. 问题先出：傅远洲在团队会上问——"`data-normalizer`——这个函数谁在维护？"沉默。然后冯知远举手——"我。半年了。"
  2. 为什么痛：他不是owner——他没有被指定——他只是这个函数的使用者。他的报表依赖它——它坏了会直接影响他的月度结算。"一开始我只是改了一行。后来改了一个条件——再后来加了一个缓存——半年——我已经不记得原始版本是什么样了。"
  3. 引出方法：隐性维护的双面性——(a) 正面：保障了系统在制度缺失下仍能运转 (b) 负面：维护者不被承认——他的知识不会被传递——如果他离职——这个函数的维护就断了
  4. 项目落地：傅远洲在`data-normalizer`的owner字段写上了"冯知远"——不是因为他建了它——是因为他维护了它。"维护的人——比建的人——更是owner。建是开始。守是继续。"
  5. 多方复盘：冯知远——"我不需要被感谢。我需要——这个函数的依赖者知道——我是它的owner。以后如果它变了——我知道。以后如果我不在了——我的名字还在这里——下一个维护它的人能看到我做了什么。"
  6. 高层收束：隐性维护不是美德——是制度缺失的补偿。冯知远是驿河的英雄——但英雄的存在证明制度有漏洞。

- **入门检查**：前置：Ch17 / 新术语：隐性维护（shadow maintenance）、ownership转移（ownership transfer）（≤2）
- **三问预检**：🩻断史（冯知远的半年维护没有任何记录——如果他不说——永远不会有人知道） 😣冯知远——他的隐性劳动在ownership制度下才被看见 🛤️是——ownership让隐性维护变成显性
- **并发/观测/简洁/部署**：goroutine/日志/隐性→显性/scp

### 第19章：绿色谎言之后

- **核心对象层**：阵→阵（健康检查骗了所有人——但知道被骗，已经比不知道怎么被骗要好。下一步是让"不可见"变成"可见"。）
- **核心相与失守**：（收束章——绿色谎言的系统性认知被建立。不是一个人的疏忽——是整个监测体系的层次缺陷。）
- **工程锚点**：从"知道有盲区"到"知道盲区里有什么"——需要工具。日志（logs）→发生过了什么。链路（traces）→跨了哪些服务。指标（metrics）→趋势在向哪走。这三视图是下一步——但驿河现在连完整的结构化日志（structured logging）都没有。
- **张力曲线**：收束型（傅远洲总结了绿色谎言的四个层面→"下一步——不是修健康检查。是让'运行'变得可见。"→秦望秋的名字被反复提起——"我们需要一个能建观测体系的人。"）
- **角色焦点**：傅远洲（从"修补事故"到"建立可见性"的转向）
- **六拍骨架**：
  1. 问题先出：傅远洲总结绿色谎言的四个层面——每个层面都有对应的盲区
  2. 为什么痛：四个层面——(a) 心跳假象：服务活着≠在做正确的事 (b) 日志不足：服务出了事——但日志里没有"为什么" (c) 链路不可见：一个请求经过了七个服务——没有人能看全 (d) 告警失能：43条传讯牌——28条假阳性——真正的告警被淹没
  3. 引出方法：观测的三视图（迹·脉·势）——在Ch24将被秦望秋展开。此处是概念铺垫
  4. 项目落地：傅远洲在记录板上写下："观测——不是再多一个工具。是让'运行'变成可见的。像石录让代码历史可见——观测让代码的'正在发生'可见。"
  5. 多方复盘："需要一个人来建——专门的人。不是我们兼职做。"
  6. 高层收束：绿色谎言之后——不是修复。是重新定义"看见"。

- **入门检查**：前置：Ch11-18 / 新术语：结构化日志（structured logging）、观测三视图（observability triad）（≤2）
- **三问预检**：🩻乱流（四个层面的盲区被理清了——但盲区还在运行） 😣所有依赖绿色监控的人——他们的安全感是建立在假象上的 🛤️开始——意识到需要建立观测体系
- **并发/观测/简洁/部署**：goroutine/观测意识觉醒/绿色谎言终/Docker意识

### 第20章：失明之前

- **工程锚点**：观测的层次——"看见=知道+可见"。驿河现在有了"知道"（知道问题在哪）——但还没有"可见"（让问题实时在监控中浮现）。没有可见——"知道"会在下一次事故中失效——因为没有人看到它在发生。
- **张力曲线**：悬疑过渡型（"下一个事故——会在我们最确定'能看见'的地方发生。就在日志端点——我们以为最可靠的'看见'。"→卷三的预告。）
- **角色焦点**：傅远洲（"我学了——凌晨三点不应该是只有一个人醒着的时候。但如果下一次——连那个醒着的人也看不见呢？"）

  1. 问题先出：傅远洲整理完二卷的所有发现——感觉有了方向

  3. 引出方法：知识的层次——(a) 已经发生的：被记录→可被分析 (b) 正在发生的：被监控→可被发现 (c) 将要发生的：被模拟→可被预防
  4. 项目落地：傅远洲在记录板上——绿色谎言总结旁边——留了一大片空白。"这是'我们还不知道的东西'的区域。下一次事故会在这片空白里发生。"

- **入门检查**：前置：Ch19 / 新术语：观测层次（observability layers）、可见性（visibility）（≤2）
- **三问预检**：🩻乱流（失明之前——知道盲区存在但不能预防下一次失明） 😣傅远洲——不安但无法提前行动 🛤️即将——卷三的失明事故是观测体系建立的直接触发
