# 卷十「平台」Ch 91-100：共同体治理

## Section 总览

- **章段**：Ch 91-100
- **叙事主题**：从"傅远洲的驿河"到"驿河团队的驿河"——共同体治理（platform as commons）。服务目录建立、健康检查2.0（行为验证）、SLO/SLI、feature flag、零停机部署。同时在背景中——远古告警频率在加速——从每时辰变成每刻——它在催——傅远洲开始意识到这个告警可能不是bug。
- **核心冲突**：平台立住了——但平台不只是工具链的集合。一个真正的平台——是"一群人共同维护——每个人都觉得'这是我的地板'"。从个人治理到共同体治理——不是一个技术问题——是"让每个人都在手册上签名、在决策上有声音、在凌晨有地板——在天花板上有名字"。
- **工具链阶段**：service catalog / 健康检查2.0 / SLO/SLI / feature flag / graceful shutdown / 远古告警加速
- **对象层**：阵→阵→门（从平台内部的阵法——到平台对外的门——SLO是对外部使用者的承诺——健康检查2.0是让"活着"变成"在做正确的事"）
- **主相→蚀**：契 → （正向——SLO/SLI是平台对外的契约化。健康检查2.0是内部契约的升级——从"我活着"到"我在做正确的事"。）
- **主角状态**：傅远洲从制度建立者到平台的"守门人"（steward）——不再是"我在建"——是"我在守——然后交给他们"。乔落和团队在手册上签名、在决策上发声——驿河开始有"我们"的归属感。
- **卷尾落点**：平台治理成型——但远古告警越来越急——它在催。向卷十一（成阵——史约诞生）过渡。

### 第91章：共同治理

- **核心对象层**：人→阵（从"傅远洲的驿河"到"我们的驿河"。不是傅远洲离开——是他主动把决策权交给团队。服务目录的建立——不是他建——是团队各自认领自己的服务——写服务描述、依赖列表、SLA承诺——"每一个签名——都是'这是我的服务——我负责'。"）
- **核心相与失守**：（正向——共同治理。"一个人建的平台——是那个人的延伸。一群人共同治理的平台——是文明的基质。"）
- **工程锚点**：服务目录（service catalog）——不是清单——是"每一个服务的出生证+所有权+依赖+承诺"。目录条目：(1) 服务名称 (2) owner(s) (3) 描述 (4) 依赖的服务 (5) 被谁依赖 (6) 对外承诺的SLO (7) runbook位置 (8) 部署信息。
- **张力曲线**：建设型（傅远洲宣布——"服务目录不是我来写——是每个owner写自己的服务。从今天开始——驿河的记录板——不再只有我的笔迹。"团队开始认领——每个owner在记录板上写下自己服务的条目——"这是我的——我负责。"）
- **六拍骨架**：
  1. 问题先出：傅远洲宣布——服务目录由团队共建——不是自上而下
  2. 为什么痛：如果服务目录只有傅远洲写——他不在——目录就是"他的记忆"——不是"平台的记忆"
  3. 引出方法：服务目录是"公共地图"——每个owner画自己的那块——然后拼起来
  4. 项目落地：51个服务——23个人——每一个owner写了目录条目——"不是傅远洲说了算——是我写的——我对这张条目负责"
  5. 多方复盘："服务目录不只是技术文档——是'我负责'的公开声明。每一个签名——都是一份公开的承诺。"
  6. 高层收束：平台不是一个人的——是每一个在上面签名的人。傅远洲只是第一个签名的人——不是唯一一个。

### 第92章：服务目录

- **核心对象层**：门→门（服务目录完成——51个服务——每一个都有owner、描述、依赖、承诺。从服务目录中——依赖图变得清晰——不再是"傅远洲脑子里的图"——是"记录板上的——所有人可见的——可以质疑的图"。）
- **工程锚点**：服务目录的可操作化——不只是"列表"——是"可以从中生成"：(1) 谁on-call——从owner (2) 变更影响谁——从依赖列表 (3) 谁在依赖我的SLO——从被依赖列表 (4) 事故排查入口——从runbook位置。
- **张力曲线**：展示型（服务目录完成——记录板上——51个条目——每一条都有签名。"这不是傅远洲的驿河。这是我们的驿河——每一个签名的——都是驿河的所有者。"）
- **六拍骨架**：
  1. 问题先出：服务目录完成——51个条目——23个owner签名
  2. 为什么痛：之前——"这个服务谁负责"→"问傅远洲"。现在——"看目录"——"目录上有签名——签名的人负责"
  3. 引出方法：目录是去中心化的第一块砖——"不需要中心节点——目录上的签名——是分布式的责任"
  4. 项目落地：目录上线——每一个条目可以链接到runbook、部署记录、on-call排班
  5. 多方复盘："目录不只是一张表——是驿河的宪法第一条——'每一个服务都有一个公开的负责人'。"
  6. 高层收束：服务有owner——不是"这个服务属于他"——是"这个服务的凌晨——由他来接。"

### 第93章：健康检查2.0

- **核心对象层**：流→流（健康检查的进化——从"心跳"（Ch06-07的"它还活着"）到"行为验证"（"它不只在呼吸——在做事——而且事做对了"）。健康检查1.0问："进程在吗？端口开吗？"健康检查2.0问："最近的请求成功了吗？数据最近同步了吗？对账一致吗？"）
- **核心相与失守**：（修复乱流——健康检查1.0是"式"——结构检查。2.0是"流"——行为检查——"做正确的事"比"活着"更重要。）
- **工程锚点**：健康检查2.0——从被动心跳到主动行为验证。(1) 基本心跳——进程活着、端口开 (2) 依赖健康——依赖的服务可达 (3) 业务健康——最近的N个请求成功率是否正常 (4) 数据健康——数据最近同步的时间在阈值内。"健康不是二极管——是连续谱。从'活着'到'做正确的事'——中间有很多层。"
- **张力曲线**：进化型（"Ch06-07——傅远洲发现健康检查全绿——但对账卡在30%。那时候我们以为'绿色=健康'。现在我们知道——绿色只是'它还活着'——不是'它在做正确的事'。"团队将健康检查升级为三层检查——"之前——goroutine泄漏藏了三个月——因为健康检查只看心跳。现在——健康检查2.0会看到goroutine数量每周涨3%——因为它看趋势——不只是状态。"）
- **六拍骨架**：
  1. 问题先出：回顾Ch06-07的教训——健康检查全绿≠系统健康
  2. 为什么痛：心跳检查让无数问题藏在绿色后面——从goroutine泄漏到对账停滞
  3. 引出方法：健康检查2.0——从心跳到行为验证——分层检查——每层检查不同的"健康维度"
  4. 项目落地：全平台部署健康检查2.0——"告警不再因为'进程死了'才响——在'进程正在死'的阶段就响了"
  5. 多方复盘："健康检查1.0告诉我们'它还活着'。2.0告诉我们'它在做正确的事吗'。后者比前者难——但后者才能真正防止凌晨的传讯牌。"
  6. 高层收束：健康检查的进化——从"看灯"到"听行为"。一个系统——不是活了就好——是"做对的事"才好。

### 第94章：SLO/SLI

- **核心对象层**：契→契（SLO（Service Level Objective）和SLI（Service Level Indicator）——平台对外部的公开承诺。不是"我们会尽量快"——是"我们承诺——对账99.9%在T+1小时内完成——如果不满足——我们会知道——并告诉你为什么"。）
- **核心相与失守**：契 → （正向——契约化。"SLO不是技术指标——是公共承诺。你没有SLO——外部系统不知道能期待什么——他们要么盲目信任——要么不敢依赖——两者都会在凌晨传讯牌响起时——变成指责。")
- **工程锚点**：SLO/SLI——可靠性工程（SRE）的核心概念。SLI=测量什么（请求延迟、错误率、吞吐量）。SLO=承诺多少（P99延迟<500ms、错误率<0.1%）。Error budget（错误预算）=1 - SLO——"可以失败的空间"。不是追求100%——是承诺"在X%内——我们保证"。超过错误预算——冻结新功能——只修可靠性。
- **张力曲线**：对峙型（"99.9%——是不是太低了？意思是我们允许0.1%的失败？""不是允许——是承认。0.1%的失败——是给'人可以犯错'的空间——给'凌晨有人接传讯牌'的空间——给'不是所有事都能预测'的空间。100%的承诺——是谎言——因为没有人能在凌晨保证一切。""所以SLO是对外部诚实——'我们保证在这个范围内——超过这个范围——我们承认'？""对——诚实——比完美更有用。完美是不可持续的——承认不完美——让可持续成为可能。"）
- **六拍骨架**：
  1. 问题先出：驿河需要对外承诺——但"我们会努力"不是承诺——"我们保证"可能是谎言
  2. 为什么痛：没有SLO——外部系统不知道驿河的可靠性到底是多少——在凌晨传讯牌响时——只能指责
  3. 引出方法：SLO是"可验证的承诺"——基于测量、基于数据、有错误预算——超过预算就暂停新功能
  4. 项目落地：驿河对关键服务定义SLO——对账服务99.9%<1小时、结算服务99.95%<30分钟——全局error budget仪表盘
  5. 多方复盘："SLO不是技术规范——是公共道德。承诺一个数字——意味着你接受'做不到'时——别人有权追问。"
  6. 高层收束：SLO是契约的数字形式。不是不可企及的完美——是"我们承诺——在这个范围内——我们在。——超过了——我们承认——然后修复。"

### 第95章：feature flag

- **核心对象层**：门→门（feature flag（特性开关）——变更控制的新维度——不是"上线还是不上线"——是"先给1%的人——然后10%——然后50%——然后全部"。变更不再是二进制开关——是渐进交付。）
- **核心相与失守**：（正向——变更安全。"一次全部上线——等于一次性信任你的测试和你的假设。渐进上线——等于承认你的测试可能不够——你的假设可能不完全——'先让1%的人验证你的假设'。")
- **工程锚点**：feature flag / progressive delivery（渐进交付）——不是"上线后再修bug"——是"在1%流量上发现bug——不让其他99%受影响"。feature flag的三个层次：(1) 开关——on/off (2) 百分比——1%/10%/50%/100% (3) 定向——特定用户/特定条件。flag的生命周期——创建→上线→渐进扩大→全量→清理（删除flag代码）——"flag不是永远的——是有保质期的——否则flag本身变成复杂性。"
- **张力曲线**：进化型（傅远洲在部署系统中引入feature flag——"之前——部署是'scp上去——重启——祈祷'——Ch57后是'部署——有回滚锚点'——现在是'部署——1%流量——等五分钟——看指标——OK——扩大到10%——再看——OK——全量'。"）
- **六拍骨架**：
  1. 问题先出：回顾Ch61——优化让服务变快——因为时序假设改变——炸了下游。"如果有feature flag——先给1%流量——在1%上发现时序变化——不会炸99%。"
  2. 为什么痛：全量部署=信任一切测试。但测试不能复制生产——"1%的生产流量是唯一真正的测试"
  3. 引出方法：feature flag的三阶段——创建flag→渐进上线（1→10→50→100%）→验证→全量→清理flag
  4. 项目落地：第一个feature flag用于Ch95的部署——"部署——1%——观察五分钟——指标正常——扩大到10%——再观察——扩大到50%——全量。"
  5. 多方复盘："flag不是永远的——flag的保质期是两周——两周后——要么全量——要么删除。flag留在代码里——是新的'43项模板'。"
  6. 高层收束：特性开关——让"上线"从一次赌博——变成一次可控的实验。不是让变更更慢——是让变更更安全。

### 第96章：零停机部署

- **核心对象层**：流→流（零停机部署（zero-downtime deployment）——服务在更新时——不中断正在处理的请求。graceful shutdown——"服务可以体面地退场"——不是被kill——是"处理完当前请求——不接受新请求——优雅退出"。）
- **核心相与失守**：（正向——部署文明的终极形态。"一个服务——不该在被杀死的时候——把正在处理的请求也一起带走。每一个请求——背后可能有一个人在等——在凌晨——它等的不只是一个response——是'世界还在运转'的信心。")
- **工程锚点**：graceful shutdown（优雅关闭）——进程收到SIGTERM→停止接受新请求→处理完当前请求→关闭连接→退出。配合：(1) 健康检查——标记服务unhealthy——负载均衡器停止发送新请求 (2) 等待现有请求完成——或超时 (3) 关闭数据库连接池 (4) 清理临时文件 (5) 退出。"服务不是'被杀死'——是'宣布我即将离开——请不要再给我新任务——让我做完手头的——然后我安静地走'。"
- **张力曲线**：进化型（"之前——部署=scp然后重启——所有正在处理的请求——全部中断。Ch57之后——部署有了回滚锚点。Ch95之后——部署有了feature flag。现在——部署有了graceful shutdown——请求不会中断——用户不知道我们刚部署了。""部署从'祈祷'到'让用户无感知'——是文明的进步。"）
- **六拍骨架**：
  1. 问题先出：一次部署中断了正在进行的对账请求——对账需要重新开始——损失了10分钟
  2. 为什么痛：不是部署有问题——是部署的方式——"kill"夺走了正在处理的请求——每一个请求背后——都有等待的人
  3. 引出方法：graceful shutdown——不是"更快地部署"——是"不让部署伤害正在运行的请求"——"部署是运维的事——关心请求是服务的事——不要让运维的事——伤害服务的事"
  4. 项目落地：全平台实现graceful shutdown——每个服务在收到SIGTERM后——15秒内体面地退出
  5. 多方复盘："服务被杀死——和——服务宣布退场——是两种文明的差距。前者是暴力——后者是尊重。"
  6. 高层收束：零停机不是技术成就——是公共责任。每一个请求——不该因为部署而被牺牲。

### 第97章：秦望秋的发现

- **核心对象层**：史→史（**史约锚点升级**。秦望秋在持续追踪远古告警——从Ch25-26首次发现——到Ch48继续查——到现在——他发现告警的频率在加速。原来每时辰（两小时）一次——现在每刻（15分钟）一次——频率增加了8倍。）
- **核心相与失守**：史 → 断史（远古告警在加速——它在催什么？"这不是bug——bug的频率是稳定的——或随机的。这种加速——像心跳——在某种压力下——越来越快。"）
- **工程锚点**：信号的时序模式——不只是看信号的内容——看信号的频率变化——频率变化是另一个层级的信号。远古告警从每时辰→每刻——频率增加了8倍——不只是"还在运行"——是"运行在加速"。加速的模式有两种可能：(a) 被监控的条件在恶化 (b) 发送者判断"时间到了"——在倒计时。
- **张力曲线**：悬疑升级型（秦望秋把远古告警的频率图贴在记录板上——一条从三年前开始的时间线——频率变化——"看——至少三年前——它一直很稳定——每时辰一次——第11,742次也是。从卷八开始——频率开始涨——从每时辰——到半个时辰——到现在——每刻。它在催。""催什么？""不知道。但它从稳定变为加速——意味着——它监控的条件——在变化——而且变化很快。"）
- **角色焦点**：秦望秋（"我的观测能看到的——是三年。三年前它就在发送。每时辰一次——稳定。现在——每刻一次——不。它比我们任何一个服务存在的时间都长——而现在——它在做什么——我完全不知道。我只知道——它在加速。加速的终点——是什么？"）
- **六拍骨架**：
  1. 问题先出：秦望秋展示远古告警频率变化——从每时辰→每刻——8倍加速
  2. 为什么痛：不是告警在变——是被监控的东西在变——而他们不知道被监控的是什么
  3. 引出方法：频率变化是另一个信号层——稳定的信号是"维持"——加速的信号是"时间到了"
  4. 项目落地：远古告警频率图贴在记录板上——在平台治理最成熟的时候——它的频率最快
  5. 多方复盘："驿河在进步——观测、契约、治理、部署——全在变好。但这个告警——比驿河老——它不在乎驿河在变好——它在计自己的时。"
  6. 高层收束：观测能看到三年——但远古告警跑的可能比任何观测都长。"它不在我们的时区里。它在自己的时钟上——而它的秒针——在加速。"

### 第98章：告警在催

- **核心对象层**：念→念（认知转变——傅远洲开始意识到——远古告警可能不是bug。它不是在报告错误——它在等待回应。"它不是在说'出错了'。它在说'我需要执约人介入'。它一直在等——等了几十年——等一个回应。"如果它是在等回应——那它的加速——意味着"它认为时间快到了"——或者"被监控的条件恶化了"——或者"耐心耗尽了"。）
- **核心相与失守**：（认知转变——不是蚀——是"史"的重新理解。远古告警是"史约"的残留信号——是第一代修补者建立的免疫系统的一部分——它在执行第一代修补者的指令——"校验首约——不符则请求执约人"。它不知道执约人已经不在了——所以它一直在等。）
- **工程锚点**：（这不是工程话题——是文明话题——远古告警是创始者时代遗留的免疫信号。"如果它是一个契约的守护者——那它守护的契约——是什么？——谁签的？——为什么需要持续校验？——为什么校验不通过？")
- **张力曲线**：认知颠覆型（傅远洲盯着远古告警的频率图——"秦望秋——它不是bug。Bug不会加速。它是在等——等了很久——现在——它在催。因为它等的人——可能快到了——或者——它认为被监控的东西——快崩溃了。""被监控的是什么？""不知道。但如果我们不找到它——它会在加速的终点——变成我们处理不了的事故。"）
- **六拍骨架**：
  1. 问题先出：傅远洲重新审视远古告警——不是作为"遗留bug"——是作为"等待回应的信号"
  2. 为什么痛：如果它是免疫信号——它的加速意味着"驿河正在触发什么——而不知道"
  3. 引出方法：不是修bug——是找出信号源——找到它在监控什么——在等待什么回应
  4. 项目落地：傅远洲决定——"我不再忽略它。它的加速告诉我——时间不多了。我要找到它的源头。"
  5. 多方复盘："我们建的观测——能看到三年。它在运行的时间——可能比三年长得多。观测有天花板——有些东西——在天花板之后。"
  6. 高层收束：最好的观测——也只能看到自己时代内的事情。远古告警——在观测之外——在文明的另一个时代里。

### 第99章：平台之后

- **核心对象层**：阵→史（平台治理成型——服务目录、健康检查2.0、SLO/SLI、feature flag、零停机部署——全在。但傅远洲知道——"平台立住了——但平台不是终点。平台是后来者的地板——但远古告警在告诉我们——有些地板——在更早的时候——就被铺好了——而我们不知道它下面是什么。"）
- **工程锚点**：平台治理的终态——不是"完美了"——是"有自反能力的平台"——能自我诊断、能自我修复、能自我质疑。自反的三个层次：(1) 技术层——健康检查2.0 (2) 制度层——postmortem+手册进化 (3) 文明层——远古告警——"我们不知道它在监控什么——但它在检查我们。"
- **张力曲线**：收束型（傅远洲——"平台有了——但平台不是答案。平台是让后来者可以问更好的问题——而不是重复前人的问题。远古告警——就是这些'更好的问题'之一——我们终于有能力问它了——因为平台让我们不用再担心'凌晨传讯牌谁来接'。"）
- **六拍骨架**：
  1. 问题先出：平台治理体系完整——傅远洲回顾——"从Ch01到Ch99——驿河从一个模板盲目扩张的平台——到一个有自反能力的共同体"
  2. 为什么痛：不是"到了"——是"可以开始问下一个问题了"——远古告警——是那个问题
  3. 引出方法：平台的终极目标——不是稳定——是让平台上的每个人——有余裕去面对"未知"
  4. 项目落地：平台稳定——团队可以抽调力量追查远古告警——"平台让凌晨的人有地板——也让我们有余力——去追天花板之后的事"
  5. 多方复盘："平台不是让一切完美——是让'不完美'的地方——可以被看见——可以被追查——而不是被传讯牌淹没。"
  6. 高层收束：平台是手段——不是终点。平台让后来者——可以不再只盯着自己的脚——可以抬头——看远处——看远古——看地板下面。

### 第100章：成阵之前

- **核心对象层**：史→史（过渡章——远古告警每刻一次——频率持续增加。傅远洲准备出发——追查告警的源头。秦望秋提供了告警信号的最高精度追踪——指向一个位置——在驿河的旧区——"那里很久没有人了。""很久是多久？""至少——比驿河任何服务都久。"）
- **工程锚点**：（过渡——"我要去追。这个告警在催了几十年——它等的——不是我们——但我们在它的时钟上——它加速的终点——我们不知道是什么。但如果我们不去——后来者会去——在更坏的条件下。"）
- **张力曲线**：紧张型（记录板上——远古告警的频率图——曲线像心电图——越来越快。"它在倒计时。我不知道倒计时到什么时候——但它在倒计时。"秦望秋追踪到源头位置——旧区——"第一个修补者最早工作的地方。"）
- **六拍骨架**：
  1. 问题先出：远古告警频率加速到每刻一次——秦望秋追踪到源头位置
  2. 为什么痛：源头在旧区——"第一个修补者最早工作的地方"——这暗示远古告警可能与修补者谱系直接相关
  3. 引出方法："我要去。不是因为我准备好了——是因为它等的人——可能从来就没有来过——而我们——是最近的了。"
  4. 项目落地：傅远洲准备出发——告警还在加速——"秦望秋——帮我追踪——我去旧区。"
  5. 多方复盘：平台在运行——传讯牌由乔落和团队接力——"傅远洲在追远古——驿河在运行——不需要他。"
  6. 高层收束："成阵——不是傅远洲一个人的决定。是告警催了几十年——终于有一个人决定'我去看看'。"

> 📝 卷尾。平台治理成型——共同体建立。远古告警加速到每刻一次——源头追踪到修补者旧区。傅远洲准备出发——向卷十一（成阵——史约诞生）过渡。整个简阵卷的终局即将开始。
