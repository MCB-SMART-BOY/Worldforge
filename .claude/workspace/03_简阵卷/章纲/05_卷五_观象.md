### 第41章：看得见的与看不见的

- **核心对象层**：阵→阵（trace/metrics/logs三视图——让运行变成可见的。秦望秋正式展开观测体系建设。）
- **工程锚点**：OpenTelemetry（分布式追踪标准）——跨服务调用链的三大支柱：traces（看到请求的完整路径）、metrics（看到服务的性能趋势）、logs（看到离散的事件）。三者合一=可观测性。
- **张力曲线**：建设型（秦望秋在驿河全面部署OpenTelemetry→从第一个服务到所有51个→"之前——你只能看到'从A到B有调用'。现在——你看到'A在T+0调用B——B在T+45ms调用C——C在T+230ms调用D——D在T+1500ms超时'——你可以停在任何一层看——看什么、看多久。")
- **六拍骨架**：
  1. 问题先出：秦望秋在data-aggregator上部署OpenTelemetry的第一个tracing agent
  2. 为什么痛：第一个trace——一个对账请求经过了七个服务——用了2,300毫秒。之前——没有人知道这个数字——因为没有人能看到完整的路径
  3. 引出方法：tracing的价值：不是"看到单个服务"——是"看到服务之间的空白"——哪里最慢、哪里在等
  4. 项目落地：第一个trace图贴在记录板上——七个服务的瀑布图——最宽的一栏是"database query"——1,400ms——占了60%的时间
  5. 多方复盘：冯知远——"我的服务不是在等别人——是在等数据库。之前我一直在优化自己的代码——但真正的瓶颈是数据库查询。tracing让我看到了——之前我以为的'慢'——不是我的。"
  6. 高层收束：观测——让看不见的变成看得见。第一个trace——不只是一条线——是一个世界的运行时在说话

- **并发/观测/简洁/部署**：goroutine群/OpenTelemetry/trace→可见/scp→deploy体系

### 第42章：OpenTelemetry

- **核心对象层**：阵→门（全平台OpenTelemetry部署——51个服务的跨服务调用链终于可见。分布式追踪——不是装一个工具——是给每个请求贴一个"护照"。）
- **工程锚点**：OpenTelemetry的三大信号(signals)——traces:请求路径 + spans:路径上的每一站 + metrics:每站的耗时和成功率。Trace ID在整个请求生命周期中保持不变——是观测的"身份证号"。
- **张力曲线**：震撼型（全部部署后——秦望秋展示驿河的全景trace仪表盘→傅远洲看到一个对账请求的完整trace——展开了27个spans→"这就是我们的系统。它不是在51个服务里跑——是在27个站点之间的空白里跑。"）
- **六拍骨架**：
  1. 问题先出：秦望秋完成全部51个服务的OpenTelemetry部署——全景trace仪表盘上线
  2. 为什么痛：一个对账请求——27个spans——跨七层服务——总耗时2,800ms——其中1,900ms是等数据库——600ms是等gRPC——300ms才是业务逻辑。"我们的业务逻辑只用了10%的时间——90%在等。这不是'慢'——这是'不可见'变成了'可见的浪费'。"
  3. 引出方法：traces不是监控——是叙事。每个trace讲了一个请求的故事
  4. 项目落地：全景trace仪表盘在记录板上方——第一个24小时——团队围在它前面——看到一个请求的完整路径真相比任何文档都清楚
  5. 多方复盘：乔落——"之前我凌晨排查事故——只能看到一个服务的日志。现在我看到整个请求走过的每一步——在哪一步花了多长时间——在哪一步出了错误。"
  6. 高层收束：OpenTelemetry不是工具链——是文明的叙事能力。之前——驿河在运行时是无言的。现在——它在说话。

- **并发/观测/简洁/部署**：goroutine/OpenTelemetry全平台/全景trace

### 第43章：goroutine泄漏

- **核心对象层**：流→流（一个goroutine泄漏——藏在"绿色"健康检查后面。goroutine数量每周涨3%——没有人注意到——因为健康检查只看"活着"不看"数量"。）
- **核心相与失守**：流 → 乱流（goroutine泄漏——不是bug——是设计疏忽。一个goroutine被创建——但没有cancel逻辑——永远不会退出——积压越来越多——最终耗尽内存。）
- **工程锚点**：goroutine泄漏——Go并发最常见但最隐蔽的病。`go func()`——没有context——没有wait group——没有errgroup。忘了回收——goroutine变成永久居民——数量每分每秒在涨。"pprof的goroutine分析——不是看'有多少'——是看'在等什么'。113个goroutine全在等——没有一个人在干活。"
- **张力曲线**：悬疑型（秦望秋在metrics中注意到一个pattern→goroutine数量每周涨3%→追溯→发现是在`rate-limiter`服务中——一个goroutine每次被创建去等一个下游确认——但下游确认永远不会到——所以一直等。）
- **角色焦点**：秦望秋（发现——"这不是警报——这是慢性死亡。不是一天炸——是三个月后内存耗尽——突然死。现在——它藏在绿色健康检查后面——因为进程还活着——goroutine数是200——它还在增长——没人知道极限在哪。"）
- **六拍骨架**：
  1. 问题先出：秦望秋在metrics中注意到goroutine数量曲线——每周涨3%
  2. 为什么痛：追溯——113个goroutine在`rate-limiter`中——全在等一个永远不会到的下游确认。每处理一个限流请求——创建一个goroutine等确认——确认从来不到——goroutine永远不退出。
  3. 引出方法：goroutine泄漏的三症状——(a) goroutine数量持续增长——不回落 (b) pprof显示goroutine都在"waiting"——不在"running" (c) 内存使用持续增长——每次泄漏都带走一小块内存
  4. 项目落地：秦望秋修复——加了context超时和errgroup——每个goroutine现在有超时——超时后自动cancel——不再永久等待。"这不是'goroutine太危险'——这是'没有owner的goroutine——等于没有owner的服务。'"
  5. 多方复盘："绿色健康检查骗了我们——进程活着——里面113个goroutine僵尸在排队等死。"
  6. 高层收束：观测不只查心跳——查数量、趋势、行为。每一个在增长的曲线——都是一个未来的OOM。

- **并发/观测/简洁/部署**：goroutine泄漏/pprof/metrics/告警

### 第44章：秦望秋的三视图

- **核心对象层**：阵→阵（迹·脉·势系统化——三个阶段的可视化展示。全章秦望秋展示完整的观测体系设计。）
- **工程锚点**：三视图的完整部署——(a) 迹(logs)：结构化日志+slog→所有服务统一格式 (b) 脉(traces)：OpenTelemetry→全链路trace (c) 势(metrics)：Prometheus+Grafana→RED/USE仪表盘
- **张力曲线**：展示型（秦望秋在团队会上展示完整三视图→三个仪表盘——三个维度——合在一起——"这是驿河——不是三个图——是同一个现实——三种看的方式。之前——你看第一个图——不知道问题在哪。看第二个——知道在数据库。看第三个——知道数据库慢不是一直的——是每小时整点出现一个高峰。三个一起看——你知道——整点——有定时任务在跑——它在抢数据库——你的对账也在用同一个数据库——所以你每整点被它拖慢一次。三个视图——三个线索——合在一起——真相。")
- **六拍骨架**：
  1. 问题先出：秦望秋展示完整三视图——团队成员第一次看到这个层次的可见性
  2. 为什么痛：不是三个工具——是三种提问。迹问"发生了什么"。脉问"在哪里发生"。势问"是不是在变好/变坏"
  3. 引出方法：不同的视图适合不同的提问。调试——看迹。追链——看脉。趋势——看势
  4. 项目落地：三视图集成——迹->脉->势连接——从一个trace中的异常span——点一下→跳到对应的日志行→再点一下→跳到该服务的指标趋势
  5. 多方复盘："之前——监控是看灯。绿灯好——红灯坏。现在——监控是听它说话——听它自己的——不是灯的颜色。"
  6. 高层收束：三视图——不是工具——是文明的眼睛——它的第一个视角——在驿河建立了。

- **并发/观测/简洁/部署**：channel模式/三视图完整/简洁→需要可见

### 第45章：RED/USE

- **核心对象层**：阵→阵（RED/USE指标设计——不是越多越好——是问对问题。RED（Rate/Errors/Duration）——面向用户的服务——回答"用户感受到什么"。USE（Utilization/Saturation/Errors）——面向基础设施——回答"资源在承受什么"。）
- **工程锚点**：RED指标（Rate每秒请求/Errors错误率/Duration延迟分布）+ USE指标（Utilization利用率/Saturation饱和度/Errors错误）——来自Google SRE的监控设计哲学。"不是全部指标所有服务都该有——是不同服务——需要不同类型的问题。面向用户的服务——问'用户有多快、多准、多可靠'——RED。基础设施——问'资源用了多少、快满了没、有没有错'——USE。问错问题——指标越多越没用。"
- **张力曲线**：展示型（秦望秋在团队会上——"RED——问你服务的'用户视角'——请求率、错误率、延迟——这是你的使用者关心的。USE——问你机器的'资源视角'——CPU、内存、磁盘、网络——这是你的运维关心的。——两种问题——两个视角——同一个系统。"）
- **角色焦点**：秦望秋（"不是'我要监控什么'——是——'谁在看——在什么时间——需要什么信息'——凌晨接传讯牌的人和早上看仪表盘的人——需要看到不同的东西。"）
- **六拍骨架**：
  1. 问题先出：OpenTelemetry部署后——每个服务有几十个指标——团队不知道看哪个
  2. 为什么痛：指标太多——等于没有指标——"告警在响——但你不知道哪个指标告诉你根因——因为太多——每个都看起来重要"
  3. 引出方法：RED/USE——不是选"最好"的指标——是选"问对了问题"的指标——面向用户的用RED——面向资源的用USE
  4. 项目落地：秦望秋为驿河的51个服务分类——API类用RED——数据库/队列类用USE——每个服务不超过10个核心指标
  5. 多方复盘："指标不是越多越安全——是问对了问题才安全。问错问题的指标——是噪音——噪音会淹没凌晨正在发生的事故。"
  6. 高层收束：问对了问题——观测才有用。RED/USE——不是技术选择——是"站在凌晨接传讯牌的人的视角——选指标"。

### 第46章：告警设计

- **核心对象层**：念→念（从43条传讯牌到有意义的告警——"什么情况下值得叫醒一个人？"不是所有告警都需要在凌晨响——有些可以等到早上——有些不该存在。告警设计——不是技术——是"对人的注意力的尊重"。）
- **工程锚点**：告警设计（alerting design）——不是"有指标就告警"——是"告警的条件——是'需要人立即行动'。"四个核心告警条件：(1) 数据丢失——不可逆 (2) 对账停滞超过半小时——影响下游结算 (3) 关键下游连续失败——会扩散 (4) 错误率突然跳跃>正常值5倍——可能正在扩展。其他——可以等到早上。"每一条告警都在消耗人的注意力。注意力=后来者凌晨的安全感。"
- **张力曲线**：对峙型（"什么情况下——值得叫醒一个人？""数据在丢——对账停了——下游全炸了——这些——叫。其他的——早上再说。""但如果我不想等到早上——我想现在就知道？""那就不要用告警——用仪表盘——你自己看。告警——是'必须有人醒了'——不是'有人好奇'。——凌晨两点——人的注意力——是最稀缺的资源。")
- **六拍骨架**：
  1. 问题先出：43条传讯牌→有意义的告警。"43条——没有一条告诉你——'这需要你现在——立刻——处理'。"
  2. 为什么痛：告警太多——人会麻木——"传讯牌响——你接——然后发现——'又是这个——没事的'——第44次——你会开始不接——第45次——真正的紧急——进来了——你没接。"
  3. 引出方法：告警的唯一标准——"这条告警——需要人立即行动吗？"如果不需要——它不是告警——是通知——可以等到天亮
  4. 项目落地：秦望秋设计驿河的告警策略——4条核心告警——其余降级为仪表盘指标或早间邮件
  5. 多方复盘："减少告警——不是减少信息——是减少'凌晨两点的噪音'。注意力——是凌晨接传讯牌的人——最稀缺的资源。"
  6. 高层收束：告警——是对人的注意力的请求。请求——不是越多越好——是越精确越好——"每一条告警——都是——'我需要你——现在'。"

### 第49章：观象之后

- **核心对象层**：念→念（观象体系建成——但"看得见——不等于'看得全'。内部可见了——但边界呢？外部来的东西——化形卷过来的模块、对接的外部系统——这些在观测范围之外。"观测——建了内部的眼睛——但世界的边界——还在盲区。")
- **工程锚点**：观测的边界——内部观测（traces/metrics/logs）能看到服务之间的调用——但看不到"外部系统"——看不到"不在你的trace里的人"。跨平台调用——化形卷的模块——外部API——这些——观测不到——因为它们的trace不在你的OpenTelemetry里。
- **张力曲线**：收束型（秦望秋——"内部——已经能看到。每一个goroutine、每一个请求、每一个对账——在我们的trace上——都有名字。但边界——是下一个盲区——顾迁舟从化形卷带来的模块——外部系统——它们的内部——在我们的观测之外。")
- **六拍骨架**：
  1. 问题先出：观测体系建成——但傅远洲问——"化形卷过来的模块——在我们的观测里吗？"
  2. 为什么痛：内部观测能看到自己的51个服务——但外部模块的行为——不在观测内——它们的错误——只能在它们影响驿河之后——才被看到
  3. 引出方法：观测需要延伸到边界——API契约层面——不只是看到"调用成功/失败"——是看到"外部调用——在什么条件下——发生了变化"
  4. 项目落地：秦望秋在观测中加入"外部调用监控"——至少记录——谁调用了我们——什么时候——多少次——成功率
  5. 多方复盘："内部看得见了——但边界——是'别人的内部'——你不可能观测别人的内部——你只能观测——'在边界上——发生了什么'。"
  6. 高层收束：观象——是让内部可见。边界——是让"外部的东西——在影响我们之前——有个窗口"。

### 第50章：边界之前

- **核心对象层**：门→门（过渡章——"下一步——看清边界。内部——已经能看到。边界——是下一个盲区——那些'我以为你知道'——那些没有签契约的接口——那些口头约定的API。——内部治理——ownership+on-call+观测——在内部建立——但服务和外部之间——没有——还是口头的。——口头的边界不是边界——是'我以为'。"——向卷六过渡：API契约+gRPC+顾迁舟到来。）
- **工程锚点**：边界治理——不是"外部的人不可靠"——是"和外部之间——需要白纸黑字的契约——因为'口头的'——在凌晨——不存在——只有'我没被告知'。"
- **张力曲线**：过渡型（傅远洲——"内部观测——建了——但外部——每次对接——都是'我以为你知道'——然后凌晨炸——双方都说——'我以为'。下一步——边界——不是内部——是服务之间的门——门——需要契约——白纸黑字的。"）
- **六拍骨架**：
  1. 问题先出：傅远洲回顾——"内部治理——ownership有了——on-call有了——观测有了——但外部——还是'口头的'。"
  2. 为什么痛：口头边界——在凌晨——不存在——"我以为你知道我改了API"→"我不知道——你的API——不是我的API——是你的——但你的变更——影响了我。"
  3. 引出方法：边界需要契约——protobuf——gRPC——版本化——兼容承诺——"不是口头——是白纸黑字——在proto文件里——机器可验证"
  4. 项目落地：向卷六过渡——傅远洲宣布——"下一步——API契约。内部治了——外部——也需要治。"
  5. 多方复盘："治理——不是从内到外——是从'有owner'到'有契约'——从'我的服务'到'我们的门'。"
  6. 高层收束：观象——看见了内部。下一步——看清边界——契约——让门——不是'口头'——是'proto'。

> 📝 卷尾。向卷六（边界——gRPC契约+顾迁舟从化形卷到来）过渡。

- **核心对象层**：念→念（观测哲学——"观测不是工具链。是'让后来者看见前辈看见了什么'。"这是秦望秋的核心命题。）
- **工程锚点**：观测的文化意义——工具会过时。但"让不可见变得可见"的理念——不会。秦望秋在驿河的观测体系——不是最终版——但它是第一个让后来者能"看见"的版本。"以后的人——不需要我问'这个系统在做什么'——因为他们能看到——用三视图——用trace——用RED——用告警。他们看到的不只是数字——是我们在这一卷里建立的东西。"
- **六拍骨架**：秦望秋在记录板上写下观测哲学——"观测不是监控。监控是'告警响了->人去查'。观测是'人来的时候——一切都在——前面的所有人看到的——后来的所有人都能看到'。"
