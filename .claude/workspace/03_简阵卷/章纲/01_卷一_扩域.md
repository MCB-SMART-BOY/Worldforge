# 卷一「扩域」Ch 1-10：平台扩张

## Section 总览

- **章段**：Ch 1-10
- **叙事主题**：驿河平台在膨胀——第47个服务接入，模板全绿，但可知范围在缩小。Go的"简洁"让任何人都能建服务——但建完之后呢？
- **核心冲突**：模板让搭建变简单——也让思考变简单。"照模板做就行"——模板开始代替判断。
- **工具链阶段**：goroutine入门 / 健康检查=心跳 / 简洁信仰 / 手动部署
- **对象层**：器→器（从单个服务到"一片服务的海洋"——器在增殖但没人知道器之间的关系）

- **主角状态**：新任平台负责人——驿河不是他建的，是他接的。他面临的不是"建立什么"——是"理解已经存在了什么"。
- **张力引擎**：扩张的代价——越扩张越不可知。每接入一个新服务——所有人都更了解这个平台——或者更不了解。
- **卷尾落点**：平台在膨胀——表面全绿——下面是什么？

### 第01章：扩域

- **核心对象层**：器
- **核心相与失守**：史 → 断史（第47个服务接入——没人能说清楚前面46个服务之间的关系）
- **工程锚点**：平台扩张（platform scaling）——微服务（microservices）的爆炸式增长。Go的模板让创服务像复制粘贴一样容易——但模板不教你治理（governance）。
- **张力曲线**：攀升型（第47个服务接入→模板全绿→服务在跑→但傅远洲翻看服务目录——注意到他不知道前15个服务是干什么的）
- **角色焦点**：傅远洲（主角建立——驿河不是他建的。他是第三任平台负责人。他面前是一张51个服务的清单——其中三分之一他不认识。）
- **六拍骨架**：
  1. 问题先出：第47个服务接入——用标准模板生成，健康检查全绿，部署成功。团队庆祝。

  3. 引出方法：Go的模板哲学——"Go的方式只有一种"。模板让标准化变得容易——也让"不去想为什么"变得容易。
  4. 项目落地：傅远洲在公共记录板上画出驿河的服务拓扑——大片空白。很多服务之间有线相连——但线的含义是"应该有调用"而非"确认有调用"。
  5. 多方复盘：团队沉默。不是因为不知道答案——是因为之前没人问过这个问题。
  6. 高层收束：平台在膨胀——越膨胀越不可知。模板全绿不是健康——是不自知。

- **入门检查**：前置：无（卷首章）/ 新术语：微服务（microservice）、模板（service template / boilerplate）、平台治理（platform governance）（≤3）

### 第02章：模板的代价

- **核心对象层**：器→念（模板让人停止思考——"照模板做就行"）
- **核心相与失守**：式 → 失式（模板规定的结构被当成不需要理解的结构——模板从"工具"变成了"替代判断"）
- **工程锚点**：脚手架（scaffolding / boilerplate）的工程心理——模板降低了入门门槛，也降低了思考门槛。"只要是模板生成的——就是对的"——但实际上，模板只是"前人觉得这样比较好"的快照。
- **张力曲线**：认知型（傅远洲审查标准模板→43项配置→每一项都有人为它辩护→他追问每一项的"为什么"→大多数人答不上来）
- **角色焦点**：傅远洲（追问"为什么"——"模板不是不对——但依赖模板而不理解模板的人——是对的吗？"）
- **六拍骨架**：
  1. 问题先出：傅远洲打开驿河服务模板——43项配置，每一项都有合理的默认值
  2. 为什么痛：他问团队"为什么健康检查端口是8080而不是别的？"——没人知道。"模板上说8080。"
  3. 引出方法：模板的代价——模板把"为什么"从每个人脑子里移走，放进了一个不会说话的文件里
  4. 项目落地：傅远洲逐项审查模板——43项中至少15项是"因为当时有人觉得好"——当时是三年前。当时驿河有11个服务。现在是51个
  5. 多方复盘："模板不是敌人——是冻结的判断。冻结的判断——不会随着现实更新。"
  6. 高层收束：照模板做——等于在三年前某人的判断上建东西。那个判断可能错——更可能过时。但模板不会告诉你。

- **入门检查**：前置：Ch01 / 新术语：脚手架（scaffolding / boilerplate）、默认值（default value）、冻结的判断（frozen judgment）（≤3）
- **三问预检**：🩻失式（模板的43项成了"不需要想"的装饰——结构变成了遮挡） 😣后来的服务创建者——他们在不知道"为什么"的情况下依赖了过时的判断 🛤️开始——提问"为什么"是解冻判断的第一步
- **并发/观测/简洁/部署**：goroutine入门/心跳/模板信仰/手动

### 第03章：傅远洲接手

- **核心对象层**：念（主角建立——驿河不是他建的，是他接的。接手的平台负责人——面对的不只是一堆代码，是一堆"别人的决定"。）
- **核心相与失守**：（人物建立章——傅远洲的定位：他不是创造者，是接管者。接管的代价是他必须理解"前人为什么这样选"——而前人已经不在了。）
- **工程锚点**：平台接手的工程心理学——接手一个已有平台比从头建更难。建的人有当时的环境记忆——接的人只有代码。"每个代码的默认值——都是前人在某种压力下做的选择。选择本身可以质疑——但必须先理解。"
- **张力曲线**：人物建立型（傅远洲翻阅驿河的历史记录→从第一个服务到第47个→发现服务之间的依赖关系是在"刚好醒着"的凌晨临时加的→没有设计——只有积累）
- **角色焦点**：傅远洲（全章POV——接管者的视角。不是来推翻的——是来理解的。"我不是来批评前人的——是来完成他们没有时间做的事。"))
- **六拍骨架**：
  1. 问题先出：傅远洲翻阅驿河自第一个服务以来的所有文档——发现最早的服务连文档都没有，只有一个README写着"先跑起来"
  2. 为什么痛：驿河不是被"设计"的——是被"积累"的。51个服务不是51个独立决策——是无数个"先这样"叠加的结果
  3. 引出方法：接管的三阶段——(a) 理解已经在运转的东西 (b) 找到不可见的地方 (c) 建立可见性
  4. 项目落地：傅远洲在公共记录板上写下："驿河不是一个人建的。是51个服务×23个人×三年积累。我的任务是——不推翻。让后来者能继续。"
  5. 多方复盘：团队中有人说："之前的负责人也是这样想的。"傅远洲："然后呢？""然后他走了。""他走的时候留了什么？"沉默。
  6. 高层收束：接手——最难的不是学，是知道"前人的判断已经过期了"——但没有标注。

- **入门检查**：前置：Ch01-02 / 新术语：平台接管（platform handover）、遗留系统（legacy system）（≤2）
- **三问预检**：🩻断史（前人的判断没有被传递——只剩代码） 😣傅远洲——他必须独立重建前人的决策背景 🛤️开始——接手也是"后来者"的一种
- **并发/观测/简洁/部署**：goroutine入门/心跳/接手者信仰/手动

### 第04章：服务边界

- **核心对象层**：器→流（goroutine/channel/context——Go并发原语的首次深度展示）
- **核心相与失守**：（认知章——并发不是魔法。goroutine不是免费的——但模板让它们看起来像是免费的。）
- **工程锚点**：Go的并发三原语——(a) goroutine（协程）：轻量级执行单元——不同于OS线程——Go运行时调度 (b) channel（通道）：goroutine之间的通信管道——"通过通信来共享内存" (c) context（上下文）：跨goroutine传递截止时间、取消信号、请求范围的值
- **张力曲线**：认知型（傅远洲审查一个典型服务的并发代码→发现goroutine被随意使用——"go func()"出现在十一处——没有一处有超时→"如果有人用了context——至少知道什么时候放弃。但没有人。"）
- **角色焦点**：傅远洲（学习Go并发——不是从语法开始——是从"有多少goroutine在跑"开始。没人能回答。）
- **六拍骨架**：
  1. 问题先出：傅远洲审查一个对账服务的代码——发现goroutine被当成了默认的"异步"工具
  2. 为什么痛：`go func()`出现11次——没有一处有context超时——没有一处有errgroup——没有一处记录了goroutine的owner
  3. 引出方法：goroutine的三个责任——(a) 谁在等它 (b) 它什么时候结束 (c) 它失败了谁会知道
  4. 项目落地：傅远洲在服务代码里加了一行注释："TODO: 这个goroutine——不知道谁会等它的结果。"他跑了一下pprof——发现51个服务一共开了超过三千个goroutine。没有人知道这个数字。
  5. 多方复盘："goroutine不是免费的——是廉价的。廉价的代价——是数量会膨胀到不可见。"
  6. 高层收束：并发的第一条规则不是"怎么并发"——是"谁在等、多久、失败了谁管"。驿河的每个人都在用goroutine——没有人在负责任。

- **入门检查**：前置：Ch03 / 新术语：goroutine（协程）、channel（通道）、context（上下文）、超时（timeout）（≤4）
- **三问预检**：🩻乱流（goroutine无owner无timeout——运行时状态不可见） 😣后来的维护者——goroutine泄漏会在凌晨咬他们 🛤️开始——提问"谁在等"是治理的开始
- **并发/观测/简洁/部署**：goroutine入门/心跳/简洁信仰/手动

### 第05章：51个服务，23个人

- **核心对象层**：器→域（规模的压迫——51个服务不是51个独立存在——是51×50÷2=1275个潜在的依赖关系）
- **核心相与失守**：契 → 背契（"每个服务独立运行"的承诺——在51个服务互相依赖时——无法兑现）
- **工程锚点**：服务规模的管理挑战——"23个人维护51个服务"意味着平均每人维护2.2个服务。但这不是均匀分布的——有些人维护了0个（已离职），有些人维护了7个。
- **张力曲线**：挤压型（傅远洲把所有服务和责任人列在墙上→23人×51服务的矩阵→大多数单元格是空白→"谁在维护它？""不知道。""它依赖谁？""不知道。""谁依赖它？""不知道。"）
- **角色焦点**：傅远洲（面对规模——不是个人能力问题——是制度问题。23个人不可能用口传管理51个服务。）
- **六拍骨架**：
  1. 问题先出：傅远洲在墙上列出所有51个服务和23个人的名字——连线
  2. 为什么痛：九个服务——白板上没有名字。不是"忘了写"——是没有人维护。创建它们的人已经走了。
  3. 引出方法：服务所有权的缺失——不是一个技术问题。没有人被正式赋予"这个服务是你的责任"
  4. 项目落地：墙上的矩阵——大片空白。傅远洲在空白处写上"未知"——然后数了一下。37个"未知"。
  5. 多方复盘："23人×51个服务——你们不是在维护平台。你们是在给51个独立的人在23个不同的方向上发工资。没有制度——就没有平台。"
  6. 高层收束：规模让"口传"失效。23个人不可能同时知道51个服务在干什么——需要制度。

- **入门检查**：前置：Ch04 / 新术语：服务所有权（service ownership）、矩阵管理（matrix management）（≤2）
- **三问预检**：🩻背契（"每个服务独立"的承诺——在互相依赖网络中无法成立） 😣被遗忘的服务——它们还在跑，没人在看 🛤️开始——把空白写在墙上
- **并发/观测/简洁/部署**：goroutine入门/心跳/规模压力/手动

### 第06章：绿色但不活着

- **核心对象层**：流→流（健康检查全绿——凌晨对账卡在30%。健康检查（health check）的谎言："活着"≠"有效"。）
- **核心相与失守**：流 → 乱流（运行时状态"绿色"——但业务功能"卡住"。健康检查只查了心跳——没查行为。）
- **工程锚点**：健康检查（health check）的分层——(a) 存活检查（liveness）：进程在跑——最基本 (b) 就绪检查（readiness）：能接受请求——进一层 (c) 行为检查（behavior）：真的在做该做的事——最深。驿河只用到了第一层。
- **张力曲线**：倒钩型（凌晨两点→监控屏全绿→傅远洲被传讯牌叫醒→"对账卡在30%"→追查发现对账服务本身正常运行——但它调用的下游服务挂了→那个下游的健康检查——也是绿的。）
- **角色焦点**：傅远洲（凌晨被叫醒——不是第一次。但这一次他决定追到根。）
- **六拍骨架**：
  1. 问题先出：凌晨对账卡在30%——监控全绿，没有告警
  2. 为什么痛：健康检查只查了"进程活着"——没查"对账在进展"。服务还活着——但对账逻辑被一个下游超时卡住——不动了。
  3. 引出方法：健康检查的三层——心跳/行为/业务。心跳是"我还活着"——但活着不等于对。"一个在空转的服务——比一个死了的服务更危险。因为死了有告警——空转没有。"
  4. 项目落地：傅远洲追查发现——对账服务的下游处理服务返回空数据——因为它的数据库连接池耗尽了。那个服务的健康检查——查的是8080端口。端口活着——数据库死了。健康检查不知道。
  5. 多方复盘："健康检查骗了我们。不是恶意的——是无知的。我们在检查'活着'——但我们需要知道的是'在做正确的事'。这两者之间的差距——就是凌晨对账卡住的三个时辰。"
  6. 高层收束：绿色不是活着——是不知道死了没有。

- **入门检查**：前置：Ch05 / 新术语：健康检查（health check）、存活/就绪/行为（liveness/readiness/behavior）、连接池（connection pool）（≤3）
- **三问预检**：🩻乱流（健康检查的欺骗——运行时状态看起来正常，实际上异常） 😣凌晨被叫醒的傅远洲——还有所有依赖对账结果的外部团队 🛤️开始——健康检查2.0的种子被种下
- **并发/观测/简洁/部署**：goroutine/心跳谎言/绿色信仰/手动

> 📝 Ch06是简阵卷的核心诊断章——与Ch11（绿色不意味着活着）形成铺垫→高潮的弧线。

### 第07章：健康检查只查心跳

- **核心对象层**：念→阵（健康检查的哲学——从"查心跳"到"查行为"——需要制度。不是改一行代码——是重新定义"活着"。）
- **核心相与失守**：式 → 失式（健康检查在系统中只是装饰——没人依赖它做决策，因为它从来不报错。不报错——不等于正确。）
- **工程锚点**：健康检查的设计哲学——"检查什么"决定"看不见什么"。如果检查的是"我能ping我自己"——你不会知道你的数据库挂了。因为是数据库会回答——不是你。
- **张力曲线**：哲学型（傅远洲和团队讨论："什么是一个服务'活着'？""进程在跑。""够了？""能处理请求。""那它能处理——但处理的结果是错的呢？"沉默。）
- **角色焦点**：傅远洲（"我们需要的不是更好的健康检查——是另一套定义：不是'活着'——是'在做该做的事'。"）
- **六拍骨架**：
  1. 问题先出：事故后，傅远洲要求重新定义健康检查——团队抵抗："改健康检查会让所有服务重启——风险太大。"
  2. 为什么痛：现有的健康检查制度——不是因为"它不够好"被维持——是因为"改的危险大于不改的便利"。这是典型的"制度性惯性"。
  3. 引出方法：渐进式健康检查改革——不一次改所有服务的检查逻辑——而是增加新的检查层。保留心跳（不破坏现有部署），增加行为检查端点——只有新的服务必须实现。
  4. 项目落地：傅远洲在公共记录板上提出"健康检查1.5"——新增可选的行为检查端点（behavior check endpoint）。服务可以选择实现——不强制。但做了的——会在监控上显示"已验证行为"。没做的——显示"仅心跳"。
  5. 多方复盘：秦望秋（即将在Ch23登场——"我可以设计行为检查的标准——不是每个服务都需要检查同样的行为。")——首次被提及。
  6. 高层收束：健康检查不是技术问题——是哲学问题。"什么是活着"——是每个服务的作者必须回答的。制度只能问问题——不能替人回答。

- **入门检查**：前置：Ch06 / 新术语：行为检查（behavior check）、监控面板（dashboard）、渐进式改革（incremental reform）（≤3）
- **三问预检**：🩻失式（健康检查结构性不足——所有服务共用同一个"心跳"定义） 😣维护者——他们被要求在不破坏现有系统的情况下改进 🛤️开始——行为检查层的引入
- **并发/观测/简洁/部署**：goroutine/心跳→行为/简洁反思/手动

### 第08章：谁在建

- **核心对象层**：器→器（模板让任何人都能建服务——但建完之后呢？所有权的缺失让"建服务"变成了"遗弃服务"。）
- **核心相与失守**：契 → 背契（建服务的人——和负责服务的人——不是同一批人。模板让他们可以建——但没有让他们负责。）
- **工程锚点**：服务生命周期（service lifecycle）——创建→维护→退役。模板简化了"创建"——但掩埋了"维护"和"退役"。每建一个新服务——未来就有一个人要为它接凌晨的传讯牌。那个人现在不知道。
- **张力曲线**：对峙型（傅远洲提出新服务需要指定owner→团队抵抗——"你这是在限制创新。"""不。我是在确保创新的人——凌晨会被叫醒。""）
- **角色焦点**：傅远洲（所有权制度的提出——不是限制——是让"建"和"守"绑在一起）
- **六拍骨架**：
  1. 问题先出：傅远洲追问"第47个服务是谁建的"——建的人说"模板生成的。只花了半天。"傅远洲："谁在维护它？"建的人:"——不是一直在跑吗？"
  2. 为什么痛：模板让建的成本降到几乎为零——但维护的成本不为零。为零的建+非零的维护=服务数量膨胀→维护者被淹没
  3. 引出方法：服务所有权的核心理念——不是"谁建"。是"谁凌晨会接这个服务的传讯牌"。两件事——可以是不同的人。但不能是"没人"。
  4. 项目落地：傅远洲提议——任何新服务接入驿河时必须在模板第一行写："on-call owner: [名字]。如果写'待定'——这个服务不能通过健康检查——因为'没有owner'本身就是最不健康的状态。"
  5. 多方复盘：团队沉默——然后是："之前的47个——owner怎么填？""之前的47个——我们一个一个找。找不到的——写'未知'。写'未知'不是羞耻——是诚实。诚实的下一步——是找到。"
  6. 高层收束：建是自由——守是责任。模板给了自由——制度需要给责任。两者不冲突——但需要被明确分开。

- **入门检查**：前置：Ch07 / 新术语：服务所有权（service ownership）、on-call owner、服务生命周期（service lifecycle）（≤3）
- **三问预检**：🩻背契（建的承诺和守的承诺被分离——模板让建的人不用承诺守） 😣后来被叫醒的人——他们继承了别人建的服务的传讯牌 🛤️开始——所有权制度的提出
- **并发/观测/简洁/部署**：goroutine/心跳/责任vs自由/手动
