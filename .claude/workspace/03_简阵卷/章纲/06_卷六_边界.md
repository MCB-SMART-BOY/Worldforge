# 卷六「边界」Ch 51-60：API契约

## Section 总览

- **章段**：Ch 51-60
- **叙事主题**：API契约——gRPC/protobuf/"我以为你知道"到"白纸黑字"。顾迁舟从化形卷到来——带着桥账和退场日期的执念。部署系统从手动到自动化。
- **核心冲突**：契约是驿河治理的最后一块空白。内部治理（ownership+on-call+观测）已建立——但服务之间的边界还是"口头的"。口头的边界不是边界——是"我以为"。
- **工具链阶段**：gRPC+protobuf / 版本化+semver / 部署系统+回滚 / 桥的分类学
- **对象层**：门→门（从内部结构到对外边界——API是第一道门）
- **主相→蚀**：契 → 背契（口头的约定不是约定——契约必须可被机器验证）
- **主角状态**：傅远洲从内部治理扩展到边界治理——与顾迁舟的合作让驿河学到了"桥的生命周期"。
- **卷尾落点**：契约写清楚了——但契约能防止"炸"吗？不能——但契约让"炸了之后谁该知道"变得清楚。

### 第51章：边界

- **核心对象层**：门（"我以为你知道"——一个外部对接系统的API变更炸了驿河的结算。"我们没签契约——因为我们以为'和以前一样'"）
- **核心相与失守**：契 → 背契（口头约定——API的语义不在任何地方——只在双方的"我以为"里）
- **工程锚点**：API契约（API contract）的必要性——(a) 输入/输出的schema——protobuf (b) 语义——字段的含义和约束 (c) 版本——哪个版本有什么承诺 (d) 兼容性——什么变更算breaking
- **张力曲线**：倒钩型（外部系统改了API→驿河结算炸了→追查——对方的解释："我在更新日志里写了"→驿河:"我们没有订阅你们的更新日志——因为从来没有人告诉我们需要。"）
- **角色焦点**：傅远洲（"边界不是技术边界——是信任边界。信任——不能靠'我以为'。需要白纸黑字。")
- **六拍骨架**：
  1. 问题先出：外部对接系统改了返回格式——驿河结算炸了
  2. 为什么痛：双方都以为是对方的责任——但其实谁都没错——因为根本没有契约
  3. 引出方法：API契约的四要素——schema + 语义 + 版本 + 兼容性承诺
  4. 项目落地：傅远洲和外部团队签了第一份正式API契约——protobuf定义的接口。每一个字段有注释、有约束、有版本号
  5. 多方复盘："不是签了契约就不会炸。是炸了之后——我们知道谁该知道。"
  6. 高层收束：边界——是契约的起点。没有契约的边界——不是边界——是幻觉。

- **并发/观测/简洁/部署**：channel/观测完整/gRPC→protobuf

### 第52章：gRPC的契约

- **工程锚点**：gRPC+protobuf——契约不再靠"我以为"。`.proto`文件是API的唯一真相来源（single source of truth）——服务端的接口、客户端的stub全部从proto生成。"改proto就是改契约——改契约就会有版本号——有版本号就有迁移指南。"
- **张力曲线**：建设型（傅远洲把驿河内部服务间调用从REST+JSON迁移到gRPC——"不是REST不好——是REST的契约不是机器可验证的。你的JSON schema——在人的脑子里。gRPC的schema——在proto文件里——机器会验证。"）
- **六拍骨架**：迁移第一个服务间调用→proto定义→生成stub→两端都用同一个proto——"之前——服务A调用服务B——字段名拼错了——传到B——B用默认值处理——结果静默错误。现在proto定义不允许拼错——编译期就爆。"

---

### 第53章：版本化

- **工程锚点**：API版本化（API versioning）——v1到v2不是改数字——是重新承诺。semver应用于API——MAJOR=不兼容变更，MINOR=新增功能（兼容），PATCH=bug修复（兼容）。"版本号是给使用者的地图——告诉他们——你依赖的接口什么时候会变。"
- **张力曲线**：对峙型（"我们内部服务——为什么也要版本化？""因为你不知道谁在依赖你。Ch21——改日志格式——不知道七层在依赖。如果日志格式有版本——那个工程师在改之前会看到——v1→v2是MAJOR变更——不兼容——需要通知依赖者。")

---

### 第54章：兼容承诺

- **工程锚点**：向后兼容（backward compatibility）——不是技术能力——是公共责任。"不兼容就好比——你保证的接口突然不在了——依赖你的人——被推到了凌晨。兼容承诺就是说：'我保证——你现在用的——至少到下一个MAJOR版本——还在。'这不是技术决定——是道德决定。"
- **六拍骨架**：傅远洲在记录板上写API契约准则:"1.任何不兼容变更必须提前一个MINOR版本公告。2.任何公告必须有迁移指南。3.任何迁移指南必须经过至少一个使用者的独立验证。4.违反以上任何一条→MAJOR版本不能发布。"

---

### 第55章：顾迁舟到来

- **核心对象层**：人→门（**跨卷人物登场**——顾迁舟从化形卷过来。带着桥账——七条桥——三条已删、两条已迁、两条永久。每座桥都有退场日期或永久声明。）
- **核心相与失守**：（跨卷章——顾迁舟的桥账是简阵卷与化形卷的连接。驿河有同样的"桥"：模板生成的adapter——默认的shim——没有人认领的桥。）
- **工程锚点**：桥的分类学从化形卷移植到简阵卷——(a) shim：薄适配——容易删 (b) adapter：转换——需要迁移 (c) bridge：跨系统——可能永久
- **张力曲线**：登场型（顾迁舟翻开桥账——"我来帮驿河整理桥。每个平台有桥。你们的桥——在模板里——在adapter里——在没有人认领的shim里。"→傅远洲:"什么是桥？""任何被依赖但不被承认的中间层——都是桥。"）
- **六拍骨架**：顾迁舟调查驿河——发现至少12座桥——模板自动生成的中间层——配置之间的转换——服务之间的默认shim——"都是等什么时候就拆。"

### 第56章：驿河的桥

- **核心对象层**：门→门（顾迁舟为驿河的每座桥建出生证和退场日期。和化形卷Ch42同样的分类学——不同的桥文化。"驿河的桥更隐蔽——因为它们不是人搭的——是模板生成的。每一套模板——在生成服务时——自动搭了adapter——自动设了默认shim——没有人知道它们存在——因为它们是'自动的'——自动——等于'没有人认领'。"）
- **核心相与失守**：式 → 失式（模板生成的桥——是"式"的过度——模板为了"方便"——自动搭了中间层——但这些中间层——没有人知道——没有人维护——没有人认领——"方便——变成了——不可见——不可见——变成了——定时炸弹。"）
- **工程锚点**：自动生成的adapter/shim/bridge——模板（template）在生成服务时自动创建的中间层——"不是因为需要——是因为模板默认包含"。——桥的出生证（birth certificate）：创建时间、创建原因、创建模板/创建人、预期退场日期、当前依赖者列表。
- **张力曲线**：考古型（顾迁舟翻开驿河的模板——发现43项模板中——有7项会自动生成adapter——"这些adapter——在51个服务中——每一个——都生成了——然后——被部署——然后——被依赖——然后——没有人知道——没有人认领——没有人维护。"→桥账——12座桥——全部来自模板——全是"自动的"——全是"盲区"。）
- **角色焦点**：顾迁舟（跨卷人物——"化形卷的桥——是人搭的——至少人知道自己在搭桥。驿河的桥——是机器搭的——机器不知道自己在搭桥——它只是按照模板——自动生成——自动部署——自动被依赖——自动变成'永久的临时的'。"）
- **六拍骨架**：
  1. 问题先出：顾迁舟调查驿河——发现至少12座桥——全部由模板自动生成
  2. 为什么痛：自动生成——等于"没有人决定搭桥——没有人知道桥存在——桥就被依赖了"
  3. 引出方法：桥账——为每座桥建出生证——什么模板生成的——什么时候——被谁依赖——退场日期
  4. 项目落地：顾迁舟翻开桥账——12座桥——全部标注出生证+退场日期——"不是桥不能存在——是桥不能不被承认。"
  5. 多方复盘："驿河的桥——是模板的'方便'的代价。方便让你不去想——不去想的——变成不可见——不可见——变成没有人能负责。"
  6. 高层收束：自动生成的——不等于不需要被承认。每一个自动——背后需要一个人——签——"我知道它在——我负责它在'临时的'时期——不退化成'永久的'"。

### 第57章：deploy/rollback

- **核心对象层**：阵→阵（从两个时辰降到半个时辰——自动化部署系统。"部署不是'把代码放上去'——是声明——'这个版本——从此刻起——是生产版本。'回滚不是'把旧的放回去'——是声明——'上一个版本——重新成为生产版本。——部署和回滚——是对称的——是同一个系统的两个方向。"）
- **工程锚点**：部署系统（deployment system）——声明式部署（declarative deployment）：定义目标状态——系统自动达到——而非手动执行步骤。"部署从两个时辰降到半个时辰——不是因为人变快了——是因为部署从'人做步骤'变成'机器执行声明'。回滚从'不知道滚回哪里'变成'部署系统的反向命令'。"
- **张力曲线**：建设型（傅远洲——"之前——部署是——'我scp上去——重启——检查——如果不对——再scp旧版本——重启——检查——两个时辰。现在——部署是——'cargo deploy v1.2.3'——机器做——人在看——半个时辰——不是快了——是不需要人在每一步上等。")
- **六拍骨架**：
  1. 问题先出：部署时间两个时辰——占半天——期间——服务不稳定——"部署窗口内——没有人敢动"
  2. 为什么痛：手动部署——每一步——人必须执行——人必须等待——人在凌晨——做重复的事——会出错
  3. 引出方法：声明式部署——定义目标状态——系统自动执行——人只需要声明——不需要执行步骤
  4. 项目落地：傅远洲建立自动化部署系统——deploy命令——声明版本——系统自动完成——半个时辰
  5. 多方复盘："部署从人做变成机器做——不是替代人——是让人不用在凌晨——做重复的事。凌晨——是做判断的——不是做步骤的。"
  6. 高层收束：部署——不是技术——是声明。"这个版本——从此刻起——是生产的。"回滚——是反声明。

### 第58章：不是越快越好

- **核心对象层**：念→念（变更管理不是限制速度——是让速度的方向不杀人。"deploy可以自动化——但自动化的速度——不等于安全。快——是好的——但如果快——改变了时序——在还没有告知下游的时候——快——不是好——是突袭。"）
- **工程锚点**：变更管理（change management）——"不是审批——是声明。快——不代表不需要声明——声明——不代表慢。快——但先声明——声明后——快——依赖者知道你要快——他们准备——你变快——他们不意外。——不是越快越好——是'快——但先告诉会被你影响的人'。"——这是卷七行序事故（Ch61）的主题预告。
- **张力曲线**：对峙型（"部署自动化了——我们可以一天部署十次——""快——是好的——但如果你一次部署——改变了三个服务的时序——不告诉它们——它们凌晨炸——它们的传讯牌——你接吗？""我可以不接——我的部署是自动的——""你不能不接——因为你没告诉它们——你的部署——没有声明——没有声明——你就是在凌晨——突袭了别人的服务。")
- **六拍骨架**：
  1. 问题先出：部署自动化后——有人提议"我们可以每天部署多次"
  2. 为什么痛：快——但不声明——等于"你的快——是别人的凌晨"
  3. 引出方法：变更管理——不是让变更变慢——是让变更"在被知道的情况下——快"——声明→部署→验证
  4. 项目落地：傅远洲在部署系统中加"变更声明"——每次部署前——系统要求声明影响范围——自动通知依赖者
  5. 多方复盘："不是不让快——是'快——要先被知道'。快是好的——但突袭——不是。"
  6. 高层收束：部署的速度——不应该是'能做到多快'——是'在依赖者都知道的情况下——能多快'。快——是你的自由——但自由——不能建立在别人的凌晨上。

### 第59章：边界之后

- **核心对象层**：念→念（契约写清楚了——但契约能防止"炸"吗？不能——但契约让"炸了之后谁该知道"变得清楚。"两件事同时改——各自遵守自己的契约——但合在一起——炸了。因为契约管'什么'——不管'什么时候'。——A的契约说——'我会返回X'——B的契约说——'我接受X作为输入'——都是对的——但A改了X的时间——B还没准备好——两件事——各自遵守契约——但合在一起——时序冲突。——契约——让'炸了之后——知道怪谁'——但不够——不够让'炸之前——知道会因为'时序'炸。'"）
- **工程锚点**：契约的边界——API契约管"什么"（what）——但不管"什么时候"（when）。两个服务各自的API契约是正确的——但变更的顺序（谁先部署、谁后部署）——不在契约里——在行序（deployment ordering）里。"契约告诉你——改了会炸谁的接口。行序告诉你——什么时候改——炸的可能最小。契约管'什么'。行序管'什么时候'。"
- **张力曲线**：收束型（傅远洲——"边界——契约——建了。但契约——不是'不会炸'的保证——是'炸了——我们知道——是谁的契约——没被满足'。——但还有'什么时候'的问题——两件事——各自对——但先后——错了——合在一起——不对。——边界——是'什么'的边界。下一步——需要'什么时候'的边界。——行序。"）
- **六拍骨架**：
  1. 问题先出：两个服务——各自修改——各自遵守契约——但合在一起炸了——因为时序冲突
  2. 为什么痛：契约管'什么'——不管'什么时候'——两个正确的变更——在错误的时间相遇——变成错误
  3. 引出方法：行序（deployment ordering）——不是'谁能先部署'——是'谁的变更——在什么条件下——不会炸别人'
  4. 项目落地：傅远洲在记录板上加第三层——"API契约✔ → 下一步：行序——变更顺序。"
  5. 多方复盘："契约让边界可见——但时序——是边界的另一个维度——'什么'和'什么时候'——两个维度——都需要治理。"
  6. 高层收束：边界之后——不是没有事故——是事故有了名字——"谁的契约——被违反了"。行序——让事故有了另一个维度——"谁的变更——在不该在的时候——来了。"

### 第60章：行序之前

- **核心对象层**：门→史（过渡章——"契约在——但执行顺序呢？谁先谁后——是行序。契约管'什么'。行序管'什么时候'。不是'先到的先部署'——是'谁的变更——不会伤害别人——谁先。'"——向卷七过渡：行序——变更影响+OOM入侵——化形卷模块在驿河。）
- **工程锚点**：行序（deployment ordering / change sequencing）——不是FIFO——是"谁的变更影响最小——谁先——谁的变更影响大——声明后——在所有人准备好之后——再部署。"行序——是"部署的公民道德"——"不是我先——是因为我最不影响别人。"
- **张力曲线**：过渡型（傅远洲——"边界——有契约了。内部——有治理了。但'什么时候'——还没有。——接下来——行序——不是限制谁先部署——是让'最先部署的'——是'最不影响别人的人'。——我们不是赛跑——是排队——排在前面的——是不会撞到别人的。"）
- **六拍骨架**：
  1. 问题先出：契约在——但"谁先部署"——没有规则——"先到先部署"——但先到的——可能影响所有后来者
  2. 为什么痛：没有行序——等于"部署顺序是随机的"——随机——等于"炸——也是随机的"
  3. 引出方法：行序——基于影响分析——影响最小的先部署——影响大的——声明后——在窗口期部署
  4. 项目落地：向卷七过渡——傅远洲——"下一步——行序。不是更快——是更有序。"
  5. 多方复盘："契约——告诉了'什么'。行序——告诉'什么时候'。两个都知道了——变更——不再是在凌晨——突袭别人。"
  6. 高层收束：边界之后——契约有了——下一步——行序。向卷七——行序——变更影响+跨卷入侵——化形卷模块在驿河OOM。
