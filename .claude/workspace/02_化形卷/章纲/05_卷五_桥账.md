# 卷五「桥账」Ch 41-50：顾迁舟的桥

## Section 总览

- **章段**：Ch 41-50
- **叙事主题**：顾迁舟带着七条桥的账本到来——每一条都是"等新版本出来就拆"。桥不是路——但所有桥都变成了路。
- **核心冲突**：三层已经有了——但三层之间的连接是用"临时桥"搭的。桥让三层能运作——也让三层之间的边界形同虚设。
- **工具链阶段**：uv锁定 → mypy全量类型检查 → pytest测试王国
- **对象层**：阵→门（从三层的内部秩序到"三层之间的通道"——桥的治理）
- **主相→蚀**：契 → 背契（桥不是承诺——但桥上的依赖者把桥当成了承诺）
- **主角状态**：从建设者到"桥的管理者"。三层建好了——现在要面对的是连接三层的那些"临时"通道。
- **张力引擎**：桥的悖论——每一座桥都是"等新版本出来就拆"，但新版本永远没出来。桥的寿命 — 不是设计决定的，是被依赖决定的。
- **卷尾落点**：七条桥——至少三条可以开始删。但在删之前——要先给桥写退场日期。typing的迟到让息壤的契约没法被机器验证——mypy的237个警告是桥上的裂缝。

### 第41章：桥不是路

- **核心对象层**：门→史（顾迁舟的桥账——每条桥都有出生日期，没有退场日期）
- **核心相与失守**：契 → 背契（桥被当成了路——临时通道成了长期基础设施）
- **工程锚点**：桥（adapter/wrapper）的工程分类——shim（薄适配）vs adapter（厚转换）vs bridge（跨系统通道）vs compatibility layer（兼容层）。不同厚度、不同退场策略。
- **张力曲线**：登场型（顾迁舟带着桥账到来→摊开账本→七条桥——每一条都是"临时"的→最老的一条搭了四年→"这已经不是桥了——这是路。人们在上面建立了依赖关系。你拆了它——人会跟你拼命。"）
- **角色焦点**：顾迁舟（渡桥人登场——不是来拆桥的，是来让桥"有出生证和死亡证"的）；周栖野（第一次从桥的视角看息壤——三层之间确实全是桥）；叶藏拙（"我一直记的是脚本。桥——我从来没见过这么系统地记录桥的人。"）
- **六拍骨架**：
  1. 问题先出：顾迁舟到息壤——摊开桥账。"七条桥。全部没有退场日期。"
  2. 为什么痛：最老的桥——`xirang-cpp-bridge`——一个从Python调用C++模块的FFI（Foreign Function Interface）包装。搭了四年。当时说的是"等玄枢那边的新接口出来就拆"。新接口在第二年就出来了——但没人来拆桥。
  3. 引出方法：桥的悖论——每一座桥在搭的时候都有"退场条件"。"等新版本出来"、"等那边修好"、"等我们迁移完"。退场条件到了——但桥还在。因为拆桥比搭桥痛苦十倍。
  4. 项目落地：顾迁舟逐条审计七条桥——"(1) xirang-cpp-bridge：FFI到C++ (2) xirang-excel-adapter：Excel导入导出 (3) xirang-old-api-shim：旧API兼容 (4) xirang-r-report：R语言统计桥 (5) xirang-legacy-db：旧数据库连接器 (6) xirang-temp-migration：三年前的一次临时迁移 (7) xirang-unknown：不知道谁搭的、搭来干什么的。"
  5. 多方复盘：周栖野认出第六条——是他自己三年前搭的。他说的是"两周的临时方案"。顾迁舟在账本上写——"实际寿命：三年。原因：方案生效了。没人想动。"
  6. 高层收束：桥不是路——但桥被走成了路。不是任何人的错——是没有人负责桥的退场。
- **入门检查**：前置：Ch40 / 新术语：适配器（adapter）、兼容层（compatibility layer / shim）、FFI（Foreign Function Interface）（≤3）
- **三问预检**：🩻背契（每座桥在搭的时候都有一个"我会拆"的承诺——那个承诺从来没有被兑现） 😣桥上的依赖者——桥成了他们的基础设施，他们不知道桥是临时的 🛤️开始——顾迁舟的桥账让"桥的退场日期"成为一个公开话题
- **包管理/类型/异步**：uv锁定/dynamic/sync

> 📝 **路标章**：对应旧Ch08。保留顾迁舟带桥账登场的核心场景。新增七条桥的详细审计。与驭器卷Ch51-60（旧桥谱系）跨卷互文——两种完全不同的桥文化。

### 第42章：桥的出生证

- **核心对象层**：史（桥的考古——每座桥都有自己的出生理由。只是那个理由——和桥一起被忘了。）
- **核心相与失守**：史 → 断史（桥的"为什么"丢失了——只剩桥本身）
- **工程锚点**：桥的考古学（bridge archaeology）——追溯每座桥的：谁搭的（author）、什么时候（date）、为什么（reason）、谁在用（consumers）、退场条件（sunset condition）、为什么退场条件未触发（why sunset missed）。
- **张力曲线**：考古型（顾迁舟逐桥追溯→每座桥的出生证都讲了一个故事→"这座桥——搭它的人三年前就离开息壤了。他只在桥的注释里留了一行：'Sorry. This is ugly. But it works.'"）
- **角色焦点**：顾迁舟（渡桥人的方法论——"桥必须写明退场日期——哪怕那个日期是错的。错了可以改。没有日期——就是'永远不会拆'。"）；周栖野（协助考古——"C++桥是我搭的。我知道为什么——我以为写了注释。"翻出来——注释写的是"TODO: remove after migration"。没有日期。）
- **六拍骨架**：
  1. 问题先出：顾迁舟开始给每座桥补出生证——不是重新写，是把桥上的注释、git log、群聊记录里的"当时为什么"找出来
  2. 为什么痛：六座桥的出生理由——全部合理。每一个都是当时最好的选择。没有一座是"恶意"的——没有一座是"懒"的。但每一个"最好的选择"都变成了长期的维护负担。
  3. 引出方法：桥的出生证格式——Author / Date / Reason / Sunset Condition / Consumers / Why Sunset Missed。不只是记录"桥存在"——是记录"桥什么时候该死"。
  4. 项目落地：顾迁舟调查第七条"unknown"桥——`xirang-unknown`。发现它是在凌晨三点被部署的——没有git commit记录、没有作者、没有任何文档。只有一条部署日志——"hotfix - 3:17am"。三年后的此刻——没有人知道它在修什么，它在桥接什么，它通向哪里。
  5. 多方复盘：叶藏拙查他的账本——"三年前的凌晨三点——玄枢断火。那条晚上息壤有好几个外部接口报错。有人紧急搭了这条桥——但没留名。可能是周栖野——也可能是林过川。他们可能在半梦半醒中搭的——第二天醒来——桥已经在了。问题已经消失了。于是没人提。"
  6. 高层收束：桥的出生证不只是考古——是为拆桥做准备。你不知道桥为什么出生——你就不知道它能不能死。
- **入门检查**：前置：Ch41 / 新术语：桥的考古学（bridge archaeology）、退场条件（sunset condition）、出生证（provenance record）（≤3）
- **三问预检**：🩻断史（桥的"为什么"丢失了） 😣3:17am搭桥的那个人——他可能自己都不记得搭过 🛤️开始——出生证让每座桥的"为什么"可见
- **包管理/类型/异步**：uv锁定/dynamic/sync

### 第43章：七条桥

- **核心对象层**：门→史（七条桥的完整审计——每条桥一条故事）
- **核心相与失守**：契 → 背契（全都是"等...就拆"。不同的人。同一个措辞。和Ch28的"后来者应该自己判断"一模一样——"这是第二种守缺者信仰。"）
- **工程锚点**：桥的复杂分类——从"薄shim可以删"到"厚adapter需要迁移计划"到"跨系统bridge可能永远不能删——但永远不能删也需要被声明"。桥的分类决定了删桥策略。
- **张力曲线**：分类型（顾迁舟逐桥分析→分类：可删/可迁/不可删→分类的过程让周栖野不适——"你把我的桥分成了——'能死'和'不能死'。"）
- **角色焦点**：顾迁舟（桥的分类学——不同的桥有不同的治理策略）；周栖野（"为什么我的桥全是不能删的？"——因为他的桥不是shim——是跨系统通道。他们解决的是更复杂的工程问题——不易拆）
- **六拍骨架**：
  1. 问题先出：顾迁舟把七条桥分成三类——"可删：退场条件已满足。可迁：需要迁移下游使用者。不可删：被多个外部系统深度依赖——删除的代价太高。"
  2. 为什么痛：三类分布——可删2条，可迁3条，不可删2条。不可删中最老的那条——就是3:17am的hotfix桥——没有人知道它桥接了什么东西，但拆了之后北岭设备集群的一个数据管道坏了。马上回滚。没有人敢再碰。
  3. 引出方法：桥的治理原则——(a) 可删→写退场计划 (b) 可迁→写迁移指南+弃用声明 (c) 不可删→接受它的"永久"状态——但必须声明它是永久的，不再假装它是"临时"的。
  4. 项目落地：周栖野看着"不可删"的标签被贴在自己的C++桥上——"所以它是——永久建筑。""是的。""但在我的head里——它一直是临时的。""你的head——不是息壤。在息壤的桥账上——它是永久的。不是你搭它的意图决定的——是它的依赖者决定的。"
  5. 多方复盘：顾迁舟——"桥的寿命不由搭的人决定——由用的人决定。你想拆——你得问桥上的人同不同意。这座桥——用的人比搭的人多一百倍。你不再是主人了。你是看守。看守的职责不是拆——是让桥上的人安全地过完——然后你才能拆。"
  6. 高层收束：桥的分类不是惩罚——是诚实。在息壤的过去——没有人区分可删和不可删——因为没有人管理桥。现在有了管理——桥的命运不再由遗忘决定。

- **入门检查**：前置：Ch42 / 新术语：桥的分类学（bridge taxonomy）、迁移指南（migration guide）、永久声明（permanence declaration）（≤3）
- **三问预检**：🩻背契（桥的"临时"承诺被依赖者打碎——桥的寿命不由搭桥者决定） 😣桥上的依赖者——他们的工作建立在"没人敢拆"的基础上 🛤️是——桥的分类让"什么能拆"从虚假的期望变成可执行的计划
- **包管理/类型/异步**：uv锁定/dynamic/sync

### 第44章：typing的迟到

- **核心对象层**：约→文（类型标注（type hints）——为什么息壤最需要却最晚拥有）
- **核心相与失守**：式 → 失式（没有类型标注——"快"的代价累积到边界破裂。类型不是枷锁——是在沼泽里画边界线的工具。）
- **工程锚点**：Python的类型系统演化——PEP 484 (Type Hints) 2014年提出，Python 3.5 (2015)正式引入。息壤长期不使用——因为"动态是自由的"。但当沼泽大到一定程度——自由变成了不可知。
- **张力曲线**：对峙型（周栖野："类型是枷锁。"宋既明翻出Ch11季晚禾的报错——"这个报错——如果周栖野的函数有类型标注——季晚禾在调用它的时候就会被mypy警告。她不会在生厂环境炸掉。"→周栖野沉默——"Typing——不是为了约束我。是为了保护季晚禾。")
- **角色焦点**：宋既明（倡导typing——不是美学，是安全。类型标注是手段——保护使用者是目的。）；周栖野（"我讨厌类型不是因为它是约束——是因为我知道我的代码大部分情况下类型不确定。标注它们——意味着我要承认：我一直在靠'它恰好是这样'在跑。"）
- **六拍骨架**：
  1. 问题先出：宋既明提议在固核层强制类型标注（type hints）——"入世层的API没有类型——外部调用方得猜你的函数接受什么、返回什么。"
  2. 为什么痛：周栖野反对——"类型会让试法变慢。要写类型——我得先想清楚函数签名。化形之道的速度——就是因为不用想清楚。"
  3. 引出方法：渐进类型（gradual typing）的哲学——不强制全量——但关键路径上必须有。入世层的接口——是外部使用者的安全线。入世层的函数如果没有类型——使用者只能靠看源码（source code）和猜。
  4. 项目落地：宋既明翻出一个实际的例子——Ch11季晚禾的报错。当时周栖野的函数`parse_fields(data)`接受`data`参数——可能是DataFrame、dict、list、None。函数内部对不同类型有不同的处理逻辑。季晚禾传了None——触发了未处理的None分支——炸了。如果函数有类型标注`def parse_fields(data: pd.DataFrame) -> dict`——mypy在季晚禾传None时就会警告她。
  5. 多方复盘：宋既明——"类型不是为了约束作者——是为了保护使用者。你写类型的时候花的每一秒——都在替季晚禾省下她排查报错的时间。类型是作者和使用者之间的契约——机器可以验证这份契约。"
  6. 高层收束：Typing的迟到——不是因为技术难。是因为化形之道的"自由"被神圣化了——类型标注被视为"违背化形之道"。但现在看清了——类型不是枷锁，是边界线。没有边界线的自由——是沼泽。

- **入门检查**：前置：Ch43 / 新术语：类型标注（type hints / PEP 484）、渐进类型（gradual typing）、静态类型检查（static type checking / mypy）（≤3）
- **三问预检**：🩻失式（缺少类型标注——使用者和作者之间的契约无法被机器验证） 😣季晚禾——Ch11的报错如果有类型标注就不会发生 🛤️是——typing让"接口承诺"变成机器可验证的
- **包管理/类型/异步**：uv锁定/Type Hints→mypy/sync

### 第45章：mypy的警告

- **核心对象层**：文→约（第一次全量mypy检查——237个警告。每一个警告都是一个潜在的季晚禾的报错。）
- **核心相与失守**：式 → 失式（237个警告——不是237个bug。是237个"在某种条件下可能变成bug的用法"。mypy不说"这不对"——它说"这不够确定"。）
- **工程锚点**：mypy的初次运行——从`pip install mypy`到`mypy . --strict`。第一次全量类型检查的体验——不是多巴胺，是恐怖。每一个警告都在说"我知道你在依赖一个你自己没说清楚的假设。"
- **张力曲线**：崩塌型（mypy run→一行行输出→10个→50个→100个→237个→周栖野看着屏幕→"这是什么？""这是你的代码在别人机器上可能报错的237种方式。不是一定会报错——是机器不知道它会不会报错。因为它不够确定。"）
- **角色焦点**：周栖野（第一次面对mypy——从抗拒到沉默）；宋既明（解释mypy的哲学——"mypy不是打分——是翻译。它把你代码里的不确定翻成你能读的语言。"）；唐野渡（"如果type hint让我慢一半——我宁愿不要。"
→"那如果半年后季晚禾因为你的'不确定'排查了三天呢？你宁愿她排查三天——也不愿自己花一个小时加type hint？"）
- **六拍骨架**：
  1. 问题先出：宋既明在入世层的field-mapper模块上跑mypy——`mypy xirang_gate/field_mapper.py --strict`
  2. 为什么痛：237个警告。不是237个bug——是237个"mypy不确定的地方"。`Argument 1 to "parse_fields" has incompatible type "Optional[DataFrame]"; expected "DataFrame"`——意思是：你的函数期望DataFrame——但调用方可能传None。你没有处理None的情况。
  3. 引出方法：mypy的输出结构——(a) 类型不匹配：函数期望的和调用方传入的不一致 (b) 可能的None：在可能为None的值上调用了方法 (c) 缺少类型标注：函数没有声明参数类型 (d) 无用的代码：类型守卫下永远不可达的代码。
  4. 项目落地：周栖野逐行处理mypy警告——第一个警告就是`parse_fields`的Optional。他加了一行`if data is None: raise...`——警告消失。第二行——mypy提醒他被注释掉的函数仍然被import——不确定是不是死代码。第三行——一个`Any`被他传进了类型化的函数。
  5. 多方复盘：宋既明——"mypy的每一个警告——都在替后来者做判断。'你可以依赖这个吗？''不一定。'不一定——就是锁。后来者看到'不一定'——他们就得自己判断。mypy帮他们判断了——判断的结果叫warning。"
  6. 高层收束：237个警告不是终点——是起点。每消除一个警告——后来者就少一次"不确定"。mypy不是来批评代码的——是来让代码说话的。让它能清楚地告诉后来者：我接受这个——不接受那个。
- **入门检查**：前置：Ch44 / 新术语：mypy、类型不匹配（type incompatibility）、Optional（≤3）
- **三问预检**：🩻失式（类型的不确定——使用者和作者之间的契约模糊） 😣后来的维护者——他们被迫猜测每个函数真正接受什么 🛤️是——mypy的每一个警告修正都让契约变得更清晰
- **包管理/类型/异步**：uv锁定/mypy全量/sync

### 第46章：顾迁舟的方法

- **核心对象层**：约→门（桥的治理方法——退场日期、弃用声明、迁移窗口）
- **核心相与失守**：契 → 背契（桥没有退场日期——等于桥承诺了"永远"。但没有桥能承诺永远。）
- **工程锚点**：桥的治理协议（bridge governance protocol）——每座桥必须：(a) 写明退场日期——"哪怕那个日期是错的。错了可以改。没有日期——就是'永远不会拆'" (b) 弃用声明（deprecation notice）——提前一个版本公告 (c) 迁移窗口（migration window）——让使用者有时间过渡。
- **张力曲线**：方法论型（顾迁舟："给每座桥填退场日期。日期可以是错的——但空白不行。"→周栖野："但那个日期谁知道？"→"你写的日期——是对桥上的人说：'在这个日期之前——你需要准备好了。'不是对你说的——是对他们说的。"）
- **角色焦点**：顾迁舟（渡桥人的核心方法论——桥必须写明退场日期）；周栖野（学习写退场日期——发现每一座桥需要不同的处理）；叶藏拙（"退场日期——让后来者知道他们依赖的东西什么时候会消失。这不是威胁——是尊重。")
- **六拍骨架**：
  1. 问题先出：顾迁舟给七条桥分别写退场日期——发现最后一列的空白比前三列加起来都大
  2. 为什么痛："退场日期空白——意味着桥永远不会被拆。不是没人想拆——是没有人敢说'我会拆'。""说'我会拆'意味着：你承认桥是临时的。你承认这座桥的存在是一个过渡状态。而在息壤的文化里——承认'这是临时的'等于承认'这不是最好的'。没有人想承认自己的产物不是最好的。"
  3. 引出方法：退场日期的心理工程学——写日期不是在写计划——是在写承诺。"我会在X日期前通知桥上的人——这座桥要退场了。"日期可以是错的——错了可以改。但没有日期——等于什么都没承诺。

### 第47章：pytest的王国

- **核心对象层**：约→文（测试体系——从"跑一下看看"到"不通过就不能合"）
- **核心相与失守**：（建设章——测试是背契的疫苗。每个测试都在对后来者说：这是被承诺的行为。）
- **工程锚点**：pytest——Python的测试框架。不是第一个，而是最被广泛使用的。`@pytest.fixture`、`@pytest.mark.parametrize`、`conftest.py`的层级共享——测试不是写得更多，是组织得更好。
- **张力曲线**：建设型（周栖野写第一个pytest→从"测试是负担"到"测试是说明书"→第一次看到一个测试让后来者独立判断"这是对的行为还是bug"）
- **角色焦点**：周栖野（从"我不想写测试"到"测试是给后来者的说明书"）；宋既明（"测试不是验证代码——是定义'对'。"）；白又新（验证——"这个测试告诉了我：parse_fields应该接受DataFrame，返回dict。如果返回的不是dict——那就是bug。我之前不知道。我一直以为parse_fields有时返回DataFrame——有时返回dict——看心情。")
- **六拍骨架**：
  1. 问题先出：宋既明要求固核层的每个模块必须有测试——"不通过就不能合。"
  2. 为什么痛：周栖野写第一个pytest——`def test_parse_fields(): ...`。写了五个测试用例。三个通过——两个不通过。不通过的原因不是代码有问题——是他的代码在某个边界条件下的行为是"未定义的"——没有人定义过它应该怎样。
  3. 引出方法：测试的哲学——测试不是验证代码当前的行为——是定义代码应该的行为。今天你写"parse_fields(None)应该raise ValueError"——你在对后来者说："这件事——是设计好的。不是恰好这样——是应该这样。"
  4. 项目落地：周栖野为field-mapper写了30个测试用例——不同的输入类型、边界条件、错误输入。每一个测试不仅验证——还记录了：为什么这个输入是边界条件（"因为Ch11季晚禾传了None"）。测试变成了代码的"使用说明书"。
  5. 多方复盘：白又新独立跑测试——30个全绿。他第一次不用问周栖野——就知道field-mapper应该怎么用。"测试告诉了我'什么是故意的'和'什么是无意的'。之前我分不清——现在我不用分了。测试帮我分了。"
  6. 高层收束：pytest王国不是"测试多了"——是"代码的契约变得可被机器验证"。测试是作者对后来者说的话："这些行为——我是故意的。那些——我不知道。"

- **入门检查**：前置：Ch46 / 新术语：pytest、测试用例（test case）、边界条件（edge case）、fixture（≤3）
- **三问预检**：🩻（建设章——测试让"代码的契约"变成可被机器验证的——防止背契） 😣后来者——测试告诉他们"什么是故意的" 🛤️是——测试是后来者的说明书

### 第48章：测试≠信任

- **核心对象层**：约（测试全绿≠行为正确——一个"测试全绿但行为不对"的故事）
- **核心相与失守**：契 → 背契（测试的承诺可以被误读——测试只验证"代码做了测试说的事"，不验证"代码做了所有该做的事"）
- **工程锚点**：测试的局限性——(a) 测试不能覆盖未预料的行为 (b) 测试不能验证测试本身是否正确 (c) 全绿不代表没有问题，只代表"所有已知问题都解决了"
- **张力曲线**：倒钩型（测试全绿→部署→炸了→追查→"测试全绿——但测试没有覆盖这个场景。"→"没有人想到需要测试这个。因为没有人知道这个场景存在。"）
- **角色焦点**：周栖野（测试通过了——以为安全了——结果炸了）；宋既明（"测试全绿不代表安全。代表——你能想到的所有错误都处理了。但你能想到的不等于所有的。"）；白又新（发现未测试的边界条件——"pandas的read_csv在文件为空时返回Empty DataFrame——但你的测试假设它总是有数据。我用了一个空文件——全绿。在线上——只要有一个空文件就被调用了——就炸了。"）
- **六拍骨架**：
  1. 问题先出：field-mapper 30个测试全绿——部署到生产。一个小时后——线上报错。`ValueError: Empty DataFrame`。
  2. 为什么痛：追查发现——pandas的`read_csv`在文件为空时返回Empty DataFrame——而周栖野的函数假设输入DataFrame非空。测试为什么没发现？因为所有测试用例都提供了非空的DataFrame。没有人想到需要测试"空文件"——因为在现实中不会出现。"现实就是出现了。""
  3. 引出方法：测试的盲区——测试只能验证"作者想到了什么"。作者没想到的场景——测试不会提醒你。属性测试（property-based testing / hypothesis）能部分弥补——"在所有可能输入下"验证属性——不只是给定输入。
  4. 项目落地：白又新在代码里加了三个字——`if df.empty: return {}`。然后写了第十一个测试用例——`test_parse_fields_empty_dataframe`。全绿。但这次只花了五分钟。"不是我们没做测试。是我们没想到。"
  5. 多方复盘：宋既明——"测试全绿不代表安全——代表'从你意识到的问题的角度看，是安全的'。这不是安慰——而是更诚实的说法。每一次炸场——都在扩大你知道的问题的半径。你加了一个测试——半径扩大了一毫米。一百次后——半径大了很多。但永远有未知。"
  6. 高层收束：测试≠信任——测试是诚实。诚实地说"我测试了这些"。诚实地说"我没测试那些"。诚实比安全更重要——因为诚实让后来者知道"安全区"的边界。
- **入门检查**：前置：Ch47 / 新术语：属性测试（property-based testing）、测试盲区（test blind spot）、happy path偏差（≤3）
- **三问预检**：🩻背契（测试的承诺被误读——测试全绿不等于安全） 😣线上的使用者——空文件炸了之后才知道测试有盲区 🛤️是——诚实的测试比完美的测试更有用
