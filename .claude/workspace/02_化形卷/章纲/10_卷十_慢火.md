### 第91章：慢一步活得更久

  6. 高层收束：快与慢的道路开始分裂。不是共存——是选择。每个人选择站在哪一边——不是技术选择，是身份选择。

### 第93章：profiling的真相

- **核心对象层**：流→流（cProfile/py-spy——速度不是感觉，是可量化的。快——在数据中可能并不快。）
- **核心相与失守**：（认知章——之前的"快"是基于直觉。profiling揭示：直觉中的"快"可能在某些关键路径上——比预期的慢得多。）
- **工程锚点**：cProfile/py-spy——Python的性能分析（profiling）工具。不是"让代码更快"——是"让热点（hot spot）可见"。cProfile是标准库，给出函数级别的调用次数和时间。py-spy是采样型profiler——可以在不修改代码的情况下attach到运行中的进程。
- **张力曲线**：认知震撼型（周栖野对field-mapper做profiling→发现最费时的不是他的核心逻辑——是pandas的`read_csv`在解析某个特殊格式→"我以为我的解析最快——因为'跑的时候感觉很快'。数据显示——最慢的恰好是我最骄傲的那段。")
- **角色焦点**：周栖野（面对profiling数据——速度的自我认知被颠覆。他一直以"快"为身份——但数据说有些地方他并不快。）；岑照渠（同样的数据让她重新理解"快"——"快不是感觉。快是可量化的。你最快的部分——是算法选择。你最慢的部分——是I/O。"）
- **六拍骨架**：
  1. 问题先出：周栖野对field-mapper做profiling——"让我看看哪里最慢。"
  2. 为什么痛：数据让他不舒服——他引以为傲的字段映射逻辑——不是最慢的。最慢的是CSV解析——依赖pandas的C引擎。他的代码在等pandas——pandas在等磁盘I/O。"我的'快'——在pandas的等待中——没有任何意义。"
  3. 引出方法：profiling的三层洞察——(a) 热点：哪个函数用时间最多 (b) 调用次数：哪个函数被调用最频繁 (c) 等待：CPU闲的时候在等什么（I/O、锁、网络）
  4. 项目落地：py-spy生成的火焰图（flamegraph）——视觉化的性能地图。最宽的横条——pandas的文本解析——占了60%的时间。周栖野自己的代码——不到15%。"我以为我在run这个show。我在等——大多数时候。"
  5. 多方复盘：岑照渠——"你最快的部分——是你的算法直觉。你最慢的部分——不是你的错。是pandas的解析。优化pandas的调用——比优化你自己的代码更有价值。这就是profiling的价值——它告诉你——不要把力气花在自己的代码上——如果瓶颈在别处。"
  6. 高层收束：快不是感觉——是可量化的。Profiling不只让代码更快——它还原了"快"的真相：作者以为的快——可能在等待中被消耗。认识到"在等什么"——比"写更快"更有效。
- **入门检查**：前置：Ch92 / 新术语：性能分析（profiling / cProfile / py-spy）、火焰图（flamegraph）、热点（hot spot）（≤3）
- **三问预检**：🩻（认知章——profiling让"快"从感觉变成数据——更诚实） 😣周栖野的自我认知——"我最快的部分"在数据中并不最快 🛤️是——profiling让优化有方向
- **包管理/类型/异步**：uv制度化/mypy制度化/anyio制度化

### 第94章：GIL的边界

- **核心对象层**：流→流（GIL——全局解释器锁。什么时候它是瓶颈，什么时候不是。化形卷的异步/并发认知的深化。）
- **核心相与失守**：流 → 乱流（并发模型中的错误假设——以为`asyncio`解决了所有并发问题。但GIL在CPU密集型任务中——仍然是锁。）
- **工程锚点**：GIL（Global Interpreter Lock）的工程真相——(a) 它只在CPython中存在 (b) 它主要影响CPU密集型多线程代码——I/O密集型不受影响（因为线程在等I/O时释放GIL） (c) 替代：多进程（multiprocessing）、C扩展（释放GIL）、或等Python 3.13的free-threaded版本
- **张力曲线**：认知型（周栖野试图用多线程加速profiling中发现的热点→性能反而下降→"不是线程的问题。是GIL——一次只有一个线程执行Python字节码。你的多线程不是在并行——是在排队。")
- **角色焦点**：周栖野（学习GIL——"我以为多线程会让它更快。GIL说——不行。"）；岑照渠（"GIL不是bug——是设计决定。它让CPython的单线程更快——让内存管理更安全。它的代价是多线程CPU密集型任务。知道边界——你就知道什么时候绕过GIL、什么时候接受它。"）
- **六拍骨架**：
  1. 问题先出：周栖野试图用`threading`加速field-mapper的CPU密集型解析→性能没有提升——反而下降了
  2. 为什么痛：线程都在等GIL——看起来是并行的——实际上一次只有一个在执行。"我以为我在用四只手——实际上四只手都在等同一根接力棒。"
  3. 引出方法：GIL的真相——(a) I/O密集型（asyncio）：线程在等I/O时释放GIL→多线程有效 (b) CPU密集型：线程在CPU上运行时持有GIL→多线程无效→应该用`multiprocessing`
  4. 项目落地：周栖野把CPU密集型部分改成`concurrent.futures.ProcessPoolExecutor`——多进程绕过GIL。性能提升了3.5倍。"GIL不是敌人——是边界。知道边界在哪——你就知道在哪战斗——在哪撤退。"
  5. 多方复盘：岑照渠——"很多人以为asyncio替代了多线程——不是的。asyncio是单线程并发的——它没有多线程的GIL问题。但CPU密集型——asyncio也帮不了。你需要多进程——或者C扩展。""所以化形之道的并发——不是一种。是三种：asyncio处理的是'等'——多进程处理的是'算'——GIL决定什么时候用哪种。"
  6. 高层收束：GIL不是障碍——是边界条件。后来者知道边界在哪——就不会在边界之内浪费资源。文明的意义不是消除限制——是标注限制。
- **入门检查**：前置：Ch93 / 新术语：全局解释器锁（Global Interpreter Lock / GIL）、多进程（multiprocessing）、CPU密集型vs I/O密集型（CPU-bound vs I/O-bound）（≤3）
- **三问预检**：🩻乱流（误用多线程在CPU密集型任务——GIL使并行变成排队） 😣以为多线程能加速的后来者——他们会浪费资源 🛤️是——标注GIL的边界让后来者知道什么时候用多进程
- **包管理/类型/异步**：uv制度化/mypy制度化/anyio+GIL认知

### 第95章：制度vs空白

- **核心对象层**：约→域（**跨卷对话**：傅远洲（简阵卷）与周栖野的远程对话——两个"少"的本质差异。）
- **核心相与失守**：契 → 背契（两种"少"：制度的"少"是选择（傅远洲选择了最重要的四项规则），空白的"少"是诚实（周栖野不知道什么该标所以不标）。它们看起来都是"少"——本质完全不同。）
- **工程锚点**：制度（institution）vs空白（blankness）的工程哲学——(a) 制度的"少"：基于判断选择了最重要的几项约束——知道为什么选这几项。"四项必填"是选择——可能错、可能过期。(b) 空白的"少"：基于谦逊不标注——承认不知道什么最重要。"不标注"是诚实——但可能让后来者缺少引导。
- **张力曲线**：哲学对话型（傅远洲："在驿河——我们强制性要求四项必填：内存上限、并发上限、健康检查端点、优雅关闭超时。只四项——不是二十项——因为我们只选了最致命的。"周栖野："在息壤——我不标注——是因为我不知道什么该标。如果错了——标注就是在撒谎。")
- **角色焦点**：傅远洲（跨卷对话者——简阵卷的平台工程视角。制度是"基于判断的选择"——选了最可能致命的项。）；周栖野（化形卷的试法视角——"我的'不标注'不是偷懒——是承认我不知道。如果不知道——不标比标错更诚实。"）
- **六拍骨架**：
  1. 问题先出：驿河事故后——傅远洲联系周栖野讨论标注标准。驿河有"四项必填"——化形卷没有强制标注项
  2. 为什么痛：两人的不同立场——傅远洲的"制度之少"是基于判断：判断哪些标注最可能致命——选了最重要的几项强制要求。周栖野的"不标注"是基于谦逊：不确定的东西不标注——标注的只有确认的。"我们都是在管理'少'——但你的少是判断，我的少是诚实。这两种少——看起来一样——但来源不同、风险不同。"
  3. 引出方法：两种"少"的辨析——(a) 制度之少：选择了N项最关键的——基于经验和判断。可能错——可能过期——但至少有方向。(b) 空白之少：不选任何——承认不知道——给使用者最大自由。不引导——不误导——但也不帮助。
  4. 项目落地：周栖野的理解——"你的四条——是驿河的血的教训。你们经历过足够多的事故——所以知道哪些标注最关键。息壤——还年轻。我们的事故——有的还没发生。我们不知道哪些最关键——这就是为什么我不强制标注。不是拒绝——是'还不到时候'。"
  5. 多方复盘：傅远洲——"制度不是一步到位的。是事故驱动的。每一个必填——背后都有一个'OOM杀掉了整个集群'。等息壤经历足够多的事故——你们也会有自己的'四项必填'。但现在——你的空白——可能更诚实。"
  6. 高层收束：制度与空白的对峙——不是对错。是成熟度不同。制度是积累后的选择——空白是坦诚前的等待。两种诚实——在不同的阶段。
- **入门检查**：前置：Ch94 / 新术语：制度之少（institutional minimalism）、空白之少（blankness minimalism）、事故驱动（incident-driven）（≤3）

### 第97章：不标注

- **核心对象层**：念→约（周栖野的不标注哲学——与傅远洲的四项必填形成对照。空白是诚实——不知道什么该标，所以不标。不是偷懒，是承认不知道。）
- **核心相与失守**：式 → 失式（不标注的风险——关键信息缺失。但标注错误的风险——误导后来者。两者的权衡：在"少"的两种方式之间——化形卷选择诚实的不标注。）
- **工程锚点**：不标注的工程哲学——(a) 空白作为"预留的未知" (b) 不标注优于错误标注 (c) 标注的前提：你知道什么会被别人依赖。息壤的经验还不够——"我们还不知道什么会更致命"。
- **张力曲线**：对话型（周栖野向傅远洲解释——"你的四项——是简阵卷的故事。息壤的故事还在写。我会犯错——但我不想在犯错的同时假装'这是对的'。我的不标注——不是拒绝你的制度——是承认我的经验还不够。你的经验够你的四项——我的经验不够。我不知道我们的'四项'是什么——因为没有足够的事故来告诉我。"）
- **角色焦点**：周栖野（"不标注是诚实的——但诚实不等于足够。只是目前——诚实是我能提供的最好的东西。"）；傅远洲（理解——"总有一天——你会有你的'四项'。不是因为你变聪明了——是因为你被伤得够多了。在那之前——不标注比标错更让人信任。")
- **六拍骨架**：
  1. 问题先出：周栖野解释——"我不强制标注——不是因为不重视。是因为我不想假装我知道什么最重要。"
  2. 为什么痛：标注的风险——"如果我强制标了峰值内存——但标错了。后来者信了——在低于实际的配置下部署——炸了。这是标注的背叛——比不标注更伤害信任。不标注——后来者至少知道'这里没有被验证'——他们会更谨慎。错误标注——让他们相信一个谎言——他们不做额外的检查。"
  3. 引出方法：诚实的空白vs虚假的安全——错误标注创造虚假的安全感。不标注——让人保持警觉。在"无知"和"误知"之间——无知更安全——因为你知道自己不知道。"你不打没有把握的标注——和你写下'我未测试'——本质上都在说同一句：这里需要你自己判断。"
  4. 项目落地：周栖野为固核层的标注加了一层元标注——"已确认"vs"最佳估计"vs"未验证"。"已确认：经过跨场景验证。最佳估计：基于息壤典型场景。未验证：我们没有足够的数据——请自己判断。""这三点——是我对傅远洲的回答。不是'我什么都不标'——也不是'我全标了'——是'我标了我确认的。剩下的——我告诉你我不知道'。"
  5. 多方复盘：傅远洲——"在你的阶段——这是诚实的。在我们阶段——不够。但不是批评。是——你的世界和我的世界——在时间轴上的不同位置。"
  6. 高层收束：不标注不是缺陷——是阶段。息壤在它的工程生命周期中——处于"积累事故"的阶段。不是"已经有足够事故来定义必填项"的阶段。诚实地说"还不够"——是现阶段最先进的认知。
- **入门检查**：前置：Ch96 / 新术语：空白诚实（blankness honesty）、元标注（meta-annotation）——已确认/最佳估计/未验证（≤3）
- **三问预检**：🩻失式（不标注的风险——但错误标注的风险更大） 😣信任错误标注的后来者——他们以为自己在安全的地方 🛤️是——元标注让"确认程度"可见——比全不标注更诚实，比全标注更可信

### 第98章：红色标签规则

- **核心对象层**：约→域（周栖野在息壤公共记录板上加规则——"引用：允许。但你必须声明。"红色标签——制度与空白的和解。）

- **工程锚点**：红色标签规则（Red Label Rule）——"任何模块——无论是lab/core/gate——被外部引用时——引用方必须声明：'我引用了X模块——及其已知的语境限制。'不要求作者标注所有东西——但要求使用者声明自己知道在引用什么。"
- **张力曲线**：制度型（周栖野设计红色标签→"之前的问题是：使用了不稳定的东西——不知道自己在使用。红色标签不阻止引用——但让引用可见。可见的依赖——可以被管理。不可见的——是沼泽。"
- **角色焦点**：周栖野（制度与空白的和解——"林过川的空白是'不知道——所以不说'。傅远洲的制度是'知道——所以必填'。红色标签是第三条路——'不知道——但说了'。说了'我引用了X'——后来者就能trace。说了'我的语境限制'——后来者就能判断。"）
- **六拍骨架**：
  1. 问题先出：周栖野提出红色标签规则——"任何引用——必须声明。不要求作者标注——但要求使用者负责。"
  2. 为什么痛：规则的精妙之处——它不强迫任何人改变标注习惯。但它改变的是"引用"这件事本身的可见性。"当你import一个模块——你承担了责任——'我知道我在依赖它，我知道它的语境限制'。如果后来者出问题——不是作者的错——是引用者的错——因为他们没有声明自己的引用。"
  3. 引出方法：红色标签的机制——(a) 引用声明表：每个模块的`DEPENDENCIES.md`——列出所有被引用的模块及其声明 (b) 自动化检查：CI可以在构建时核对依赖声明表 vs 实际import (c) 可见而非阻止：不阻止任何引用——但让所有引用可见
  4. 项目落地：红色标签规则贴在公共记录板上——"引用：允许。但你必须声明。声明的内容：你依赖了谁——他们的语境限制是什么——你的场景在他们的语境之内吗？如果不——你做了什么额外的防护？"
  5. 多方复盘：岑照渠——"这比傅远洲的四项必填——更轻量。比林过川的空白——更有结构。它是化形之道自己的规则——不是从驿河借来的。"

- **入门检查**：前置：Ch97 / 新术语：红色标签规则（Red Label Rule）、引用声明表（dependency declaration manifest）、可见而非阻止（visible not blocked）（≤3）
- **三问预检**：🩻（制度章——红色标签让依赖可见——不阻止自由，但让责任可追溯） 😣后来的维护者——他们能从引用声明表中看到所有依赖链 🛤️是——红色标签是化形之道对"后来者"的最终答案
