# 卷二「沼泽」Ch 11-20：沼泽生长

## Section 总览

- **章段**：Ch 11-20
- **叙事主题**：沼泽不是一个人制造的——是每个人都以为"先这样"只是自己一个人的事。环境漂移、版本混乱、notebook神谕——沼泽的四种生长方式。
- **核心冲突**："我这边能跑"从救场法宝变成系统性风险。不是"写得乱"——是"临时方案开始被长期依赖"。
- **工具链阶段**：venv隔离 → requirements.txt意识（但尚未制度化）
- **对象层**：文→骨（从脚本森林到"需要一套骨架"的初步意识）
- **主相→蚀**：式 → 失式 + 流 → 乱流（结构失序 + 环境状态不可复现）
- **主角状态**：从"最快的点火者"到"被迫面对沼泽的人"。叶藏拙的账本让他不能再假装看不见。
- **张力引擎**：读者在卷一结束时已经知道沼泽存在——卷二的任务是让读者看见沼泽的四种具体生长机制。每一种都让读者在心里喊："这不就是我的团队吗。"
- **卷尾落点**：沼泽画出了边界——但画地图的工具还没有。下一步需要的是分层，而不是清理。

### 第11章：上周还能跑

- **核心对象层**：文（一个脚本的状态从"能跑"到"不能跑"——没有代码改动）
- **核心相与失守**：式 → 失式（环境漂移——系统的结构取决于运行它的机器的状态）
- **工程锚点**：环境漂移（environment drift）——`requirements.txt`冲突、虚拟环境（venv）缺失、系统级依赖变更。作者机可用（works on my machine）≠ 交付成立（delivery-ready）。
- **张力曲线**：悬疑型（季晚禾打开脚本→报错→没人改了代码→问题在哪？→逐层排查→环境漂移的四个层面同时暴露）
- **角色焦点**：季晚禾（核心POV——关键时刻脚本打不开，追查原因）；白又新（接手追查——第一步就卡死）；周栖野（远程试图"替别人跑一遍"——然后意识到这不是偶发事故）；宋既明（明确指出："不是bug——是入口根本不存在"）
- **六拍骨架**：
  1. 问题先出：季晚禾在月度结算截止前打开上周还能跑的notebook——报错。不是业务逻辑——是导入了上周不存在的依赖冲突。
  2. 为什么痛：离结算截止只有六个时辰。如果这个脚本不能跑——下游全部延期。代价落在季晚禾这样一个不写代码但依赖代码的人身上。
  3. 引出方法：环境漂移的四个层面——(a) Python版本差异 (b) pip包版本漂移 (c) 系统级依赖变更 (d) 隐式配置文件的环境变量依赖
  4. 项目落地：周栖野远程SSH到季晚禾的机器——"我这边能跑"——然后发现她的pandas版本和他不一样。不是代码的问题——是环境的问题。他开始在季晚禾的机器上重建环境——但发现缺的不只是pandas版本。
  5. 多方复盘：宋既明总结——"这不是偶发事故。是入口根本不存在。你所谓的'入口'是你自己机器上的那个环境——那个环境是独一无二的。没有人能复现。包括三个月后的你。"
  6. 高层收束：脚本能跑的真正前提是"周栖野在那台机器上配置过那个环境"——而周栖野已经忘了自己配置过什么。
- **入门检查**：前置：Ch10（沼泽的意识）/ 新术语：环境漂移（environment drift）、复现性（reproducibility）、依赖冲突（dependency conflict）（≤3）
- **三问预检**：🩻失式（环境的"结构"取决于不可见的配置历史） 😣季晚禾——她在deadline前发现入口是虚假的 🛤️否——问题被"远程帮跑"暂时绕过，但入口问题未解决
- **包管理/类型/异步**：venv有但不完整/dynamic/sync

> 📝 **路标章**：对应旧Ch04。保留环境漂移+季晚禾deadline的核心场景。新增：环境漂移四层面系统化分析（宋既明的方法论）。旧Ch04的"远程帮跑先顶过去"保留。

### 第12章：基座差异

- **核心对象层**：文→骨（Python版本差异暴露了息壤缺少"基座声明"——所有脚本都默认了一个从未被写下来的前提）
- **核心相与失守**：流 → 乱流（同一个脚本在不同Python版本上有不同行为——而且不是报错，是"行为不同"）
- **工程锚点**：Python版本兼容性——3.9 vs 3.11 vs 3.12的差异：不只是语法，还有标准库行为变更、弃用警告（deprecation warning）、以及静默行为差异
- **张力曲线**：认知张力（三个人的机器→三个Python版本→同一个脚本三个不同结果→更难的是：不是报错——是"都跑通了但结果不对"）
- **角色焦点**：周栖野（试图理解为什么"自己的Python是3.11"成了一个关键变量）；叶藏拙（记录不同版本差异——"你们每个人的基座都不一样。你们以为你们在同一个息壤上——其实不是。"）；白又新（继续作为"后来者"的代表——他的机器是3.9，他的报错和3.11不一样）
- **六拍骨架**：
  1. 问题先出：同一个脚本，三个人跑——三个不同结果。季晚禾报错，白又新跑通了但输出少了三列，周栖野完全正常。
  2. 为什么痛：不是报错——是静默行为差异。"跑通了但结果不对"比"跑不通"更危险——因为使用者不会质疑结果。
  3. 引出方法：Python版本间的行为差异——dict的迭代顺序、标准库函数的弃用、类型标注的运行时行为变化
  4. 项目落地：叶藏拙在三个人的机器上跑同一个脚本，记录差异——"季晚禾：3.9 → dict顺序不同 → 输出表头错位。白又新：3.9 → f-string的`=`语法不存在 → 报错。周栖野：3.11 → 一切正常。"
  5. 多方复盘：叶藏拙的结论——"你们每个人都在自己的基座上建东西。基座不统一——你们不是在同一块息壤上工作。你们是在三块不同的息壤上——它们刚好叫同一个名字。"
  6. 高层收束：基座差异的本质是"默认的前提没有被声明"。Python版本只是一个最明显的例子——还有更多隐式前提。

- **入门检查**：前置：Ch11 / 新术语：Python版本兼容性（Python version compatibility）、弃用警告（deprecation warning）、静默行为差异（silent behavior difference）（≤3）
- **三问预检**：🩻乱流（多版本的运行时状态各自不同且不可见） 😣季晚禾和白又新——他们以为自己在用同一个工具，其实不是 🛤️开始——叶藏拙的记录让版本差异可见
- **包管理/类型/异步**：venv意识/dynamic/sync

### 第13章：requirements.txt考古

- **核心对象层**：骨→史（一个`requirements.txt`里的内容不是技术声明——是历史沉积层）
- **核心相与失守**：史 → 断史（依赖文件的演化历史丢失——没人知道为什么有这个依赖，但谁都不敢删）
- **工程锚点**：`requirements.txt`的局限——没有分层（直接依赖vs间接依赖）、没有版本锁定（`>=`不等于`==`）、没有用途标注（为什么需要这个包？）
- **张力曲线**：考古悬疑型（叶藏拙拿出息壤最早的`requirements.txt`→逐行审计→三分之一已不需要，三分之一是错的→每删一行都有一个人说"等等——可能在用"）
- **角色焦点**：叶藏拙（考古学家模式——逐行追问："这个包是谁加的？四年前。为什么？不知道。能不能删？没人敢说能。"）；周栖野（第一次参与依赖审计——从"烦"到"恐惧"）；唐野渡（"别删——可能有人在用"的化身）
- **六拍骨架**：
  1. 问题先出：叶藏拙拿出息壤最早的`requirements.txt`——四年前创建的。上面有六十三个包。他问："哪些是还在用的？"
  2. 为什么痛：周栖野逐行审阅——发现十几个包他从未import过。但每当他想删一个——就有人说："等等——好像XX脚本依赖了那个。"
  3. 引出方法：`requirements.txt`的三层考古——(a) 顶层：直接依赖，你import的 (b) 中层：间接依赖，你import的包import的 (c) 底层：过时依赖——曾经需要的，现在不需要了，但没有机制检测
  4. 项目落地：叶藏拙跑了一遍全量`pipdeptree`——画出所有依赖关系。六十三个包——十九个是顶层依赖，二十八个是间接依赖，十六个是"可能已经不需要的"。
  5. 多方复盘：十六个"可能不需要的"——每一个背后都有一个故事。"这个——是林过川四年前做那个数据清洗的时候加的。那个清洗脚本已经三年没人跑了。但这个包——还在requirements.txt里。"
  6. 高层收束：`requirements.txt`不只是过时——它是遗迹。它的每一行都是一个曾经合理但现在已经无人记得的决定。删它的每一行——你都在替一个已经离开的人做判断。

- **入门检查**：前置：Ch11-12 / 新术语：直接依赖（direct dependency）、间接依赖（transitive dependency）、依赖审计（dependency audit）（≤3）
- **三问预检**：🩻断史（依赖的"为什么"丢失——只剩一行包名） 😣四年间所有继承这个requirements.txt的人——他们继承了一个无法验证的依赖清单 🛤️开始——依赖审计让"不知道为什么的依赖"变得可见
- **包管理/类型/异步**：requirements.txt审计/dynamic/sync

### 第14章：notebook神谕

- **核心对象层**：文（notebook的特殊性质——它既是代码又是文档又是"证据"——三种角色的冲突）
- **核心相与失守**：式 → 失式（notebook的线性执行模型制造了隐式的顺序依赖——"你必须先跑了第三个cell才能跑第七个"）
- **工程锚点**：notebook的"神谕化"问题——输出被当成真理，但执行顺序、隐藏状态、未执行的cell都是不可见的。notebook适合试法（exploration），不适合作为长期解释权中心（source of truth）。
- **张力曲线**：悬疑型（一个notebook的输出被当成"金标准"→季晚禾试图复现→跑出来的结果不一样→查原因→notebook的第三个cell没有被执行过——它是手写的数字）
- **角色焦点**：季晚禾（POV——作为使用者，她信任notebook的输出——直到发现那个输出不是程序算出来的，是手写的）；周栖野（羞愧——"那一次太急了，第三个cell怎么都跑不通——我就直接把数字写进去了"）；宋既明（"这不是bug。这是notebook作为工具的根本缺陷：它不强迫你区分'程序的结果'和'你写进去的结果'。"）
- **六拍骨架**：
  1. 问题先出：季晚禾试图复现一个notebook——输入相同，输出不同。她以为是自己的环境有问题——重建了三次。结果每次都不一样。
  2. 为什么痛：这个notebook的输出被用来做月度结算的基准线——"和这个数字不一样就是有bug"。但那个数字可能本来就不对。
  3. 引出方法：notebook的执行模型——cells可以不按顺序执行，状态在kernal里累积，输出可以被手动修改。"你能看到输出——你永远不知道输出来自哪个cell、在什么状态下执行的。"
  4. 项目落地：季晚禾逐cell检查——发现第三个cell从来没有被成功执行过。那个数字是周栖野手写进去的——因为"那一次太急了，第三个cell怎么都跑不通。数字是另一个接口查出来的——我就直接放进去了。"
  5. 多方复盘：宋既明——"我见过的最危险的东西之一——就是一个好用的notebook。用久了，没人分得清哪些是程序说的、哪些是作者说的、哪些是程序说的但基于一个已经过期的状态。这三个东西看起来完全一样——都是输出格里的数字。"
  6. 高层收束：notebook从"最好用的试法工具"变成了"最危险的神谕"。不是工具的错——是"用试法工具做长期基准线"这个用法的错。

- **入门检查**：前置：Ch13 / 新术语：notebook执行模型（notebook execution model）、内核状态（kernel state）、神谕化（oracle-ization）（≤3）
- **三问预检**：🩻失式（notebook的"结构"取决于不可见的执行历史） 😣季晚禾——她信任了一个"看起来像计算结果的手写数字" 🛤️开始——宋既明的方法论让notebook的固有问题被清晰定义
- **包管理/类型/异步**：requirements.txt审计/dynamic/sync

### 第15章：神谕与迷雾

- **核心对象层**：文→约（notebook输出被当成"契约"——但notebook从未签过这份契约）
- **核心相与失守**：式 → 失式（黑箱化——输入明确，输出明确，中间过程无人能看）
- **工程锚点**：notebook输出作为"不可质疑的真理"的组织动力学——当足够多的人依赖一个输出，质疑输出就等于质疑所有依赖它的人的工作
- **张力曲线**：对峙型（岑照渠指出神谕问题→团队抗拒——"我们一直这样用的"→白又新被迫通过猜测模仿→"神谕"的维护成本落在没有人身上的身上）
- **角色焦点**：岑照渠（"别人看到结果，不代表别人看得懂路径。"）；白又新（继承者试图理解神谕——"我只知道结果长这样。我不知道为什么长这样。我按同一个输入跑——输出不一样——我只好复制粘贴上一次的输出。"）；周栖野（"我们什么时候把自己锁在了自己画的牢里？"）
- **六拍骨架**：
  1. 问题先出：团队开始把某些notebook输出当成不可质疑的"神谕"——月度结算的结果必须和这个notebook的输出一致，否则"有问题"
  2. 为什么痛：白又新接手一个神谕维护——发现他不知道怎么产生那个输出。他只能复制粘贴上一次的输出——然后把输入数据手动调整到让输出"看起来对"。
  3. 引出方法：黑箱化（black-boxing）——当系统的内部逻辑不可见时，维护者只能通过猜测输入来"匹配"输出。这不再是工程——是降神。
  4. 项目落地：白又新向岑照渠展示了他的"维护流程"——改输入→等输出→和上一次的输出比对→如果不一致就继续改输入。"我在猜。我猜了一年——越来越不准。因为我在猜上一个猜的结果。"
  5. 多方复盘：周栖野看着白又新的"维护流程"——"这不是维护。这是——""是降神。"岑照渠说。"你们把一个工具变成了神谕。不是因为它是对的——是因为质疑它的代价太大了。太多人的决策建立在它的输出上了。"
  6. 高层收束：notebook本身无罪。但把它放在"不可质疑"的位置上——它就从工具变成了笼子。

- **入门检查**：前置：Ch14 / 新术语：黑箱化（black-boxing）、神谕维护（oracle maintenance）（≤2）
- **三问预检**：🩻失式（神谕的内部逻辑不可见——系统的结构从"可知"变成"只能猜"） 😣白又新——他成了神谕的祭司，每天在猜上一任祭司留下的密码 🛤️开始——岑照渠说清了问题，但解法还没出现
- **包管理/类型/异步**：requirements.txt有/dynamic/sync

> 📝 对应旧Ch06。保留notebook神谕的核心场景。新增：白又新的"维护流程"（猜输入的视觉呈现）——作为继承者被神谕吞噬的具象化。

### 第16章：叶藏拙的记录

- **核心对象层**：史（叶藏拙的账本——把沼泽的每一次生长变成可追溯的记录）
- **核心相与失守**：史 → 断史（如果没有记录，沼泽的生长是不可见的——它只是"越来越难用"）
- **工程锚点**：工程记录的文化——不是bug追踪（bug tracking），是"前提追踪"（dependency tracking）。叶藏拙记录的不是"什么坏了"——是"什么能让它不坏"。
- **张力曲线**：情感复合型（叶藏拙公开账本→团队第一次看见沼泽的全貌→"上周还能跑"的脚本清单→不只是列表——每一个条目背后都有一个人和一个deadline→沉默笼罩房间）
- **角色焦点**：叶藏拙（守门者的核心展示——他不是在批评，是在建立历史。"每一个'上周还能跑'背后都有一个后来者——他们走进来，卡住，放弃了。你们不知道他们的名字。我知道。"）；全团队（第一次集体面对沼泽）
- **六拍骨架**：
  1. 问题先出：叶藏拙在团队会议上公开他的记录——"过去三个月，息壤的共享目录中有三十一个脚本被引用超过三次。其中十八个——已经不能被作者以外的任何人复现。"
  2. 为什么痛：每一条记录都是一个具体的人和一个具体的时刻。"3月17日——季晚禾试图跑周栖野的field_mapper.py——pandas版本不匹配——放弃，改用手工映射——花了三个时辰。"三个时辰。本来应该是一键的事。
  3. 引出方法：工程记录的两种形式——(a) bug追踪：记录"什么坏了" (b) 前提追踪：记录"什么能让它不坏"。叶藏拙做的是后者——他在记录每一个脚本的隐藏前提
  4. 项目落地：叶藏拙展开完整的记录——十八个不可复现的脚本对应着二十三个后来者的失败尝试。八个放弃了。七个去问了别人。六个找到了workaround——但他们的workaround又成为了新的隐式前提。剩下的两个——他们还没放弃。他们在等。
  5. 多方复盘：房间沉默。不是因为被批评了——是因为"看不见的代价"第一次被看见了。每个人都知道沼泽存在——但没有人知道沼泽里有多少人有名有姓。
  6. 高层收束：叶藏拙合上账本——"我不是来批评你们的。我只是想让你们知道——你们的速度每快一步，就有一个人在后面试图跟上你们的脚印。有些跟上了。有些没有。那些没有的——你们不知道。现在你们知道了。"
- **入门检查**：前置：Ch07, Ch15 / 新术语：前提追踪（dependency tracking）、工程记录（engineering log）（≤2）
- **三问预检**：🩻断史（沼泽的代价如果没有记录就是不可见的——叶藏拙把不可见变成了可见） 😣二十三个有名有姓的后来者——他们的失败第一次被记录 🛤️是——看见代价是付代价的第一步
- **包管理/类型/异步**：venv意识/dynamic/sync

### 第17章：不是你的错

- **核心对象层**：域（沼泽的系统性——它不是某个人造成的，是"每个人都以为自己的'先这样'不会伤害别人"造成的）
- **核心相与失守**：契 → 背契（系统性问题——每一个人的"临时方案"都对后来的某个人形成了未签署的契约）
- **工程锚点**：技术债的系统性——它不是个人品德问题，是激励结构（incentive structure）问题。当组织持续奖赏速度，没有人有动机做清理——清理没有奖赏。
- **张力曲线**：收束型（周栖野在叶藏拙的账本后沉默→想道歉→叶藏拙："不是你的错。"→沼泽不是一个人制造的→但每个人都可以是清理沼泽的第一步）
- **角色焦点**：周栖野（从自责到系统性认知——"沼泽是组织行为的结果。清理沼泽也需要是组织行为。"）；叶藏拙（"沼泽不是一个人制造的——是每个人都在救火时留下的脚印。救火没有错。错的是没有人负责在火灭了之后——把脚印扫掉。"）
- **六拍骨架**：
  1. 问题先出：团队会议后，周栖野独自来找叶藏拙——"我想道歉。"叶藏拙："道什么歉？""我制造了最多不能复现的脚本。"
  2. 为什么痛："你道歉是在暗示这是你一个人的问题。它不是。"叶藏拙翻开账本的另外几页——岑照渠的、唐野渡的、甚至林过川的。每个人都有"不能复现的脚本"。
  3. 引出方法：激励结构分析——为什么每个人都在制造沼泽？因为组织奖赏的是"做出结果"——不是"做出可复现的结果"。谢催成表扬的是"快"——不是"三年后还能跑"。
  4. 项目落地：叶藏拙的分析——"你看看每个人被奖赏的是什么。你——被谢催成表扬'最快'。岑照渠——被表扬'最聪明'。唐野渡——被表扬'最能出奇招'。没有一个人被表扬'最可复现'。甚至没有这个词。"
  5. 多方复盘："所以沼泽不是bug——是feature。"周栖野苦笑。"沼泽是组织把所有资源投在'产出'上、一分不给'维护'——的结果。你们没有一个人是懒惰的。你们都很努力——在组织唯一奖赏的方向上。"
  6. 高层收束："不是你的错"不等于"不是你的责任"。下一章——他们需要开始画地图。不是清理沼泽——是先搞清楚沼泽里有什么。
- **入门检查**：前置：Ch16 / 新术语：激励结构（incentive structure）、组织行为（organizational behavior）（≤2）
- **三问预检**：🩻背契（系统性的"只奖赏速度不奖赏可复现性"） 😣所有被激励结构推着走的人——他们不是坏人，是系统里最正常的人 🛤️开始——系统性认知是改变的第一步
- **包管理/类型/异步**：venv意识/dynamic/sync

### 第18章：岑照渠的并行

- **核心对象层**：文→骨（同门者的并行轨迹——和周栖野一样快，一样留下沼泽。但她的反思方式不同。）
- **核心相与失守**：契 → 背契（"快"的不同版本——周栖野的快是本能，岑照渠的快是选择。选择可以被重新评估。）
- **工程锚点**：同门者（peer）的角色——在面对同样问题时，不同工程师会走向不同方向。岑照渠不是批评者——她是另一个版本的"快"，她的存在让周栖野看到：快不是唯一的路。
- **张力曲线**：对话型（周栖野和岑照渠深夜对话→"你也制造了沼泽。""我知道。""那你怎么办？""我准备停下了。"→"你说什么？"→"先停下来——看看沼泽的全貌。再决定往哪走。")
- **角色焦点**：岑照渠（同门者独立场景——"我不是比你更好。我只是比你更早发现——再快下去，沼泽会吞掉我们所有的快。"）；周栖野（从"你凭什么停下来"到"我也许也该停下来"）
- **六拍骨架**：
  1. 问题先出：岑照渠在公共记录板上贴了一张条——"即日起暂停本人所有新脚本的开发。为期一周。仅做清理和文档。"
  2. 为什么痛：谢催成第一个反对——"下周还有新的需求。"岑照渠："下周的需求——建立在二十个不能复现的脚本之上。我做不动了。"
  3. 引出方法：停下来的工程价值——"清理"不是消极行为。在沼泽里，清理是最积极的工程决策——但组织不认可它。
  4. 项目落地：岑照渠和周栖野深夜对话。她摊开她自己的沼泽清单——"十二个脚本，六个不能复现。我的记录不比你好。但我做出这个决定——不是因为我觉得自己比你更负责任。是因为我算了一笔账。"她给周栖野看她的计算——"每个新脚本增加三个间接依赖。清理每个旧脚本需要两倍的时间。如果我现在不清理——三个月后清理所有东西需要的时间超过我的工作时间。我永远清理不完。"
  5. 多方复盘：周栖野看着她的计算——同样的数学，他自己也能算。他只是从来没有算过。因为他不敢算。
  6. 高层收束：不是所有人的速度都有同样的终点。岑照渠停下来了——不是因为她更慢，是因为她看见了终点线不是"交付"——是"交付之后"。

- **入门检查**：前置：Ch17 / 新术语：清理（cleanup/maintenance）、技术债利息（technical debt interest）（≤2）
- **三问预检**：🩻背契（持续制造新脚本而不清理旧脚本的积累效应） 😣岑照渠自己——停下来意味着失去"最快"的身份标签 🛤️是——停下来是画地图的前提
- **包管理/类型/异步**：venv/dynamic/sync

### 第19章：沼泽之后

- **核心对象层**：域→图（从"感受到沼泽"到"需要画地图"的转变）
- **核心相与失守**：式 → 失式（沼泽的边界被画出来了——边界之内是什么？需要一套新的秩序。）
- **工程锚点**：技术债的三维测绘——依赖图（dependency graph）、使用频次（usage frequency）、可复现等级（reproducibility tier）。不是清理——是先量化。
- **张力曲线**：建设型（团队第一次集体行动→给所有脚本打标：绿的（可复现）、黄的（有条件可复现）、红的（不可复现）→打完标的墙令人窒息——但也有了一种奇怪的安心："至少我们现在知道。"
- **角色焦点**：周栖野（组织集体测绘）；叶藏拙（提供数据——三个月的记录）；岑照渠（设计标色体系）；整个团队（第一次集体面对问题而非各自为战）
- **六拍骨架**：
  1. 问题先出：周栖野提议集体给息壤的所有脚本打标——"我们不需要一次清理。我们先知道自己有什么。"
  2. 为什么痛：打标过程暴露的真相——绿的占15%，黄的占45%，红的占40%。每十个脚本，有四个是"根本不知道为什么还能跑"的。
  3. 引出方法：技术债测绘（technical debt mapping）——不是清理，是让债可见。可见的债是可管理的。不可见的债会在你最需要的时候咬你。
  4. 项目落地：墙上贴满了脚本的名字和颜色。从远处看——像一面病态的彩虹。近看——每一个红色标签上都有叶藏拙记录的"后来者失败次数"。
  5. 多方复盘：团队沉默地看着墙。不是绝望——是一种奇怪的安心。之前沼泽是"感觉很大"。现在是"140个脚本，56个红色"。具体的。可数的。可管理的。
  6. 高层收束：沼泽画出了边界。但画地图只是第一步。下一步是分层——哪些是实验，哪些是稳定，哪些被外部依赖。那是另一套工具——他们还没准备好。

- **入门检查**：前置：Ch18 / 新术语：技术债测绘（technical debt mapping）、可复现等级（reproducibility tier）（≤2）
- **三问预检**：🩻失式（沼泽的边界被画出来了——结构的缺失被量化了） 😣整个团队——面对量化后的沼泽是一种情感冲击 🛤️是——从"感觉"到"数据"是付代价的关键一步
- **包管理/类型/异步**：venv有/dynamic/sync

### 第20章：图层之前

- **核心对象层**：图→约（从"看清楚了"到"需要一个协议"——三层息壤的概念萌芽）
- **核心相与失守**：式 → 失式（需要的不只是清理——是新的组织结构。沼泽之所以是沼泽，是因为所有东西都堆在同一个平面上。）
- **工程锚点**：分层（layering）的工程哲学——实验代码、稳定代码、外部服务代码需要不同的治理标准。统合治理 → 沼泽。分层治理 → 秩序。
- **张力曲线**：展望型（团队讨论→"我们需要分层"→什么是层？→三层雏形第一次被画出来→但没人知道怎么实现→"我们需要更多工具——和更多时间"）
- **角色焦点**：周栖野（画出三层雏形——"试法的试验田、稳定的固核、被外部依赖的入世层"）；岑照渠（"问题是谁来守边界？"）；叶藏拙（看着三层图——"这是第一步。但路线图本身也需要维护。"）
- **六拍骨架**：
  1. 问题先出：测绘完成后，周栖野画了一张新图——不再是依赖关系，是三个同心圆
  2. 为什么痛：为什么沼泽永远长？因为所有东西都在同一个平面上——实验代码和关键业务逻辑共享同一个目录、同一个`import`空间、同一个`requirements.txt`
  3. 引出方法：三层息壤的概念——试法层（xirang-lab，随便试，不保证）、固核层（xirang-core，稳定下来的，值得维护）、入世层（xirang-gate，被外部依赖的，有契约）。
  4. 项目落地：三层图被贴在测绘墙旁边。从"沼泽地图"到"秩序设计图"——同一个房间的两面墙。一面是现状——一面是"如果"。
  5. 多方复盘：岑照渠指着试法层和固核层之间的线——"这条线谁来守？"没人回答。叶藏拙指着固核层和入世层之间的线——"这条线呢？"没人回答。三层是设计——但"边界"需要工具和制度。那些东西现在不存在。
  6. 高层收束：沼泽画出了边界，沼泽后面是三层图。但需要有更多工具、更多认知——以及面对更深层的遗迹。林过川的名字又一次被提到——"他的脚本林在三层图中的哪个位置？"

- **入门检查**：前置：Ch19 / 新术语：分层（layering）、三层治理（three-tier governance）、实验代码vs生产代码（experimental vs production）（≤3）
- **三问预检**：🩻失式（结构的缺失被三层图弥补——但三层图只是设计，尚未实现） 😣尚未知——边界守卫者的角色还没有人承担 🛤️方向有了——但实现需要更多工具
- **包管理/类型/异步**：venv→requirements.txt→pyproject.toml意识/dynamic/sync
