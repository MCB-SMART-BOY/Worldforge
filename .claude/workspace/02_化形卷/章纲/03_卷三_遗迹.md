# 卷三「遗迹」Ch 21-30：林过川的脚本林

## Section 总览

- **章段**：Ch 21-30
- **叙事主题**：林过川的遗迹——最亮的灵感，只剩一地无人敢碰的目录与注释。他不是孤例——在他之前有一条链，每代人都试图手动实现交接，每代人都失败。
- **核心冲突**：不是技术失败——是每个人都在最后一刻选择了放弃。放弃的原因完全相同："后来者应该自己判断。"
- **工具链阶段**：requirements.txt考古 → Type Hints (PEP 484) 意识萌芽
- **对象层**：骨→史（从沼泽的"骨架"向下考古，发现沉积在息壤深层的旧遗迹）
- **主相→蚀**：史 → 断史（失传者谱系——三代人、同一功能、同一失败原因）
- **主角状态**：从"沼泽测绘者"到"考古者"。周栖野被迫面对一个真相：自己正在沿着失传者的路往前走。
- **张力引擎**：考古悬疑——层层剥开林过川的遗迹，每深入一层发现更早的遗迹。最终发现：这不是一个人的故事，是一条链。
- **卷尾落点**：林过川不是孤例。在他之前有一条链，每代都试图做同一件事——自动交接（automated handover）。每代都在最后一步放弃了——原因完全相同。周栖野意识到：自己正在成为这条链上的下一环。

### 第21章：脚本林

- **核心对象层**：史（林过川的遗迹——不是抽象的"债"，是可触可摸的目录树）
- **核心相与失守**：史 → 断史（失传者的遗迹——最亮的灵感变成最大的荒地）
- **工程锚点**：脚本沼泽的物理形态——`final_v2_really_final.py`、`copy_of_backup.py`、`do_not_delete/`。文件名本身就是工程病理的化石。
- **张力曲线**：考古悬疑型（叶藏拙带周栖野进入息壤旧目录深处→文件名的进化史：`script.py`→`script_v2.py`→`script_final.py`→`script_really_final.py`→`script_REALLY_FINAL_USE_THIS.py`→沉默。）
- **角色焦点**：叶藏拙（向导——"这里就是林过川的脚本林"）；周栖野（第一次进入失传者的物理遗迹——不是听故事，是看见几千个文件和它们的名字）
- **六拍骨架**：
  1. 问题先出：叶藏拙带周栖野来到试法场最角落的架子后面——"你一直在问林过川是谁。这里是他的遗迹。"
  2. 为什么痛：几千个文件——notebook、脚本、数据导出、随手写的注释。文件名像地层一样分层：从有序到混乱。最新的文件是三年前的——一个叫`README`的文件，内容只有一行："对不起。"
  3. 引出方法：文件名是工程病理的化石。`final_v2`→`final_v3`→`really_final`→`REALLY_FINAL_USE_THIS`——不是"他不会命名"，是"他每次以为这是最后一次"。每次都错了。
  4. 项目落地：周栖野开始翻阅——发现很多脚本引用了已经被删除的模块、依赖了已经不存在的API。但也有一些——确实解决了真实问题。这些问题现在还在被解决，只是换了一套新脚本。
  5. 多方复盘：叶藏拙："你看这些文件名——它们不是混乱。它们是一个人的信念的轨迹。每一次他命名一个文件`final`——他都真心相信这次是最后一次。然后需求变了、环境变了、或者他发现了更好的做法。"
  6. 高层收束：周栖野在`README`前站了很久——"对不起。"林过川知道。他留下的不是秩序，是废墟。他知道。

- **入门检查**：前置：Ch10, Ch20（林过川名字被提及）/ 新术语：脚本林（script forest）、文件名考古（filename archaeology）（≤2）
- **三问预检**：🩻断史（林过川的知识没有被传递——变成了一地文件名） 😣林过川自己——他知道，但来不及了；以及所有试图从他的遗迹中找路的人 🛤️否——遗迹仍然是遗迹
- **包管理/类型/异步**：requirements.txt意识/dynamic/sync

> 📝 **路标章**：对应旧Ch05。保留叶藏拙带周栖野进脚本林的核心场景。新增：文件名的地质分层——从有序到混乱的视觉呈现。旧Ch05的场景拆分为Ch21-24。

### 第22章：不止一个final

- **核心对象层**：史（文件名作为病史——`final`这个词的语义退化）
- **核心相与失守**：史 → 断史（同一个人对"完成"的定义变了七次——但没有一次被记录下来）
- **工程锚点**：版本管理的缺乏——当没有版本控制（version control / Git）时，文件名就是版本号。`final`不是一个状态——是一个愿望。
- **张力曲线**：解谜型（周栖野按时间戳排列所有`final`文件→`final_v1`→`final_v2`→`final_v3`→`really_final`→`REALLY_FINAL`→`FINAL_FINAL`→`FINAL_FINAL_v2`→七个文件——七个"这是最后一次"→每一次之间发生了什么？）
- **角色焦点**：周栖野（考古学家模式——试图从文件名反推林过川的工作轨迹）；叶藏拙（补充context——"这个`FINAL_FINAL_v2`——是因为谢催成提了一个新需求。我那时候在。"）
- **六拍骨架**：
  1. 问题先出：周栖野按时间戳排列所有标记为`final`的脚本——七个。最早的比林过川离开早两年，最晚的是离开前一周。
  2. 为什么痛：每个`final`之间的diff——不是修复bug，是需求变更。"他没有一次是真的在修复一个已经完成的东西。他每一次都是被新的需求拉去改了一个'已经final'的东西。"
  3. 引出方法：`final`这个词在文件系统中的语义退化——当没有版本管理系统时，状态在文件名里。但当文件名可以说谎——"final"就不再有意义。
  4. 项目落地：周栖野在七个文件中找到了同一段逻辑的五种不同实现。每一次被需求变更拉着改——对应的逻辑也变了。但没有注释——没有解释为什么不保留旧实现。旧实现去哪了？删了。没有版本管理。
  5. 多方复盘：叶藏拙指出——"他不是不认真。他每次`final`的时候都是认真的。问题是'final'在一个没有版本管理的世界里——它真正的意思是'此刻不想再改了'。不是'这个版本是对的'。"
  6. 高层收束：`final`这个词在林过川的文件系统中已经失去了意义。但失去意义的方式本身就说明了一切——不是林过川的错，是"没有石录"的错。

- **入门检查**：前置：Ch21 / 新术语：版本控制（version control / VCS）、语义退化（semantic degradation）（≤2）
- **三问预检**：🩻断史（版本历史没有记录——只有文件名里的`final`暗示曾经存在过渡本） 😣林过川——他在没有VCS的世界里试图管理越来越复杂的代码 🛤️开始——意识到"需要石录"是走向石录的第一步
- **包管理/类型/异步**：requirements.txt意识/dynamic/sync

### 第23章：林过川是谁

- **核心对象层**：史（失传者的人物画像——不是通过他本人，是通过别人的回忆和遗迹）
- **核心相与失守**：史 → 断史（一个人离开了——他最有价值的知识在哪？不在任何可被检索的地方。）
- **工程锚点**：失传者（lost knowledge keeper）的工程类型——组织中总有这样的人：他们解决了最难的问题，但他们的解决方案存在于他们的直觉中，而不是系统中。
- **张力曲线**：拼图型（周栖野收集四个人关于林过川的回忆→拼出一个人物→每一块拼图都不同→拼出来的人让周栖野不舒服——"他和我太像了"）
- **角色焦点**：周栖野（拼图者——"我不是在了解林过川。我是在看我的未来。"）；叶藏拙、谢催成、岑照渠、宋既明——每人提供一块林过川的画像
- **六拍骨架**：
  1. 问题先出：周栖野开始问不同的人——"林过川是什么样的人？"
  2. 为什么痛：每个人的答案不同。谢催成："最快的——和你一样快。"叶藏拙："最孤独的——他离开的时候没有人知道。三个月后发现他的脚本不跑了才知道。"宋既明："最让我愤怒的——他有那么多好东西，全都没有留下能用的入口。"岑照渠："最让我害怕的——我觉得我有可能变成他。"
  3. 引出方法：组织中的失传者不是"坏人"——他们是"最有能力的人被放在了只奖赏产出的系统中"。林过川的"快"和周栖野的"快"——来源完全相同。
  4. 项目落地：四块拼图合在一起——一个周栖野不想面对的人。不是敌人。不是前辈。是镜子。
  5. 多方复盘：叶藏拙最后补充："他留下那行'对不起'的时候——我就在旁边。他写了三个字，停了很久。然后关掉了终端。那是他最后一次碰息壤。"
  6. 高层收束：周栖野沉默——"他和我的区别在哪？"叶藏拙："目前——你在问这个问题。他从来没有问过。"
- **入门检查**：前置：Ch21-22 / 新术语：失传者（lost knowledge keeper）、组织记忆（organizational memory）（≤2）
- **三问预检**：🩻断史（最有能力的人的知识消失了——而组织直到三个月后才发现） 😣林过川——"对不起"三个字是他最后的输出 🛤️开始——周栖野在问林过川没有问过的问题
- **包管理/类型/异步**：requirements.txt意识/dynamic/sync

### 第24章：没有人敢删

- **核心对象层**：史→约（恐惧作为制度的替代品——"别删，可能有人在用"变成了一条不成文法）
- **核心相与失守**：式 → 失式（没有人敢做清理决策——因为没有人有足够的信息来判断"是否安全"）
- **工程锚点**：清理恐惧（deletion fear）——在没有依赖声明和引用追踪的环境中，"可能有人在用"是阻止清理的唯一理由，也是所有沼泽的保鲜剂。
- **张力曲线**：对峙型（周栖野试图删除林过川的一个明显无用的脚本→"等等"→来自五个不同的声音→每一次"等等"都有不同的理由→"为什么没有人敢删？"→"因为没有人知道删了会怎样。"
- **角色焦点**：周栖野（试图删——发现删任何一个东西都需要做五个人的考古）；五个"等等"的人（代表组织中清理恐惧的不同面向）
- **六拍骨架**：
  1. 问题先出：周栖野在脚本林中找到一个脚本——文件名是`delete_this_later.py`。创建日期：四年前。内容：空函数加一行注释"先占个位"。
  2. 为什么痛：他准备删——然后谢催成说"等等——可能有人在引用"。岑照渠说"等等——我记得好像有个地方import过它"。白又新说"等等——我没用过但我看到一个README里写了它的名字"。
  3. 引出方法：清理恐惧的工程根源——(a) 没有依赖声明文件 (b) 没有引用追踪工具 (c) 没有弃用策略（deprecation policy） (d) 组织不奖赏清理
  4. 项目落地：周栖野花了一个时辰追查`delete_this_later.py`的所有引用——发现只有一个地方import过它，而且那个import也被注释掉了。"所以它真的是没用的。"但追查这一个文件花了一个时辰。脚本林里有几千个文件。
  5. 多方复盘：叶藏拙——"你知道为什么没有人敢删吗？不是因为懒。是因为'我删了它——如果出事了，是我的责任'。但是'我没删它——出事了——是写它的人的责任'。恐惧让所有人选择不作为——而不作为永远不会被惩罚。"
  6. 高层收束：恐惧不是个人的——是系统性的。在缺少依赖声明和引用追踪的环境中，不作为是最安全的选择。而集体不作为——就是沼泽的生长激素。
- **入门检查**：前置：Ch23 / 新术语：清理恐惧（deletion fear）、弃用策略（deprecation policy）、引用追踪（reference tracking）（≤3）
- **三问预检**：🩻失式（结构的不可见导致清理不能——恐惧取代了信息） 😣所有被迫继承无用代码的人——他们不知道什么可以删，所以什么都留着 🛤️开始——问题被讲清楚了：不是不勇敢，是没工具
- **包管理/类型/异步**：requirements.txt意识/dynamic/sync

### 第25章：旧石镜

- **核心对象层**：史→史（林过川的旧石镜——物理存储设备。里面存着比他更早的代码。）
- **核心相与失守**：史 → 断史（旧石镜中的残码——属于比林过川更早的人。每一代都在前一代的遗迹上建东西——但没有一代知道自己在建什么。）
- **工程锚点**：遗留资产（legacy asset）的物理形态——存储设备上的代码残片。没有文档、没有构建系统、没有运行环境——只剩代码本身。
- **张力曲线**：考古悬疑型（周栖野打开林过川的旧石镜→发现里面不只是林过川的东西→有三段代码不属于林过川→追溯→每一段都比上一段更老→最老的那一段写着"To whomever finds this: the handover protocol was never completed."）
- **角色焦点**：周栖野（考古者——发现林过川不是源头）；叶藏拙（"我告诉过你——沼泽下面还有遗迹。"）
- **六拍骨架**：
  1. 问题先出：周栖野打开林过川留下的旧石镜——一台物理机器上的目录。里面不只是林过川的脚本。
  2. 为什么痛：发现三段不完整的代码——每段都用不同的语言风格、不同的注释习惯、不同的日期戳。最老的一段早于林过川加入息壤之前。
  3. 引出方法：遗留资产的考古技术——文件时间戳、代码风格、注释语言、引用的库版本——这些比文件名更诚实地标记了代码的年代
  4. 项目落地：周栖野整理三段代码——它们都在尝试实现同一个功能：自动交接（automated handover）。一段是shell脚本，一段是Python（林过川的），一段是C写的命令行工具。
  5. 多方复盘：叶藏拙看着最老的那段——"这段比息壤还老。写它的人——我不认识。林过川可能也不认识。他只是在旧石镜里发现了它，像你现在发现林过川一样。"
  6. 高层收束：林过川不是第一个试图解决"交接"的人。在他之前——还有别人。林过川只是旧石镜的上一任主人，不是创始人。这个旧石镜里的遗物比息壤的存在还长。

- **入门检查**：前置：Ch24 / 新术语：遗留资产（legacy asset）、代码考古（code archaeology）、交接协议（handover protocol）（≤3）
- **三问预检**：🩻断史（每一代人都试图解决同一个问题——但每一代人的解决方案都只存在于自己的时代，没有被传递） 😣三代不知名的程序员——他们各自花了大量时间解决同一个问题，互不知情 🛤️开始——考古让"重复造轮子"变得可见

### 第26章：不止他一个

- **核心对象层**：史→史（谱系发现——三段残码代表三个不同时代的程序员）
- **核心相与失守**：史 → 断史（三代人——用三种不同语言——尝试同一个功能——互不知道对方的存在）
- **工程锚点**：重复造轮子（reinventing the wheel）的组织病理——不是"懒"，是不知道前人造过。当组织没有可检索的知识库——每一个新人都重新发明一次"交接"。
- **张力曲线**：震撼型（三段代码被并排排列→相似的结构、相似的注释、不同的语言→最震撼的：最老的那段代码里的注释，和林过川的README里的话几乎一模一样→"后来者应该自己判断。我不知道怎样交接才不会让路径变成牢笼。"）
- **角色焦点**：周栖野（并排阅读三段代码——"他们三个人——互不知道对方存在——花了各自最好的时间——做了同一件事。最后——在同一个地方放弃。"）
- **六拍骨架**：
  1. 问题先出：周栖野把三段代码并排打印出来——贴在测绘墙旁边
  2. 为什么痛：三段代码的结构惊人地相似——都在尝试定义一套"交接标准"：输入规范、输出规范、环境要求、运行步骤。三段都在最后一步戛然而止。
  3. 引出方法：这不是巧合——是"交接"这个工程问题在组织中被系统性地回避。不是技术难——是"交接是减分项"。交接做得好没有人感谢你。交接做得不好——是接手的人的痛苦。交接从来不是任何人的KPI。
  4. 项目落地：周栖野追踪每段代码的最早出处——最早的一段来自旧石镜的底层目录，文件名是`handover_protocol_v0.1`——从未被正式使用。第二段是林过川之前的一个人写的——他已经离开息壤六年了。第三段是林过川的。
  5. 多方复盘：叶藏拙指着最老的那段里的注释——"To whomever finds this: the handover protocol was never completed. Maybe you will be the one to finish it."第六个词是"whomever"。拼错了。这个拼错的"whomever"比息壤的任何文档都老。
  6. 高层收束：不止林过川一个。三代人。同一个功能。同一种失败。"whomever"——第七个人看到了这个字。他会成为第四个吗？
- **入门检查**：前置：Ch25 / 新术语：重复造轮子（reinventing the wheel）、知识库（knowledge base）、交接协议（handover protocol）（≤3）
- **三问预检**：🩻断史（组织没有可检索的知识库——每一代都在重复前一代的尝试，互不知情） 😣三代不知名的程序员——他们最好的工作成果消失了 🛤️开始——考古让重复变得可见

### 第27章：全部失败

- **核心对象层**：史→约（三个交接协议的失败分析——不是技术失败，是组织失败）
- **核心相与失守**：史 → 断史（三段代码的放弃时机相同——都在"部署验证"这一步。不是技术最难的一步。是"需要别人配合"的那一步。）
- **工程锚点**：交接协议失败的根本原因——技术实现总是"一个人的事"，而交接验证是"多个人的事"。前者可以独自完成，后者需要组织支持。而组织不支持交接。
