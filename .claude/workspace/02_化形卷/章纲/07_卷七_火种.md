# 卷七「火种」Ch 61-70：林过川遗迹的清理

## Section 总览

- **章段**：Ch 61-70
- **叙事主题**：林过川遗迹中的火种——能迁走的和只能留的。白又新登场——继承者不依赖任何原作者，独立走通。
- **核心冲突**：清理遗迹不只是删除——是判断哪些有长期价值、哪些只能归档。最困难的不是技术判断——是面对林过川的"空白不是偷懒"信仰。
- **工具链阶段**：pytest全面应用 / trio-anyio引入（异步生态分裂） / 三层文档体系萌芽
- **对象层**：史→骨（从"遗迹"到"可继承的火种"——林过川遗产的救赎）
- **主相→蚀**：史 → 断史（清理遗迹的每一步都是对断史的对抗——把不可传的知识变成可传的）
- **主角状态**：从删桥者到"火种守护者"。帮助白又新独立走通——但开始质疑：林过川为什么不整理？
- **张力引擎**：继承的悖论——继承者必须独立走通，但独立走通需要的"入口"正是前人不愿（或不能）提供的。
- **卷尾落点**：林过川的信仰被揭示——"整理太好，会让后来者不再自己理解。"这不是偷懒——是另一种守缺者信仰。但白又新的成功证明了这个信仰的盲区：不给入口不是恩赐——是试炼。继承者不需要试炼——需要地图。

### 第61章：火种与废土

- **核心对象层**：史（林过川遗迹的分类——能迁走的火种和只能留下的废土）
- **核心相与失守**：史 → 断史（遗迹里有火种——但要找到它们，需要穿越废土）
- **工程锚点**：遗留资产的三分法——(a) 火种：有长期价值的代码——可迁入固核层 (b) 废土：不可迁移的遗留物——只能归档 (c) 骨殖：曾经有功能但现在无法判断是否有价值的代码——需要考古判断
- **张力曲线**：考古行动型（周栖野和叶藏拙在林过川的遗迹中寻找火种→分类→每一个分类决定都在暴露：很多代码的价值无法判断——没有人知道它们解决的是什么问题→"我们不知道它有没有价值——因为它从来没有被解释过。"）
- **角色焦点**：周栖野（火种评估者——在废土中寻找火种）；叶藏拙（协助分类——"有些代码——林过川认为理所当然，但在我的账本里——它们在运行。十一个脚本依赖了这些没人解释的代码。"）
- **六拍骨架**：
  1. 问题先出：周栖野开始清理林过川遗迹——目标是找到还能用的火种，迁入固核层
  2. 为什么痛：三千多个文件——能明确判断有价值的不到10%。大部分是"不知道有没有价值"。它们可能在跑——但没有人知道它们在哪跑、谁在依赖它们。
  3. 引出方法：遗留资产分类——火种（可迁）、废土（归档）、骨殖（待判断）。每一类有不同的处理方法。火种需要补文档+测试+MRC。废土需要归档+标注+保留"为什么不能迁"。骨殖需要有考古者进行判断。
  4. 项目落地：周栖野分类了前三百个文件——找到了十二个火种。包括一套数据清洗流水线、一个API速率限制工具、一个日志解析器。这些代码质量很高——就是没有文档。"如果林过川多花一个时辰写文档——这些东西可以直接进固核。"
  5. 多方复盘：叶藏拙翻出林过川的一个工具——`auto_field_mapper`。这个函数在四个不同的脚本中被import——每个脚本都复制了一份（copy-paste）。没有人知道原始版本在哪里。"这就是火种的价值——如果不迁出它——它会继续被复制——每次复制离原版更远——每次复制都不能被更新。"
  6. 高层收束：火种存在于废土中。它们不是不存在——是"没有人能确认它们的存在"。清理遗迹的第一步——是找到火种。第二步——给火种写文档、测试、MRC。第三步——让后来者能独立使用它们——不需要林过川。
- **入门检查**：前置：Ch30, Ch40（林过川遗迹的伏笔）/ 新术语：遗留资产分类（legacy asset triage）、火种（viable artifact）、废土（wasteland artifact）（≤3）
- **三问预检**：🩻断史（林过川的火种被埋在废土中——因为没有任何文档指示它们的存在） 😣林过川的火种——被复制了四年，越来越乱，但还在跑 🛤️开始——火种分类让有价值的代码第一次被"看见"
- **包管理/类型/异步**：uv锁定/mypy/sync

> 📝 **路标章**：对应旧Ch11前半部分。保留林过川遗迹清理的核心场景。

### 第62章：白又新登场

### 第63章：从README开始

- **核心对象层**：文→文（白又新只有一份林过川的README——"对不起"。从这三个字出发——他必须独立走通林过川的火种。）

- **张力曲线**：悬疑型（白又新从"对不起"出发→阅读代码→推断设计意图→重现运行环境→每一个推断都可能对也可能错→对的部分——他在替林过川写缺失的文档。错的部分——他也在替林过川承受沉默的代价。）
- **角色焦点**：白又新（全章POV——极限继承的体验。从"对不起"到"我懂了"——但懂的代价是独自穿越林过川的思维废墟。）；周栖野（旁观——"他在做我应该在Ch10做的事——理解前人的沉默。"）
- **六拍骨架**：
  1. 问题先出：白又新选择了一份林过川的火种——`data_cleaner`。只有一个README——"对不起。"必须从代码本身重建所有知识。

  3. 引出方法：推断式考古——从代码中重建设计意图：(a) 函数签名→输入输出类型 (b) 硬编码的路径→预期的文件结构 (c) 异常处理→作者预期的不正常情况 (d) 注释→作者认为值得标注的信息

  5. 多方复盘：周栖野看白又新的MRC——"你用两天时间——填补了林过川沉默了三年的空白。""不是填补。是翻译。林过川在代码里说了所有东西——但他没有翻译成'后来者能读的语言'。我做了翻译——不是创造。"
  6. 高层收束：极限继承的价值——继承者不是被动的接收者，是主动的翻译者。林过川的沉默不是恶意——但翻译是必需的。不是所有继承者都有时间翻译——这就是为什么需要一个人先翻译好。那个人——曾经应该是林过川自己。

### 第65章：只能留的

- **核心对象层**：史→史（不能迁的火种——废土的处理。归档、标注、保留——作为考古证据。不是删除。）

- **工程锚点**：废土归档（wasteland archiving）——不是删除——是标注"这些代码在X时间被认为不再可用。原因：Y。保留至Z时间供考古参考。"
- **张力曲线**：情感复合型（处理废土——最难的不是删——是面对林过川的失败。有些代码写得很好——但依赖的系统已经不存在了。有些代码解决了真实问题——但后来有更好的解决方案。有些代码——永远无法判断价值——因为永远无法复现它运行的环境。）

  2. 为什么痛：有些代码的价值无法判断——不是代码不好——是它依赖的外部系统已经消失了。"林过川写了一个数据管道——连接到一个已经关闭的数据源。管道本身是完美的——但它接入的系统——三年前就关了。"
  3. 引出方法：废土归档标准——(a) 标注为什么不能迁 (b) 保留代码作为考古证据 (c) 如果判断可能错误——设定"重新评估日期"

  5. 多方复盘：叶藏拙在归档目录前说——"这不是失败。这是历史。历史本身是有价值的——即使历史中的东西不可用了。后来的考古者会感谢你保留了它们——而不是删了。"
  6. 高层收束：废土不是垃圾——是文明的沉积层。每一层都有它的故事——即使故事已经结束了。保存废土——是对后来的考古者的尊重。
- **入门检查**：前置：Ch64 / 新术语：废土归档（wasteland archiving）、沉积层（sedimentary layer）、重新评估日期（re-evaluation date）（≤3）
