### 第81章：最低限度的存在

- **核心对象层**：骨→约（宋既明的全量固核审查——每块固核都必须能独立复现。也是Ch35-36标准的再次应用。）
- **核心相与失守**：（建设章——复现性审查是固核的底线验证。如果一块固核不能独立复现——它不具备"存在"的资格。）
- **工程锚点**：复现性验证（reproducibility verification）——(a) 独立环境：在新机器上从零开始 (b) 只需MRC和代码 (c) 所有测试通过 (d) 所有依赖可被uv.lock精确还原
- **张力曲线**：审查型（宋既明逐块审查固核→通过的系统性地快乐→不通过的各有各的痛苦→"不是你的代码有bug——是你的存在声明有bug。"）
- **角色焦点**：宋既明（核心POV——全章展示审契者的工作。不是裁判——是验证者。他的存在让"存在"有了定义。）；被审查的模块作者（各自面对"你以为能跑但换了个环境就不能跑"的羞辱）
- **六拍骨架**：
  1. 问题先出：宋既明开始固核层的全量复现性审查——每一块模块必须在新环境中独立复现
  2. 为什么痛：在干净的机器上——依赖被精确锁定（uv.lock）——MRC被严格执行。21块固核模块——14块一次性通过。7块不通过。问题不是代码——是环境声明漏了前提：一个系统包、一个编译选项、一个CUDA版本。
  3. 引出方法：复现性审查暴露的本质问题——不是"模块不稳定"，是"模块的前提没有完全声明"。每个失败的模块都有一个"我以为所有人都有"的前提。
  4. 项目落地：宋既明审查了所有固核模块——通过的贴绿色标签"已成立"，不通过的贴黄色标签"待补充前提声明"。公共记录板上——固核层状态从"大多数稳定"变成"精确：14/21完全复现，7/21需补充声明。"
  5. 多方复盘：宋既明——"这不是批评。这是精确性。之前——我们说'大部分稳定'。现在——我们知道哪些稳定——精确到新机器上的每一步。后来者看到这张表——他们知道哪些模块可以无条件信任——哪些需要'跟你确认你的环境'。"
  6. 高层收束：复现性不是美德——是文明底线。后来者不应该需要猜"我应该信任哪个模块"——模块自己应该声明"我是完全可复现的"或"我的前提还没声明完"。
- **入门检查**：前置：Ch76 / 新术语：复现性验证（reproducibility verification）、清洁环境（clean room）、精确声明（exact declaration）（≤3）
- **三问预检**：🩻（建设章——复现性审查让"稳定"从模糊变成精确） 😣7个模块的作者——他们的前提声明不完整暴露了 🛤️是——精确声明让后来者知道哪些能信任

### 第82章：CI for Python

- **核心对象层**：阵→阵（CI/CD——tox/nox：多版本多平台的自动化验证。从"手动审查"到"机器守卫"。）
- **核心相与失守**：（建设章——CI让审查不是一次性的——是每次提交都自动执行的。审契者不再需要手动跑——机器替他跑。）
- **工程锚点**：tox/nox——Python的CI工具。(a) tox: 在多个Python版本中运行测试 (b) nox: 用Python编写的tox替代——更灵活的会话定义。CI的核心价值：不是"现在能跑"——是"每次改代码后都重新验证，确保没有回退"。
- **张力曲线**：建设型（周栖野设置tox.ini→配置Python 3.9/3.10/3.11/3.12四个环境→第一次全量tox run→发现两个模块在3.9上有warning→"之前我们不知道——因为我们没有在3.9上测过。现在机器会替我们测了。"）
- **角色焦点**：周栖野（设置CI——"让机器做审查者"。机器没有偏见、不会忘记、不需要休息。）；宋既明（"我之前的工作——手动跑MRC——机器现在替我做了。不是抢我的工作——是让我的工作从'检查'变成'看异常'。"）
- **六拍骨架**：
  1. 问题先出：固核层的模块需要在多版本Python上验证——宋既明不可能在每个新版本上手动跑MRC
  2. 为什么痛：手动审查的成本随模块数量线性增长——21个模块×4个Python版本=84次手动跑。这不只是慢——是不可能持续进行的。
  3. 引出方法：tox配置——`[tox] envlist = py39,py310,py311,py312`。`[testenv] deps = -r requirements-dev.txt; commands = pytest`。一次配置——以后每次改代码后自动在多版本上验证。
  4. 项目落地：`tox run`——四个环境并行跑。3.11和3.12全绿。3.10——一个模块在import时failed。3.9——两个模块的测试不通过。"这些问题在宋既明手动审查时不会发现——因为他用的是3.11。现在机器告诉我们了。"
  5. 多方复盘：周栖野修复了3.9和3.10的问题——tox再次全绿。"之前——3.9的用户可能不会报告问题——他们以为是自己不会用。其实——是模块真的在3.9上有bug。"
  6. 高层收束：CI不是让审查者失业——是让审查者从"验证器"升级为"异常分析师"。机器跑常规检查——人看在常规之外的东西。这是审契者的进化。
- **入门检查**：前置：Ch81 / 新术语：tox/nox、多版本测试（multi-version testing）、CI/CD（≤3）
- **三问预检**：🩻（建设章——CI让复现性验证自动化——不会因为审查者的疲劳而遗漏） 😣Python 3.9的用户——之前他们的问题被默默忍受 🛤️是——机器守卫让后来者不会掉进版本陷阱
- **包管理/类型/异步**：uv制度化/mypy制度化/anyio制度化

### 第83章：lint的凝视

- **核心对象层**：文→约（ruff/mypy的持续凝视——不是一次性修复，是每次提交的自动检查。）
- **核心相与失守**：（建设章——lint的自动化让"写得不好"在提交时就被挡下。不是事后修正——是事前预防。）
- **工程锚点**：ruff——用Rust写的Python linter——速度极快。整合了几乎所有Python linting规则（pyflakes, pycodestyle, isort, etc.）。mypy——类型检查。两者的组合让"代码质量"从人的判断变成机器的判断。
- **张力曲线**：制度型（周栖野配置pre-commit hooks——ruff+mypy在每次git commit时自动运行→第一次提交失败——"不是代码不通过——是pre-commit不通过。""不通过的理由在命令行里——机器告诉你哪里可以改进。不需要人告诉你。"）
- **角色焦点**：周栖野（配置lint+Hooks——"机器在教作者写好代码。不是从美学的角度——是从'后来者能不能读懂'的角度。"）；唐野渡（第一次被pre-commit拦住——"它说我的import顺序不对。顺序。""是的。import顺序——在你要import二十个东西的时候——是后来者的地图。无序的import——是无序的地图。"）
- **六拍骨架**：
  1. 问题先出：周栖野在固核层配置了pre-commit hooks——ruff check + mypy在每次提交时自动运行
  2. 为什么痛：第一次提交——被ruff拦住了。不是bug——是代码风格问题。"ruff说——这个变量定义了但未使用。这个import重复了。这个f-string可以简化。这些——都不影响功能——但它们让代码更难读。"
  3. 引出方法：lint的哲学——不是'漂亮'，是'可读'。可读的定义：后来者在凌晨三点——最快的理解代码意图的方式——不被不必要的噪音干扰。每一个ruff规则都是对这种噪音的一种消除。
  4. 项目落地：所有固核层模块都配置了pre-commit hooks。提交记录显示——最初几天被拦截的commit很多。一周后——几乎为零。不是审查更严了——是作者内化了规则。"机器在训练你们——不是惩罚。训练的是——后来者眼睛的舒适度。"
  5. 多方复盘：宋既明——"之前lint要手动跑——有人会忘记。现在机器不会忘记。机器不会累。机器不会说'这次算了——下次注意'。机器就是机器——它会一直说——直到你改。"
  6. 高层收束：lint不是审查——是文明的基础设施。就像道路上的护栏——不是限制——是保护。保护后来者不受不可读的代码的伤害。代码在提交之前——机器替后来者做第一轮判断。
- **入门检查**：前置：Ch82 / 新术语：ruff、pre-commit hooks、代码质量（code quality / linting）（≤3）
- **三问预检**：🩻（建设章——lint自动化让"可读"变成机器可验证的规则） 😣唐野渡——他的代码被机器拦住，但他学会了 🛤️是——机器替后来者做第一轮判断
- **包管理/类型/异步**：uv制度化/ruff+mypy制度化/anyio制度化

### 第84章：hypothesis

- **核心对象层**：约→约（property testing——不是"这个输入对不对"，是"在所有可能输入下，什么属性必须成立"）
- **核心相与失守**：（建设章——hypothesis补齐了传统单元测试的盲区：你只能测试你想到的输入。hypothesis生成你没想到的输入。）
- **工程锚点**：hypothesis——Python的属性测试（property-based testing）框架。不是"给定X→应该Y"，而是"对于所有满足条件的X→属性P应该成立"。框架自动生成边缘案例（edge cases）——包括你从来没想过的空列表、负数、Unicode、超长字符串。
- **张力曲线**：震撼型（周栖野第一次用hypothesis→写了一个简单属性→hypothesis跑了200个例子→第47个例子失败→"这个输入——我永远不会自己写进测试。空DataFrame with Unicode column names。我以为这种情况不存在。hypothesis说——它存在。"）
- **角色焦点**：周栖野（学习hypothesis——从"测试所有可能的输入"的恐惧到"机器替我找我不想想的输入"的安心）；宋既明（"hypothesis不是替代pytest——是补充。pytest验证你想到的。hypothesis验证你没想到的。"）
- **六拍骨架**：
  1. 问题先出：Ch48的测试盲区——field-mapper在"空文件"上炸了——因为没有人想到测试空文件
  2. 为什么痛：hypothesis自动发现——空DataFrame、全NaN列、Unicode列名、百万行数据、named index vs default index——在200个自动生成的例子中发现了3个失败
  3. 引出方法：属性测试的哲学——不是"这个输入对不对"——是"对所有可能的输入——什么属性应该始终成立？"如："parse_fields(df)返回的dict的keys应该等于df的columns。"hypothesis生成了1000个随机DataFrame——检查这个属性是否始终成立
  4. 项目落地：周栖野为field-mapper写了三个属性测试——hypothesis生成了3000个随机输入——发现了5个边缘情况。每一个都被修复并加到了pytest的固定用例中。"hypothesis找到了我永远不会想到的输入——因为它们荒谬。但线上——荒谬的输入每天都在发生。"
  5. 多方复盘：宋既明——"hypothesis是在替你执行'如果...'。你写：当输入是X时，属性P成立。hypothesis跑：当输入是X1, X2,  ..., XN时——P还成立吗？其中几个Xk你从来没有想过。这就是为什么hypothesis比手工测试更诚实。"
  6. 高层收束：属性测试不是替代传统测试——是补充。传统测试验证"已知的安全区"，属性测试探索"安全区的边界"。边界之外——就是线上事故。hypothesis让边界更快被发现。

- **入门检查**：前置：Ch48, Ch83 / 新术语：属性测试（property-based testing / hypothesis）、边缘案例（edge cases）、随机生成（random generation）（≤3）
- **三问预检**：🩻（建设章——hypothesis发现了人从未想过的边缘案例——补全了传统测试的盲区） 😣线上遇到荒谬输入的使用者——之前他们遇到的bug没人能提前发现 🛤️是——机器生成的边缘案例让后来者更安全
- **包管理/类型/异步**：uv制度化/mypy制度化/anyio制度化

### 第86章：未标注的负载

- **核心对象层**：流→流（性能瓶颈在跨域后暴露——同样的代码在驿河的场景下有不同的资源需求。）
- **核心相与失守**：式 → 失式（峰值负载未标注——在息壤的语境下不需要标——因为处理的是小批量短时任务。但这个假设在驿河不成立。）
- **工程锚点**：资源声明（resource declaration）的跨语境差异——在息壤（脚本驱动、短期运行）中不关键的限制——在驿河（服务驱动、长期运行）中变成致命的。默认512MB——在息壤处理几十条记录足够——在驿河全量加载11个集群数据时不够。
- **张力曲线**：揭示型（模块部署→正常运行→三个小时后→驿河的监控显示内存持续增长→逼近512MB→OOM（Out of Memory）→进程被kill→"在哪？""驿河。""数据集多大？""全量加载——11个集群的季度数据。比息壤的测试数据大两个数量级。"）
- **角色焦点**：周栖野（面对OOM——"我以为'默认'就够了。在息壤——真的够了。在驿河——不够。")
- **六拍骨架**：
  1. 问题先出：模块在驿河正常运行——三个小时后OOM killed
  2. 为什么痛：追查——林过川的代码（在`auto_field_mapper`基础上改写的）有一个全量加载逻辑——把11个集群的数据一次性加载到内存。在息壤（处理一个集群的小批量）中——这部分从200MB。在驿河（处理全部11个集群的全部数据）——内存使用量是2.3GB。默认512MB不够——远不够。
  3. 引出方法：资源声明是契约的一部分——不只是"这个代码需要内存"，而是"在什么场景下需要多少内存"。场景不同——需求不同。在息壤的典型场景中"不标注"看似合理——但在跨域交付中就是致命的前提遗漏。

### 第88章：认知冲击

### 第89章：语境声明
