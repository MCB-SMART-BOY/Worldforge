# 卷六「删桥」Ch 51-60：第一次填退场日期

## Section 总览

- **章段**：Ch 51-60
- **叙事主题**：第一次有人填退场日期——然后执行删桥。第一条桥的拆除比预想的难。第三条桥——收到来自驭器卷的runbook——炸了。
- **核心冲突**：删桥不是说删就删。每条桥上都有依赖者。有些依赖者自己不知道。而当来自另一个世界的runbook以"理所当然"的前提到达息壤——桥炸了，但炸的方式揭示了一个更深的问题。
- **工具链阶段**：mypy全量 / hypothesis引入 / deprecation制度化

- **主角状态**：从桥的管理者到真正的删桥者——第一次亲手拆除自己搭的桥。也在跨卷入侵中被迫面对：自己的"理所当然"——在另一个世界里是致命的缺口。

### 第51章：删桥

- **核心对象层**：门（第一条桥的正式拆除——xirang-old-api-shim）
- **核心相与失守**：（建设章——删桥是契约管理的终极测试。如果删桥成功——说明桥的治理体系是完整的。）
- **工程锚点**：桥的退场执行——(a) 弃用公告已发 (b) 迁移窗口已到 (c) 所有依赖者已确认迁移 (d) 执行删除→验证→记录。
- **张力曲线**：执行型（第一条桥的拆除→每一步都按计划→但每一步都比预想的更令人不安→因为"按计划"意味着"有人已经在依赖这座桥两年——现在他们必须搬家"）

- **六拍骨架**：
  1. 问题先出：三个月迁移窗口到期——xirang-old-api-shim的退场日
  2. 为什么痛：顾迁舟执行删除——七个依赖者全部确认迁移完成。但过程有三个"但是"——一个人迁移了一半才发现自己的脚本里有一个hidden import——另一个人迁移完后发现新API的性能比旧桥慢了一倍——第三个人是林过川时期的最后一个活跃用户——他的迁移意味着林过川在息壤的最后一行active代码消失了
  3. 引出方法：删桥的三个验证步骤——(a) 依赖者确认：所有已知使用者确认迁移完成 (b) 运行时验证：监控旧桥的最后24小时——确认没有意外的调用 (c) 代码删除：移除桥代码→移除import→移除requirements→记录在桥账上标注"已退场"
  4. 项目落地：顾迁舟执行删除——桥的代码被归档（archive）而非删除（delete）——"桥的代码应该保留——作为'我们曾经需要这座桥'的证据。以后的人考古时应该看到这段历史——不是'不知道为什么有这段代码'——而是'这是桥X——它活了两年——死于Ch51——死于旧API不再被需要'。"
  5. 多方复盘：第三条依赖者的迁移——他是林过川时期最后一个活跃用户。他的脚本里import过旧API——新API的接口完全不同。他重写了迁移——十五分钟。然后他说——"这是林过川的API——被用到了现在。它不再存在了。"
  6. 高层收束：第一条桥拆除成功。不是技术的成功——是治理的成功。桥有出生日期——桥有退场日期——桥的被依赖者提前知道了。这是息壤历史上的第一次。

### 第52章：弃用声明

- **核心对象层**：约→文（deprecation（弃用）的工程艺术——不是删，是先公告）
- **核心相与失守**：（建设章——弃用声明是契约管理的核心机制。提前告知使用者：你依赖的东西即将消失。）
- **工程锚点**：弃用策略（deprecation policy）——(a) 弃用声明（deprecation warning）：运行时警告——"xirang-old-api-shim is deprecated since v2.3, will be removed in v3.0." (b) 语义化版本（semver）：MAJOR版本变更表示不兼容 (c) 迁移指南：让使用者知道怎么迁
- **张力曲线**：方法论型（第二条桥的弃用声明→更大的使用者群→弃用声明发出后群聊反应→"你在给我的月度结算加deadline。"→"是的。因为你的月度结算依赖的桥——在腐烂。"）
- **角色焦点**：顾迁舟（制度化弃用流程——"弃用声明不是惩罚——是尊重。我在告诉你——你依赖的东西即将消失。你不是被偷袭的——你是被提前告知的。"）；季晚禾（代表大量使用者——"弃用声明让我可以做计划。没有弃用声明的bug修复——那才是偷袭。"）
- **六拍骨架**：
  1. 问题先出：第二条桥的弃用声明发出——xirang-excel-adapter，使用者更多（11个）。群聊反应激烈。
  2. 为什么痛：弃用声明被误解为"你们做得不好所以要被删"——有人辩护说"我的脚本全靠这个"。顾迁舟——"不是它不好——是它已经完成了使命。它是一座桥——桥的使命是让人通过。所有人都通过了——桥就成了障碍物。"
  3. 引出方法：deprecation的三个层级——(a) 代码级：`warnings.warn("deprecated", DeprecationWarning)`——运行时提醒 (b) 文档级：在CHANGELOG和README中标注 (c) 沟通级：给每个已知使用者发通知——"你依赖的东西即将变更"
  4. 项目落地：顾迁舟为第二条桥做了完整的弃用公告——版本号、退场日期、迁移路径、联系人。公告贴在公共记录板上。群聊反应从抗拒→接受。"弃用声明让我知道了'什么时候需要迁移'。之前——我最怕的是——某天早上打开脚本，发现它不跑了——没人提前告诉我。"
  5. 多方复盘：季晚禾——"弃用声明让'突然坏了'变成了'计划中的变更'。这两者之间的区别——就是后来者能不能安全地走在路上的区别。"
  6. 高层收束：弃用不是惩罚——是最基本的尊重。但尊重需要沟通。沟通需要制度。制度——需要有人承担"告诉别人坏消息"的角色。
- **入门检查**：前置：Ch51 / 新术语：弃用（deprecation）、弃用警告（DeprecationWarning）、语义化版本（semantic versioning / semver）（≤3）
- **三问预检**：🩻（建设章——弃用声明让桥的退场不再是偷袭） 😣桥上的依赖者——他们收到了一条"你依赖的东西即将消失"的消息——这是坏消息，但也是尊重 🛤️是——弃用声明让后来者能计划未来
- **包管理/类型/异步**：uv锁定/mypy制度化/sync

### 第53章：第一条桥的拆除

- **核心对象层**：门→史（第二条桥的实际拆除——比第一条更难。因为桥上的使用者更多——而且他们不是被动依赖——他们在桥上建了东西。）
- **核心相与失守**：契 → 背契（拆除过程暴露——桥上的使用者不仅import了桥，他们还依赖了桥的内部实现细节。他们的代码不是"通过桥"——是"住在桥上"。）
- **工程锚点**：桥的内部依赖——使用者的代码不仅调用了桥的公开接口，还依赖了桥的内部工具函数（utility functions）。当桥被拆——这些内部工具函数也消失了。
- **张力曲线**：爬升型（第二条桥的拆除→第一个使用者迁移顺利→第二个也顺利→第三个——他的代码依赖了桥的一个内部`_helper`函数——那个函数从未被文档化，从未被声明——但被他发现了，并且用了两年→"那是私有函数——你不应该依赖它。"→"它不是私有的——它没有下划线前缀。而且它解决了我的问题。"）
- **角色焦点**：顾迁舟（处理意外——桥的内部实现泄露）；周栖野（面对自己遗留的债——`_helper`是他三年前写的——"我以为没人会看见它。"）；第三个使用者（"它就在那里——我import了它——它跑了两年。现在你说它是'不该存在的'"）
- **六拍骨架**：
  1. 问题先出：第二条桥的拆除——前两个使用者迁移完成。第三个——卡住了。"我import了`xirang_excel_adapter._helper.auto_detect_encoding`。你的迁移指南里没有提到这个函数。"
  2. 为什么痛：`auto_detect_encoding`是一个内部工具函数——周栖野三年前写的。它没有一个下划线前缀（Python的"私有"约定），也没有文档。它只是"在那里"——被发现了。这个使用者依赖了它两年。
  3. 引出方法：内部API的可见性——Python的"没有绝对的私有"哲学：`_`前缀只是约定，不是强制。使用者可以import任何东西。这就意味着——所有没有被显式隐藏的函数——都是潜在的公开API。不管你意图如何。
  4. 项目落地：周栖野必须决定——是把`auto_detect_encoding`迁移到新API中，还是在弃用声明中加入它的替代方案。他选择了后者——"这个函数从来不是正式的——但它解决了一个真实的问题。问题还在——解法需要进入正式的接口。"
  5. 多方复盘：顾迁舟翻出旧代码——`auto_detect_encoding`的注释:"临时方案——等chardet更新后删除。"chardet更新了三次。这个函数还在。而且不是临时的了——有人在依赖它。"在三年前——它是临时的。两年后——它是另一个人的基础设施。你从来不知道——因为你从来没有告诉这个人'这是临时的'。"
  6. 高层收束：桥的拆除暴露了一个更深的真相——在息壤的历史上，有无数个临时的helper函数——它们从来没有被声明为"公共"或"私有"。它们只是在"那里"。被发现了——就成了基础设施。桥账需要记录的不仅是正式的桥——还有这些隐式的内部依赖。
- **入门检查**：前置：Ch52 / 新术语：公开API vs 内部API（public API vs internal API）、私有约定（`_` prefix convention）（≤2）
- **三问预检**：🩻背契（内置helper函数——从未被声明为公共接口，但被当作公共接口使用了两年） 😣第三个使用者——他依赖的东西即将消失，而他不知道这是临时的 🛤️开始——桥账需要扩展到内部依赖
- **包管理/类型/异步**：uv锁定/mypy制度化/sync

### 第55章：收到runbook

- **核心对象层**：约→门（**跨卷入侵事件**：纪承钧为息壤写的迁移runbook——17步。从驭器卷寄来。）
- **核心相与失守**：契 → 背契（来自另一个世界的"帮助"——带着那个世界所有默认的前提。当这些前提在息壤不成立时——runbook不是帮助——是炮弹。）
- **工程锚点**：跨域runbook的兼容性问题——一份在"玄枢"（C++世界）写成的迁移方法论，应用到"息壤"（Python世界）时，隐含的前提假设会断裂。世界术语不同，工程假设不同，默认工具链不同。
- **张力曲线**：悬疑型（收到来自驭器卷的包裹→纪承钧写的runbook→"为息壤桥退场准备的迁移流程——共17步，基于驭器卷渡桥司的桥治理标准。"→周栖野打开runbook→前两步——术语对不上→第三步——"确认所有下游依赖方已全部迁移"→这一行下面没有验证步骤→"他假设我们有依赖声明文件。")
- **角色焦点**：周栖野（接收方——"这是好意。"但同时意识到——"这份runbook的每一条指令都默认了玄枢的架构假设——我们不成立。"）；顾迁舟（谨慎——"很多前提不一样"）；季晚禾（尝试按runbook执行——"我到第三步就无法继续了。"）
- **六拍骨架**：
  1. 问题先出：顾迁舟收到来自驭器卷的包裹——纪承钧写的迁移runbook。"听闻息壤在整理桥账——附上驭器卷渡桥司的桥退场标准流程。共17步。供参考。"
  2. 为什么痛：周栖野打开runbook——前两步是术语翻译（"桥=adapter，退场=sunset"）。第三步——"确认所有下游依赖方已全部迁移。"这一行下面没有验证步骤。没有脚本。没有命令。没有工具。因为纪承钧默认——"依赖声明文件"是存在的前提。在玄枢——每座桥都有依赖声明文件。在息壤——没有。根本不存在。
  3. 引出方法：跨域知识的"默认前提"问题——每个世界的工程方法都建立在一套基础设施假设上。玄枢的假设：(a) 每个模块有依赖声明 (b) 构建系统能输出依赖图 (c) 桥的关系在注册表中。息壤的假设：(a) 大部分依赖靠import推断 (b) 没有统一的构建系统 (c) 桥的关系在人的脑子里。
  4. 项目落地：季晚禾尝试执行runbook——到第三步——"确认所有下游依赖方已全部迁移——如果无法确认，标记为'待确认'，继续下一步。"她标记了"待确认"。然后第四步也标记了"待确认"。第五步。第七步。第十五步——她标记了十一个"待确认"。整个runbook——在她的世界里——无法执行。
