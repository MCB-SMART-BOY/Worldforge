### 第71章：纸墙

- **核心对象层**：门
- **核心相与失守**：式 → 失式（wrapper的结构性脆弱）
- **工程锚点**：边界脆弱——wrapper/adapter的安全边界设计
- **张力曲线**：攀升型（Section开局——从观测结果逐步暴露边界的脆弱）
- **角色焦点**：纪承钧（看到观测结果后震惊——原来玄枢的边界都是纸做的）；沈照痕（'我告诉过你——先照后立。现在照出来了。'）
- **六拍骨架**：
  1. 问题先出：沈照痕的观测体系运行一个月的成果——一份玄枢边界脆弱性报告。报告标题：'纸墙'
  2. 为什么痛：17处wrapper——11处从未被审计过边界安全。外部调用方不知道自己在调用什么。维护者不知道改了什么会影响谁
  3. 引出方法：观测（tracing/metrics/logging）暴露了每一个边界的实际行为——和文档中声称的行为之间的差距
  4. 项目落地：沈照痕展示一份对比表——文档声称的边界 vs 观测到的实际行为。三分之二不一致
  5. 多方复盘：钟守玄看着报告——'这些wrapper——有一半是我搭的。我当时觉得够安全了。'
  6. 高层收束：纸墙不是没有墙——是墙在，但一推就倒。而推它的——可能是任何人在任何时间做的任何'对的事'
- **入门检查**：前置：观测三视图（Ch61-70）/ 新术语：wrapper审计（wrapper audit）、边界脆弱性（boundary vulnerability）（≤2）
- **三问预检**：🩻失式（边界结构脆弱） 😣外部依赖方（他们不知道自己在纸墙上） 🛤️开始——观测让纸墙可见

> 📝 **路标章**：对应旧Ch11。保留纸墙发现的核心场景。扩展：旧Ch11是纪承钧写诊断流程被陆踏痕指出'你假设我已经知道这些了'——新Ch71将纸墙的范围从诊断流程扩展到所有边界。

### 第72章：unsafe的地图

- **核心对象层**：门
- **核心相与失守**：式 → 失式（unsafe边界缺乏系统标注）
- **工程锚点**：unsafe审计——FFI边界、裸指针、手工内存管理
- **张力曲线**：倒钩型（发现未标注的unsafe→追溯历史→意识到系统性缺失→建立地图）
- **角色焦点**：纪承钧（绘制unsafe地图——发现有些从未被标注）；陆踏痕（协助——追溯每一个unsafe的历史）；沈照痕（提供观测数据）
- **六拍骨架**：
  1. 问题先出：纪承钧试图绘制玄枢的unsafe边界地图——发现很多边界从未被标注为unsafe。它们就是'普通代码'——只是恰好做了unsafe的事
  2. 为什么痛：一个FFI调用——跨了三个语言边界（C++ → C → Fortran → 硬件接口）。每一层都假设下一层是安全的。没有一层验证过
  3. 引出方法：unsafe不是禁区——是需要显式标注和审计的区域。Rust用`unsafe`关键字强制标注——C++没有这个机制，所有unsafe都是隐式的
  4. 项目落地：陆踏痕逐条追溯unsafe边界——发现最早的一条是十二年前的，为了调用一个已经停止维护的Fortran库
  5. 多方复盘：钟守玄：'那个Fortran库——在卫千枢来之前就有了。我问过——'为什么用Fortran？'——回答是'因为当时只有Fortran能算这个'。'
  6. 高层收束：unsafe的地图不是用来'消除unsafe'的——是用来让后来者知道：'这里需要额外的谨慎。这里——你越过了编译器能保护你的边界。'
- **入门检查**：前置：FFI概念（Ch73有铺垫）/ 新术语：unsafe、裸指针（raw pointer）、FFI（≤3）
- **三问预检**：🩻失式（unsafe边界未标注） 😣未来的维护者——他们不知道哪里是雷区 🛤️开始——地图是第一步

### 第73章：FFI的地狱

- **核心对象层**：门
- **核心相与失守**：式+契 → 失式+背契（FFI边界破坏了两侧的承诺）
- **工程锚点**：FFI深度——C ABI作为通用接口的代价和陷阱
- **张力曲线**：倒钩型（追溯一次FFI事故→发现跨语言边界的系统性脆弱→理解为什么FFI是'地狱'）
- **角色焦点**：纪承钧（追溯FFI调用链——发现跨了三个语言边界）；陆踏痕（协助追踪——发现C ABI的隐式假设）；沈照痕（观测FFI边界的运行时行为）
- **六拍骨架**：
  1. 问题先出：一次外部调用失败——追溯到一处FFI边界。数据在C++侧是正确的——经过C ABI后——在Fortran侧变成了乱码
  2. 为什么痛：FFI的每一层都在做隐式转换——C++的`std::string`→C的`char*`→Fortran的`CHARACTER`。每一步都有ABI假设——没有一步被验证过
  3. 引出方法：C ABI是'通用接口'——但'通用'意味着它不保证任何语言特定的行为。内存布局、字符串编码、错误处理——全部是隐式的
  4. 项目落地：陆踏痕画出这条FFI的完整调用链——跨了五个编译单元、三个语言、两个操作系统。任何一环的假设变了——整条链就断
  5. 多方复盘：钟守玄：'这就是为什么旧桥那么多。不是我们喜欢搭桥——是FFI地狱逼出来的。桥是地狱里的路。'
  6. 高层收束：FFI不是邪法——是'自负额外证明之责'。越过语言边界的人——必须自己证明安全。这个责任——以前被'刚好能跑'掩盖了
- **入门检查**：前置：ABI概念（Ch35）/ 新术语：C ABI、调用约定（calling convention）、字符串编码（string encoding）（≤3）
- **三问预检**：🩻背契（FFI边界破坏了两侧的承诺） 😣依赖FFI的外部调用方 🛤️开始——显式标注FFI边界

### 第74章：谁在墙外

- **核心对象层**：门→阵（从边界本身到边界上的使用者）
- **核心相与失守**：契 → 背契（使用方不知道自己在依赖什么——承诺是单向的）
- **工程锚点**：使用者盲区——依赖方不知道依赖了什么、依赖了什么版本
- **张力曲线**：悬疑型（逐一揭示玄枢的外部调用者→每个都不知道自己在调用什么→累积恐惧）
- **角色焦点**：纪承钧（调查外部调用方——发现盲区的规模）；外部调用方代表（'我们不知道——我们只是照着上次的做法做'）
- **六拍骨架**：
  1. 问题先出：纪承钧决定走访玄枢的外部调用方——第一个是北岭设备集群的运维负责人。'你们怎么调用玄枢？''不知道。我们这边——有人五年前搭了桥。他走了。桥还在。'
  2. 为什么痛：每个调用方都依赖玄枢——但没有一个人能说清依赖的是什么版本、什么接口、什么行为。他们依赖的——是'上次能跑'的玄枢
  3. 引出方法：依赖声明（dependency declaration）——不是技术工具，是制度。每个调用方必须显式声明：依赖哪个接口、什么版本、期望什么行为
  4. 项目落地：纪承钧制作了一张'玄枢外部依赖方地图'——37个调用方。12个能说清依赖。25个——'不清楚'。其中5个——已经因为旧接口被废弃而出过事故
  5. 多方复盘：沈照痕：'纸墙的另一面——是盲人。墙是纸的——推的人看不见——被推的人不知道被推了。直到塌了。'
  6. 高层收束：边界不是一个人的事——是两边的事。玄枢这边在画边界——但墙外的人根本不知道墙在哪
- **入门检查**：前置：依赖图（Ch13-20）/ 新术语：依赖声明（dependency declaration）（≤1）
- **三问预检**：🩻背契（依赖方不知道承诺的内容） 😣墙外的调用方——他们在纸墙上走 🛤️开始——画出了墙外的人

### 第75章：收到诊断报告

- **核心对象层**：门→契（一份来自青炉的诊断报告——对的事，在错的世界里）
- **核心相与失守**：契 → 背契（契约的善意vs语境的鸿沟）
- **工程锚点**：🔗 入侵事件——青炉诊断报告v0.3.1到达玄枢，标注'可安全废弃'的旧接口
- **张力曲线**：倒钩型（收到报告→评估→看似合理→部署→未知的后果在暗处等待）
- **角色焦点**：纪承钧（收到报告——评估——决定应用）；沈照痕（'标注很清楚。但——它的标注是基于青炉的语境。不是我们的。'）
- **六拍骨架**：
  1. 问题先出：玄枢收到一份来自青炉（明契之道）的诊断报告v0.3.1——作者：沈见微。报告用Rust的`cargo-audit`和静态分析生成，标注了玄枢对外暴露的旧接口中'可安全废弃'的部分
  2. 为什么痛：报告本身是正确的——基于青炉侧的依赖分析。但它假设的'安全'前提——在玄枢的世界里不一定成立
  3. 引出方法：诊断报告含免责声明：'未知依赖不在检查范围内'——这是沈见微写下的边界。但'已知依赖'的范围——在青炉和玄枢之间，差距巨大
  4. 项目落地：纪承钧评估报告——三分之二的建议是合理的。三分之一——涉及沈见微标记为'可安全废弃'的接口。其中一个：legacy-report-gateway
  5. 多方复盘：沈照痕仔细阅读报告：'这个人——他做了很认真的工作。但他不知道我们这边的事。不是他的错。是他的位置——看不见。'
  6. 高层收束：纪承钧决定应用报告中的大部分建议——包括删除legacy-report-gateway。他写了一条传讯给沈见微：'谢谢。你的报告很有用。'
- **入门检查**：前置：FFI/边界（Ch71-74）/ 新术语：cargo-audit、静态分析诊断（static analysis diagnostics）（≤2）
- **三问预检**：🩻背契（契约的善意越过了语境的鸿沟） 😣即将落在北岭设备集群 🛤️开始——但方向可能是错的
- 🔗 **跨卷入侵（被入侵）**：青炉诊断报告v0.3.1到达。全系列四条入侵链中的第四条——沈见微→纪承钧。

### 第76章：炸了

- **核心对象层**：阵（多个外部系统的连锁反应）
- **核心相与失守**：流+契 → 乱流+背契（运行时崩溃+契约被打破）
- **工程锚点**：🔗 入侵事故——legacy-report-gateway被删→北岭设备集群结算失败→玄枢断火
- **张力曲线**：崩塌型（删除→一切正常→丑时→爆炸→连锁降级→追查→噩梦成真）
- **角色焦点**：纪承钧（噩梦——他亲手删的接口炸了整个系统）；钟守玄（沉默——不是指责，是'我见过这个模式'）；沈照痕（追查——'不是你的错。是那个标注的前提在我们的世界里不成立。'）
- **六拍骨架**：
  1. 问题先出：legacy-report-gateway被删除——测试通过，部署到生产。一切正常——直到丑时
  2. 为什么痛：北岭设备集群的每日结算任务——凌晨丑时运行。它依赖legacy-report-gateway——这个依赖在任何文档里都没有。只在一条六年前的Makefile注释里
  3. 引出方法：纪承钧追查——发现legacy-report-gateway在青炉侧的调用统计是零（沈见微的标注是对的——在青炉侧）。但在玄枢侧——北岭的调用路径完全不同
  4. 项目落地：玄枢因为北岭调用失败而产生连锁反应——三个外部系统降级。和两年前的断火——一模一样的模式。但这一次——不是病发的。是被治病的药炸的
  5. 多方复盘：钟守玄没有指责——他的手放回旧机器上，用同样的私有命令托住玄枢。'这不是沈见微的错。也不是你的错。是——边界。你不知道那边有什么。他也不知道。'
  6. 高层收束：诊断报告做了所有对的事——标注、免责声明、静态分析。但它炸了。不是因为做错了——是因为'对的事'在一个你不知道的语境里，就是'不够的事'
- **入门检查**：前置：Ch75 / 新术语：无（事故章，以叙事为主）
- **三问预检**：🩻乱流+背契（运行时崩溃+对北岭的承诺被破坏） 😣北岭设备集群的操作者——凌晨两点被叫醒 🛤️否——但这一炸逼出了最重要的认知
- 🔗 **跨卷入侵事故**：全系列最重要的跨卷回声之一。沈见微在明契卷Ch77-78写的诊断报告，在驭器卷Ch75-76炸了玄枢。叙事时序：读者先看到'被炸'→到明契卷才看到'炸人'的源头。

### 第77章：追查三个时辰

- **核心对象层**：史（追溯事故的因果链）
- **核心相与失守**：史 → 断史（为什么北岭依赖legacy-report-gateway——这个信息从未被传递）
- **工程锚点**：🔗 跨卷追查——从断火追溯到青炉，从青炉追溯到'写清楚'的边界
- **张力曲线**：攀升型（从事故表面→逐层深入→发现根源→面对一个无法指责的人）
- **角色焦点**：纪承钧（三个时辰的追查——从愤怒到困惑到理解）；沈照痕（协助追查——'不是他错了。是我们从未告诉过他。'）
- **六拍骨架**：
  1. 问题先出：丑时。玄枢断火。纪承钧开始追查根因——三个时辰。从legacy-report-gateway的删除追溯到北岭的依赖，追溯到青炉的诊断报告
  2. 为什么痛：每一个环节都是'当时不知道'——不知道北岭依赖它，不知道青炉的静态分析会标注它，不知道删除它会触发连锁反应。信息在每个环节都是缺失的
  3. 引出方法：不是工具的问题——cargo-audit是正确的，观测是正确的，删除流程也是正确的。问题是——每个正确的前提都是不完整的
  4. 项目落地：纪承钧重建了事故的完整因果链——一条线从青炉的workspace开始，穿过cargo-audit，穿过诊断报告，穿过legacy-report-gateway，穿过北岭的六年前Makefile注释，最终落到玄枢的断火
  5. 多方复盘：沈照痕的总结：'沈见微做了所有对的事。他的标注、免责声明——都是对的。他唯一不知道的——是他不知道的那些事。而那些事——在我们这边。'
  6. 高层收束：追查三个时辰的结果——不是找到了'谁错了'。是找到了'为什么对的事也会错'。这比找到罪人更难——因为这意味着没有罪人。只有不够的信息
- **入门检查**：前置：Ch76 / 新术语：事故因果链（incident causality chain）（≤1）
- **三问预检**：🩻断史（北岭依赖未被传递） 😣纪承钧——他亲手删的 🛤️开始——理解到'对的事也会错'

### 第78章：传讯

- **核心对象层**：契→史（传讯——伤痕的公共化）
- **核心相与失守**：契 → 背契→契（从契约破裂到建立新的契约——伤痕作为公共记忆）
- **工程锚点**：🔗 传讯原文——'你做了所有对的事。然后我这边炸了。'
- **张力曲线**：情感崩塌型（从追查结束→坐下来写传讯→每一个字都很难→发出→沉默）
- **角色焦点**：纪承钧（全章核心——写传讯的过程本身就是认知转变）；钟守玄（看着纪承钧写——'你写的东西——和我不一样。你写了你的局限。'）
- **六拍骨架**：
  1. 问题先出：三个时辰后——事故恢复。纪承钧坐在玄枢的控制台前，打开传讯界面——收件人：沈见微（明契·青炉）
  2. 为什么痛：他要告诉一个人——'你做了所有对的事。然后我这边炸了。'这不是指责——这比指责更难写。因为对方没有做错任何事
  3. 引出方法：传讯的写作过程——纪承钧写了删，删了写。每一版都在'这不是你的错'和'但事情发生了'之间挣扎。最终他选择了最诚实的版本

  3. 引出方法：公共记录板——不是私人笔记，是公共的、永久保留的伤痕记录。任何人在任何时间都可以看到——'这里曾经炸过。为什么炸。谁修的。修完之后——留下了什么。'

  6. 高层收束：伤痕不是耻辱——是路标。'这里曾经有人摔过。你看——他的脚印还在。你不需要再摔一次。'
