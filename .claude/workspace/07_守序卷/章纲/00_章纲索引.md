## 卷级设定

- **语言**：Java（企业级生态——Spring/annotation/设计模式）
- **核心道**：守序之道——"秩序不是被设计的——是沉积的。每一行旧代码都是一次决策——只是决策的理由已经丢了。"
- **工程命题**：legacy system migration / institutional memory / organizational knowledge / COBOL interop
- **核心张力**："沉默的秩序比没有秩序更难改——因为它还活着——只是没人知道它为什么活着。"
- **四相主相**：史（历史的沉积）+ 契（被遗忘的约定）

## 卷一「旧序」Ch 1-10

| 章 | 标题 | 核心 |
|----|------|------|
| 1 | 旧序不眠 | 一个运行数十年的Java系统——凌晨——一个`@Scheduled`任务悄然改变行为——没有人改过代码——但依赖的库升级了版本 |
| 2 | 没人敢碰 | 系统有百个模块——最老的模块的作者已离职多年——"这段代码——三年前有人试图改——改完后全链路崩溃——回滚——再没人碰过" |
| 3 | 注解的沉默 | `@Transactional(readOnly = true)`——这一行注解——在某个方法上——"写了这个的人——已经不在——没有人知道为什么是readOnly" |
| 4 | Spring的魔法 | Spring容器启动——bean的依赖注入——AOP代理——"一切都在容器里自动发生——直到自动做错了" |
| 5 | 旧的为什么 | 每一个旧配置——追溯它的来源——"找到了二十三项配置——只有四项还能解释为什么" |
| 6-10 | 事故恢复——建立旧序审计——卷尾："沉默的秩序——需要被翻译成声明的秩序" |

## 卷二「注解之下」Ch 11-20

| 章 | 标题 | 核心 |
|----|------|------|
| 11 | 注解的魔法 | `@Transactional`/`@Autowired`/`@Component`——"注解让代码简洁——也让人不知道简洁的背后发生了什么" |
| 12 | 注解的沉默假设 | 一个`@Cacheable`注解——"缓存策略——在注解里——没有人读——直到缓存炸了——才发现策略过时了" |
| 13 | AOP的背面 | 面向切面编程——"代码在A方法里——但在A之前和之后——自动插入了B和C——没有人看到B和C" |
| 14 | 注解不是文档 | "注解是给机器读的——但后来者需要知道——机器读了之后做了什么" |
| 15 | 注解的考古 | 每一个`@Transactional`——追溯它的传播行为/隔离级别/超时——"这些参数——是谁设的——为什么" |
| 16-20 | 建立注解审计——卷尾："注解不是魔法——是用语法糖包裹的沉默承诺——承诺需要被声明" |
