# 简阵卷 · 第32章 · context 的旅程

傅远洲回看日志端点失明事故的调用链，发现跨服务追踪还没有建成。日志里能找到几段服务自己的记录，却很难确认它们是否属于同一个请求。更基础的断点是：有些服务调用下游时没有传递 `context.Context`。

Go 的 context 不只用于传参数。它可以把取消信号和截止时间沿着调用链交下去，也可以在进程内承载请求范围的值。上游取消请求时，下游应停止不再需要的工作；到达截止时间后，调用方不应继续等待。但 context 本身不会自动生成完整的追踪瀑布图，跨进程传递请求标识还需要明确的传递方式。

没有 context 的那些调用，仍像向虚空发出请求：上游已经取消，下游却不知道，继续运行并浪费资源。没有共同的请求标识，几段结构化日志也无法可靠地拼在一起。秦望秋的面板能看到部分服务各自的事件，却还不能还原一个请求的完整路径。

“context 不只是传参数——也是把请求的边界交给下游。你说明谁在等这个结果、最多等多久；下游才知道什么时候该停。”傅远洲说，“至于观测怎么把这些记录连成一条线，还要继续建设。”

傅远洲先给 `data-aggregator` 到四个下游的调用补上 context 传播。每个 HTTP 调用都带着截止时间；下游在执行中检查取消信号，不再让已经失效的请求继续占用资源。他们还通过请求头传递同一个 `request_id`，让这几处结构化日志能够按请求检索。

这个标识还不是 OpenTelemetry 的 trace ID，面板也没有 span 瀑布图；它只让散落的记录开始有机会被放在一起。秦望秋把这条调用链记为后续追踪建设的候选路径。下一步，她要把一个真实请求沿着这条路径完整追出来。
