## 技术准确性与因果边界

### Rust、安全与所有权

多份章纲把 Rust 写成编译器会“让你犯不了”资源错误、所有权能替代组织责任归属、Send/Sync 能阻止 goroutine 泄漏或证明并发代码安全。这些句子适合作为人物早期信念或修辞，不应当作事实叙述。Safe Rust 的确保证不发生数据竞争；但逻辑竞态、死锁、错误结果仍可能发生，`unsafe`/FFI 若不 sound 还可能让安全代码触发未定义行为。`unsafe` 也不会关闭借用检查器；它只是允许少数额外操作，并把相应安全义务交给程序员。官方说明见 [Rustonomicon: Data Races and Race Conditions](https://doc.rust-lang.org/nomicon/races.html)、[Rust Book: Unsafe Rust](https://doc.rust-lang.org/book/ch20-01-unsafe-rust.html) 与 [Rust Reference: Undefined Behavior](https://doc.rust-lang.org/reference/behavior-considered-undefined.html)。

具体需收敛之处：`01_卷一_凡火.md` 第10章称 Rust 是“写清楚就是一切”的化身；`02_卷二_立约.md` 第17章把 C++ 里的借用错误写成会“随机 crash”；`03_卷三_成形.md` 第24章称 Option/Result 让编译器“不让你忘”，但 `.unwrap()`、显式丢弃结果等写法正说明编译通过不等于已恰当处理；`07_卷七_守界.md` 第61、63、66章把 Rust 保证扩展到了“没有数据竞争”“goroutine 不泄漏”与跨 FFI 的整体链路。应写清保障边界，并让角色用具体代码/输入/后果证明，而不是把编译器拟作全知审判者。

卷七第63—66章的并发事故尤其需要修因果：第63章说旧桥在并发环境下改全局临时状态；第66章把 C 库升级后多线程作为原安全论证失效的原因；第61章又把“不正确读取对象”归结为内存安全。Rust 安全代码不应直接出现由普通共享读写导致的数据竞争；剧情需说明是旧 C 库、`unsafe` 封装不 sound、外部共享状态或业务级竞态中的哪一种。升级版本也不会自动证明“线程安全→不安全”，必须点出 API 契约、回调生命周期、共享全局状态或调用顺序具体变化。

### Cargo、workspace、发布

`05_卷五_立制.md` 第45—46章把 workspace 描述成各 crate “同一个 V1.0”，并说依赖者不会因 core 变化被迫升级；这是把共享构建/锁文件与包版本、发布/依赖规则混为一谈。Cargo 官方定义是 workspace members 共享根目录 `Cargo.lock` 与输出目录；它不保证各包使用同一 package version，也不自动保证公共 API 稳定（见 [The Cargo Book: Workspaces](https://doc.rust-lang.org/cargo/reference/workspaces.html)）。应改成 workspace 统一管理多 package 的构建和解析，再分别说明版本、path dependency 和发布策略。

`02_卷二_立约.md` 第19章及多个材料把 Cargo.toml 中“改了就要改版本、写 changelog、通知所有依赖者”说成普遍规则；应限定为影响公开行为、包发布内容或兼容承诺的变更，不能把每个 manifest 元数据修改都设为版本升级。`04_卷四_筑基.md` 的“公开 API 生命周期永久（或到 MAJOR）”也过于绝对，可改为“会提高兼容责任，具体按版本政策与 API 稳定承诺”。

### 容断卷索引

`05_容断卷/章纲/00_章纲索引.md` 第1章将外部 API 异常格式直接推成七层服务崩溃并反复重启，第2章说 5 秒内重启 3 次后 supervisor 放弃。后一个阈值只有在采用相应策略配置时才成立；OTP supervisor 的 restart intensity 超限后会终止子进程并终止自身，再由上层 supervisor 按树结构决定下一步，并非系统“放弃”。见 [Erlang/OTP Supervisor Behaviour](https://www.erlang.org/doc/system/sup_princ.html)。第1章应明确：异常输入经哪一层未经校验，为什么触发进程崩溃而非具名错误，重启为何不能清除毒化输入，以及哪些独立服务受同一共享依赖影响。

“let it crash”也不应等于错误都视为诊断报告、或一遇错误就重启；只有进程失败边界与监督策略恰当时，重启才是容断设计的一环。卷六混沌工程的“在生产注入故障”应补上稳定态假设、授权、爆炸半径、止损/终止条件，避免把生产故障注入写成普遍默认。

## 剧情、人物动机与同源风险

### 灰印与修补者谱系：从匿名注释推演出确定血缘

卷一第05章先说旧注释“没有署名、没有日期”，旋即断言“这九个字是梁故川留下的”；卷四第35章再出现被删除的上下文，卷四第39章让韩砺年叙述梁故川经历；卷七第68章又提出“第一位修补者可能写过，也可能是其学生的学生梁故川”；卷十第95—98章却安排出现完整笔记并确定梁故川动机。它可以是悬疑线，但应把每一阶段的**证据**与**人物推测**分开，否则从匿名文本直接得到作者身份和心理动机是跳步（证据：`01_卷一_凡火.md` 第05章；`04_卷四_筑基.md` 第35—39章；`07_卷七_守界.md` 第68章；`10_卷十_问鼎.md` 第95—98章）。

跨卷“残码—灰印—桥账—远古告警”目前多处被写成同一个四卷史约线索网，但材料没有建立同一作者、同一年代或同一事件的证据。尤其容断索引 Ch95 直接叫“与旧屋告警同源”，守序索引则明确说“信号关系待核实”。建议把“同源”写成角色假说/读者回声，直到找到独立交叉证据前，不要让提纲把它定成正典因果。

### 诊断报告“炸了玄枢”：免责声明与工具输出相互打架

明契卷 Ch77 说工具仅检查直接依赖，并明确把间接、动态、环境依赖列为范围外；但跨卷事件又说工具因“没有活跃依赖”而输出“可安全废弃”，继而用户删除模块，三服务崩溃。若工具能知道“无活跃依赖”，结论为什么仍忽略其显式未覆盖的隐式依赖？若不能知道，谁/哪一步把有限检查升格成权威判决？需要给出真实输出字段、措辞、调用者理解、删除审批路径和无回滚原因，否则事故是作者强行让免责声明失效以完成主题，而非从工具设计自然发生（证据：`08_卷八_出山.md` 第77—78章；`11_卷十一_道争.md` 第105—108章；`00_章纲索引.md` §六）。

更可信的因果可以是：工具只给出“扫描范围内未发现依赖”，而玄枢把它映射成高置信度“可安全废弃”；责任既落在输出语义设计，也落在审批/组织流程，并让纪承钧指出哪些隐式依赖证据未被纳入。这样沈见微承担工具作者责任，纪承钧也不是单纯“没看免责声明”的失误承担者。

### 人物动机与文学表达

明契卷的主要人物位置清晰，但章纲/样场常由所有人连续说出完整的主题判断：苏野平代表快、闻衡代表审契、贺时进代表窗口、程知序代表用户、韩砺年代表历史、季循代表后来者。`11_整卷重写策略_去云化与提质.md` 已准确识别“一个很清醒的作者借不同嘴说同一种判断”、世界有制度无生活、技术停留在解释等问题；这个诊断应作为本次重写验收项，而不是再新增更多口号章纲。

具体建议：苏野平要有真正救人的快路胜局及其具体利息；贺时进的绩效判断应有真实期限/预算/受影响的人，不要只作反派催促；程知序要有自身工作目标与连续选择，不只负责证明文档不足；季循的继承成长应从可观察的误判和修正发生，不要只以“第一接火者/后来者”命名；沈见微由“写清楚一切”到“写前提”的转变，应通过一次信任受损和修复，而不只是思想升级独白。以上属于改稿方向，不应倒写为正文已完成的事实。
