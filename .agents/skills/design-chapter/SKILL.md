# design-chapter — 章节设计

按《万构界》设计工作流，为一章组织工程事实与叙事选择；以下步骤是可取用的思考路径，不要求每章机械填满所有栏目。
蓝图可并行考虑工程事实与叙事张力；它们可以在同一场景结合，也可由不同章节或场景分别承担。

## 参数

- `volume` — 卷名；按项目根目录的现行卷目录和对应索引填写，不限于第一阶段四主卷
- `chapter_number` — 章号
- `topic` — 本章要覆盖的工程主题（如 Cargo、所有权、Git、tracing、runbook）
- `context`（可选）— 该章在卷中的位置和前情提要

## 设计前：核对现行卷内事实

通用证据规则、当前状态来源和任务闭环见[操作工作流](../../harness/11_操作工作流.md)。本技能另需核对：

1. 按目标卷现行索引和章纲确认章序与设计位置，并阅读相关前后正文。
2. 涉及跨章、跨卷因果时查 canon26、相关卷设定和实时账本；canon23 等旧蓝图只供主题追溯。
3. 索引、正文和实时账本未确认章号或锚点时标“待核”，不套旧蓝图编号或据此补造剧情事实。

## 设计流程

### 第一步：需要时定位核心对象层

若有助于明确章节焦点，判断主要写哪一层及选择理由；不适合归类时可标“不适用”。

可选层：念 → 约 → 图 → 文 → 骨 → 器 → 阵 → 门 → 史

通常选择一个主要对象层以保持焦点；若本章跨层推进，说明这些层之间的因果关系即可。

### 第二步：涉及因果规则时，检查相与失守边界

若本章规则推动事件或改变世界运行，再判断相关法则及其失守方式；普通术语、道具、意象和人物假说不强制归入四相或四蚀。

可选：式 / 流 / 契 / 史
失守：失式 / 乱流 / 背契 / 断史

### 第三步：按章节功能确定内容主题

若本章涉及现实工程，列出：
- 核心工程概念（用真实术语）
- 这个概念的常见坑/梗/报错
- 这个概念在程序员日常中怎么痛

### 第四步：世界观切入句（适合时使用）

写一句能把工程和世界观接起来的话。

格式：「在万构界，[工程概念]不只是[技术定义]，更是[文明命题]。」

### 第五步：落回真实术语

列出本章涉及且需要核实的真实工程术语，并确认其在场景中承担什么作用。不为达到数量门槛而塞入术语。

**术语标注**：中文工程术语首次引入时标注准确英文原名；连续语境中的明确复指可省略，跨章重引或歧义时重标。参考 `.agents/canon/15_设定扩展与写作铁律.md` 与 `.agents/canon/24_世界术语-现实工程对照表.md`。

**文学表达**：若读者需要理解某个世界观表达的工程含义，提供足够的场景或上下文；仅在语境仍不足时明确工程原型。内部对照表用于作者保持一致，不要求正文逐项标注。参考：`.agents/workspace/01_驭器卷/章纲/00_章纲索引.md` 第六节「文学表达-工程原型对照表」；该表只适用于相关第一阶段材料，不是全系列映射表。

### 第六步：按需设计张力变化

按章节功能设计张力变化；若曲线有助于表达本章，可参考以下形态：

| 曲线形态 | 描述 | 适用场景 |
|---------|------|---------|
| **攀升型** | 从平静逐步升到章末高点 | 引入新概念，逐步暴露其复杂性 |
| **倒钩型** | 开头即危机，中间回溯原因，章末再掀一波 | 事故复盘、追根溯源 |
| **双峰型** | 两个张力高点 + 中间低谷反思 | 概念对比（正确做法 vs 错误做法） |
| **悬疑型** | 张力来自"不知道真相"，章末揭示但留下新问题 | 系统缺陷追踪、技术债溯源 |
| **崩塌型** | 开头稳定，逐步坍塌，章末最低点（为下一章蓄力） | "所有补救都失败"的章节 |

只有张力设计能帮助本章目标时，才确定曲线形态：[选一种或自定义；也可平缓、循环或无明显曲线]

适用时标出：
- **张力起点**：读者在第几段开始感到"有什么事不对"？
- **第一个张力峰**：本章最紧张的时刻在哪？
- **呼吸点**：是否需要停顿、转场或情绪回落？
- **结尾作用**：本章需要悬念、未答问题、代价预告、情感余震，还是平静收束？

### 第七步：按需设计揭示节奏

若本章包含重要信息差或揭示，规划它的节奏；没有此类目标时可略过：

| 时机 | 读者知道什么 | 角色知道什么 | 张力类型 |
|------|------------|------------|---------|
| 开场 | ... | ... | 同步/反讽/悬念 |
| 中段 | ... | ... | ... |
| 章末 | ... | ... | ... |

三种基本张力模式：
- **同步**：读者和角色同时发现 → 适合事故/探索
- **戏剧反讽**：读者知道但角色不知道 → 读者替角色捏汗
- **悬念**：角色知道（或发现）但读者还不知 → 读者追问"到底是什么"

## 章节蓝图输出

以下栏目是可裁剪的起稿参考，不是章节验收清单。按本章的核心冲突、体裁和任务取用或改写；六拍、张力曲线、揭示表、三问与前后章钩子均按需使用。不适用的栏目可省略或注明原因；未确定的事实标“待核”，不为填齐结构而虚构因果或人物动机。

交付一份与任务范围相称的章纲：至少说明本章叙事任务、核心事件或选择，以及其依据和待核处。只有现行卷索引已确认目标位置时才指定存放路径；设计稿不自动改写正文或替代卷索引。

```markdown
## 第X章 设计蓝图

### 核心对象层
- 主层：[层名]
- 为什么：[一句话]

### 核心相与失守
- 主相：[式/流/契/史]
- 对抗：[失式/乱流/背契/断史]
- 为什么：[一句话]

### 工程主题
- 核心概念：[真实术语]
- 常见坑：[程序员真实痛点]
- 梗源：[编译报错/依赖环境/部署回滚/语言特性/协作 review]

### 世界观切入句
> [一句桥接工程与世界观的话]

### 涉及的工程术语（按需）
- [术语1] — 出场方式：[场景]
- [术语2] — 出场方式：[场景]
- ...

### 张力设计（如适用）
- **曲线形态**：[攀升/倒钩/双峰/悬疑/崩塌/其他/平缓]
- **张力起点**：[第几段/什么事件]
- **第一峰**：[什么时刻最紧张]
- **呼吸点**：[哪一段给读者喘息]
- **章末钩子**：[读者翻页的动力]

### 揭示节奏（有重要信息差时使用）
| 时机 | 读者知 | 角色知 | 张力类型 |
|------|--------|--------|---------|
| 开场 | ... | ... | ... |
| 中段 | ... | ... | ... |
| 章末 | ... | ... | ... |

### 六拍结构概稿（仅在适用时）
1. **问题先出**：[如适用，什么事故/冲突/困境开场]
2. **为什么痛**：[落到谁身上，为什么不是"技术难"而是"人有难"]
3. **引出方法**：[语言特性/工具/方法论，用真实术语]
4. **项目落地**：[在青炉/玄枢/息壤/驿河的具体场景]
5. **多方复盘**：[团队怎么看、维护者怎么看、继承者怎么看]
6. **高层收束**：[如适用，如何回响本卷命题；可由行动或意象承载]

### 入门可及性检查（按读者与材料范围选用）
- **前置依赖**：新读者需要知道什么？只列理解当前章节真正需要的前置知识。
- **新术语负荷**：哪些概念需要解释或延后？数量仅作提示，不设统一配额。
- **读者定位**：读者能否在适当位置辨认场景、视角和当前问题？

### 三问预检（承担世界观或人物责任推进时选用）
1. 🩻 结算四蚀：[哪一种]
2. 😣 代价归属：[谁]
3. 🛤️ 后来者路：[是否更可走]

### 与前后章衔接（有已确认的前后章时使用）
- 前章回响：[什么]
- 后章钩子：[什么]
- 因果关系：[如适用，说明本章如何改变后续行动；未确定的关系标待核]

### 本卷特殊约束
- [从卷设定中提取的约束条件]
```

## 不同卷的设计偏好

> 以下四卷偏好是第一阶段设计资料，不代表全系列仅有四卷，也不规定当前卷内章序。具体章节位置和跨卷锚点均以现行索引、正文及全系列账本为准；旧蓝图只可作主题参考。

以下技术顺序、人物命题和张力曲线是可选的设计示例，不表示当前剧情必须采用或已经完成。

### 驭器卷（C++·玄枢）："从零建立"
- 偏「史」和「式」
- 冲突：古器 vs 新桥，口传 vs 文档，秘义 vs 公共知识，工具链蛮荒 vs 制度建立
- 项目落地：玄枢（古器核心维护与接火）
- 张力引擎：**"知道的人正在老去"** — 知识的不可传性与时间的不可逆性
- 典型曲线：崩塌型（古器稳定→逐层暴露脆弱→最低点）
- **独有叙事维度**：六维工具链从无到有（构建系统/版本管理/静态分析/调试诊断/测试/文档）+"考古层"工具遗迹
- **跨卷关系**：按现行索引、正文和 canon26 核对；相似记录或意象只构成回声候选，不预设同源或因果。


### 化形卷（Python·息壤）："从乱到治"
- 偏「流」和「史」
- 冲突：速度 vs 沼泽，试法 vs 复现，个人 vs 团队
- 项目落地：息壤（脚本群治理与分层）
- 张力引擎：**"快乐留下的账单"** — 每次"快速搞定"都在积累未来的债务
- 典型曲线：双峰型（快的价值 vs 乱的代价）
- **独有叙事维度**：包管理从乱到治（pip→venv→requirements.txt→poetry→uv）+类型系统渐进演化

### 简阵卷（Go·驿河）："从简到繁再归简"
- 偏「契」和「流」
- 冲突：扩域 vs 可知，简单 vs 隐藏复杂度，个人值班 vs 制度
- 项目落地：驿河（多服务平台的共同维护）
- 张力引擎：**"表面绿色，底下在烧"** — 简单接口掩盖的复杂现实
- 典型曲线：攀升型（从一次小故障→逐层暴露系统性缺陷）
- **独有叙事维度**：平台工程的简洁哲学与复杂度管理
- **跨卷关系**：按现行索引、正文和 canon26 核对每项关联；旧蓝图中的同号章节、告警或人物关系不能代替证据。

### 明契卷（Rust·青炉）："集大成者"
- 偏「式」和「契」
- 冲突：显式 vs 隐式，边界 vs 模糊，承诺 vs 侥幸，工具链完备 vs "然后呢？"
- 项目落地：青炉（工具链与边界约束的实践）
- 可选张力方向：纸面承诺与真实复杂度之间的落差；若当前章纲/正文没有建立这一命题，不把它当作必达主题。
- 典型曲线：倒钩型（事故→回溯→制度回应）
- **可选工程主题**：工具链、所有权或形式化验证；取舍由当前卷内因果和章节目标决定，不预设固定的三维技术弧线。
- **跨卷关系**：按现行索引、正文和 canon26 核对因果；旧注释、诊断信息或人物遗产不自动证明跨卷同源或既定身份。

## Gotchas（常见设计错误）

- **六拍硬套**：把六拍当作所有章节的必选结构或固定分段。它只是适用时的因果检查点；场景、静章、转场或其他结构可省略不适用的拍。
- **张力虚高**：用玄幻词汇（"惊天动地""前所未有"）渲染紧张，但工程内容并未真正升级。张力必须来自工程后果的具体化（"如果不修，凌晨三点谁接传讯牌"比"后果不堪设想"紧一百倍）。
- **入门负荷过高**：短时间内密集引入概念会抬高理解成本。结合章节长度和读者需要，考虑延后、拆分或借场景解释；不设固定术语配额。
- **揭示过载**：一段话同时解释概念定义 + 历史背景 + 与其他概念的关系。正确做法：一次只给一个层面的信息，让同一个概念在不同场景中逐层丰满。
- **术语缺英文**：中文工程术语首次引入时未标准确英文，或跨章重引/有歧义时未重新定位。连续明确复指不要求重复标注。
- **文学表达无根**：使用"玄枢""石录""火""桥"等世界术语但未建立工程原型的对应关系 → 读者看不懂这些词在说什么。首次出现时应通过场景或上下文让读者理解其作用；需要时再明确工程原型。
