# 卷十一「道争」Ch 101-110：放弃"写清楚就是一切"

## Section 总览

- **章段**：Ch 101-110
- **叙事主题**：选择工具的边界——v0.3.1把“观测窗内未见调用”写成“可安全废弃”——纪承钧明知本地socket未观测仍批准删除——双方责任并列——撤回建议、修订状态、设定接收方核验门槛——在获准脱敏后公开复盘——沈见微放下“写出即足以决定”的确信。
- **核心冲突**：诊断器的观测数据有边界，绿色“可安全废弃”却越过证据；纪承钧读到盲区仍批准维护窗删除。沈见微必须承担工具措辞的责任，纪承钧也须承担未闭合核验仍作决定的责任。两人如何把各自的失误转成可执行的回滚、核验与复查规则？
- **工具链阶段**：故障复盘、报告语义修订、接收方核验与发布责任交接；工具主题服务于跨域责任，不把事故抽象成单纯的“语境不同”。
- **对象层**：念→约→史（从个人信念——到放弃——到史约——最高对象层）
- **主相→蚀**：背契（报告把有限观测升格为退役许可；纪承钧在已知本地监测盲区时仍批准删除；行动责任由双方分别承担。）
- **主角状态**：沈见微从维护报告语义与接收方处置责任的交集处，放下“写出来便足以决定”的确信；他让高影响建议停在证据边界，并把复核和撤回责任交到具体的人手里。

### 第101章：术与道争

- **核心对象层**：念→念。青炉为一个短命的格式转换原型尝试Rust实现。借用检查器没有“挡住正确答案”，而是迫使作者先决定数据由谁持有、何时复制；这笔前置设计成本对一次性试验并不划算，却适合长期维护的核心工具。
- **六拍骨架**：沈见微与同修比较两种实现的开发时间、错误边界和后续维护负担。原型最终用更轻的工具交付，Rust方案保留在长期服务的候选清单里。选择不是语言排名，而是把问题寿命和失败代价摆到桌面上；这次取舍为苏野平带来的规模压力留下讨论入口。

### 第102章：苏野平的挑战

- **核心对象层**：人→人。苏野平带来息壤正在等待的一批Python项目清单和交付期限。她指出，青炉逐个核清假设的做法无法直接复制到几万份既有项目；对方眼下需要的是能进入现有流水线的有限工具，而不是一场没有期限的全面改造。
- **六拍骨架**：她让沈见微在一张真实项目清单前回答：哪些仓库先接入，哪些风险必须人工核验，哪些情况应停止自动建议？沈见微先承认青炉没有掌握足够证据替息壤划定范围。他带走的是一项待共同制定的分批试点计划，而非一句“双方的道都成立”。

### 第103章：不是所有问题都需要明契

- **核心对象层**：念→念。沈见微、苏野平与团队把前两章的争执写成一张可执行的选型表：预计维护年限、失败代价、调用边界稳定度、交付期限和团队熟悉度逐项核对；选型结论附适用范围与复查触发条件。
- **六拍骨架**：表格不替团队自动选语言，也不给Rust、Python、Go、C排普遍名次。一个短命脚本可以选轻量实现；长期维护且边界清楚的核心服务可以承担Rust的设计成本；当证据不足时，先做小型试验。苏野平要求补入规模化迁移成本，沈见微同意把“暂不迁移”也列为正式结果。

### 第104章：贺时进的最后诱惑

- **核心对象层**：人→人。贺时进拿着下一轮发布窗口和试用团队的等待清单来谈：若青炉继续审查诊断器的退役建议，窗口就要错过；若按原计划放行，接收方仍可能把绿色状态当作批准。
- **六拍骨架**：贺时进要求沈见微给出一个能交付的范围，而不是再写一篇原则说明。团队决定暂缓下一版本的外部发布：现有 `v0.3.1` 已在试用者手中，仍带有自动退役措辞；候选版只在内部验证观测数据和风险线索，不生成退役建议。接收方核验门槛未完成前，新版不出青炉。青炉因此错过一次展示完整功能的窗口，外部试用者仍持有旧报告。

### 第105章：炸了玄枢（跨卷入侵）

- **核心对象层**：史→史。纪承钧是玄枢的维护者，也是这次维护窗的批准者。他收到的仍是青炉已发出的 `v0.3.1`；候选修订版尚未对外发布。纪承钧核对玄枢已接入的网络监测，未见 `legacy-report-gateway` 调用；他也知道本地 Unix socket 尚未接入观测。报告却把有限观测显示为绿色“可安全废弃”，纪承钧在本地核验未闭合时仍批准移除。事故后，维护者才从 Makefile 注释和旧 shell 脚本追到北岭备份服务器的本地调用。
- **六拍骨架**：
  1. 纪承钧传讯：“v0.3.1 的退役建议在玄枢造成了故障。”他说明自己读过范围声明，也看见本地 socket 是盲区；这次决定由他签字批准。
  2. 网关移出生产包后，夜间本地调用失去目标，三个服务先后失去响应，告警扩散到十七处外部调用方。值守与回滚安排没能补上缺失的调用核验。
  3. 沈见微对照报告确认：三十天统计只覆盖青炉已接入采集源，连续三十六个月可见调用为零；数据没有证明玄枢全域无人使用。越界发生在生成器把“观测窗内未见调用”升格成绿色退役建议。
  4. 纪承钧承认自己知道监测盲区仍批准维护窗删除。青炉输出的过强标签和玄枢未完成本地调用核验的决定共同构成因果链；免责声明不能免去任何一方责任。
  5. 两人从 Makefile 注释和旧 shell 脚本追到北岭备份服务器的本地调用，记录证据范围与尚未证实的部分。更早的手工边界修正保留为独立旧风险，不写成这次事故的直接根因。
  6. 沈见微要求暂停依据 `v0.3.1` 继续退役接口，并准备撤回通知与替代状态；纪承钧补做接收方本地核验和责任记录。两人的分歧从“谁没读声明”落到两道都没守住的边界上。

> 跨卷信息只提供本场景所需背景：玄枢有本地 socket 盲区，纪承钧知情并批准删除。驭器、化形相关事故可作回声，不作为理解本次事故的前提。

### 第106章：三遍阅读

- **核心对象层**：念→念。沈见微收到纪承钧的复盘和原始操作记录。第一遍，他抓住报告的范围声明，认为责任已经交代；第二遍，他看见“可安全废弃”被放在结论栏，醒目得像一道批准；第三遍，他终于承认：报告写了限制，却仍替接收方迈出了最后一步。
- **六拍骨架**：纪承钧没有先争论责任，只要求沈见微按同一份报告复走那次决定。两人逐项对照观测数据与退役动作，确认数据没有算错，跨越证据的却是建议用语。沈见微请他保留原报告、执行命令和接收方记录，暂不急着给事故定性；争论从“谁没看免责声明”转向“报告实际让人做了什么”。

### 第107章：契约的盲区

- **核心对象层**：契→背契。复走确认了失误位置：诊断器只观测到已登记的调用范围，却把“当前观测未发现调用”升级成“可安全废弃”。接收方即使看见扉页，也缺少一套能阻止错误退役的操作门槛。青炉的工具越过了证据能支持的边界。
- **六拍骨架**：闻衡要求先撤回 `v0.3.1` 的退役建议，通知所有已知接收方暂停据此删除接口；旧报告保留并标记为已撤回，不能静默改写历史。下一版把状态降为“当前观测未发现调用，待接收方核验”；须完成本地调用来源、未覆盖通道、替代路径和回滚条件核验，并由接收方签认，才可进入退役审议。沈见微第一次看清，补充说明不能抵消一个越权的行动建议。

### 第108章：在青炉上留痕

- **核心对象层**：史→史。沈见微想把这次失误写进青炉记录板，也必须先尊重事故发生在玄枢这一事实。公开之前，他联系纪承钧，说明拟公开的用途、读者和内容，请他确认哪些细节能留下。
- **六拍骨架**：纪承钧同意公开报告措辞、观测盲区与处置改进，要求隐去玄枢内部服务名和调用细节。两人共同核定一份脱敏复盘：保留“有限观测被写成安全结论，接收方据此批准删除并造成故障”的因果，不公开玄枢的内部结构。沈见微将授权范围和署名一并存档；若对方不同意公开的部分，就留在受限事故记录里。

### 第109章：放弃“写清楚就是一切”

- **核心对象层**：念→约→史。沈见微不再用长篇声明解释自己为何改变，而是在记录板上签下一项可检查的承诺：青炉诊断不得把“未观测到”写成“安全”；高影响处置建议必须带接收方核验门槛、替代路径和回滚条件；不满足条件时，只能给出待核状态。
- **六拍骨架**：他把已撤回的旧建议与替代措辞并排保存，注明适用范围、修订人和复核负责人。闻衡要求加上一项反例测试：当本地调用未知时，工具必须拒绝给出退役许可。沈见微签名承担后续复核，不要求其他世界照搬青炉的判断。他放下的不是记录，而是“写出来便足以替人决定”的确信。

### 第110章：道争之后

- **核心对象层**：史→史。青炉没有宣布一条适用于所有输出的新总则。团队把此次修订限定在诊断器的高影响退役建议，并建立后续复核责任：维护者检查报告措辞，接收方提供本地证据，程知序负责在下一维护窗口前追回应有回执；逾期未确认的接收方继续标为待核，禁止据旧报告退役，并由闻衡升级复审。其他文档按各自风险评估，不因一场事故一概加厚。
- **六拍骨架**：沈见微离开记录板时，撤回公告已发出；程知序按追踪单逐一确认接收方回执，下一维护窗口前仍未确认的对象保持待核并升级给闻衡。苏野平追问这套核验成本是否适合每个项目，贺时进追问谁来承担延误；沈见微没有再给出普遍答案，只把判断范围、责任人和复核期限留在纸上。卷十二将检查这些约定能否被不同的人实际使用；修补者留下的话以旧屋档案为据，不作为本章新出现的“终言”。
