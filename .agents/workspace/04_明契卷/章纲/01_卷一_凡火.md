# 卷一「凡火」Ch 1-10：错版夜发之后，先把未知分清

> 本章纲属于明契卷120章目标结构。现有根正文索引仍是旧30章阅读序列；旧稿迁位与新章正文补齐尚在进行。以下只把现行正文已经证明的事实写成确定语气，因果假设须明确标待核。

## Section 总览

- **章段**：Ch 1-10
- **叙事主题**：同一版号在多处出现不同结果，命令回报成功却不能证明各处拿到同一条路。Ch01可证实的是结果分流、回滚依赖熟手和裴照川实施了止火操作；本地缓存、未记录环境值及旧钩子顺序仍是线索，当前正文尚未锁定错版夜发的唯一直接触发。脚本依赖和口传知识须各自核查。
- **事件边界**：本卷一处理青炉内部的错版夜发。后来青炉报告被玄枢用于退役 `legacy-report-gateway`、导致北岭本地调用失去目标，是另一场跨卷事故，须按 canon22 与其现行章节映射单独呈现，不能倒并为Ch01的根因。
- **核心冲突**：危机并非证明旧工具链“从来没有秩序”，而是暴露出同版结果不一、回滚路径依赖少数熟手，现有记录不足以支撑复现和验证。人物必须在恢复服务、查清影响和承担操作责任之间取舍。
- **工具链阶段**：rustup/toolchain入门（卷尾Ch10选道——为什么是Rust）
- **对象层**：念→约（从"先修再说"的念——到"我们需要约"的觉醒）
- **主相→蚀**：史 → 断史 + 契 → 背契（当前证据支持行为与说明不一致、维护知识散落；具体缺失记录和事故直接机制须逐项核实。）
- **主角状态**：沈见微——旧工具链的救火者之一。正式owner与值守安排未明；昨夜多人因熟悉现场而临时到场，不能据此称某一人是唯一响应者。
- **卷尾落点**：急火已压住，根因仍未收敛；沈见微决定先记录已知、未知和验证责任，再立青炉的范围与语言选择。不得把事故升级为“已经证明预防即可消除所有故障”。

### 第01章：凡火未明

- **核心对象层**：念→念（同一版号在三处呈现不同结果；一处走新说明，一处命中本地缓存后回落旧插件壳，一处因未写明的启动条件熄火。命令成功不证明三处产物或运行路径相同。）
- **核心相与失守**：史 → 断史（可确认的是版本号相同而观察结果不同；本机旧状态、未记录环境值、缓存和旧钩子顺序都是排查线索，尚不能断定哪项先造成分流。）
- **工程锚点**：发布（deployment）与配置管理（configuration management）——不是"能发布就行"——是"发布时的世界状态——和上一次发布时——有没有被记录下来的差异"。CI/CD的前提不是自动化——是"自动化知道自己不知道什么"。
- **张力曲线**：崩塌型（凌晨——发布系统报"成功"——但产物上线后——三十分钟——用户开始报错——错误蔓延——沈见微被传讯牌叫醒——"什么情况？""发布了。""谁的发布？""自动的——和昨天一样。""昨天之后——有人改过配置吗？""......不知道。"）
- **六拍骨架**：
  1. 问题先出：凌晨自动发布——命令成功——产物上线——炸了
  2. 为什么痛：发布系统只知道"我做了"——不知道"有人在我不知道的地方改了东西"
  3. 引出方法：发布不是自动化就够了——是"发布时的世界状态——被记录——被比对——差异被公开"
  4. 项目落地：沈见微整理三份回铃、发布产物、回滚步骤和环境差异；把已证实结果与待核原因分栏，不以未记录配置改动作为既定根因。
  5. 多方复盘：让每名参与者说明自己看到的证据与未覆盖部分；停止用“发布成功”代替一致性结论。
  6. 高层收束：命令成功只证明该命令报告成功；版本、运行条件与回滚路径仍须分别核验。

### 第02章：谁在值守

- **核心对象层**：人→人（紧接事故后的白天，众人回看昨夜谁被叫到、谁有权批准降级、谁能操作旧钩子。没有明确值守和服务责任，救火靠熟人临时聚拢；本章不再倒叙事故爆发前夜。）
- **核心相与失守**：契 → 背契（没有值班制度——不等于是自由的——等于是"没有人承诺过会接"。每个人都在睡——但每个人都被传讯牌叫醒——然后每个人心里都在想——"为什么是我？"）
- **工程锚点**：on-call轮值与ownership——与简阵卷Ch31-40形成跨卷对照。明契卷的旧工具链——和驿河的51个服务——同一种病在不同的阶段。"没有人认领的服务——在凌晨——是所有人的噩梦——但没有一个人的责任。"
- **张力曲线**：余震型（几人核对昨夜的呼叫记录与处置权限，发现有响应人却没有清楚的服务owner；让具体的等待和交接缺口显形，不把“无人接听”写成已经证实的事故原因。）
- **六拍骨架**：
  1. 问题先出：复盘昨夜的呼叫链，区分收到通知、能操作和承担最终决定的角色
  2. 为什么痛：临时响应者承受等待、信息缺失与授权不明的成本；不得将影响扩大写成未经证实的必然因果
  3. 引出方法：on-call不是"让人不睡觉"——是"让人知道——今晚——就是我——没有别人——我不接——没人接"
  4. 项目落地：本章只建立责任缺口清单和临时联络人；轮值、owner与升级路径留待后续讨论，不凭空宣布制度已建立
  5. 多方复盘："没有制度——是最累的。制度不是束缚——是让你知道——'今晚不是我——我可以睡'。"
  6. 高层收束：收到告警、能做处置、批准风险和承担后果是不同职责，必须分别记录。

### 第03章：脚本成墙

- **核心对象层**：器→器。团队把Ch01现场出现的旧插件壳、回退暗令、临时补丁与不同环境结果放在一张图上，核对入口和依赖；图上已知与待查路径分开，不能把脚本数量直接当作事故根因。
- **核心相与失守**：式 → 失式。脚本、缓存和环境前提散落在不同位置，维护者难以还原同一版号为何走出不同结果；具体触发顺序仍待记录与复现证明。
- **工程锚点**：脚本依赖与调用方盘点。记录入口、依赖、版本、环境前提、维护者和验证范围；显式依赖声明能改善可见性，但不能单独证明运行时行为。
- **张力曲线**：考古型。沈见微从三份回铃和发版记录逐项追查：一处命中新入口，一处回落旧插件壳，一处缺少未写明的启动条件。团队找到了彼此相关的脚本和配置，却无法证明哪一项先造成分流。
- **六拍骨架**：
  1. 问题先出：同一版号对应三种结果，操作记录却只写“发布成功”。
  2. 为什么痛：接手者看见了脚本和返回码，却没有足够证据重建每台机器当时的路径。
  3. 引出方法：把观察事实、调用假设、环境差异和复现结果分栏记录。
  4. 项目落地：沈见微与季循为三种结果各自标出已见入口；缓存、本机状态、环境值和钩子顺序保留为待核项，不合成单一根因。
  5. 多方复盘：苏野平说明临时补丁的适用范围，韩砺年区分亲历与记忆，程知序补充发布台能证明和不能证明的内容。
  6. 高层收束：依赖图不是根因判决；它先让后来者看清哪里有证据、哪里仍隔着墙。

### 第04章：口传之链

- **核心对象层**：文→史。事故复盘中，沈见微向韩砺年核对配置与旧工具的来历。韩砺年掌握不少历史背景，也明确说出自己记不清、没有记录或无法证明的部分；他的经验有价值，但不是完整档案。
- **核心相与失守**：史 → 断史。口述能补充背景，却会受记忆和视角限制。若后人把“熟手如此说”当作唯一证据，猜测就会悄悄变成规则。
- **工程锚点**：知识交接与设计决策记录。记录已知理由、来源、适用范围、验证状态和未知项；不把“问过某人”伪装成独立核验。
- **张力曲线**：有限回答。沈见微追问一项旧配置的由来，韩砺年给出记忆中的事故背景，却无法指出原始记录；另一个配置他明确说“不记得”。两人的分歧不在谁愿意帮忙，而在记忆能否承担风险批准。
- **六拍骨架**：
  1. 问题先出：排查中多次需要韩砺年补充背景，现有文件无法回答部分“为什么”。
  2. 为什么痛：熟手可以补上下文，却无法证明所有前提仍然成立。
  3. 引出方法：将可确认的理由、证据来源、适用范围和未知项分栏记录。
  4. 项目落地：沈见微记录一项可回查的说明，并把韩砺年无法确认的另一项明确标为待核。
  5. 多方复盘：团队讨论谁能验证旧决策、谁有权批准风险；不把记忆负担继续压给单一维护者。
  6. 高层收束：留下一份记录只是交接起点；后来者仍需理解并验证它的前提。

### 第05章：灰印

- **核心对象层**：史→史。沈见微在旧代码旁发现一条无署名、无日期的注释：“此处逻辑不应被文档化。”原文可以确认，作者、写下时间、针对的逻辑及其语气均未确认。他将它抄录为待查线索，不据此认定有人故意隐瞒。
- **核心相与失守**：史 → 断史。留下的文字没有说明适用对象和理由，后来者容易把一句局部提醒扩大为禁令；也可能只是脱离上下文后的残句。本章让解释保持开放。
- **工程锚点**：遗留注释与缺失上下文。把原文、载体、发现位置和当前解释分开记录；与其他卷的相似文本只能作为读者并置，不能因此认定同一作者、同一来源或同一组史约事件。
- **张力曲线**：悬疑引入型。众人围绕注释提出互相冲突的解释：警告、临时便笺、脱离上下文的句子，甚至转录错误。没有一方能拿出足以定案的证据；沈见微只登记原件位置和待查问题。
- **六拍骨架**：
  1. 问题先出：沈见微发现注释“此处逻辑不应被文档化”。
  2. 为什么痛：它没有署名、日期和上下文，无法判断这是决定、警告还是残缺文本。
  3. 引出方法：保留原件，并把可见文字与解释、推测分别记录。
  4. 项目落地：沈见微抄录原文，登记载体和发现位置，并注明“作者、时间、上下文待核”。
  5. 多方复盘：众人不能将文字当作禁止修改的命令，也不能因其不完整就删去；先保留原件，再寻找可验证的关联材料。
  6. 高层收束：空白不替他们作答；它只迫使后来者承认自己还不知道。

- **跨卷参照**：若读者将此注释与其他卷的残码并读，只能形成主题上的对照。共同作者、年代、传承关系和“史约”含义均无证据，后续章节不得把并置写成已确认的线索网。

### 第06章：止火者

- **核心对象层**：人→人。裴照川已在Ch01抵达并参与止火。本章不重演他的登场和操作，而是让沈见微、韩砺年、苏野平与值守者回看变更记录、当时的判断和各自未看见的部分。
- **核心相与失守**：契/史。裴照川的经验可以帮助止损，却不能代替调用方清点、影响评估和事后记录。团队既感激他的判断，也必须追问：哪些证据支持操作、哪些风险由谁批准、哪些步骤仍只有他能复现。
- **工程锚点**：事故止损与复盘。区分缓解措施、直接触发点、遗留风险和未证假设；快速恢复不是根因已查明，也不自动形成可复用流程。
- **张力曲线**：复盘型。服务已恢复，事故记录却无法说明哪些调用路径得到验证；裴照川的记忆补足了操作过程，却无法回答所有未观测调用是否恢复。
- **六拍骨架**：
  1. 问题先出：服务已恢复，记录却没有列出验证过的调用路径。
  2. 为什么痛：团队的感激与依赖遮住了操作授权和验证范围的空白。
  3. 引出方法：复盘记录分开写时间线、已执行缓解、验证结果和未知风险。
  4. 项目落地：沈见微与值守者依据各自记录还原步骤；裴照川补充记忆，也把记不清的部分标作未知。
  5. 多方复盘：让执行人、批准人、观测责任人各自确认职责和未覆盖路径，不把判断责任推给单一熟手。
  6. 高层收束：止火者能争取时间；能否把方法交给后来者，取决于团队怎样核验和记录，而非传奇本身。

- **跨卷锚点**：裴照川在其他卷中的选择可与本卷互相映照；具体经历须由对应卷正文独立交代。不得将相似事故或处置方式写成师承、共同履历或同源证据。本卷当前只确立他参与本次止火及团队需要补全记录。

### 第07章：不是第一次

- **核心对象层**：史→史。沈见微翻查旧事故记录，找到一份表面相似的报告；他逐项比较时间、受影响对象、处置动作和证据范围，不将“相似”直接写成同一根因。
- **核心相与失守**：史 → 断史。旧报告的结论若没有适用范围、验证记录和后续责任人，后来者可能只复用一句“加强测试”，却不知道当年测试了什么、哪些路径未覆盖。
- **工程锚点**：事故分析（incident analysis / postmortem）。复盘要回答发生了什么、为何当时未发现、处置覆盖了什么、后续如何验证；不得把不同事故压成相同根因。
- **张力曲线**：对照型。旧报告与本次事故在告警外观上相似，但追到变更和调用记录时出现差异；团队必须放弃一个省力却证据不足的解释。
- **六拍骨架**：
  1. 问题先出：旧报告的告警描述与本次相近。
  2. 为什么痛：若只按标题归类，错误的经验会被当作可复用结论。
  3. 引出方法：对照证据、处理范围、缺失记录和后续验证，不只比较结论句。
  4. 项目落地：沈见微把可比项和不可比项分栏，确认旧报告没有证明本次调用路径已被覆盖。
  5. 多方复盘：决定哪些旧措施仍可参考，哪些必须重新验证，并标出责任人与截止时间。
  6. 高层收束：历史能提供问题，不会替今天的人完成核验。

### 第08章：见病

- **核心对象层**：念→念。从追求更快止损转向降低重复失效的可能、缩短发现时间并明确谁承担验证。沈见微不再把“写得足够清楚”当作可以消除所有事故的答案。
- **核心相与失守**：契/史。若修复只靠熟手记忆，责任与经验就无法稳定交接；若把规则写得过度绝对，又会把未知和例外藏起来。沈见微由此开始寻找可以验证、可以修订的边界。
- **工程锚点**：从事故响应走向预防与恢复能力建设。目标是减少可避免的故障、及早发现并限制影响，不承诺事故永不发生，也不把专业响应者视为可以被消灭的角色。
- **张力曲线**：觉醒型。Ch07已为三项初查指定临时负责人，但复盘仍有未验证调用路径，也没有为后续持续验证逐一路径设定责任人；沈见微必须决定是立即宣布“问题已经解决”，还是承认边界未明并继续承担调查成本。
- **六拍骨架**：
  1. 问题先出：复盘记录留下未验证调用；Ch07的临时初查分工尚未覆盖长期验证责任。
  2. 为什么痛：依赖熟手能降低眼前损失，却无法保证下一班识别同一风险。
  3. 引出方法：从个人记忆转为范围明确、可复核的责任和验证约定。
  4. 项目落地：沈见微列出待核路径、临时负责人和复查时间，不把方案写成永久保证。
  5. 多方复盘：讨论哪些故障可以预防，哪些只能更早发现或限制影响，并为每项安排验证人。
  6. 高层收束：见病不是宣称已知全部病因，而是把已知触发、未知路径和下一步核验写在同一张记录上。

### 第09章：立炉之前

- **核心对象层**：约→约（边界先行——不是先做，是先说清不做什么。沈见微在开始建青炉之前——先写scope——"这个项目——要解决什么——不解决什么"。这是"写清楚"的第一步——不是代码——是承诺。）
- **核心相与失守**：（正向——约的雏形。"写下来——不是'我决定了'——是'我承诺——这是边界——边界之内——我负责——边界之外——我不负责——但如果你的需求在边界之外——告诉我——我们可以重新谈边界。'"）
- **工程锚点**：scope definition（项目范围定义）——不是"做什么"——是"不做什么"。"不做什么"比"做什么"更重要——因为"做什么"会膨胀——"不做什么"是边界——保护项目不被膨胀压垮。
- **张力曲线**：建设型（沈见微写第一份scope——"青炉——不是替代旧工具链——是让工具链可以被理解、被测试、被传递。"贺时进——"为什么不先做——让大家先用上？""因为不说清楚——'让大家先用上'——就是'让旧工具链继续膨胀'——不先写边界——永远是救火。")
- **六拍骨架**：
  1. 问题先出：沈见微决定建新工具链之前——先写scope
  2. 为什么痛：旧工具链的问题——就是"没有边界"——什么都能加——加到谁都看不懂
  3. 引出方法：scope不是"做什么"——是"不做什么"——"不做什么"保护项目不被膨胀压垮
  4. 项目落地：沈见微写了第一份scope——"青炉——管理构建、测试、发布——不做运行时监控——不做数据分析——不替代运维系统。"
  5. 多方复盘："边界——不是拒绝使用者——是告诉使用者——'这是我的范围——你的需求如果不在范围内——告诉我——我帮你找对的人。'"
  6. 高层收束：立炉之前——不是先做——是先写——"写——不是束缚——是指南。"

### 第10章：选道而行

- **核心对象层**：念→念（为什么是Rust——不是因为它最强——是因为它的"道"——是"写清楚"。"Rust通过所有权、借用和类型检查，在编译期拒绝一类违反约束的程序；它不能证明所有业务约定，也不能保证运行时绝无事故。C++也能借类型、RAII、分析器和团队规范表达许多约束，但默认路径与迁移成本不同。"——这是沈见微选择Rust的原因——也是他将在卷十一放弃"写清楚就是一切"的起点。）
- **核心相与失守**：（正向——选道。“Rust适合眼下的青炉，是因为它把一部分所有权和类型边界纳入编译检查；它仍留下业务前提、运行环境和未覆盖路径，须由团队验证。”）
- **工程锚点**：工程锚点：ownership（所有权）、borrowing（借用）、lifetime（生命周期）、Option/Result（显式表达缺省值与可恢复错误）、Send/Sync（跨线程共享/转移的类型约束）。它们能让部分错误在编译期暴露，但不等于所有契约都被证明或运行时绝无事故。"
- **张力曲线**：决断型（沈见微——"为什么Rust？因为它的'道'——就是青炉需要的：写清楚。但——"他停顿了——"写清楚——够吗？我不知道。但至少——Rust能在编译期拦下一类所有权与类型错误，却不能替他们发现每种运行时故障。"）
- **六拍骨架**：
  1. 问题先出：沈见微比较团队能力、迁移成本和工具链约束，说明为何选择Rust
  2. 为什么痛：旧工具链混用多种语言和脚本，构建与调用前提分散；不能把问题归咎于“别的语言没有编译器保障”
  3. 引出方法：Rust把部分内存与类型约束放进编译检查，其他业务和环境承诺仍需测试、观测与责任人
  4. 项目落地：沈见微写下选道声明——"青炉——Rust——不是因为Rust最强——是因为它的道——最接近'写清楚'。"
  5. 多方复盘：沈见微把语言选择写成有范围的决定，并列出需要由使用者验证的条件；后续经历将逐步检验“写清楚是否足够”，不预告结论。"
  6. 高层收束：选道是带着理由、迁移成本与验证边界作出的决定，不是语言优劣的终局判决。

> 📝 卷尾。事故处置与证据边界逐步明朗——裴照川的止火在Ch01已发生，后续复核其验证范围；无署名注释仍待考——沈见微开始寻找可检验的承诺，并选择Rust。向卷二过渡：从工具链与manifest建立可检查的约定，再进入ownership初识。
