# 卷七「守界」Ch 61-70：内存安全·并发·unsafe

## Section 总览

- **章段**：Ch 61-70
- **叙事主题**：内存安全的真实含义——lifetime=时间契约——Send/Sync=并发安全在类型层面——unsafe/FFI责任边界——裴照川的另一面揭示——修补者谱系线索。"边界守住了——但边界之外的东西呢？"
- **核心冲突**：safe Rust 的类型系统能检查一部分内存与并发约束；生命周期标注描述引用关系，Send/Sync 约束线程间传递与共享，但它们不解决业务竞态、死锁或外部库的不透明行为。unsafe/FFI 把论证责任交还给人，且论证依赖具体版本、调用路径和共享状态，条件变化后必须复核。"
- **工具链阶段**：Send/Sync / Mutex/RwLock / unsafe / FFI / lifetime annotation
- **对象层**：骨→骨（所有权深层——lifetime——Send/Sync——类型系统的最高层级）
- **主相→蚀**：乱流（并发不安全——数据竞争——死锁——共享状态的代价）
- **主角状态**：沈见微逐步看清编译器的证明边界：类型检查能替团队排除一部分危险状态，却不能替他们保证程序行为、锁顺序和外部 C 库契约。

---

### 第61章：肉身不坏

- **核心对象层**：骨→骨。沿用旧 Ch61 作为路标来源。说明 safe Rust 中 ownership、borrowing 和 lifetime 如何让编译器拒绝一部分悬垂引用与别名冲突；不把这项保证扩展到违反 unsafe 前提或外部 C 代码。
- **工程锚点**：引用的有效期、共享/可变借用约束与安全抽象边界。旧 C 模块改写后，编译器拒绝可能同时存活的冲突借用；这是静态检查案例，不证明程序所有错误都会在编译期暴露。
- **六拍骨架**：沈见微解释编译器拒绝的具体借用关系，并把拒绝范围和 C/unsafe 责任分开；以一个尚待说明的跨函数引用关系引出 Ch62。

### 第62章：借命

- **核心对象层**：骨→骨。新增章：沈见微为报表视图保留对配置文本的引用，后来者想让视图活过配置对象；编译器拒绝这组生命周期关系。
- **工程锚点**：生命周期参数（lifetime parameter）用于表达引用之间的有效期关系，不会延长任何值的寿命。用 `ReportView<'a>` 或返回引用的函数签名说明借用者不能超过所有者。
- **六拍骨架**：季循先把 `'a` 当成“延长生命”的符号；沈见微让他沿着 owner 的作用域走一遍，再以拥有数据或缩短借用来解决。借用时间问题已解，但批处理跨线程仍未处理，承接 Ch63。

### 第63章：心魔难驯

- **核心对象层**：流→乱流。沿用旧 Ch62 为路标来源。report 模块把 `Rc<Config>` 捕获进 `thread::spawn` 闭包，编译器因 `Rc` 不满足跨线程要求而拒绝；替换为 `Arc` 只解决共享计数的线程安全，不保证业务顺序正确或无死锁。
- **工程锚点**：`Send` 表示值可安全地转移线程；`Sync` 表示共享引用可安全地跨线程共享。二者是线程安全约束的一部分，不等同于“编译器证明整个程序无数据竞争/无并发错误”。
- **六拍骨架**：季循修正共享配置的所有权方式后，沈见微补充这只是类型层面的检查；报表竞争仍要看共享状态与同步设计，引出 Ch64 的锁等待。

### 第64章：锁与等

- **核心对象层**：流→流。新增章：两个报表任务都能安全访问受 `Mutex` 保护的数据，但一个持锁期间进行慢速格式化，另一个任务只能等待。安全不等于没有延迟或死锁。
- **工程锚点**：互斥锁（mutex）、读写锁（RwLock）、锁竞争与锁顺序。展示缩短临界区、复制必要数据后再格式化；不声称 Rust 编译器能防止死锁。RwLock 只在读多写少且有证据时采用，不为术语完整而强行引入。
- **六拍骨架**：值班视图显示等待增长；团队测量锁持有区，把格式化移到锁外，再观察延迟变化。留下“锁住 Rust 数据后，外部 C 调用是否也受同一保证”的问题。

### 第65章：禁术与誓约

- **核心对象层**：契→背契。沿用旧 Ch63 为路标来源。青炉以 FFI 调用旧 C 协议解析库；unsafe 标记程序员承接额外安全义务，不会关闭其余 Rust 检查，也不会替 C 代码背书。
- **工程锚点**：外部函数接口（Foreign Function Interface, FFI）、裸指针、unsafe block、调用者安全条件与 safety comment。当前版本的可重入结论只适用于已核对版本和调用路径。
- **六拍骨架**：沈见微写清指针有效性、缓冲区归属、错误返回和并发前提；闻衡提醒版本升级或调用方式变化会令论证过期，接入 Ch66。

### 第66章：越过边界

- **核心对象层**：流→乱流。新增章：依赖更新说明显示 C 库改用共享静态缓冲区，旧版“可重入”前提不再成立；并行解析时两次调用会覆盖同一缓冲区。事故限定为隔离批处理中的结果污染，不扩写成整个平台崩溃。
- **工程锚点**：FFI 安全封装必须约束调用并发和指针有效期。团队先串行化整个“调用并复制结果”区间，或固定旧版并停止并行；只在锁覆盖所有调用方时才足以保护共享缓冲区。版本变化本身不是根因，具体契约变化才是。
- **六拍骨架**：季循从依赖更新说明和双线程样本发现缓冲区地址相同；沈见微撤回旧论证并更新封装前提与回归案例，承认此前证据只覆盖旧版本。

### 第67章：裴照川的另一面

- **核心对象层**：人→人。沿用旧 Ch64 为路标来源。裴照川展示他为旧库封装写下的形式化论证；沈见微此前用可读安全说明表达前提，两者解决的是不同读者和检查能力，不设谁更高级。
- **六拍骨架**：裴照川承认即使能形式化，也只能证明选定模型、属性与前提；他过去常能止火，却没把所有判断交给同伴。修补速度留下的知识缺口成为下一章问题。

### 第68章：修补者的遗产

- **核心对象层**：史→史。新增章：裴照川翻出一段早于自己入行的旧修补记录，作者栏空白、内容只留局部动作。他猜测有人比他更早承担过类似责任，但不能据此确立第一位修补者、师承关系或梁故川身份；对应 canon26 A7 的未证状态。
- **六拍骨架**：沈见微把相似处和未知处分栏记录；裴照川承认自己也只是在空白上猜。遗产落在“留出可继续核对的证据”，而非宣布修补者谱系成立。

### 第69章：守界之后

- **核心对象层**：念→念。沿用旧 Ch65 为路标来源。总结 safe Rust、Send/Sync 与 unsafe/FFI 的不同责任边界；编译器能检查其规则覆盖的条件，外部环境与调用者仍需有相应契约和验证。
- **六拍骨架**：裴照川把可读论证和可检查证明并列归档；顾迁衡带来发布清单，提醒内部成立的边界尚未经过陌生用户和不同环境检验，转入 Ch70。

### 第70章：炉候正盛

- **核心对象层**：器→阵。新增章：青炉的构建、并发样本、FFI 封装和评审流程开始成形；团队对当前已测范围有信心，却没有把它夸成覆盖所有平台和调用场景的证明。
- **六拍骨架**：沈见微准备把候选 crate 交给外部试用；清单上仍有未覆盖的平台、环境和真实调用行为。炉火最旺时，团队决定先接受测试与发布检验，而不是宣布体系已经完备。

> 📝 卷尾。内存与线程约束逐步落地——FFI 安全前提因版本契约变化而需重审——裴照川分享可读论证与机器检查的差别——修补者谱系仍是待证猜想。向卷八（出山——测试、发布与外部调用）过渡。
