# 卷六「同修」Ch 51-60：Git·review·门规

## Section 总览

- **章段**：Ch 51-60
- **叙事主题**：从一个人到一群人——Git哲学（commit=因果秩序）、分支策略、merge conflict、review文化、闻衡打回PR、苏野平登场（化形之道同门者）、"先跑通"vs"先写清"的道统碰撞。
- **核心冲突**：团队需要更快交付，也需要让共享工具可理解、可复核。苏野平先跑通扫描脚本，沈见微要求补入口、结果解释和退场条件；两人争论的是哪些最低说明应与工具一同交付，而非快与清楚只能二选一。
- **工具链阶段**：Git / branch / merge / remote / review / PR规范
- **对象层**：门→门（从个人机制——到团队机制——到协作文化）
- **主相→蚀**：契 → 背契（merge conflict=两个人都做了对的事——但没有互相告诉）
- **主角状态**：沈见微从"我的写清楚"——到"团队的写清楚"——到"别的道——也有它的写清楚——只是写的方式不同"

---

### 第51章：留影为史

- **核心对象层**：史→史。Git commit 保存变更快照及提交元信息；提交说明可记录动机、依据和验证，但 commit 本身不自动包含设计意图，历史引用也可能被重写。
- **工程锚点**：`git log`、提交说明与可追溯变更。作者、时间戳和 diff 是线索，不足以证明实际决策缘由；原因需由参与者写下，评审讨论还需对应记录。
- **六拍骨架**：沈见微为青炉写下第一个 commit，说明它只含 scope 与 `Cargo.toml`，并承诺以后补上决策缘由；避免把 commit 描写为不可改写的因果真理。

### 第52章：分支之上

- **核心对象层**：史→史。Git 分支使提交可以沿不同方向推进；它不自动隔离共享工作目录，也不保证改动互不影响。feature branch → PR → review → merge 是青炉选择的协作流程，不是 Git 强制规则。
- **工程锚点**：分支引用、提交、合并与评审。合并前后仍要运行适当检查；分支策略降低并行改动的协调成本，不能保证冲突或生产问题消失。
- **六拍骨架**：季循、苏野平、程知序分别提交配置、扫描脚本和使用入口改动；团队约定经 PR 汇合，各自留下的提交可以比较，冲突仍需共同处理。

### 第53章：千里传书

- **核心对象层**：门→门。远端仓库成为团队约定共同维护的一份基线，不是天然的唯一真相。个人分支、未推送提交和其他远端都可能同时存在。
- **工程锚点**：Git remote、fetch、push、remote-tracking branch。抓取远端不会自动决定把何种变更纳入共享基线；`origin/main` 的权威性来自团队约定和权限流程。
- **六拍骨架**：沈见微配置青炉远端，团队说明哪些共享分支受保护、谁能合并以及如何发布；成员仍保留本地工作历史。

### 第54章：第一次冲突

- **核心对象层**：契→背契。沈见微增加配置参数，季循删除旧默认值；重叠文本导致 Git 无法自动合并。冲突标记显示工具无法决定的差异，不证明双方没有沟通过，也不替人裁决语义正确性。
- **六拍骨架**：两人对照调用方和改动理由，决定保留新参数，并将旧默认值改作显式迁移选项；把冲突当作需要协调的技术信号，不归咎于 Git 或将每次冲突道德化。

### 第55章：门规初成

- **核心对象层**：门→门。闻衡起草 Conventional Commits 约定与 PR 模板，让提交标题、变更理由、验证方法和影响范围更容易被查阅；格式只是约定，不自动保证准确、完整或生成可靠 changelog。
- **工程锚点**：`feat:`、`fix:`、`docs:`、`refactor:`、`test:`、`chore:` 及 PR template / review checklist。PR 让变更意图有机会在合并前被看见，但不保证一定发现冲突，也不替代弃用声明。
- **六拍骨架**：闻衡用 Ch54 的参数冲突说明为何需要提前告知；模板要求作者写出场景、理由、验证和影响对象，团队评估模板能否真正减轻 reviewer 猜测。

### 第56章：闻衡不通过

- **核心对象层**：契→契。一个 PR 的代码变更看似合理，但描述只有“修了一个 bug”；闻衡要求补充复现条件、修复依据及测试覆盖。
- **工程锚点**：代码评审补充编译器与测试无法替作者传达的理由；编译器只发现其规则能判定的问题，测试只覆盖已写出的情形，review 也不可能保证发现所有缺陷。
- **六拍骨架**：季循为 Ch47 的结果错配提交修复，但只写“调整输出”；闻衡退回并追问复现条件、旧测试为何漏过、双项回归样本覆盖什么。季循补齐问题、修复和验证之间的关系，不宣称一次 PR 能确保缺陷永不复现。

### 第57章：苏野平的脚本

- **核心对象层**：人→人。苏野平提交 Python 脚本调用 `pip-audit` 扫描依赖中已知漏洞并整理结果；它不负责证明依赖兼容，也不单凭漏洞扫描判定依赖过期。脚本先进入 workspace 试用，并写明当前用途。
- **六拍骨架**：闻衡问运行入口、输入输出与维护责任；苏野平认为短说明足够，不愿先写长文档。两人先把运行方式、结果解释和退场条件列为最小交接内容。

### 第58章：快与对的张力

- **核心对象层**：念→念。眼前扫描尚无结果，苏野平希望先运行再补记录；沈见微担心共享脚本成为隐式构建依赖。讨论聚焦“先交付的最小边界”与后续完善顺序，不把快说成必然造墙、慢说成必然更可靠。
- **六拍骨架**：若脚本纳入 CI，贡献者会间接依赖它，需要用途、输入、输出和维护说明；若只作一次性本地试验，则可缩小说明范围，但仍标明负责人和退场条件。

### 第59章：团队成形

- **核心对象层**：人→阵。团队成员各自负责范围说明、审契、桥账、试用、快速工具与真实使用反馈；季循在 Ch47 的隔离双项样本中发现结果错配，不写成生产环境事故。不同技能成为协作能力，不替角色贴上“快就不写文档”的标签。
- **六拍骨架**：团队把各自职责和交接边界写上记录板；闻衡的 review 成为可讨论的习惯，苏野平也为共享脚本补足最小交接信息。

### 第60章：同修之后

- **核心对象层**：念→念。提交说明只有在有人填写时才留下理由；review 记录只有被保存时才留下审查过程。团队开始明白，流程提供载体，记录仍需成员共同完成。
- **六拍骨架**：一份 review 停在 `unsafe` 代码前。裴照川作为卷首危机中曾用旧经验止火的前辈，递来安全论证模板；协作记录不能替编译器或人证明内存边界，顺势进入 Ch61–70 的安全与责任议题。

> 📝 卷尾。Git 提交与评审留下协作线索——苏野平的快速试法与沈见微的边界说明发生碰撞——团队开始分担交接。向卷七（守界——内存安全、并发、unsafe——裴照川的另一面）过渡。
