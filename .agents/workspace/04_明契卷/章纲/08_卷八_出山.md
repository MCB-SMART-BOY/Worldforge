# 卷八「出山」Ch 71-80：测试·发布·未知边界

## Section 总览

- **章段**：Ch 71-80
- **叙事主题**：把已知风险写成可复验测试，在发布压力下区分二进制入口与公共库承诺，并让诊断报告的观测范围与处置建议显出落差。卷内只埋下误读风险，不提前揭示玄枢事故。
- **核心冲突**：青炉准备离开沈见微的机器，但“测试通过”“版本发布”“报告有边界”都只能证明各自覆盖的部分。门外能否复走，取决于前提有没有落到可核验的步骤。
- **工具链阶段**：Rust测试与集成测试 / `cargo install`二进制入口 / SemVer与变更日志 / 依赖诊断报告
- **对象层**：器→门（从内部器胚——到对外发布——"门"——承诺公开）
- **主相→蚀**：式 → 契（测试固定已知承诺，却不能证明未覆盖场景；报告若把有限观测写成处置结论，就可能让读者把建议当保证。）
- **主角状态**：沈见微仍相信写明范围能帮助后来者；卷尾让他第一次看见“尚未列出的未知”，不预知未知的具体内容。

### 第71章：器成可试

- **主对象层**：器→契。测试把已知承诺变成可重复执行的证据，不是对所有输入和环境的证明。
- **迁移来源**：旧 Ch22。保留段迟舟三次运行 `qinglu doctor` 后仍无法判断“更稳是否只是北院自说自话”的质疑，以及四组测试落点：旧别名回滚、桥内外说明一致、旧桥异常状态码、北岭真实样例端到端演练。
- **场景推进**：程知序要求不靠维护者在场也能复核。四个问题分别落进单元、集成、契约和端到端测试；最后一组由第一次收窗的人照 `README`、`--help` 和样例走完。绿灯只证明这些样例与断言通过。
- **工程锚点**：`#[test]`、`tests/`、`cargo test`。`#[cfg(test)]`只作实现细节，不把测试等同完整用户文档。
- **章末**：段迟舟追问“换一台机器，哪些前提还没试？”引出发布前验收。

---

### 第72章：不可信的通过

- **主对象层**：式。发布前验收暴露可复现的接口约定缺口，不以抽象的“环境不同”代替事件。
- **场景推进**：开发机上的端到端样例继承了 shell 中的 `QINGLU_TARGET_ROOT`，因此绿灯；北岭在清洁环境照 README 复走时没有该变量，命令明确停止，因为目标目录未声明。测试通过只证明了带该环境变量的那条路径。
- **修订动作**：增加显式 `--target-root` 参数，为缺少目标目录给出具名失败；清洁环境下运行端到端测试，并更新帮助页。此为发布前验收发现，不与 Ch83 生产事故混为一谈。
- **人物推进**：沿用 Ch11 已建立的 CLI、配置、环境优先级；程知序的清洁环境复走揭示测试夹具继承了开发机状态。
- **章末**：贺时进带来外部交付窗口：若安装入口与迁移说明再延期，北岭本期不会纳入青炉。

### 第73章：法宝传世

- **主对象层**：门。版本号与变更日志表达发布者愿承担的兼容承诺；版本号本身不能判定行为兼容。
- **迁移来源**：旧 Ch23。旧桥从“前提不满足仍顺手重试”改成“拒绝进入”，门外流程依赖重试；拟定的 qinglu-v0.8.1 因此不能当作无影响的修补版。团队延期，补迁移说明、弃用路径与 changelog。
- **规则限定**：项目当前为 0.y.z，须明示自身预发布兼容政策；不把 MAJOR/MINOR/PATCH 机械套用于所有零版本。Cargo 对初始开发版本另有兼容约定，兼容仍须靠项目声明与人工核查。
- **工程锚点**：SemVer、Cargo package version、changelog、deprecation note。Cargo.lock 锁定调用方所解析的依赖版本，不限制发布者今后发布新版本。
- **章末**：延期不再是抽象谨慎，而是门外仍有人走旧桥；下一章先给他们能安装、能判错的入口。

### 第74章：开炉布道

- **主对象层**：门。首发目标是稳定的命令行二进制入口，不是公开 qinglu-core 库 API。
- **迁移来源**：旧 Ch24 已裁定先把二进制入口做实，核心库暂不作为公共依赖；保留用户问单“怎么装、怎么跑、怎么判错”、帮助/版本入口，以及克制公开内部 API 的选择。
- **场景推进**：第一版命令器以 cargo install qinglu 供 Rust 用户安装；发布清单核对帮助页、安装、版本输出、变更日志及回滚说明。区分可安装 package、可执行二进制和未承诺稳定的核心库接口。
- **技术边界**：已发布的具体版本不可覆写；维护者可发布新版本，调用方是否更新取决于依赖约束与锁文件解析。不得写成 Cargo.lock 把发布者锁死。
- **章末**：真实试用者依入口完成安装，却问“这条诊断究竟看见了什么？”转向后续报告线。

### 第75章：贺时进的高峰

- **主对象层**：人。贺时进代表窗口期和短期交付压力，不替主角复述谨慎立场，也不写成轻率反派。
- **具体诱惑**：北岭愿在本期试用青炉，但只留一个交付窗口；他们急需旧桥迁移说明和可用安装入口。贺时进提出先发已通过测试的命令器，把长版迁移手册、额外兼容矩阵和诊断器美化排到下一版，并承诺亲自接收首周反馈。
- **人物选择**：沈见微接受“先交付可复走的安装与回滚说明”，拒绝把旧桥已知破坏行为藏进小字。他保住窗口，却缩小发布范围：只覆盖已验证的北岭样例，不宣传普遍兼容。
- **人物底色**：贺时进指出拖延也让使用者承担旧工具成本；他的判断有现实依据，隐藏的历史创伤不在本章提前揭穿。
- **章末**：苏野平指出遗留项目不可能等所有说明完备才动；争论转到“哪些材料必须随发布，哪些可以边跑边补”。

### 第76章：苏野平与沈见微

- **主对象层**：念。本章不重复 Ch58 的“快与正确”辩论，改讨论遗留脚本的兼容登记与发布责任。
- **具体对象**：苏野平带来一个息壤迁移脚本：它依赖青炉旧桥对不完整输入的再试行为。脚本能跑，但调用来源、失败处理和退出条件未登记。沈见微要求声明接口前提；苏野平认为若每个历史脚本都先补档，团队会困在迁移准备。
- **共同规则**：分三层：立即停止会造成数据损坏或错误成功的路径；可控且可回滚的路径先加观测与负责人；其余脚本在真实运行中补调用记录、维护人和退场条件。缺负责人或回滚路径的项目不得算作“已迁移”。
- **人物推进**：沈见微承认先跑通能产生真实证据；苏野平承认“跑过一次”不等于安全接管。二人形成操作边界，不互相改宗。
- **章末**：迁移清单添上“来源、覆盖、负责人、待核状态”四栏，成为 Ch77 报告的模板伏笔。

### 第77章：诊断报告

- **主对象层**：器→门。诊断器只报告实际取得的数据，不把审核工具写成兼容性判决。
- **迁移来源**：根目录旧 Ch72《青炉诊断报告》提供报告生成场景。`qinglu-diagnose v0.3.1`是独立诊断器版本，不等同于 Ch74 命令器版本；新版稿不迁入旧稿提前泄露的事故细节。
- **实际能力**：`cargo-audit`检查锁定依赖中的已知安全公告；青炉静态分析列出自身公开函数；调用统计来自已接入的外部 Rust crate，观测近三十天。报告不检查完整部署环境，不宣称覆盖所有兼容性；不添加正文尚未出现的 `cargo-deny` 或兼容性检查器。
- **因果缺陷**：旧调用索引连续三十六个月未见某接口的可见调用，最近三十日的已接入明细也无记录；生成器据此标成“可安全废弃”。数据可复核，处置结论却超出数据范围。报告列出观测源、窗口和覆盖说明，并要求接收方核对；强势状态仍与谨慎脚注冲突。
- **信息边界**：读者与沈见微都只知道统计范围有限，不知道具体遗漏了什么、由谁依赖。不得点出玄枢、纪承钧、本地 socket、备份任务或未来事故机制。
- **章末**：报告发往试用团队。程知序问：“接收者去哪里核对？”

### 第78章：免责声明

- **主对象层**：契。将“请人工审核”拆成接收方能执行的核验提示；操作建议不等于报告已能自动验证核验完成。
- **场景推进**：闻衡检查模板，指出扉页只说“请确认依赖与实际调用”，没有列清接收方应查什么。团队提出四项核验：本地调用来源、未覆盖通道、替代路径与回滚条件、核验负责人及结论状态。
- **边界保留**：团队先把核验卡作为报告外附页试用；接收方须提供本地证据才能标为已确认。无证据时维持待核，不把“无记录”改写成“安全”。v0.3.1 已发出，报告字段调整只进入下一版候选，现有报告仍含过强的退役建议。
- **人物推进**：沈见微把免责声明改成核验清单；他仍相信写明就足以让善意读者看懂，尚未意识到“写明”与“被执行”之间的距离。
- **章末**：段迟舟按清单留下本地待核项，却因交付期限暂缓验证。报告将如何被使用仍未闭合。

### 第79章：出山之后

- **主对象层**：门。用真实外部试用结果结束“发布即完成”的幻觉，不提前演出后卷事故。
- **具体事件**：段迟舟在干净账户中安装命令器，查看版本与帮助，再按固定样例运行诊断。安装和样例成功；报告列有统计来源与截止时间，却没把每项接口对应到具体来源，也没说明仍有哪些通道未覆盖，他无法判断“无记录”覆盖了什么。
- **行动结果**：使用者不批准退役建议，标为待核并询问维护者。青炉没有故障，但入口与报告解释不足以支持独立决策；团队登记为下一版任务。
- **避免重复**：本章写外部读者提出可执行问题并暂停决定，不泛论所有未知环境，也不重复 Ch72 的测试差异或 Ch80 的内心主题。
- **章末**：沈见微发现自己能列出几项未覆盖数据，却列不完尚未想到的缺口。

### 第80章：我不知道的

- **主对象层**：念。与 Ch70 已列出的平台、配置和调用边界不同，本章转变是沈见微意识到清单也可能漏掉他尚未命名的未知。
- **场景**：他收到北岭使用者的待核回报，原想按既有清单逐项答复；对方追问“还有哪些数据源你们没想到？”沈见微无法把未知伪装成完整列表，于是把“未知项由接收方补充并留证”写进报告设计议题，不宣称这能消灭未知。
- **人物推进**：他第一次承认自己无法先列全边界；仍须给出可行动的已知步骤，并为未决项保留暂停权。
- **卷尾意象**：记录板上既有已验证栏，也有“尚未辨明”的空栏。青炉带着有限承诺离开北院；卷九从真实运行中的可观测性与事故处置继续，不预告 Ch105 的具体事故。

> 📝 卷尾：四组测试证明已知承诺可复验；二进制入口按有限范围交付；诊断报告暴露“数据正确、建议过强”的落差；外部试用留下待核反馈。玄枢事故及其具体调用机制留待后续目标章位揭示。
