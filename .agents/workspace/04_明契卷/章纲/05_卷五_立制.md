# 卷五「立制」Ch 41-50：trait·泛型·workspace

## Section 总览

- **章段**：Ch 41-50
- **叙事主题**：trait 描述可共享行为，但类型检查不验证语义；泛型与抽象的节制；workspace 与多 crate 协同；顾迁衡管理一座范围明确的兼容桥；闻衡以接口错误类型和边界为样本审契；团队共同起草可修订的门规。
- **核心冲突**：抽象让实现可替换，却可能漏写语义前提。单项样本通过、双项并行时结果顺序错配，暴露 `BuildStrategy` 未声明输出顺序的契约缺口；问题在隔离原型内被发现，不是生产事故。沈见微由此意识到，抽象除了写共同能力，也得写清哪些行为并未承诺。
- **工具链阶段**：trait / generics / trait bounds / workspace / 审契
- **对象层**：骨→阵→门（从类型系统——到多crate协同——到审契——到门规——制度开始成形）
- **主相→蚀**：式 → 失式（过度抽象——结构变成迷宫）
- **主角状态**：沈见微从建制度转向追问制度如何修订、由谁维护，防止审查规则成为新的黑箱。

### 第41章：阵法有门

- **核心对象层**：骨→骨。trait 将可共享行为的签名归在一起；编译器检查实现是否满足签名与类型约束，不验证实现是否符合全部语义预期。内部 trait 是一种抽象选择，不自动成为稳定承诺；对外发布的 trait 按其发布范围和版本政策承担兼容责任。
- **工程锚点**：Rust trait、`impl Trait for Type`、trait bound（`T: Trait`）与泛型约束。避免把 trait 与其他语言的 interface 说成完全等同或完全相斥。
- **六拍骨架**：沈见微解释类型能提供什么，随后承认“能编译”不等于“适用于所有场景”；抽象要等到共同变化需求可见后再提取。

### 第42章：多形之约

- **核心对象层**：骨→骨。trait bound 将泛型函数要求的能力写在签名中，编译器在具体调用处检查实参是否满足约束。
- **工程锚点**：`T: Trait1 + Trait2`。与驭器卷 C++ templates 对照时只描述诊断路径：未显式表达的模板要求可能在实例化时暴露；C++ concepts 也能显式表达约束。不得声称错误总在定义点出现或某语言的诊断必然更清晰。
- **六拍骨架**：玄枢旧模板的一次诊断带出较长实例化链；沈见微承认 concepts 同样可以显式写约束，重点落在需求是否出现在接口上，而非语言优劣。

### 第43章：顾迁衡的桥

- **核心对象层**：门→门。顾迁衡作为渡桥人首次出场，负责兼容桥的生命周期记录，不介入其他世界的内部实现决策。旧构建脚本仍有调用方，故设置范围明确的 `build-shim` 桥接层。
- **工程锚点**：兼容桥（compatibility bridge）、adapter/shim pattern。桥账记录负责人、依赖方、验收条件与复查日期；到期触发复查，不自动拆除。
- **六拍骨架**：顾迁衡写明六个月复查时间和“旧构建脚本调用方均完成迁移”的验收条件；若未完成，须记录依赖、理由及新日期。

### 第44章：临时的

- **核心对象层**：门→门。沈见微看着桥账中的六个月复查栏，担忧依赖方迁移不及或无人负责；这是对眼前桥账的风险推演，不写成已发生的青炉旧桥事故，也不推广为“所有临时桥都会永久化”。跨卷引用只概括可核实事实：化形 Ch42 有七座旧桥及各自状态；简阵 Ch55–56 有模板生成的十二座桥和相关审查问题，不把不同世界经验写成统一规则。
- **六拍骨架**：沈见微指出日期本身不会迁移依赖；责任人须复查调用方、验收迁移，决定拆除或有理由地延期并写入新日期。顾迁衡回应桥账如何支撑跟进。

### 第45章：宗门初立

- **核心对象层**：阵→阵。青炉早在新版 Ch14 已建立 workspace；本章是把后来新拆出的 crate 纳入现有 workspace，而非首次建立。成员仍须显式声明依赖。
- **工程锚点**：Cargo workspace 管理多个 package，可共享根 `Cargo.lock` 与默认构建目录，并提供跨成员命令；它不保证 API 兼容或成员版本号统一。
- **六拍骨架**：沈见微将新增成员登记入根清单，用 `cargo check --workspace` 核验当前成员能否一同构建；版本和接口承诺仍由各 crate 自己说明。

### 第46章：拆骨

- **核心对象层**：阵→阵。`qinglu-cli`、`qinglu-config`、`qinglu-core`、`qinglu-doctor` 已存在；本阶段再抽出 `qinglu-build` 与 `qinglu-report`，不抹去既有成员。
- **工程锚点**：按使用者、职责和变化周期拆 crate；拆分本身不保证兼容，依赖与发布仍按各 crate 的公开接口和版本策略管理。
- **六拍骨架**：程知序只需 build 能力；沈见微把核心、构建和报告边界写清，检查依赖边界是否真的让无关变更互不牵动。

### 第47章：抽象的代价

- **核心对象层**：式→失式。隔离原型的单项样本通过，双项并行样本却把完成顺序误当输入顺序，导致报告将产物配错输入。`KernelStrategy` 保持输入顺序，`BatchStrategy` 按完成顺序返回；两者均满足 trait 签名，编译器不验证这种语义。
- **工程锚点**：trait 约束与行为契约的边界；多项验收样本、稳定顺序承诺或结果请求标识。明确错误在隔离原型中被发现，没有进入生产环境。
- **六拍骨架**：季循用两项输入复现错配；沈见微承认接口漏写排序语义，补充可追溯标识并重审共同抽象，而非把问题归结为某实现“不能安全使用”。

### 第48章：闻衡的尺

- **核心对象层**：门→门。闻衡首次审契一个隔离原型 API，核对输入、输出、错误类型、隐式依赖与承诺失效条件。
- **工程锚点**：`Result<T, E>` 的 `E` 是具体错误类型；区分配置读取、依赖缺失和权限错误，并说明调用者可采取的处理。类型需提供信息，`Result` 本身不替设计者定义错误语义。
- **六拍骨架**：闻衡指出草案只写成功路径；沈见微补上错误变体与处理说明。不要把此原型评审写成程知序已发生过的生产故障。

### 第49章：门规初稿

- **核心对象层**：门→门。团队共同讨论首版贡献规范，先覆盖对外公共 API 的新增或兼容性变化、用户可见的发布记录、错误信息与 `unsafe` 安全论证。
- **工程锚点**：API review / contract review。内部 `pub` 可见性不自动等于已发布的外部 API；changelog 聚焦用户或发布相关变更；错误是否可恢复依具体调用场景判断。
- **六拍骨架**：闻衡提出草案，沈见微和同门补充适用范围、审查替代者及记录方式；规则基于当前原型与评审缺口，不伪装为已发生的生产事故。

### 第50章：立制之后

- **核心对象层**：念→念。制度也须能被修订和交接；门规记录起草者、理由、生效范围及复核条件，避免变成新的不可理解黑箱。
- **六拍骨架**：闻衡与同门共同起草门规；苏野平在“谁来维护这些规则”旁留下问号，推动把维护责任和修订记录纳入草案，承接 Ch51 的 Git 与 review 主题。
