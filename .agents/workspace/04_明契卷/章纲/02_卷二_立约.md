# 卷二「立约」Ch 11-20：工具链即承诺

## Section 总览

- **章段**：Ch 11-20
- **叙事主题**：从工具链选择走向可检查的包声明，再进入ownership、借用与编译器边界。项目文件能呈现部分约定；实际行为、兼容承诺与使用环境仍需人来说明和验证。
- **核心冲突**：立约的代价——"写清楚"意味着"你不能改得随意"。贺时进的诱惑——"先给大家用上"——短期绩效逼迫。沈见微需要在"快"和"对"之间做选择。
- **工具链阶段**：Rust工具链上手 / Cargo manifest初始声明 / ownership与borrow checker入门
- **对象层**：念→约（"写下来"从个人行为——变成公共承诺）
- **主相→蚀**：契 → 约的试行（把部分机器可读的声明写下来，并区分声明、行为证据与团队仍需维护的承诺。）
- **主角状态**：沈见微从救火者变成立约者——"我写的——不止我——后来者会看——会依赖——如果我不写清楚——他们会凌晨爬起来——找bug——像我以前一样。"

### 第11章：铸炉开篇

- **核心对象层**：约→约。沈见微带季循在一台试验机上安装并检查Rust工具链。`rustup`管理工具链的安装与选择；toolchain提供目标平台适用的Rust工具；`rustc`编译代码；Cargo组织项目、依赖与构建，并在构建时调用编译器。单机可调用不证明项目或其他环境已验证。
- **工程锚点**：区分管理器、工具链、编译器和构建/依赖工具；记录机器、所选版本及验证范围。安装成功只证明当前命令可调用，不证明青炉构建成功或发布可靠。
- **六拍骨架**：从空白试验机检查命令→按明确选项安装rustup→选定稳定工具链→分别确认rustc和Cargo可调用→把单机结果与未验证范围写入记录→以“工具已就位，项目尚未开始”为结尾，不调用`cargo new`，将manifest留给Ch12。

---

### 第12章：一纸丹方

- **核心对象层**：约→约。季循建立空项目并检查`Cargo.toml`。manifest包含Cargo需要的包元数据、依赖、目标及features等配置；它是可检查的声明，不是所有运行行为的保证，也不替代scope和用户说明。
- **工程锚点**：区分`Cargo.toml`与`Cargo.lock`：manifest描述包及依赖要求，lockfile记录具体解析结果。版本号本身不通知依赖者或自动定义兼容政策；features、targets和dependencies按实际需要声明，不为显得完整而预填。
- **六拍骨架**：从Ch11已验证工具链建立空包→解释包名、版本与edition的机器用途→围绕是否添加依赖发生争论→保持未使用依赖/features为空→说明scope、发布规则和实现各自承载什么→把manifest夹在范围草案旁，给Ch13的真实需求留出检验空间。

### 第13章：边界经受试用

- **核心对象层**：约→约（Ch09留下青炉首版范围草案，本章不再重写scope；程知序在复核草案时提出一项范围外需要：发布后，她仍想知道使用方实际运行的是哪条版本与环境路径。团队先评估这一提案，再决定是否纳入首版，不假装现有工具已经能回答。）
- **工程锚点**：范围变更管理。将请求者要解决的问题、当前范围、候选方案、数据与运维代价、验证办法、责任人和决策状态分开记录；“登记需求”不等于“纳入首版”，也不等于拒绝未来重谈。
- **张力曲线**：边界受压型。程知序的需要合理且源自错版夜发后的信息缺口；但将运行时观测并入青炉会改变Ch09的非目标。沈见微既不能用“范围外”堵住问题，也不能在没有代价与责任评估时先许诺。
- **六拍骨架**：
  1. 问题先出：程知序希望未来能确认使用方实际运行的版本与环境；Ch09的首版范围草案只覆盖构建、测试和发布，尚待复核定稿。
  2. 为什么痛：没有运行时观测，就可能继续不知道发布之后各处实际走了哪条路；但增加观测也会带来数据、权限、保存和维护责任。
  3. 引出方法：把使用者问题、能力设想、成本、验证条件和决策状态拆开记录，先评估再决定是否改范围。
  4. 项目落地：沈见微登记一项待评估变更，不写成青炉已有功能；在批准范围前，团队先补齐需求与责任问题，再决定是否修订Ch09草案。
  5. 多方复盘：程知序说明她真正需要的是事故后能查清覆盖范围；苏野平估算接入观测的维护代价；闻衡追问数据由谁看、保存多久、怎样验证；没有人在这一章替这些问题填上未经讨论的答案。
  6. 高层收束：边界不是拒绝改变，而是让改变先有理由、代价和负责人。需求已登记，草案尚未定稿，给Ch14“先给大家用上”的催促留下现实压力。

### 第14章：贺时进的声音

- **核心对象层**：人→人。贺时进代表交付压力，也确实关心程知序等待和团队错失反馈的代价。他提出先做一个小型内部原型，让真实需求尽早碰到实现；冲突不简化为“快就是错”，而是原型会不会被误当成可交付能力。
- **核心相与失守**：契 → 约的试行。首版范围草案尚待复核，运行时观测需求也未决。先做可逆的内部实验可以帮助评估；若把实验包装成“能用版本”、接入真实发布路径或让使用方据此作决定，就会在承诺尚未厘清时制造依赖。
- **六拍骨架**：
  1. 问题先出：贺时进指出程知序还在等，团队已经花数日讨论边界，却没有可供反馈的实现。
  2. 为什么痛：只谈文档会让真实使用问题继续悬空；仓促交付又会让一段试验被误认成稳定能力。
  3. 引出方法：区分内部原型、受限试用和正式交付；每种状态写清对象、环境、数据、停止条件和责任人。
  4. 项目落地：团队同意开展一个限时、隔离、使用固定样本的内部原型，用来验证构建/测试/发布路径中一个最小环节；不接真实发布、不收集运行时数据、不对外称可用。具体样本、负责人和复核时间写进试验记录。
  5. 多方复盘：贺时进推动缩短反馈回路；程知序确认这仍不能替代她等待的真实能力；闻衡要求在结果页标明原型未覆盖什么，避免“内部跑通”被抄成“用户环境通过”。
  6. 高层收束：承诺在先不等于动手在后；它要求每一次试验先说清谁能依赖结果、结果能证明到哪里。原型开始，但范围草案与运行时观测提案仍待决。

### 第15章：气入经脉

- **核心对象层**：文→骨。沈见微与季循在内部原型中处理一份报告文本：把 `String` 交给一个按值接收的函数后，原变量不能继续使用。ownership描述程序中值的归属、移动与析构，不等于团队里的业务负责人，也不自动协调跨进程共享文件。
- **工程锚点**：Rust的ownership与move/drop。多数非`Copy`值在赋给新变量或按值传入函数时发生移动；值离开作用域时运行析构逻辑。编译器检查所有权相关的静态规则，但不能据此保证业务决策正确或外部副作用已撤销。
- **六拍骨架**：
  1. 问题先出：季循把原型生成的报告文本交给写入函数，随后又尝试从原变量读取摘要，编译器指出该值已移动。
  2. 为什么痛：若值的有效期和转移方式靠人记，错误可能在后续使用处才显露；但不应把这一编译检查说成解决共享目录竞争。
  3. 引出方法：区分所有权、借用和复制；先说明当前函数是接管值，还是只读取它。
  4. 项目落地：沈见微让季循分别尝试按值传入`String`与保留原变量，观察移动后的可用性；样本报告仍局限于隔离原型。
  5. 多方复盘：韩砺年把“程序里的值归谁”误听成“出了问题由谁负责”，闻衡当场拆开两种责任；苏野平补充，Rust不替团队选择何时删除或保留外部文件。
  6. 高层收束：所有权把一部分程序资源规则交给类型系统检查；它不是组织责任图，也不是运行正确性的证明。季循由此追问：若函数只需要看一眼，是否必须接管整份值？引向Ch16借用。

### 第16章：借与还

- **核心对象层**：骨→骨。季循不想把报告文本的所有权转给只负责统计摘要的函数，改为传入引用。借用让函数临时读取或修改值；引用有效期必须受被引用值与作用域约束。
- **工程锚点**：引用、共享借用与可变借用。安全Rust通常允许多个共享引用，或在相应范围内一个可变引用，避免同时存在会冲突的访问；这不是外部文件锁，也不自动解决多个进程写同一路径。
- **六拍骨架**：沈见微让季循给摘要函数传`&str`，再尝试把引用保存到被引用数据已离开作用域之后。编译器拒绝悬垂引用。闻衡说明生命周期标注描述引用之间的有效期关系，不会延长被引用值的实际生命；这一限制保护的是Rust能追踪的内存访问，不是所有系统资源。

### 第17章：第一次编译失败

- **核心对象层**：骨→骨。原型中的摘要函数试图返回对局部`String`的引用；Rust编译器拒绝可能悬垂的借用。对照只说明不同语言的静态规则不同，不断言任意等价C++代码都能编译或必然随机崩溃。
- **核心相与失守**：式 → 失式。失败暴露的是这段引用关系无法满足有效期要求；编译器没有替团队判断该复制文本、返回拥有值，还是重排数据结构。
- **六拍骨架**：季循先读错误指出的源值与返回位置，再提出两个修复方向：返回自有`String`，或调整所有者与调用关系。沈见微要求他说明选择的代价；“编译通过”只是这一项静态约束通过，不代表样本原型或发布路径已经验证。

### 第18章：程知序的等待

- **核心对象层**：人→人。程知序是错版夜发的直接使用者之一；青炉还停留在隔离原型，旧发布流程仍由团队承受。她并非要求跳过边界，而是要知道何时能从说明和试验走到可参与验证的能力。
- **六拍骨架**：
  1. 问题先出：程知序看过scope草案、试验记录和编译错误，却仍不能用隔离原型处理真实发布。
  2. 为什么痛：她继续承担旧流程的核验与等待；团队学习Rust的代价并没有转移给工具，也没有让她当前工作自动变轻。
  3. 引出方法：把“内部样本通过”“受限试用”“正式支持”分成不同状态，写明每次状态变化需要的证据、使用者参与和负责人。
  4. 项目落地：程知序询问最早何时能参与真实路径验证；团队给出一个有前置条件和复核日的候选里程碑，不承诺无法核验的交付日期。
  5. 多方复盘：她指出即使只支持一条路径，也要让值守者知道何时能停旧路、何处回退；沈见微承认这些工作尚未做完，不能用“原型进展”折抵使用者成本。
  6. 高层收束：写清楚不能代替交付，交付也不能免除说明。程知序仍在等，团队必须把下一步做成可由她检验的东西。

### 第19章：誓约初成

- **核心对象层**：约→约。内部原型走过固定样本后，团队回看Ch12的初始manifest：哪些包元数据、目标、依赖与features确实需要由Cargo读取，哪些行为承诺仍应写在scope或面向使用者的说明中。Cargo.toml可供协作者检查，但不自动发布、不替团队定义兼容政策，也不会因为版本字段变化就逐个通知依赖者。
- **工程锚点**：依据实际原型校准初始Cargo manifest与版本维护规则。`[package]`、目标、依赖与features只描述各自配置职责；不因“公开誓约”比喻而把所有字段都称作用户保证。是否发布、如何说明破坏性变化、何时升级版本由团队的兼容政策和发布流程承接；锁文件记录解析结果，另有职责。
- **六拍骨架**：
  1. 问题先出：贺时进想把当前版本号写大，作为青炉即将交付的信号；但原型仍只覆盖固定样本。
  2. 为什么痛：版本数字容易被当成成熟度或兼容承诺，Cargo不会替项目判断这些语义。
  3. 引出方法：逐项核对manifest中机器需要读取的配置，再把支持范围、已知限制和兼容规则写在相应的人类可读说明中。
  4. 项目落地：团队保留与当前状态相符的包版本，不虚构尚未使用的依赖或features；为未来版本变化起草团队政策，但标为待实际发布流程验证。
  5. 多方复盘：程知序指出，即使版本、目标和依赖写得清楚，她仍不知道自己的运行环境是否经过验证；manifest审阅不能代替环境证据。
  6. 高层收束：这是一份能被检查的初始声明，不是交付完成或自动生效的承诺。Ch20转向“写下了本方声明，仍不知道对方世界”的裂缝。

### 第20章：立约之后

- **核心对象层**：念→念。程知序把Ch01的三份回铃与青炉的包声明并排：版本字段能识别一个包版本，却不能证明三处实际加载了相同产物、旧入口或运行条件一致。沈见微第一次怀疑“写在本方纸上的清楚”能否覆盖使用者的世界。
- **六拍骨架**：
  1. 问题先出：程知序问，如果另一个环境报告相同包版本，青炉是否能据此说它运行了同一条路径。
  2. 为什么痛：Ch01的三处结果已说明相同标记不等于相同观察；当前原型没有真实路径或跨环境证据。
  3. 引出方法：把包身份、实际产物、运行条件和用户观察分开记录，不由版本号替代其他证据。
  4. 项目落地：团队写下下一阶段需要的环境清单与可复走证据作为待设计项；不预填支持平台、组件或通过状态。
  5. 多方复盘：程知序指出scope、manifest与原型记录分别有用，却都不能单独说明她的现场；沈见微承认使用者证据要进入验证过程。
  6. 高层收束：立约让一部分声明有处可查，也暴露声明边界。卷二不以“已经可靠”收尾，而以“下一步要在代码与真实使用条件中验证”转入卷三。

> 📝 卷尾。Cargo.toml定稿——ownership/borrowing入门——borrow checker第一次拦门——程知序的使用者视角——"写清楚"的第一个裂缝。向卷三（成形——module/Option/Result——季循误用unwrap，将Err路径转成panic）过渡。
