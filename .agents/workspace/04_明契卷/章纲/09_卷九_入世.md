# 卷九「入世」Ch 81-90：守望运行·报告失效·恢复验证

## Section 总览

- **章段**：Ch 81-90
- **叙事主题**：青炉从一次性命令进入长驻守望；北岭报告写回受旧锁阻塞，旧成功状态掩盖本轮失败；观测追出根因，团队修复状态语义并由后来者复验。
- **核心冲突**：运行进程还活着，不等于本轮检查成功；守望锁已取得，不等于报告写锁已取得。旧实现的锁和状态契约没有区分，导致失败看起来像成功。文档缺口放大影响，但不能替实现缺陷免责。
- **工具链阶段**：生产运行 / 观测（tracing/metrics/logging） / 事故诊断
- **对象层**：门→阵（从发布——到在生产中运行——到观测——到"事故"——青炉不只是工具链——是运行中的系统）
- **主相→蚀**：流 → 契/背契（旧锁状态与新守望运行形态不相容；失败被旧状态掩盖，责任边界随之模糊）
- **主角状态**：沈见微承认错误不只是“别人没读懂”：实现、状态展示和恢复步骤都须让使用者分辨本轮是否成功。

---

### 第81章：入世之后

- **主对象层**：阵。旧 Ch25 映射至此。青炉从一次性命令走向流水线和长驻守望，区分进程存活、单轮任务完成与报告成功。
- **场景推进**：北岭希望将 qinglu check 接入夜间发布流水线、让 doctor 定时深查，并试用长驻守望。韩砺年用旧抄片说明：工作目录、权限或残留锁变化，都可能让进程仍活着、却已不可信。
- **工程约定**：一次性命令、流水线调用、daemon 分开定义；长驻守望写明工作目录、唯一守望锁、轮询和退出条件。守望锁不等于报告写锁，单轮结果不等于长驻进程状态。
- **章末**：段迟舟启用北岭夜间深查。某周期结束后，总览仍显示上次成功状态，修正后的报告却迟迟未出现。

### 第82章：观天察地

- **主对象层**：阵。旧 Ch26 的观测体系建立与事故初查迁入此章；把“表面正常、结果缺失”变成可追踪的问题，不在此重复完整根因复盘。
- **事件证据**：远端只回传 doctor started / finished / report flushed 三条粗日志，无法说明报告是否写成。团队先列流程步骤：读配置、选模式、解析工作目录、取得守望锁、运行 doctor、生成 CheckPlan、写回报告、返回本轮状态。
- **观测动作**：增加 run id、关键步骤标记，以及报告写锁等待、CheckPlan条目数和实际写出报告数等少量指标。每项信号对应待回答的问题，不把日志、追踪、指标当作自动根因结论。
- **揭示节奏**：追踪显示 doctor 已完成，却连续出现 report_write_retry；报告写锁等待远高于此前。守望锁取得记录为真，但本轮没有 report_written。旧总览仍沿用上一轮的零状态。
- **章末**：证据把问题收窄到报告写回与状态呈现；旧锁语义尚未查清，引向 Ch83。

### 第83章：第一次炸

- **主对象层**：流→契。这里是青炉长驻报告链第一次本地生产故障，不是全系列首次生产事故，也不与新版Ch105玄枢事故混为一谈。
- **迁移来源**：沿用根目录旧 Ch26 的同一故障，不另造并发配置数据竞争。追踪与锁等待记录显示，旧守望遗留的单机发布锁标记未清，报告写回仍按旧锁语义等待；watch_lock_acquired 只证明守望进程取得自身唯一锁，不证明报告写锁已取得。
- **事故结果**：doctor 核心检查完成，但报告没有写出，本轮最终状态也未记录；总览沿用上一轮成功的零状态，使“本轮无结果”看起来像“本轮仍成功”。段迟舟等了半日仍拿不到修正报告。
- **技术边界**：明确这是锁生命周期和状态语义的实现缺陷；不称为 Rust 内存 data race，不归咎于使用者设置 concurrency。具体锁标记如何产生、清理条件如何失败，沿用旧 Ch26 已有证据，不补造 unsafe 路径。
- **章末**：团队拆分守望锁、报告写锁和每轮结果状态，决定先恢复可靠写回，再讨论长期扩用。

### 第84章：半日无报

- **主对象层**：人。聚焦使用者承担的时间和判断成本，不新增旧稿没有支持的用户数据损失或 02:00 事故时间。
- **场景**：程知序接过段迟舟半日未收到报告的回报。总览页曾让人以为检查已通过；他不得不回到原始工件和运行记录手工确认哪些结果仍有效，暂停下一步发布判断。
- **人物关系**：沈见微先解释旧锁，再停下；解释不能替代段迟舟错过的窗口和被迫进行的手工核对。程知序指出，使用者需要先知道“本轮没有结果”，不必先理解锁的历史。
- **章末**：沈见微接受先给每轮独立状态、失败显式呈现，再整理帮助页和恢复步骤。

### 第85章：谁的错

- **主对象层**：契→背契。复盘区分直接缺陷与影响放大的边界，不把代码故障改写成“只是文档不足”。
- **根因层次**：近因是旧锁语义阻塞报告写回，系统没有把失败写成当前周期状态；放大因素是总览复用上次成功状态、帮助页未教使用者判别“进程活着”与“本轮成功”，让失效持续不可见。
- **修改**：每轮单独写成功或失败；报告写锁失败时不得发布旧成功状态；进程退出码仅说明长驻进程如何离场。同步增加锁等待异常和缺失report_written的诊断提示、恢复步骤及复核责任人。
- **人物推进**：沈见微承认责任分在实现、状态展示和交接步骤上；文档说明不能替代代码修复，代码修复也不能替代可读的恢复路径。
- **章末**：闻衡要求由未参与实现的人复走故障与恢复，季循主动接下验证。

### 第86章：季循的成长

- **主对象层**：人→契。季循独立负责一组回归验证，不以“补一张生产清单”代替修复证明。
- **可复现场景**：在隔离环境预置旧报告锁标记，启动一轮深查；确认doctor可以完成、报告写回会重试，且本轮状态必须显示失败或待恢复，不能沿用上轮成功零值。
- **独立修复**：季循补上锁超时与清理状态检查，并让报告写入成功后才更新本轮成功状态。清理前必须有证据确认持有者已退出或锁已失效；无法确认时停止操作并升级，不默认删除锁文件。失败路径保留可追查原因。
- **外部复走**：他先按工程经验写步骤，再交给段迟舟照帮助页在干净账户复跑；段迟舟指出“如何确认上轮状态已失效”仍不清楚，季循据此补充状态检查项。
- **章末**：闻衡要求记录测试所覆盖的锁状态与仍未验证的异常退出情形，不把有限样本写成全面安全证明。

### 第87章：贺时进退缩

- **主对象层**：人。贺时进担心继续扩用会把使用者置于风险中；他提出暂停新增守望接入、先保留已验证的北岭试点，并安排人工复核作为短期恢复措施。
- **现实代价**：暂停扩用会错过下一轮采用窗口，也让其他团队继续靠旧工具；继续扩用则要求当前值守者承担未验证锁状态的风险。两边都不是零成本。
- **共同决定**：沈见微接受暂缓新增接入，但不撤销已修复的北岭试点；设定恢复条件为故障路径复现、异常本轮状态可见、外部使用者能按说明恢复。贺时进负责告知排期变化并承担窗口代价。
- **章末**：闻衡将恢复条件带入审契，不把“试点已恢复”说成“所有环境均安全”。

### 第88章：闻衡的裁决

- **主对象层**：契。事故既有实现缺陷，也有未说清的状态前提；裁决不替任何一端免责。
- **裁决内容**：守望进程取得锁，不等于每轮报告锁成功；doctor 完成，不等于报告已写出；上次成功状态不能代表当前周期。每个状态必须命名所属层次、更新时机和失败表现。
- **行动检验**：不再重复注入故障。闻衡以 Ch86 留存的失败记录和外部复走记录逐项对照状态契约，确认旧成功值未被冒充为当前结果；证据未覆盖的状态留待核实。
- **章末**：闻衡要求把分层契约写入运行手册和维护规则，供下一位值守者复走。

### 第89章：灰烬中的火

- **主对象层**：念→史。把事实、近因、放大因素、修复和未验证项放在同一份事故记录里。
- **记录边界**：保留 run id、关键步骤、报告写锁等待和 report_write_retry 作为证据；分别写明守望锁与报告锁；不把“进程活着”记成“本轮成功”，也不把此次事故外推到其他服务或环境。
- **人物行动**：段迟舟确认报告恢复后才重启后续流程；季循署名回归样本；贺时进记录试点暂停造成的排期代价；沈见微补上旧锁语义的退场责任。
- **章末**：记录板留下的不只是“不要重犯”，还有如何发现、如何止损、谁来复核。

### 第90章：每轮之后

- **主对象层**：念→契。卷尾以恢复证据和余留债务收束，不重复“世界未知/下一次更大”的感叹。
- **恢复闭环**：引用 Ch86 已完成的限定路径复走记录，不再重复故障注入。Ch90确认后续试点按 run id 与报告对应关系核验；恢复页写明锁持有者确认条件，证据不足时停止清理并升级。
- **未结事项**：仍有其他守望目录和历史锁状态未核；登记责任人、复查期限与停止条件，不把一处验证推广成全量安全结论。
- **卷尾过渡**：将 `single-host-release-lock` 的兼容行为和下游依赖列为独立技术债交给 Ch91；明确它不是顾迁衡账上的普通迁移桥。
