# 卷四「筑基」Ch 31-40：目录结构·配置·文档

## Section 总览

- **章段**：Ch 31-40
- **叙事主题**：从“能用”到“可维护”——crate边界、候选公共API、配置管理、文档体系。旧注释“此处逻辑不应被文档化”再次出现；沈见微记录可见原文、位置与查证过程，把作者、时间、对象和意图留作未知。梁故川的名字首次由韩砺年提起，但须交代说话者所知范围。
- **核心冲突**：文档写得过多且无人维护，可能过时并误导；写得过少，后来者只能反复追问。沈见微尝试记录决策缘由、适用前提和待核问题，却不把文档当作替后来者判断的答案。
- **工具链阶段**：crate边界 / workspace / config/env/CLI / 文档体系
- **对象层**：器→阵（从单个crate——到多crate workspace——"器不是孤立的——器在阵中"）
- **主相→蚀**：史 → 断史（旧注释造成记录缺口；是否出自梁故川、为何留下，现阶段均未证实）
- **主角状态**：沈见微开始建文档，也开始区分可观察事实、当时判断、适用前提与未知；他担心记录被误当成永久答案，但不把猜测写成旧注释作者的动机。

### 第31章：骨架初定

- **核心对象层**：器→阵（目录结构与核心抽离——crate边界。目录能让读者初步辨认库、可执行程序、测试和示例的位置；它不能单独说明项目行为、设计理由或全部边界。）
- **工程锚点**：Cargo 常见布局：`src/lib.rs` 为默认库根，`src/main.rs` 为默认可执行入口；额外二进制、集成测试、示例和基准测试可分别放在 `src/bin/`、`tests/`、`examples/`、`benches/`。这是帮助他人进入项目的惯例；实际目标也受 manifest 配置影响。若青炉已有 CLI，则抽出库核心是为了让二进制入口与可复用逻辑分责，不重演 Ch21 的单 crate 模块拆分。
- **六拍骨架**：沈见微不以“看目录便能懂项目”为完成标准；他把可复用核心与 CLI 入口分开，再用测试和简短说明验证边界是否可辨。

---

### 第32章：藏与露

- **核心对象层**：门→门（决定哪些路径构成候选公共接口，并说明可见性、发布状态、实际可达性和兼容政策的差别。）
- **工程锚点**：Rust 的 `pub` 控制可见性；它本身不等同于已发布的兼容承诺。是否形成兼容责任还取决于项能否从公开路径到达、库是否发布、调用方是否依赖该 API，以及项目明确的版本政策。避免宣称每个 `pub` 永远稳定或只能在 MAJOR 版本改变。
- **六拍骨架**：沈见微逐项审计核心 crate 候选接口。若保留“26项”这一数字，正文需说明它来自本次代码审计范围，并区分被移除的可达接口与 crate 内部公开项；删减理由是当前不需要承担这批 API 的维护责任，不是逐项都已对外承诺。

### 第33章：炉候可调

- **核心对象层**：器→器（配置、环境与命令行参数——config/env/CLI。"不是'写死在代码里'——是'让使用者在自己的环境里——设定自己的值'。默认值在代码里——但可以被覆盖——因为使用者的世界——和我的世界——不一样。"）
- **工程锚点**：配置管理——`clap`（CLI参数解析）/ `toml`/`serde`（序列化）/ 环境变量——"配置不是'让程序灵活'——是'承认——我不知道使用者的世界是什么样的——所以我给他们——调整的空间。'"
- **六拍骨架**：沈见微加了独立 TOML 运行配置文件，并让环境变量补充、CLI 参数覆盖文件值，形成 CLI > 文件 > 环境变量 > 代码默认值的优先级；帮助信息和示例说明各层如何覆盖。`Cargo.toml` 继续描述包和构建，不存放应用运行时配置。

---

### 第34章：默认值的重量

- **核心对象层**：史→史（一个默认值引发的用户困惑——与简阵卷Ch66"512MB的默认值"形成跨卷对照。"我设了一个默认值——30秒超时——我以为合理——但使用者场景是批处理——需要等几分钟——他的请求一直超时——改了——设了300——才能跑。"——默认值——是我的世界的合理——不是他的世界的合理。）
- **六拍骨架**：沈见微把超时默认值的选择依据、目标场景和需要重新评估的信号写下来；引用温故来与 512MB 时，只复述简阵卷现有证据：温故来维护的模板含这一默认值，选择依据尚未找到。不得将“未找到”说成“从未留下”，也不把该案例简化为仅仅因环境变化而失效。

---

### 第35章：旧注释（史约锚点深化）

- **核心对象层**：史→史。沈见微以 `git log --follow -- <path>` 定位文件版本，再用 `git show <commit>:<path>` 查看提交中的文件快照；`git reflog` 只用于追踪本地引用移动，不直接恢复文件文字。历史显示注释随代码迁过一次，提交说明没有解释注释的作者或来历。
- **证据边界**：旧版本只确认那行注释曾与相关代码并存；提交作者不等于注释作者，迁移记录也不揭示动机。不要再增加“被删去的解释性文字”或把特定担忧写成已知史实。梁故川动机仍未证实；后续可整理新增材料与人物假说，但不得为收束而强行揭谜。
- **六拍骨架**：沈见微把原文、文件位置、提交和版本差异抄入待核页；他可以提出若干工作假说，但须标明它们是他的猜测，不从空白倒推出旧作者的想法。

### 第36章：待查·未知

- **核心对象层**：史→史（沈见微留下待查问题：这句注释针对什么逻辑？如果它是警告，风险是什么？谁写下它，后来为何不再展开？）
- **六拍骨架**：本章不揭示梁故川完整动机。沈见微可以提出关于“条件性记录被当成永恒承诺”的假说，同时注明证据不足；后续章节可继续核对相关材料；若没有新证据，人物动机和旧注释意图保持未知。

---

### 第37章：经卷留痕

- **核心对象层**：文→史（文档、注释与项目记忆——文档体系建立。"不是写一本书——是写——'后来者——从这里开始——这样读代码——这样加功能——这样测试——这样发布'。"不是理论——是实践——每个文档——回答一个具体的问题。）
- **工程锚点**：README（项目概述与快速开始）、CONTRIBUTING（贡献和验证流程）、架构说明/ADR（设计决定及其上下文）、Rust 文档注释生成的 API 文档、必要的运维说明。文档测试能编译/运行被标记的示例；通常 `cargo test` 会运行库的文档测试，但 target 配置或调用参数可改变覆盖范围，且通过测试只证明所覆盖示例仍可执行。
- **六拍骨架**：沈见微写ARCHITECTURE.md——"不是写'做了哪些决定'——是写'为什么这样决定——当时考虑了什么替代——为什么没选替代——此决定在什么前提下成立——前提改变时——重新审视。'"

### 第38章：写多少才算够

- **核心对象层**：念→念（文档过度与不足之间的张力。"写太多——文档变成负担——没人维护——过时——变成误导。写太少——后来者看不懂——又要'问沈见微'。中间在哪里？——不是写所有——是写——'后来者最可能卡住的地方'——和'为什么'——而不是'是什么'——'是什么'在代码里——'为什么'——不在。"）
- **六拍骨架**：沈见微提出工作分工：代码呈现当前实现，文档补充代码难以表达的缘由和前提，测试固定被覆盖的可观察行为。三者各有盲点；后来者仍需核对当前环境和未覆盖情况。

---

### 第39章：梁故川的影子

- **核心对象层**：史→史。韩砺年首次说出梁故川的名字，并区分亲眼所见、记忆、转述与推测。他至多能确认自己记得的记录板变化或离场片段；若说“他曾写 scope/为什么”或解释其停止记录的缘由，须标明信息来源与不确定度。不得在本章把“怕后来者把文档当真理”确立为事实。
- **六拍骨架**：韩砺年承认“不知道他为什么走”。沈见微把现存注释能支持的担忧与尚未证实的动机分开记录；读者看到的是一个历史断口，不是提前揭晓的答案。后续章节可补充可核材料，但不承诺揭示离开原因；证据不足时保留历史断口。

### 第40章：筑基之后

- **核心对象层**：阵→史。青炉完成一轮有限的可维护性整理：核心与入口职责较清楚、候选 API 收敛、配置来源有序、重要决定和未知被记录；这些成果不等于所有接口已发布、所有运行环境受支持或所有知识都已传承。沈见微比较自己的做法与梁故川留下的断点，但不声称已知对方完整经历。卷尾转入 Ch41 的 trait 抽象问题；后续跨卷传讯按现行锚点处理，不提前锁定旧蓝图章号。
- **六拍骨架**：卷尾保留沈见微的未决问题：记录前提和失效条件是否足以帮助后来者继续判断？他选择暂时继续记录，也承认这种方法仍需在使用中检验。
