# 明契卷 · 第42章 · 多形之约

沈见微把 `fn process<T: Display + Debug>(item: T)` 写在纸上，递给季循看。trait bound 不是"接受任何类型"，而是"接受任何实现了 Display 和 Debug 的类型"。函数要什么能力，签名里已经写出；编译器会在具体调用处检查传入类型是否满足，但不会保证所有错误都在函数定义处出现。

季循拿来一张批次票，想把它交给`process`。沈见微把例子压到一只小试验crate里：

```rust
use std::fmt::{Debug, Display};

struct BatchTicket;

fn process<T: Display + Debug>(item: T) {
    let _ = item;
}

fn main() {
    process(BatchTicket);
}
```

诊断停在调用处：`BatchTicket`没有实现`Display`和`Debug`，因此不满足`process`声明的边界。季循给这个类型补上所需实现后，调用才有资格通过编译。问题不是函数定义写错了，而是这次调用没有提供接口要求的能力；编译器替他们拦下了这一处，未替团队判断这些约束是否适合所有未来输入。

苏野平问，这是否说明Rust总能给出更清楚的诊断。沈见微摇头：“不能这么推。在C++里，未显式写出的模板要求有时要到具体类型实例化时才暴露，诊断可能带出很深的调用链；concepts也能把约束先写出来。我们眼前这次，只能说明显式写在接口里的要求会在具体调用时受检查。接口把要求写明，后来者就有机会先看见；不能保证哪种语言的每次诊断都更清楚。”
