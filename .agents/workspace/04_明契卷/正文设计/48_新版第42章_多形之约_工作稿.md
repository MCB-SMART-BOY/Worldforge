# 明契卷 · 第42章 · 多形之约

沈见微把 `fn process<T: Display + Debug>(item: T)` 写在纸上，递给季循看。trait bound 不是"接受任何类型"，而是"接受任何实现了 Display 和 Debug 的类型"。函数要什么能力，签名里已经写出；编译器会在具体调用处检查传入类型是否满足，但不会保证所有错误都在函数定义处出现。

与驭器卷 C++ templates 形成跨卷对照——在玄枢，模板函数体里的类型要求有时没有写在接口上，要到具体类型实例化时才暴露，诊断也可能带出很深的模板调用链。在 Rust，trait bound 把要求写进函数签名；调用处缺少所需能力时，编译器通常能直接指出这次调用不满足约束。C++ 的 concepts 也能显式声明约束，两种语言的诊断质量都取决于具体代码和编译器。

"这不只是编译器的便利，也改变了要求怎样被看见。某些 C++ 模板错误会到具体实例化时才暴露，回溯也可能很长；显式约束能让接口先把要求摊开。Rust 的 trait bound 也不是在定义点替调用者解决一切——调用不满足时，编译器仍会在具体使用处报错。两种语言都能表达约束，只是写法和诊断路径不同。长期协作的接口适合把要求先写明，临时试法则不必急着背上同样的抽象重量。"
