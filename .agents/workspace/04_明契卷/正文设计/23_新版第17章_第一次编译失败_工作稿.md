# 新版第17章《第一次编译失败》工作稿

> **状态：工作稿，不是正式正文。** 承接Ch16的只读借用。本章让一个局部`String`的引用试图逃出其有效范围，展示编译器拒绝悬垂引用；修复仍由人物决定返回自有值还是调整调用关系，不把“Rust拒绝、C++必崩”写成普遍结论。

---

摘要那行代码已能读取报告，试验记录也补上了“仅限固定样本”。季循接着写一个小函数，想把报告的第一行交给调用者：

```rust
fn first_line<'a>() -> &'a str {
    let report = String::from("sample check: passed");
    report.as_str()
}
```

镜面没给他熟悉的通过回铃。编译器指出，返回的引用指向函数内部创建的 `report`；函数结束时，这个值就离开作用域，引用不能带着它留下。

季循盯了很久。“可我只把第一行借出去，又没有把整份报告搬走。”

“借用不能让值多活一刻。”沈见微说，“函数结束时，`report`的作用域结束；它的字符串存储随后会被析构。引用若还指着那里，就没有有效对象可读。”

苏野平问：“换成C++，会怎样？”

“不能把两门语言的代码和规则一对一替换。”闻衡说，“C++允许程序员用指针或引用表达很多关系，也把相当一部分有效期责任留给编写者；写错时可能形成悬垂引用，但不意味着所有类似代码都能编译，或必然以同一种方式崩溃。这里我们只看Rust指出的这一处关系。”

季循把错误位置抄到记录上，没有立刻修。他先列出两个真正不同的需求：如果调用者需要保存文本，就由函数返回一份拥有的 `String`；如果调用者只需要查看，函数就接收一份仍有效的借用，再在原值存活期间使用它。

“哪一种更合适？”程知序问。

“看调用关系。”沈见微说，“返回`String`要让值有一个明确的新主人，也可能需要复制或重新组织数据；借用能避免转移所有权，但调用者不能把它留得比原值更久。编译器只告诉我们当前写法不成立，不替我们选产品接口。”

季循决定，原型的报告摘要只在创建报告的步骤里读取，不需要从函数返回借用。他把摘要计算移到 `report` 仍有效的范围内，另一个需要保存的结果则返回 `usize`。修改后编译通过。

“这次它告诉我的不是‘你写错了一个符号’。”季循说，“而是我想让引用活得比它指向的值更久。”

“是这段代码的具体问题。”闻衡提醒，“别把它扩大成‘任何编译失败都说明设计不清楚’。也别把编译成功当成整个原型正确。”

季循在试验记录里写下：**此改动解决引用有效期；仍须检查摘要是否符合需求，并继续验证固定样本路径。**

贺时进看着两次失败、一次通过的记录。“外面只看到你们今天编译失败了两次。”

“那就告诉他们为什么失败、改了什么、还有什么没验。”程知序说，“要是只展示最后那句‘通过’，我们又回到昨夜那张只报成功的回铃。”

镜面上只亮着一个样本的构建结果。它没有替团队证明需求正确，也没有证明用户环境已支持；但这一次，失败停在了代码边界被检查的地方，没有被改写成更大的承诺。

沈见微把报错和修复一起收进原型记录。季循在旁边添了一行：“编译器指出有效期冲突；接口选择由我们负责。”

### 编辑核验备注

- 示例函数返回引用到局部`String`的切片，Rust拒绝该悬垂引用；此处不需要声称C++对应代码必然崩溃。
- 两个候选修法分别是返回拥有的`String`或调整借用关系，使引用只在原值有效期间使用；选择取决于接口需求和成本。
- 编译通过只表示当前静态检查允许该程序；摘要语义、原型功能、真实环境和发布承诺仍需独立验证。
- 本章延续内部固定样本原型，不宣布用户可用版本；Ch18应引入程知序对交付等待的现实压力，而非再次重复同一编译错误。
