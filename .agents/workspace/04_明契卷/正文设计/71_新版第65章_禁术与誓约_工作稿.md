# 明契卷 · 第65章 · 禁术与誓约

青炉需要调用一个几十年前写成的 C 库来解析北岭设备集群发来的旧协议帧——不是 Rust 不能解析这种格式，而是这个既有实现的接口使用裸指针和手工内存管理。已核验的旧版通过 FFI（Foreign Function Interface）调用时，要跨过 Rust 编译器保护边界——因此必须用 `unsafe`。

前几日停下的那份PR仍没有库名和版本。沈见微把退件记录放到一旁：“今天只论证这条资料齐全的协议库路径。它是否就是那份PR涉及的组件，现有材料还不能证明。”

Rust 的 `unsafe` 不是“关闭编译器检查”，而是标出编译器无法替人证明的安全前提。这里越过安全边界的具体动作，是调用旧 C 函数并依照它的约定处理裸指针；块内其余代码仍接受 Rust 通常的类型检查。编译器不会替他们验证指针指向的内存是否有效、返回缓冲区归谁所有，这些责任必须由调用约定和安全论证接住。

沈见微在 `unsafe` 块旁写下安全论证（safety comment），说明代码依赖哪些前提、凭什么认为它们成立。他又在对外函数的文档中补上 `/// # Safety` 段，列明调用者必须满足的条件；具体 `unsafe` 块旁则用 `// SAFETY:` 解释本处操作为何满足条件。这些是常见的记录方式，不是所有项目都必须采用同一格式。

那段文档要求调用者保证 `input_ptr` 非空、正确对齐，并指向至少 `len` 字节的有效内存；输入只借用，不转移所有权。C 函数另行返回的 `output_ptr` 可以为空；非空时，只有在它确由 C 分配并转交所有权的前提成立时，Rust 封装才接管缓冲区，并在 `Drop` 中恰好释放一次。

他们把分配与释放逐项对上：这份已核验的旧版由 C 侧通过 `malloc` 分配缓冲区，再把所有权交给 Rust 封装；封装在 `Drop` 中用匹配的 `libc::free` 恰好释放一次，借用的 `input_ptr` 不归它释放。C 侧的 `const uint8_t*` 对应 Rust 侧的 `*const u8`。旧版维护说明称解析函数可重入；已检查的调用路径也没有发现共享全局缓冲区，但这些结论只适用于该版本和路径。若新版本改变分配方式、返回内存的所有权或并发行为，`Drop` 契约就必须重查。若函数返回空的 `output_ptr`，Rust 侧把它转换为 `Option::None`；类型会暴露缺失分支，怎样呈现或处理仍由调用方决定。

沈见微在复核页末写道：`unsafe`不是安全证明。它标出编译器无法替人验证的边界；安全责任仍须由调用约定、论证和复核承担。C库升级、目标平台改变或并发方式变化，都可能使旧前提失效，届时必须重新论证。
