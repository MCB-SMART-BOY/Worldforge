# 明契卷 · 第65章 · 禁术与誓约

青炉需要调用一个几十年前写成的 C 库来解析北岭设备集群发来的旧协议帧——不是 Rust 不能解析这种格式，而是这个既有实现的接口使用裸指针和手工内存管理。已核验的旧版通过 FFI（Foreign Function Interface）调用时，要跨过 Rust 编译器保护边界——因此必须用 `unsafe`。

Rust 的 `unsafe` 不是“关闭编译器检查”，而是标出编译器无法替人证明的安全前提。这里越过安全边界的具体动作，是调用旧 C 函数并依照它的约定处理裸指针；块内其余代码仍接受 Rust 通常的类型检查。编译器不会替他们验证指针指向的内存是否有效、返回缓冲区归谁所有，这些责任必须由调用约定和安全论证接住。

沈见微在 unsafe 块旁边写了安全论证（safety comment）——不是随口说"这是安全的"，而是说明这段代码依赖哪些前提、为什么这些前提成立。他为对外暴露的 unsafe 函数写 `/// # Safety` 文档段，列明调用者必须满足的条件；在具体 unsafe 块旁则用 `// SAFETY:` 解释本处操作为什么满足条件。这是社区常用的记录方式，不是每段 unsafe 代码都必须套用同一种注释格式。

"`/// # Safety`——调用者必须保证输入指针 `input_ptr` 是非空的、正确对齐的、指向至少 `len` 字节的有效内存。这个输入只借用，不转移所有权。C 函数另行返回的 `output_ptr` 可以为空；非空时，若它指向由 C 分配并转交所有权的缓冲区，Rust 侧封装才接管该缓冲区，并在 `Drop` 中恰好释放一次。"

"C 库的生命周期——谁分配内存、谁负责释放要成对写清。这个已核验的旧版由 C 侧通过 `malloc` 分配缓冲区，再把所有权交给 Rust 封装；封装在 `Drop` 中用匹配的 `libc::free` 释放，且只释放一次。借用的 `input_ptr` 不归它释放。参数类型——C 侧 `const uint8_t*` 对应 Rust 侧 `*const u8`。旧版维护说明称解析函数可重入；我们检查过的调用路径也没有发现共享全局缓冲区，但这只适用于已核验的版本和路径。新版本若改变分配方式、返回内存的所有权或并发行为，原有 `Drop` 契约必须重新检查。失败模式——如果 C 函数返回空的 `output_ptr`，Rust 侧转换为 `Option::None`；调用方仍须明确决定如何呈现或处理这个缺失状态，类型会暴露分支，却不替团队选定业务动作。"

"unsafe 不是禁区——是签字画押。你越过编译器保护边界——必须自己留下承诺和论证。不是'我认为它安全'——是'以下是基于什么验证它是安全的——在这个前提下——此论证成立。后来者——如果前提变了——例如 C 库升级了、目标平台变了、并发模式变了——请重新论证。——前提可能不成立。"
