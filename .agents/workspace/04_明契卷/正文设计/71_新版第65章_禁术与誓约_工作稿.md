# 明契卷 · 第65章 · 禁术与誓约

青炉需要调用一个几十年前写成的 C 库来解析北岭设备集群发来的旧协议帧——不是 Rust 不能解析这种格式，而是这个既有实现的接口使用裸指针和手工内存管理。通过 FFI（Foreign Function Interface）调用它时，要跨过 Rust 编译器保护边界——因此必须用 `unsafe`。

Rust 的 `unsafe` 不是"关闭编译器检查"——是"我在此处自负其责"。`unsafe` 块内的代码仍然受 Rust 的大部分安全检查约束——但它允许你执行安全 Rust 不允许的操作，例如解引用裸指针、调用 unsafe 函数、访问可变静态变量、实现 unsafe trait，以及读取 union 字段。编译器不会替你验证这些操作是否满足安全前提；`unsafe` 标记的是由程序员承担这项论证责任，不是编译器替你背书。

沈见微在 unsafe 块旁边写了安全论证（safety comment）——不是随口说"这是安全的"，而是说明这段代码依赖哪些前提、为什么这些前提成立。他为对外暴露的 unsafe 函数写 `/// # Safety` 文档段，列明调用者必须满足的条件；在具体 unsafe 块旁则用 `// SAFETY:` 解释本处操作为什么满足条件。这是社区常用的记录方式，不是每段 unsafe 代码都必须套用同一种注释格式。

"`/// # Safety`——调用者必须保证传入的指针 `ptr` 是非空的、正确对齐的、指向至少 `len` 字节的有效内存。这个输入参数只借用，不转移所有权；若 C 库另行返回它分配的缓冲区，Rust 侧的封装类型才接管那块内存，并在 `Drop` 中恰好释放一次。"

"C 库的生命周期——谁分配内存、谁负责释放要成对写清。若 C 侧通过 `malloc` 分配并把缓冲区所有权交给 Rust 封装，封装就在 `Drop` 中用匹配的 `libc::free` 释放，且只释放一次；借用的输入指针不归它释放。参数类型——C 侧 `const uint8_t*` 对应 Rust 侧 `*const u8`。当前使用版本的维护说明称解析函数可重入；我们检查过的调用路径也没有发现共享全局缓冲区，但这份结论只适用于已核对的版本和路径。失败模式——如果 C 库返回 null——Rust 侧转换为 `Option` 并返回 `None`——调用方必须处理 `None` 情况。"

"unsafe 不是禁区——是签字画押。你越过编译器保护边界——必须自己留下承诺和论证。不是'我认为它安全'——是'以下是基于什么验证它是安全的——在这个前提下——此论证成立。后来者——如果前提变了——例如 C 库升级了、目标平台变了、并发模式变了——请重新论证。——前提可能不成立。"
