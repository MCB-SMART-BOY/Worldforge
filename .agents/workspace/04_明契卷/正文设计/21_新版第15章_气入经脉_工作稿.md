# 新版第15章《气入经脉》工作稿

> **状态：工作稿，不是正式正文。** 承接Ch14的限时隔离原型。用一份固定样本生成的报告文本讲Rust `String` 的所有权移动；所有权指程序中值的归属与析构，不等于团队责任制，也不解决跨进程共享目录的竞争。借用留给Ch16展开。

---

试验记录被钉在镜面左侧：固定样本，不接真实发布入口，两日后复核。

右侧只有一个刚写出的函数。季循把原型生成的报告文本取名为 `report`，准备让写入步骤接手它，再用原文本整理一段摘要：

```rust
fn store_report(body: String) {
    // 原型暂时只接收样本内容
}

let report = String::from("sample build: passed");
store_report(report);
println!("{report}");
```

编译器停在最后一行。镜面标出 `report` 已经被移动。

季循皱起眉：“我只是把它交给另一个步骤，怎么原来的名字就不能再用了？”

“因为这个函数按值接收 `String`。”沈见微说，“你把值交过去后，原来的绑定不再拥有它。不是报告凭空消失了，而是这次转交以后，原变量不能继续使用同一个值。”

季循盯着那行错误，又看向闻衡：“所以是程序在追问，这份东西现在归谁？”

“在这段代码里，可以这么理解。”闻衡说，“这里的‘归谁’是值在程序里的所有权关系，不是项目出了问题该由谁负责。负责人写在试验记录上，Rust类型系统不会替你们安排。”

贺时进从门边看过来：“那我多复制一份，不就两边都有了？”

“可以选择复制，但得知道数据有多大、是否真的需要两份、复制成本由谁承担。”沈见微说，“能编译不等于选择就一定好。”

季循把 `String` 交给 `store_report`，又试着将返回值写回新的变量。随后他把摘要打印放在转交之前，再跑一次。那份字符串有了清楚的来去：新建时由一个绑定持有，按值传入函数后由函数参数持有，参数离开作用域时其析构逻辑运行。

他停了一下：“这和昨夜三处路径有什么关系？它们的文件也被不同脚本碰过。”

“关系不能说得太满。”沈见微答道，“ownership能让编译器检查这一段程序里的值怎样移动、何时不再可用；它不会替多个进程管理同一目录，也不会判断哪个发布入口该保留。文件系统上的竞争，要靠隔离路径、锁、原子操作或其他适合的方案另行处理。”

苏野平点头：“所以Rust不会因为某个目录有一个‘owner’，就拦住另一台机器把目录清掉。”

“对。”沈见微说，“别把术语相似当成问题相同。”

季循在记录纸上分开写了两栏：**代码中的值：谁持有、何时移动、何时析构；团队中的责任：谁执行、谁复核、谁批准。**两栏之间没有自动连线。

他重新看那段代码。最简单的修法是先打印，再把报告交给写入步骤；但如果后面还有多个函数都要查看它，反复复制似乎也不是唯一选择。

“如果它们只是读一眼呢？”他问。

沈见微把下一张空白纸推给他：“那就别急着把值交出去。下一步，看看借用能不能表达你真正需要的关系。”

季循把“移动后不可再用”记进原型说明，却没有写“Rust保证报告只被一个人处理”。那不是这条错误所能证明的事。试验记录上的负责人和代码里的所有者仍各自在自己的纸上。

### 编辑核验备注

- Rust Book对ownership的入门规则：每个值有一个owner、一次只有一个owner、owner离开作用域时值被drop。`String`按值传递会移动；本章只覆盖这一基础路径，不扩展所有`Copy`、部分移动或析构顺序细节。
- 示例函数按值接收`String`，调用后原绑定不可继续使用；错误发生在尝试再次使用被移动值时。代码中的注释不表示函数已实际写入文件。
- `String`析构管理其自身持有的内存；它不自动删除磁盘文件。Rust所有权也不会协调独立进程或主机对共享目录的访问。
- 本章事故类比刻意收窄：旧脚本共享临时目录不是ownership能单独解决的问题。Ch16再用引用解释不转移所有权的只读访问。
