# 明契卷 · 第41章 · 阵法有门

午后，苏野平把一份“大总门”草案推到长案中央。查病、解释、试跑、落动作，四种能力都收进同一个 `trait`：

```rust
trait QingluAction {
    fn check(&self, input: &WindowInput) -> Diagnosis;
    fn explain(&self, diag: &Diagnosis) -> String;
    fn dry_run(&self, input: &WindowInput) -> Preview;
    fn apply(&self, input: &WindowInput) -> ApplyResult;
}
```

季循看得很快：“以后每种骨头都得会这四样？”

“不会的就给个默认结果，或者回一个暂不支持，后面再补。”苏野平说。

程知序指着 `apply`：“若一种骨头只负责检查，空着的落动作算什么承诺？”

没人马上回答。沈见微把草案上的“统一入口”划了一道线：“实现按类型给出了返回值，只能证明签名和类型约束满足。默认值若让调用者以为动作已经执行，签名反而替一个没有发生的行为作了保。”他们先把四种职责拆开，保留真正共享的部分；哪些能力可以抽象，等实际变化与调用前提都看得见再定。

`trait`用一组方法描述可共享的行为，和其他语言的接口有相似之处。实现该trait的类型必须满足方法签名与类型约束，编译器会检查这些要求；实现是否符合语义、调用前提是否成立，仍要靠文档、测试和使用场景说明。`impl Trait for Type`写下类型提供的行为，trait bound `T: Trait`则让函数声明它需要的能力。

沈见微把草案边上的“以后可能用”圈了起来。抽象多出一层要理解和维护；若trait成为对外发布的API，兼容责任还取决于发布范围与版本政策。共同需求尚未出现时，先保留具体实现，等变化压力可见后再提取。
