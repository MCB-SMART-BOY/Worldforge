# 明契卷 · 第31章 · 骨架初定

一次复核后，季循把现有目录图推回沈见微面前。入口参数、样本读取、检查逻辑和报告各有模块，固定样本也能按记录复走；可它们仍挤在同一个 Cargo package 里。命令行入口和可复用检查逻辑被一起构建、一起改动，测试也只能从这一个边界进出。

“模块分开以后，为什么还要拆 package？”季循问，“如果只是想让目录看起来整齐，搬几次文件就够了。”

沈见微在纸上画了两栏：左边是参数解析与终端输出，右边是输入检查和结果类型。“要让另一个入口复用检查逻辑，或者单独核对核心行为，就不该让它先依赖整套命令行。拆分要解决这个依赖方向，不能只增加目录。”

他们保留原项目根作为`qinglu-cli`，在根`Cargo.toml`中加入`[workspace]`，再把检查逻辑移进`crates/qinglu-core`。根包仍是工作区（workspace）成员，核心库另列为成员；CLI依赖核心，核心不反向调用命令行。根manifest显式把`src/main.rs`登记为名为`qinglu`的二进制目标；`crates/qinglu-core/src/lib.rs`是核心包默认的库根。集成测试放在核心包的`tests/`中，从外部可见的调用路径验证行为。他们用`cargo test -p qinglu-core`单独核对核心测试。目录惯例帮助人找到入口，实际目标仍由各自manifest和代码说明。

苏野平看着多出来的清单：“现在要维护两个包、两份声明。若它们总是一起改，拆开究竟省了谁的事？”

“如果检查逻辑只有命令行能调用，确实没有必要。”闻衡说，“我们先用依赖图和测试边界核对：CLI只负责接参数、显示结果；核心不读取终端、不决定怎样呈现。若这个边界站不住，就合回去。”

季循按旧记录复跑固定样本，再从核心库的测试入口检查同一条行为。结果没有变化，依赖方向也没有倒过来。他在目录图旁写下：**拆包只让边界更可见；理由、行为和未覆盖范围仍需另行记录。**

沈见微把根清单夹进设计记录后面。后来者现在能找到核心与入口，却仍须从下一页知道：为什么让这两条路分开，以及什么变化会让他们重新考虑这项决定。
