# 新版第101章《术与道争》工作稿

> **状态：工作稿，不是正式正文。** 以短命格式转换原型和长期维护的核心工具作对照；不把语言选择写成普遍排名。

---

沈见微把两份实现放在同一张案上。一份是为眼前格式做转换的小原型，交付窗口很短；另一份是青炉打算长期维护的核心工具，边界和调用者都还在变。

同修把 Rust 版本交给他看。借用检查器停在一处数据传递上，要求先说清谁持有这段内容、何时复制、何时释放。写原型的人改了两次，才把边界写明白。

“它没有替我找出正确答案，”那人说，“只是没让我把没想清楚的地方藏过去。”

沈见微把这句话记在两份方案旁，又逐项核对：完成原型所需时间、出错时能影响的范围、未来谁来接手、现有团队熟悉什么。短期转换任务的维护期限有限，失败也能由人工复核兜住；为它支付完整的前置设计成本，收益并不相称。长期核心工具则不同，边界一旦模糊，代价会沿每个调用者往后传。

他在原型的决议栏写下“采用更轻的实现，保留人工验收”，又把 Rust 方案放入长期工具的候选清单，附上仍待验证的前提。没有人因此宣布哪种语言更高明。

苏野平来信问：若同一套判断要落到几万份既有项目上，逐项慢慢核验还来不来得及？沈见微把信压在方案下方。眼前的选择已经作出，下一道问题却远比一份原型更大。

### 编辑核验备注

- Rust 在本章体现为显式所有权与边界约束，不写成自动保证正确或适用于一切场景。
- 原型采用轻量方案、核心工具保留 Rust 候选，均是本章决策，不扩写成全宗门统一标准。
- 苏野平的规模压力只作下一章引子；具体项目数量、清单与交付期限须按既有资料复核，不在此补造数字。
