# 明契卷 · 第74章 · 开炉布道

该发未发的热气压回去以后，北院小室安静了两日。

变更日志补齐了，弃用说明补齐了，发布检查单也终于从头走到尾。新的问题却更具体：门外的人究竟怎样得到青炉？

程知序把发布页推到长案中央。“我不关心你们内部多漂亮。我只关心三件事：怎么装，怎么跑，若它回错，我先看哪儿。”

石镜上摆着两条路。一条是把青炉核心作为 Rust 项目的公开库依赖；另一条是交付可以直接安装、运行的命令行程序。苏野平更愿意开放核心层：若别人能把青炉接进自己的器里，这才像一件真正成熟、可传的法宝。

程知序却把一张问单推到他面前。上面没有架构图，只有三个问题：“怎么装？”“装完先打哪条命令？”“它回错了，我先看哪？”

沈见微看完，做了裁定：“第一版先把命令入口做实。核心库不作为公共依赖发布。内部接口还在变，不该为了显得成熟就让门外的人背上我们的改动。”

季循原以为公开更多接口才是“传世”。这时他才看见，公开也意味着长期维护：每多承诺一条路，后来者就多一条可能走进来的路。青炉的骨头还没定型，不能把“看得见”误当成“已经准备好被依赖”。

他们把安装说明从维护者的口吻改成第一次使用者能照着走的步骤。Cargo 注册表里的 `qinglu` package 用于安装命令器：`cargo install qinglu`。这条命令得到的是可运行的入口，不代表 `qinglu-core` 已经作为稳定库 API 对外承诺。

帮助页上先放两条最短路径：`qinglu --help` 用来找入口，`qinglu --version` 用来确认手中版本。更深的 `check` 与 `doctor` 说明往后放，先让第一次进门的人知道从哪一步开始。

程知序照着新页面从头走了一遍。她在“检查输入前提”旁停住，问：“要检查哪张纸？先看哪一项？”季循没有辩解，重新写了帮助，把入口、最小样例和常见失败路径一项项补上。

与此同时，闻衡核对发布清单：包能否安装、版本是否与发布页一致、帮助和示例是否同步、旧桥迁移说明是否可找到、失败后如何回退。某个具体版本发布以后不能被原地覆写；维护者仍可以发布后续版本，依赖者是否升级则受自己的版本约束和锁文件解析影响。发布是把一份明确版本交出去，不是把未来的选择权一并交出去。

天快亮时，段迟舟按说明在另一台机器上装好命令器，先查版本，再照样例走到结果。他回传：“入口能自己走通。还有一件事：这条诊断到底看见了什么？”

沈见微看向发布页上的范围声明。安装的路已经打开，报告里的边界还需要让门外的人看得懂、查得到。

**迁移与核验备注**：明确首发为安装命令器的 binary package，不公开 `qinglu-core` 稳定 API；避免把 `cargo install`说成 `qinglu-core`库发布，也避免声称 Cargo.lock 限制发布者改动。正式版本号与发布状态仍需对照新版Ch73及正文时间线确认。
