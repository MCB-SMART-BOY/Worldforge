# 新版第105章《炸了玄枢》工作稿

> **状态：工作稿，不是正式正文。** 跨卷事故在本卷交代理解所需的因果与责任；不依赖其他卷才能看懂。事故起因是退役建议越过有限观测边界，并在接收方明知本地盲区仍批准删除。更早的手工边界修正是独立旧风险，不是本次直接根因。

---

传讯抵达青炉时，沈见微正在核对下一版的内部验证表。纪承钧的名字列在来讯末尾，后面只有一句：“`v0.3.1` 的退役建议在玄枢造成了故障。”

纪承钧维护玄枢，也批准了那次维护窗。他在复盘里写得很清楚：玄枢接入的网络监测没有发现 `legacy-report-gateway` 的调用，但他知道本地 Unix socket 没有纳入观测。盲区没有补齐，维护窗却照常开了；他批准把网关移出生产包。

删除后，旧节点上的采集代理在夜间通过本地 socket 调用时找不到目标。脚本吞掉连接错误，把空响应写成空文件并照常退出；前两夜没有告警，第三夜的汇总任务读到空文件后，故障才沿 wrapper、adapter 与信号码转发路径扩散，三个服务先后失去响应，告警抵达十七个外部调用方。处置中一次回滚又让旧适配层的补丁空转，增加了恢复难度；随后团队隔离反复重启的模块、切换备用通道，才逐步托住服务。每一步都只能说明当时找到的因果范围，不能证明其他本地路径已全部清点。

沈见微调出青炉发出的报告。统计窗口是三十天，来源只包括已接入的采集端；报告另列连续三十六个月的可见调用为零。两组数字都没有覆盖玄枢的本地 socket。生成器却把“观测窗内未见调用”写成了绿色的“可安全废弃”。数据本身没有证明全域无人使用，是措辞替数据走过了那一步。

“我看见本地 socket 不在监测里，”纪承钧说，“还是签了批准。这个决定是我的。”他没有把责任推给一条没读到的声明。沈见微也没有拿范围说明挡在前面：青炉把有限观测包装成退役建议，令接收方更容易把它当成许可。两道边界都失守了，一道在工具输出，一道在删除前的本地核验。

事故后的追查落到值守记录和旧文件上。Makefile 的注释指向那台北岭备份服务器，旧 shell 脚本留下了本地 socket 调用路径。证据足以说明这次调用确实存在，却不足以证明其他所有本地路径都已找全。更早那次手工边界修正仍登记在旧风险栏：它需要另行核查，但现有证据没有把它连成本次删除的直接原因。

沈见微在处置单上写下：暂停依据 `v0.3.1` 继续退役接口；保留原报告并准备向已知接收方发出撤回通知，替代状态改为“当前观测未发现调用，待接收方核验”。纪承钧补做玄枢本地调用来源清点、替代路径与回滚条件核验，并记录自己批准删除的经过。撤回回执尚未收齐，事故复盘也没有宣称调用清单已经完整。

两人都在各自负责的栏下签了名。报告不再替接收方说“安全”，批准人也不能把自己的签字交给报告承担。案上的数字仍很醒目：三十天、三十六个月、三个服务、十七个外部调用方；它们终于各自回到能够证明的范围里。

### 编辑核验备注

- 事故链：`v0.3.1`的绿色退役建议 → 纪承钧知道本地 Unix socket 未观测仍批准移除 → 北岭备份服务器夜间本地调用失败 → 三个服务失去响应、告警扩散到十七个外部调用方。
- 三十天采集窗口与三十六个月可见调用为零，只能描述已接入观测范围；不得写成玄枢全域无调用。
- 双方责任分开呈现：青炉为越界建议负责；纪承钧为明知盲区仍批准负责。免责声明不免除任一方责任。
- Makefile 注释与旧 shell 脚本用于追溯本地调用；更早的手工边界修正保留为独立风险，不写成本次事故根因。
- 仅写章纲已有的三个服务、十七个调用方与北岭备份服务器；受影响服务名称、精确时间、恢复时长、各方个人分工及全量调用清单仍待正文或事故记录核验。
