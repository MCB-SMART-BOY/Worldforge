# 明契卷 · 第88章 · 闻衡的裁决

闻衡把北岭面板投到记录墙上，先圈住“守望运行中”，又在旁边写下报告锁与本轮结果。旧页面曾让一个绿色状态替三件事作答；现在他要每件事各自有名字、更新时机和失败表现。

第一类是**守望进程状态**：进程是否存活、何时退出。它描述长驻进程，不能代替某轮结果。第二类是**报告写回状态**：本轮是否取得报告写锁、报告是否实际写出；没有写成，就不能展示一份仿佛属于本轮的成功报告。第三类是**单轮检查结果**：对应具体 run id 的成功、失败或待恢复。只有本轮检查与报告写回都满足约定，当前轮次才能记为成功；旧成功结果可以保留作历史，不能冒充当前结果。

有人问，若 doctor 已经结束，是否能先标成功、稍后补报告。闻衡摇头：“结束的是检查过程。使用者要依赖的是有归属的结果。过程完成、报告写成、这一轮成功，是三件有先后的事。”

闻衡没有要求他们第三次制造同一种故障。他让记录者把 Ch86 的失败记录和外部复走记录并排，逐项核对新约定：失败记录里没有 `report_written`，所以本轮不能显示成功；复走记录有新的 run id 和对应报告，才足以支持该路径恢复。凡是两份记录无法回答的状态，都留作待核，不靠面板颜色补齐。

记录者把这两份既有证据和状态转换表存档。裁决不是“凡有锁就失败”，而是不得把不同层级的状态互相代答；也不是承诺每种环境都已验证，而是把已覆盖的路径说清。

他在运行手册的页首写下三问：进程还在吗？报告写成了吗？这一轮的结果是什么？之后遇到状态冲突，值守者先按这三问拆开查，不从一个总览颜色猜答案。

**旧 Ch26 证据边界**：旧稿确立 `watch_lock_acquired` 只证明守望锁取得，报告写锁另有等待与写出步骤；缺少 `report_written` 时本轮没有报告，旧成功零状态不应沿用。三类状态的正式裁决、历史区表现及未参与修复者执行的注入故障，是新版章纲中的制度化场景，不是旧稿已完整定义的 UI 或协议。
