# 明契卷 · 第77章 · 诊断报告

沈见微把报告拆成三页，摊在长案上。

第一张来自 `cargo-audit`：锁定依赖中，它能识别的已知安全公告。第二张是青炉自身公开函数的静态清单。第三张最薄，记着最近三十天里，青炉侧已接入统计的外部 Rust crate 调用了哪些接口、调用发生在哪些版本。

三张纸各自都有来处，也各自有看不见的地方。锁文件不是整座运行世界；公开函数表不会替人推断每种使用方式；统计窗外没有记下的调用，仍然可能存在。沈见微把这几句放进报告的范围说明里，逐条核对数据源和日期。

“这一项为什么是绿的？”程知序指着末页。

旧调用索引显示，某个接口连续三十六个月没有可见调用；最近三十天已接入来源的明细也没有记录。生成器将它标作低风险，并建议“可安全废弃”。数字没有算错；错的是从“当前数据没有记录”走到“别人可以删掉它”的那一步。沈见微在备注里补上：“请在接收方环境确认依赖与实际调用。”

闻衡读完，指尖仍停在绿标旁边。“范围写在后面，结论摆在前面。接收的人先看见哪个？”

沈见微把覆盖说明移到状态之前，又加粗了统计源与观测截止日。他没有删掉建议。报告的价值在于帮人找出值得核实的地方；若每一步都退回原始数据，工具便只剩一摞纸。可他也知道，这个建议比数据多走了一步，而那一步会落在谁的脚下，他并不知道。

报告定为 `qinglu-diagnose v0.3.1`。它能汇集青炉实际取得的安全公告、公开函数与有限调用数据；它不能替接收者确认未登记的依赖、其他语言的调用或真实部署行为。沈见微将声明放在扉页，签上自己的名字。

报告发往几处试用团队后，程知序拿着安装问单走进来：“你写了没看见什么。接到它的人，知道该去哪里找吗？”

沈见微望着“请在接收方环境核对”那行字。它像一道边界，也像一扇只标了出口、没有标路的门。
