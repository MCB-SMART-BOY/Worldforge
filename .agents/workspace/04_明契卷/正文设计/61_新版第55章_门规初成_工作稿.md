# 明契卷 · 第55章 · 门规初成

闻衡写了PR模板，也为提交说明拟定团队约定：例如用`feat:`、`fix:`、`docs:`、`refactor:`、`test:`、`chore:`标出作者认定的变更类型。这些前缀让人在日志里更容易辨认变更类别；实际改了什么，仍要看diff和评审记录。格式本身不能保证说明准确，也不能代替阅读改动。

PR template——标题简短描述做了什么；描述为什么做、什么场景需要、怎么验证、影响了谁。不是"写得多"——是"让 reviewer 不需要猜"。之前 merge conflict 说两个人都做了对的事但没有告诉对方——PR 可以在实现过程中、合并之前公开变更意图——别人看到标题和描述，就可能发现自己也在改同一处，及时协调。它不是要求所有工作都在动手前先开 PR，也不保证冲突不会发生，但让协作有机会更早看见彼此。

"PR不只是审批——先是告知、讨论和review的入口。让意图在代码合并之前、影响扩散之前、凌晨炸裂之前被看见。这就像化形卷里的弃用声明在接口变更之前告诉所有依赖方——给你时间准备。但PR不是弃用声明，它也不能替代独立的影响说明与迁移方式。评审可以发现问题、要求补证，必要时暂缓合并；在团队已约定走PR的协作变更中，绕过告知和评审直接合并，容易让依赖者措手不及。闻衡的门规不是限制——是让意图和问题都能在合并前摊开。"
