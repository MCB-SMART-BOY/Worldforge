# 明契卷 · 第55章 · 门规初成

闻衡写了 PR template 和 Conventional Commits 规范。commit message 格式——`feat:` 新功能，`fix:` 修 bug，`docs:` 文档，`refactor:` 重构，`test:` 测试，`chore:` 杂务。不是形式——是信号。让后来者扫一遍 log 就知道这个版本主要做了什么。

PR template——标题简短描述做了什么；描述为什么做、什么场景需要、怎么验证、影响了谁。不是"写得多"——是"让 reviewer 不需要猜"。之前 merge conflict 说两个人都做了对的事但没有告诉对方——PR 可以在实现过程中、合并之前公开变更意图——别人看到标题和描述，就可能发现自己也在改同一处，及时协调。它不是要求所有工作都在动手前先开 PR，也不保证冲突不会发生，但让协作有机会更早看见彼此。

"不是审批——是告知。告知在代码合并之前、影响扩散之前、凌晨炸裂之前。这就像化形卷里的弃用声明在接口变更之前告诉所有依赖方——给你时间准备。但 PR 不是弃用声明，它是变更提案和 review 的入口；弃用接口还得另行说明影响和迁移方式。没有协作信号就直接合并，才像偷袭。闻衡的门规不是限制——是让意图在合并前被看见。"
