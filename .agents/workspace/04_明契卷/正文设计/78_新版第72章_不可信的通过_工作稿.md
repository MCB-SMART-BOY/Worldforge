# 明契卷 · 第72章 · 不可信的通过

北岭送来的那份样例工件不大，只有一页输入和一条预期结果。它本来是为验证发布入口留下的，后来被收进了端到端演练。季循照着记录跑完，终端亮起绿色：检查通过。

程知序没有看那盏灯。她盯着终端里的目标目录，问：“说明让第一次使用的人直接照着样例跑。为什么这台干净的守门机找不到目录？”

季循先把命令和配置逐项核对：样例里没有目标目录参数，项目配置也没有设置。青炉按约定返回“目标目录未配置”，没有误处理工件。随后他们在另一台机器复跑，同一条样例却成功了——因为沈见微的开发环境还留着 QINGLU_TARGET_ROOT，测试脚本继承了这个值。测试验证了命令在“有目标目录”的前提下会通过，却没有验证读者照着文档，在干净环境里能否完成第一次运行。

他们从空白目录重新开始。程知序清掉环境变量，只按 `--help` 和 README 写明的步骤运行。结果稳定地返回同一条配置缺失提示；再补上命令行参数 `--target-root ./release-targets`，样例才成功。开发机里遗留的环境变量正好解释了那盏绿灯，却不能替文档完成它答应第一次使用者的事。

“核心逻辑测过，完整样例也测过。”沈见微翻开 Ch71 的测试清单，“只是没有把运行环境清干净。测试把我机器里的前提也一起带进来了。”

闻衡没有把“目标目录未配置”记成青炉故障。她在测试记录旁补了两项：样例是否显式声明所需参数；测试是否清除了未列入约定的环境变量。前者关系到使用者能不能复走，后者关系到测试究竟证明了什么。

季循把样例改成显式传入 `--target-root`，并给端到端测试加上环境隔离：除了测试声明的变量，其余环境值不再从开发者的 shell 继承。随后他们分别在保留环境和清洁环境中运行，一次验证配置覆盖顺序，一次验证文档样例不靠个人机器上的暗门。帮助页也说明缺少目标目录时会停止并给出明确错误。

程知序把两份前后输出并排放好：“这次不是生产事故。机器没有按错，青炉也没有偷偷猜。是我们的绿灯带着一份没写出来的环境。”

沈见微点头。他第一次看见，绿灯只照亮测试写下的那一小块地方；测试进程继承来的变量，也会替它照亮一条没有写进说明的路。

门外的排期纸被贺时进放上长案。北岭的交付窗口只剩三天。纸的背面写着：“若本期不能安装试用，下一轮要等一个月。”
