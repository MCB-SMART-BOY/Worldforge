# 新版第102章《苏野平的挑战》工作稿

> **状态：工作稿，不是正式正文。** 苏野平带来息壤的规模与交付压力；本章形成共同试点的起点，不预先决定全面迁移。

---

苏野平把项目清单摊在桌上。名字密密排了几页，底下还压着一张交付期限。沈见微看见熟悉的 Python 标记，也看见清单上并列的维护状态、依赖和负责团队：它们不是一批可以按同一种方式处置的东西。

“青炉每次先把假设问清，再往下走。”苏野平指着清单，“这习惯救过你们。但若几万份项目都等着逐个盘完，期限先到了。我们要的是能进现有流水线的一小段工具，不是一场没有结束日期的改造。”

沈见微原想拿出一张完整的风险表，话到嘴边停住。他们没有息壤所有仓库的调用数据，也不知道各团队能承受多少人工复核。现在替对方划出自动化范围，只是把未知写成了边界。

苏野平抽出一份真实清单，逐项问他：先接哪些仓库？什么信号必须转人工？遇到什么情况应该停止自动建议？沈见微没有给出一个覆盖全表的答案。他把能确认的资料与缺失的调用信息分开，提议先由双方挑一组范围明确的项目，列出接入条件、人工关口和停止条件，再看试点暴露出什么。

“这还不是迁移方案。”苏野平说。

“是。是我们共同制定试点的第一步。”沈见微把空白处留给息壤的维护者补充，没有把青炉的经验当作对方的答案。

她收起清单时，期限仍在，试点范围也尚未定下。桌上留下的不是“全迁”或“全不迁”，而是一张需要两边签字才能填完的工作表。

### 编辑核验备注

- 清单规模按章纲所给“几万份”表达，不补充具体数量、仓库名或精确日期。
- 苏野平提出的是扩展性、流水线接入和交付期限问题；不能将她写成反对严谨或只求速度。
- 章末只达成共同制定有界试点的意向；试点范围与结论留待后续正文确证。
