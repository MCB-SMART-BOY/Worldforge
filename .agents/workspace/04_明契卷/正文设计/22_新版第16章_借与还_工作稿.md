# 新版第16章《借与还》工作稿

> **状态：工作稿，不是正式正文。** 承接Ch15的`String`移动：摘要函数只需读取报告，不必接管它。本章用共享借用展示访问关系；不把借用说成文件锁、组织授权或能替团队协调多个进程。

---

限时原型的第一份记录还不到半页。

季循把报告文本交给 `store_report` 后，原变量不再能用。昨日沈见微让他先移动值，再看编译器怎样指出转移边界。今天，苏野平又给了他一个更小的需求：从同一份报告里取出摘要长度，随后仍要把完整文本写进记录。

“这次不能先打印再转交吗？”季循问。

“可以。”沈见微说，“那只是把使用顺序改了。如果两步都需要读，你也可以考虑只借来读取。”

季循打开代码，在摘要函数里写下一个字符串参数。编译通过后，镜面上的类型提示仍显示函数取得的是一整份 `String`。他想起昨天的错误，删掉参数类型，改为 `&str`：

```rust
fn summarize(report: &str) -> usize {
    report.len()
}

let report = String::from("sample check: passed");
let length = summarize(&report);
println!("{report} ({length} bytes)");
```

这一次，原文和长度都留了下来。

“函数看了它，却没把它拿走。”季循说。

“对。”沈见微说，“`&str`是借用。`report`仍由原来的绑定持有；函数只在调用期间读取它，调用返回后，原值继续可用。”

闻衡在记录边上写下：**只读查看，不转移所有权。**

贺时进瞥了一眼：“那我每次都借给很多地方看，不就好了？这样谁也不用等。”

“只读借用可以同时有多个。”沈见微说，“但若有人需要改，同一段访问期间就要遵守另一组限制。借用不是谁都能随时动它。”

苏野平问：“加个`&mut`就行？”

“要先看现有引用还在不在用。”沈见微让季循把摘要代码改成保留一个共享引用，同时再尝试创建可变引用。编译器指出两种访问重叠。季循调整了作用范围，等只读使用结束后再修改，镜面才放行。

他看着那两段代码：“这像有人围着同一张记录看。大家可以同时读；真要改，就得先让别的查看停下来。”

“这个比喻只到程序里这份值为止。”闻衡说，“它不会拦住另一台机器改磁盘上的原文件，也不会替我们给人发权限。”

程知序把试验记录翻到实际临时目录那页。“那前天两个任务抢着清文件，不能靠这里的借用规则解决？”

“不能。”沈见微说，“不同进程各自有自己的内存和值；磁盘目录是它们共同面对的外部状态。隔离路径、锁或其他同步机制要由程序和运行环境另行设计。借用检查能约束的是Rust代码里的引用关系。”

季循在旁边画了一条短线：`report`先存在，摘要函数在这段时间借读它，调用结束后把长度交回；完整报告始终由原绑定持有。他没有把那条线延伸到磁盘目录。

“那生命周期是什么？”他问。

“先别把它当成给值续命的咒。”沈见微说，“生命周期描述引用能够有效的范围，不能让被引用的值活得更久。下一步我们让一段引用试着越过它所依附的值，再看编译器指出什么。”

季循把原型记录补上：共享借用用于读取；若要修改，必须让访问范围不冲突；这些检查不覆盖外部文件的并发操作。闻衡在纸角加了一句“适用范围：当前Rust代码”，以免后来有人只抄走前半行。

试验机上，报告仍只有那几行固定文本。季循可以读取它、统计它，再把它交给下一步；但什么时候允许另一项任务清理外部目录，依旧由试验约定负责。两种边界并排留在记录里，没有被一种术语吞掉。

### 编辑核验备注

- `&str`可从`&String`借用并读取字符串切片；`summarize`不取得`String`所有权，调用后原绑定仍可用。
- 安全Rust中的共享引用与可变引用遵守别名和可变性规则；示例需要按非重叠使用范围组织，不能把“多个只读/一个可写”扩展成跨进程或文件系统保证。
- 生命周期描述引用有效范围，不延长被引用值寿命。悬垂引用错误留给Ch17具体展示。
- 本章继续沿用Ch14的隔离固定样本原型；不得把内部试验表述为青炉已支持真实发布环境。
