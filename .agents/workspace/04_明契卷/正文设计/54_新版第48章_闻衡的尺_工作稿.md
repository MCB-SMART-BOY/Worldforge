# 明契卷 · 第48章 · 闻衡的尺

闻衡——审契者——首次介入。不是测试，不是 code review——是审契。

"这个接口——承诺了什么？承诺成立的前提是什么？如果前提不成立，接口的行为是什么？"这把尺不是找 bug——是问"你写的够不够让后来者不需要来问你？"

沈见微拿出一个隔离原型的接口草案。返回类型写着 `Result<Artifact, BuildError>`，文档却只解释了成功时会生成什么。闻衡指着错误枚举里尚未定义的分支问："配置文件读不到、依赖缺失、权限不足，调用方怎么区分？哪些可以重试，哪些应当告警，哪些必须停止？"沈见微原想回答"都是 Err"，话到嘴边停住了。

他们把错误类型拆成 `ConfigRead { path, source }`、`MissingDependency { name }` 和 `PermissionDenied { path }`，并逐项写明调用方可采取的处理。`Result` 只保证失败值有一个确定的错误类型 `E`；该类型是否提供足够信息，是接口设计者仍须交代的事。

闻衡的尺有四条度量标准。接口的所有输入、输出都有文档。所有错误情况都有文档——每种错误的含义和应对。所有隐式依赖——环境、版本、配置——都被声明。承诺失效的条件被写清楚。

"不是批评你的代码——是让接口把边界说清楚。我们现在审的是原型，不能把一次评审写成程知序已经遇过的事故。可等真实调用者拿到这个错误时，他应该能从类型和文档里知道下一步，而不是靠猜。"
