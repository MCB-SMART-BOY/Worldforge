### 第61章：先照后立

- **核心对象层**：器→阵
- **核心相与失守**：流 → 乱流（运行时状态不可见）
- **工程锚点**：观测体系建立——沈照痕的方法论，"先照后立"
- **张力曲线**：攀升型（Section开局——沈照痕建立观测体系→纪承钧从"修好它"到"先看见它"的转变）
- **角色焦点**：沈照痕（观象者建立——"观测不是为了监控。是为了让后来者看见前辈看见了什么。"）；纪承钧（从抗拒到接受——"我一直想先修。你一直说先照。——现在我知道了。"）
- **六拍骨架**：
  1. 问题先出：旧桥清理完成后——纪承钧急着开始修边界。沈照痕拦住他："不照清楚就立边界，立的是纸墙。"
  2. 为什么痛：纪承钧一直以来的模式是"发现问题→修问题"。沈照痕要改变这个模式——"先照。照清楚了——你会发现有些问题不需要修，有些问题不能那样修，有些问题——根本不是你以为的问题"
  3. 引出方法：观测三视图的建立——迹（logs/tracing）、脉（metrics）、势（profiling）。不是三个工具，是三种看的方式
  4. 项目落地：沈照痕在玄枢上部署观测基础设施——从零开始建立日志结构化（structured logging）、调用链追踪（distributed tracing）、指标采集（metrics collection）
  5. 多方复盘：钟守玄——"我花了一辈子靠'感觉'判断玄枢的状态。你三个月建立的东西——比我三十年的感觉更准确。"
  6. 高层收束：不是技术升级——是认知方式的转变。从"人脑记住运行状态"到"机器帮你看见运行状态"
- **入门检查**：前置：Ch60（向观测过渡）/ 新术语：观测三视图——迹/脉/势，structured logging（≤3）
- **三问预检**：🩻乱流（运行时不可见→可见） 😣无——制度建设 🛤️是的——后来者能看见前辈看见了什么

> 📝 **路标章**：对应旧Ch10。保留"先照后立"的核心争执和沈照痕的方法论。扩展：旧Ch10的观测较抽象——新Ch61有具体的观测基础设施部署。

### 第62章：profile之道

- **核心对象层**：器（profiling——让不可见的运行变成可见的数据）
- **核心相与失守**：流 → 乱流（性能热点不可见→火焰图让热点可见）
- **工程锚点**：perf/VTune——火焰图（flame graph）的叙事能力
- **张力曲线**：攀升型（部署perf→第一次跑→火焰图揭示了一个十年没人发现的瓶颈→震惊→理解→行动）
- **角色焦点**：沈照痕（教纪承钧看火焰图——"不是优化。是理解。"）；纪承钧（第一次看火焰图——"那个占了40%的函数——是什么？"）；钟守玄（"那个函数——是十二年前为了兼容一个已经废弃的硬件写的。还在跑。"）
- **六拍骨架**：
  1. 问题先出：沈照痕在玄枢上跑perf——生成第一张火焰图。一个函数占了40%的CPU时间——"那个函数——是什么？"
  2. 为什么痛：钟守玄认出它——十二年前为了兼容一台现在已经废弃的硬件写的workaround。硬件十年前就淘汰了——workaround还在。每年消耗无数CPU周期——从来没人知道
  3. 引出方法：火焰图不是优化工具——是理解工具。它不告诉你"这里慢"——它告诉你"程序的时间花在哪里"，然后你决定——值不值得
  4. 项目落地：移除废弃workaround——性能提升40%。但更重要的不是性能——是"为什么没人知道这个workaround还在跑"——因为没有人能看见
  5. 多方复盘：陆踏痕——"所以我们不是在'优化'玄枢——是在'看见'玄枢。以前——它在我们看不见的地方浪费了十二年。"
  6. 高层收束：profile之道——不是让程序更快，是让程序的行为从不可见变成可见。看见之后，才知道该做什么
- **入门检查**：前置：Ch61 / 新术语：火焰图（flame graph）、perf、热点（hotspot）（≤3）
- **三问预检**：🩻乱流（性能瓶颈不可见→可见） 😣无——发现并移除了一个十二年bug 🛤️是的

### 第63章：火焰图

- **核心对象层**：器（火焰图作为叙事工具——一张图讲了一个故事）
- **核心相与失守**：流 → 乱流→可见（火焰图揭示了更深层的结构性问题）
- **工程锚点**：火焰图的可视化叙事能力——从火焰图到理解系统行为
- **张力曲线**：双峰型（第一张火焰图揭示性能问题→第二张火焰图揭示调用结构的异常→更深的理解）
- **角色焦点**：沈照痕（讲解火焰图的解读方法）；陆踏痕（自己跑了一张火焰图——发现了一个异常调用模式）
- **六拍骨架**：
  1. 问题先出：陆踏痕自己跑了perf——不是为了找热点，是为了理解玄枢的运行时结构。但火焰图上出现了一个奇怪的模式——一个调用栈反复出现，每次的调用路径不一样
  2. 为什么痛：不是性能问题——是结构问题。那个反复出现的调用栈——是同一个功能被四个不同的wrapper各自实现了一遍。因为没有人知道别人已经实现了——没有人能看见
  3. 引出方法：火焰图不只展示"谁花了时间"——它还展示"谁在调用谁"。从火焰图的宽度——可以看出调用关系的复杂度。异常宽的火焰——意味着异常多的间接调用
  4. 项目落地：陆踏痕用火焰图发现四处重复实现——三个是不同人不同时期写的（因为不知道别人写过了），一个是自己写的wrapper不小心重复了已有的功能
  5. 多方复盘：沈照痕——"这就是观测的价值。不只是让机器被看见——是让人的重复劳动被看见。以前——四个人做了同一件事，没有人知道。"
  6. 高层收束：火焰图不是工具——是镜子。照出的是人的行为模式——在不可见的地方，人会重复造轮子
- **入门检查**：前置：Ch62 / 新术语：调用栈（call stack）（≤1）
- **三问预检**：🩻乱流（重复实现→可见） 😣无——发现并消除了重复劳动 🛤️是的

### 第64章：sanitizer

- **核心对象层**：器→骨（sanitizer——让UB在出事前被看见）
- **核心相与失守**：流 → 乱流（内存错误/数据竞争/未定义行为——在运行时不可见→编译期+运行期检测）
- **工程锚点**：ASAN/TSAN/UBSAN——编译器级别的运行时检测
- **张力曲线**：倒钩型（第一次跑ASAN→三千个错误→震惊→逐一分析→发现大多是误报→但有几个是真的→修复→理解sanitizer的哲学）
- **角色焦点**：沈照痕（引入sanitizer——"让UB在出事前被看见"）；纪承钧（第一次跑ASAN——三千个错误）；钟守玄（"三千个——但大多数已经跑了十年没出过事。"沈照痕："对。但它们会。在某个最不该出事的时候。"）
- **六拍骨架**：
  1. 问题先出：沈照痕在玄枢上启用ASAN（AddressSanitizer）——第一次运行。三千个"错误"——heap-use-after-free、stack-buffer-overflow、memory leak
  2. 为什么痛：三千个报告——但大多数代码已经跑了十年。钟守玄——"它们从没出过事。"沈照痕——"在当前的输入模式下没出过事。但输入模式会变——Ch75-78的诊断报告改变了输入模式——那时它们会同时爆炸。"
  3. 引出方法：sanitizer不是找bug——是让UB可见。"UB不是一定会炸——是'不保证不炸'。sanitizer让这些'不保证'变得可见——让维护者自己判断哪些可以容忍，哪些必须修。"
  4. 项目落地：逐一分析三千个报告——筛选出真正危险的：两个use-after-free和一个buffer overflow。修复——编译期+运行期双重验证
  5. 多方复盘：纪承钧的转变——"以前我以为sanitizer是工具。现在我知道——它是让'不确定'变成'确定'。让'可能炸'变成'这里可能炸——你决定修不修'。"
  6. 高层收束：sanitizer不是安全网——是探照灯。它照亮那些在黑暗里跑了十年、从未被看见的未定义行为
- **入门检查**：前置：Ch63 / 新术语：ASAN/TSAN/UBSAN、use-after-free、buffer overflow（≤3）
- **三问预检**：🩻乱流（UB不可见→可见） 😣未来的维护者——不修的话，他们会在不知道的地方踩雷 🛤️是的——危险被标注了

### 第65章：沈照痕的方法论

- **核心对象层**：阵（观测哲学——不是工具，是文明级的认知转变）
- **核心相与失守**：全部四蚀（观测作为对抗所有四蚀的元工具）
- **工程锚点**：观测哲学——"观测不是为了监控。是为了让后来者看见前辈看见了什么。"
- **张力曲线**：双峰型（理论深度+实践案例——观测如何改变文明的认知方式）
- **角色焦点**：沈照痕（全章核心——完整阐述观测哲学）；纪承钧（理解者——从工具使用者变成哲学接受者）
- **六拍骨架**：
  1. 问题先出：沈照痕的完整方法论——不是工具使用手册，是"为什么观测是文明的基础设施"
  2. 为什么痛：人脑能记住的东西是有限的——钟守玄是最强的守门者，但他也只能记住一部分。观测——让机器的状态不再依赖人脑的记忆
  3. 引出方法：观测的三层价值——第一层：让运行可见（知道现在发生了什么）；第二层：让历史可追溯（知道过去发生了什么）；第三层：让模式可预测（知道未来可能发生什么）
  4. 项目落地：沈照痕用观测三视图重新审视了玄枢的七次断火历史——发现每一次断火前三天，某个metrics都在悄悄漂移。但以前没有metrics——所以没人知道
  5. 多方复盘：钟守玄看着那个漂移的metrics——"如果二十年前有人建立了观测——这七次断火，至少有五次可以在发生之前被预警。"——守门者最沉重的承认
  6. 高层收束：观测不是为了监管——是为了传递。"后来者不需要重新经历前辈的每一个错误——因为他们能看见前辈看见了什么"
- **入门检查**：前置：Ch61-64 / 新术语：无（哲学章）
- **三问预检**：🩻全部（观测作为对抗所有四蚀的元工具） 😣钟守玄——"如果二十年前有观测..." 🛤️是的——观测让后来者看得见

### 第66章：纪承钧的转变

- **工程锚点**：观测作为世界观——不只是在玄枢上装工具，是在脑子里装"先照后立"
- **张力曲线**：情感攀升型（反思→回忆→认知升级→向沈照痕承认——"你是对的"）
- **角色焦点**：纪承钧（全章核心——从追火者到观火者）
- **六拍骨架**：
  1. 问题先出：纪承钧回顾自己从卷一以来的每一个重大判断——发现大多数都带着"没有照清楚就立了边界"的问题

  3. 引出方法：不是否定自己——是理解自己的模式来自哪里。"钟老师教的是'先让它跑'——因为在那个时代，观测工具不存在。现在观测工具在了——思维模式还没跟上来。"

  5. 多方复盘：沈照痕——"我不是要你同意我——我是要你同意数据。数据比任何人都有说服力——包括我。"
  6. 高层收束："先照后立"不是口号——是文明从'靠人判断'到'靠数据判断'的转变。纪承钧完成了这个转变

### 第67章：看不见的依赖

- **核心对象层**：阵（观测揭示了一个之前没人知道的隐式依赖）
- **核心相与失守**：流 → 乱流→可见（隐式依赖在运行时被观测暴露）
- **工程锚点**：分布式追踪（distributed tracing）——跨服务调用链的可见性
- **张力曲线**：悬疑型（观测面板上的异常→追踪→发现隐藏的依赖链→震惊→"这个依赖——存在了多久？""至少五年。没有人知道。"）
- **角色焦点**：沈照痕（发现异常——"这条调用链——不应该存在的"）；纪承钧（追踪——追溯到一个从未被记录的依赖）
- **六拍骨架**：
  1. 问题先出：沈照痕的观测面板上出现异常——一条从未被记录的调用链每夜丑时触发。调用路径穿过三个wrapper、两个adapter——最后落在一个已经被标记为"废弃"的接口上
  2. 为什么痛：这个接口被标记为废弃三年了——但每夜丑时仍被调用。调用方是谁？追踪——最终追溯到北岭的一个备份系统。这个备份系统——不在任何依赖声明上
  3. 引出方法：没有分布式追踪——这个隐式依赖永远不会被发现。等到有一天拆了那个废弃接口——北岭备份系统在丑时静默地停止工作。没有人会知道——直到需要恢复备份的那一天
  4. 项目落地：纪承钧把隐式依赖加入桥谱系——标注："通过分布式追踪发现。此前未知。依赖方：北岭备份系统。调用频率：每夜丑时一次。风险：若废弃接口被移除，备份系统将静默失效。"
  5. 多方复盘：钟守玄——"这就是我一直在怕的。不是已知的依赖——是未知的依赖。你拆了一座你知道的桥——炸了一座你不知道的城。"
  6. 高层收束：观测的价值——不是让已知的更清楚，是让未知的变得已知。每一个"不知道"被变成"知道"——都是一次文明级别的进步
- **入门检查**：前置：Ch66 / 新术语：分布式追踪（distributed tracing）（≤1）
- **三问预检**：🩻乱流→可见（隐式依赖被发现） 😣北岭备份系统——如果依赖被发现之前就拆了废弃接口 🛤️是的——隐式依赖变成显式
