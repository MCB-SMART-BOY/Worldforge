### 第31章：壳与门

- **核心对象层**：器（为脚本做壳——"门"是入口，"壳"是边界）
- **核心相与失守**：式 → 失式（三层雏形开始实现——从最表面的"壳"开始。但为快试做的壳——暴露了更多被默认的隐性前提。）
- **工程锚点**：包装（packaging）——从`setup.py`到`pyproject.toml`，从"一个.py文件"到"一个可安装的package"。壳不只是名字——是"你想让别人从哪进来"的设计决定。
- **张力曲线**：建设型（岑照渠要求周栖野定义暴露面→周栖野把一个试法成果做成别人能点开的壳→但暴露之后——发现壳里面有很多"我以为人人都知道"的前提→使用者的困惑→"你的壳——是一扇门。门后面——不是房间。是另一个沼泽。"）
- **角色焦点**：岑照渠（推动分层——"你必须决定哪些东西能对外暴露"）；周栖野（做壳——第一次从"我能用"转向"别人也能用"——但发现这两者之间的差距比他想象的大得多）；季晚禾（使用者测试——"你的README说pip install。我装了。import成功了。但一跑——报错。不是因为你的代码——是因为你的代码假设我的机器上有一个配置文件。你没有告诉我那个配置文件在哪。"）
- **六拍骨架**：
  1. 问题先出：岑照渠要求周栖野把最常用的几个脚本做成正式的包——"给它们一个门。让别人能从门进来——而不是翻窗户。"
  2. 为什么痛：做壳过程暴露——每个脚本都有周栖野自己都没意识到的前提。一个配置文件——在他的home目录下。一个环境变量——他三年前设的。一段系统级工具——他忘了是他自己装的。
  3. 引出方法：包装不只是技术动作——是"重新审视你的代码在别人的机器上是什么"。setup.py/pyproject.toml的作用不只是声明依赖——是把隐式前提变成显式声明。
  4. 项目落地：周栖野做了第一个壳——`pip install xirang-field-mapper`。季晚禾测试——import成功，一跑报错。配置文件不存在——因为周栖野的壳里没有包含那个文件的创建逻辑。
  5. 多方复盘：岑照渠——"你的壳是一扇门。门后面——你放了你的函数、你的变量、你的docstring。但你在门口放了一个守门人——叫'你该知道配置文件在哪'。而季晚禾不知道。她甚至不知道有这个守门人。"
  6. 高层收束：做壳不难。难的是意识到——你的代码运行的前提不都在代码里。有些在你的环境里——而你的环境不是别人的环境。
- **入门检查**：前置：Ch30 / 新术语：包装（packaging）、隐式前提（implicit prerequisite）、pyproject.toml（≤3）
- **三问预检**：🩻失式（壳暴露了更多未被声明的依赖） 😣季晚禾——她以为"点开"就是"能用" 🛤️开始——做壳让隐式前提被发现了
- **包管理/类型/异步**：setup.py→pyproject.toml意识/dynamic/sync

> 📝 **路标章**：对应旧Ch07。保留做壳暴露隐性前提的核心场景。新增：季晚禾的"门后面不是房间"比喻——作为化形卷的经典意象。

### 第32章：pyproject.toml

- **核心对象层**：文→图（pyproject.toml——现代Python项目的"出生证"）
- **核心相与失守**：式 → 失式（项目的元数据（metadata）分散在setup.py/setup.cfg/requirements.txt/MANIFEST.in中——没有单一的"真相来源"）
- **工程锚点**：PEP 517/518——`pyproject.toml`作为现代Python项目的单一配置源。替代setup.py的setup()调用——不是更好看，是更结构化。结构化的配置可以被工具自动读取——非结构化的配置只能靠人读。
- **张力曲线**：认知张力（周栖野对比setup.py和pyproject.toml——"为什么需要换？""因为setup.py是代码——代码可以说谎。pyproject.toml是声明——声明不能说谎。"）
- **角色焦点**：周栖野（学习pyproject.toml——从setup.py的"灵活"到pyproject.toml的"约束"——"约束是机器的语言。灵活是人的语言。机器需要约束才能帮你。"）；宋既明（讲解现代打包标准）
- **六拍骨架**：
  1. 问题先出：宋既明指出——"你的setup.py里有逻辑。逻辑意味着——不同的环境可能有不同的行为。setup.py不是声明——是代码。代码可以说谎。"
  2. 为什么痛：setup.py中的条件判断——`if sys.platform == 'darwin': ...`——导致在macOS上和在Linux上安装了不同的依赖。这种行为在setup.py里是隐藏的。
  3. 引出方法：pyproject.toml的哲学——声明式配置（declarative configuration）。"[build-system] requires"——构建时依赖。"[project] dependencies"——运行时依赖。"[project.optional-dependencies]"——可选依赖。没有if——没有else——没有隐藏。
  4. 项目落地：周栖野把field-mapper从setup.py迁移到pyproject.toml——发现了一个在代码里藏了三年的条件判断——它只在"特定的Python版本+特定的OS"组合下触发。pyproject.toml不允许这种隐藏。
  5. 多方复盘：宋既明——"pyproject.toml不是终极答案。但它是目前最诚实的项目管理方式。它强迫你——把每一个依赖、每一个可选特性、每一个构建步骤——写成声明而非代码。机器读得懂声明。机器读不懂你的意图。"
  6. 高层收束：从setup.py到pyproject.toml的迁移——不只是工具的替换。是"项目元数据从来不是代码"这个认知的建立。
- **入门检查**：前置：Ch31 / 新术语：pyproject.toml、声明式配置（declarative configuration）、构建系统（build system）、PEP 517/518（≤3）
- **三问预检**：🩻失式（元数据的分散和隐式判断——在setup.py的代码逻辑中藏着不可见的前提） 😣在不同平台上构建息壤的人——他们遇到的是同一个项目的不同版本 🛤️是——pyproject.toml让"这个项目需要什么"变成可被机器验证的声明
- **包管理/类型/异步**：pyproject.toml建立/dynamic/sync

### 第33章：venv的哲学

- **核心对象层**：域（虚拟环境——每个人有自己的"独立息壤"）
- **核心相与失守**：流 → 乱流（所有项目共享同一个Python——全局环境是所有人的污染的交叉感染）
- **工程锚点**：virtualenv/venv的隔离哲学——隔离不是洁癖，是"让后来者知道从哪里开始"。一个venv = 一份独立的依赖清单 + 一个确定的Python版本 + 一条可复现的路径。
- **张力曲线**：哲学对话型（周栖野："为什么要隔离？我的机器上所有东西都能跑。"宋既明："你的机器是一个花园——你种了三年。每个后来者的机器是一块荒地。他们需要的不是你的花园——是一份种子清单和种植说明。"）
- **角色焦点**：宋既明（哲学输出——"隔离不是洁癖——是'让后来者知道从哪里开始'"）；周栖野（从"venv太麻烦了"到"venv是后来者的地图"）
- **六拍骨架**：
  1. 问题先出：周栖野抗拒venv——"太麻烦了。每次都要`source .venv/bin/activate`。我的机器上所有东西都能跑。"
  2. 为什么痛：宋既明在季晚禾的机器上跑周栖野的最新脚本——报错。季晚禾的全局pip里有三十几个包——来自五个不同的项目。其中一个包（requests的旧版本）和息壤的新需求冲突。"她的机器不是你的花园——是五个人的垃圾场。"
  3. 引出方法：venv的隔离哲学——(a) 每个项目独立的Python二进制 (b) 每个项目独立的site-packages (c) 每个项目独立的依赖树。从一个venv内部——`pip list`只显示这个项目的东西。
  4. 项目落地：周栖野为息壤创建官方venv——`python -m venv xirang-env`——然后把所有已验证的依赖锁定在里面。他做了测试——在自己的机器上删除全局pandas，息壤仍然能跑。因为venv里有它自己的一份pandas。
  5. 多方复盘：宋既明——"venv是一面墙。墙不是监狱——墙是保护。墙之内——你知道你在依赖什么。墙之外——那些东西影响不到你。后来者走进这面墙——他们看到的一切都是你需要他们看到的。没有意外。"
  6. 高层收束：隔离不是洁癖——是后来者的地图。每一面venv的墙都在说："这是你需要的东西。墙外的东西——与你无关。"

- **入门检查**：前置：Ch32 / 新术语：虚拟环境（virtualenv/venv）、site-packages、隔离（isolation）（≤3）
- **三问预检**：🩻乱流（全局依赖污染——所有项目共享同一份site-packages的交叉感染） 😣季晚禾——她的机器是五个人的垃圾场 🛤️是——venv让后来者知道"这是这个项目需要的"
- **包管理/类型/异步**：venv制度化/dynamic/sync

### 第34章：poetry/uv

- **核心对象层**：器→约（依赖锁定——从"知道需要什么"到"锁定确切版本"）
- **核心相与失守**：契 → 背契（没有lock file——"依赖的依赖"是不确定的。`pandas>=1.3`意味着今天和明天装的pandas可能不一样。）
- **工程锚点**：poetry/uv的lock file——`poetry.lock`/`uv.lock`记录整个依赖树的精确版本哈希。不是"需要pandas≥1.3"——是"需要pandas==1.5.3，其依赖numpy==1.24.3，其依赖的依赖..."。依赖的依赖也是依赖。
- **张力曲线**：认知张力（周栖野运行`poetry lock`→看到输出的lock file→"我不认识这些包——但它们会影响我的代码？""是的。""这就是我需要的——但我在requirements.txt里从来没写过它们。"→"但你的代码依赖了它们。它们一直在——只是隐形的。"）
- **角色焦点**：周栖野（第一次认识到"依赖的依赖"——以及为什么lock file是必须的）；宋既明（"conda→pip→poetry→uv——这条演化线不是'更好'，是'更诚实'。uv是目前最诚实的——它不假装解决了所有问题，但它解决了最基础的：让后来者知道——你代码依赖的每一个字节是从哪来的。"）
- **六拍骨架**：
  1. 问题先出：周栖野的`requirements.txt`里有`pandas>=1.3`。宋既明问——"你装的是pandas的哪个确切版本？""最新的。""明天——最新的可能就变了。明天后来者装的pandas——不是你今天用的pandas。"
  2. 为什么痛：依赖的依赖——pandas依赖numpy。numpy依赖libc、libgfortran、libopenblas。这些系统级依赖在不同平台上有不同行为。`pip install pandas`——成功。但在macOS上装的可能和Linux上装的编译方式不同。
  3. 引出方法：lock file的哲学——不是"锁定"，是"诚实"。`uv lock`生成一个文件——里面精确记录了每一个依赖包的版本哈希（hash）。包括间接依赖。总共有80多个包——远比requirements.txt里的19个多。
  4. 项目落地：周栖野运行`uv lock`——生成uv.lock。80多个包。他看着屏幕——"这里面有61个包——我从来没有import过。但它们在我的代码运行时被加载了。它们一直在——我从来没有声明过。"
  5. 多方复盘：宋既明——"conda试图回答'非Python依赖怎么办'。pip试图回答'怎么装'。poetry试图回答'怎么锁'。uv试图回答'怎么快且怎么锁对'。它们都不是终极答案。但uv是目前最诚实的——它让依赖的依赖不再是隐形的。"
  6. 高层收束：lock file不是"锁死"——是"让依赖链的每一环都可见"。后来者不需要知道pip的历史——他们只需要知道`uv.lock`里的哈希值是对的。
- **入门检查**：前置：Ch33 / 新术语：锁定文件（lock file）、依赖解析（dependency resolution）、uv/poetry（≤3）
- **三问预检**：🩻背契（未声明的间接依赖——依赖的依赖是隐形的承诺） 😣在不同时间安装依赖的人——他们的"最新版"可能不一样 🛤️是——lock file让依赖链完全可见
- **包管理/类型/异步**：poetry→uv锁定/dynamic/sync

### 第35章：宋既明登场

- **核心对象层**：约（审契者建立——复现不是美德，是底线）
- **核心相与失守**：契 → 背契（"跑一下看看"作为唯一的验证——无法保证任何人任何时间能复现）
- **工程锚点**：复现性标准的建立——从"作者能跑"到"任何人、任何兼容环境、任何时间都能跑"。三条标准：环境声明、依赖锁定、最低复现链。
- **张力曲线**：对峙型（宋既明和团队对峙——"你们写的每一个脚本——都是在向我承诺一件事：它能跑。我来验证这份承诺。"）
- **角色焦点**：宋既明（审契者核心建立——不是来挑刺的，是来保底的。他的存在让"能跑"从作者的感觉变成机器可验证的事实。）；周栖野（从抗拒到尊重——"你不是来挑刺的。你是来替季晚禾做她做不了的事。"）；团队（被审契者的标准刺痛——因为一半以上脚本过不了）
- **六拍骨架**：
  1. 问题先出：宋既明在公共记录板上贴出三条标准——"第一：环境声明完整（Python版本+OS+依赖锁）。第二：最低复现链从`git clone`到`python main.py`不能断。第三：不能有'我的机器上可以'。"
  2. 为什么痛：周栖野按这三条标准跑自己的脚本——十五个脚本，九个不通过。不是因为代码有问题——是因为环境声明不完整。没有记录Python版本——没有记录安装步骤——没有记录"在这之前需要先装openssl"。
  3. 引出方法：审契者（Reviewer/QA/Verifier）的角色定位——不是写完代码后审查——是定义"什么是'存在'"。不能复现就不算存在。
  4. 项目落地：宋既明对每个不通过的脚本贴了"未成立"标签——"不是你的代码不好。是你的代码'不存在'。它只存在于你的机器上——那是你的想象。在我的标准下——它不存在。"
  5. 多方复盘：团队集体抗拒——"太严了。""不是严——是一致。你们之前的标准——'周栖野的机器上能跑'——那才是随意。三条标准对所有脚本、所有人、所有时间一样。这是公平。"
  6. 高层收束：宋既明被确立为审契者。他的角色不是被欢迎的——但他让"能跑"这个词有了可验证的含义。之前"能跑"=周栖野的直觉。之后"能跑"=机器验证通过。
- **入门检查**：前置：Ch34 / 新术语：复现性（reproducibility）、最低复现链（minimal reproduction chain）、审契者（verifier）（≤3）
- **三问预检**：🩻背契（"能跑"的承诺无法被验证——审契者建立了验证标准） 😣周栖野——他的九个脚本被判定为"未成立" 🛤️是——"能跑"从直觉变成了可验证的契约
- **包管理/类型/异步**：uv锁定/dynamic/sync

### 第36章：最低复现链

- **核心对象层**：约→文（最低复现链——把"能跑"变成可执行的步骤）
- **核心相与失守**：式 → 失式（"能跑"的路径没有结构——每个人走的路线不同。最低复现链定义了唯一路线。）
- **工程锚点**：最低复现链（minimal reproduction chain / MRC）——从`git clone`到`python main.py`的所有步骤。每一步都是机器可执行的命令。没有"确保你的环境是正常的"——没有"你应该知道要装什么"——没有人类判断的空间。
- **张力曲线**：实操型（周栖野试图为一个脚本写MRC→每一步都漏东西→"我以为这是常识"→"常识是最大的盲区"）
- **角色焦点**：周栖野（写第一份MRC——反复失败——每一步失败都在暴露一个新的隐式前提）；白又新（作为验证者——独立跑MRC——不依赖周栖野的任何口头说明）
- **六拍骨架**：
  1. 问题先出：宋既明要求每个脚本在进入固核层之前必须有MRC——"从零开始，不需要问任何人，10步内跑通。"
  2. 为什么痛：周栖野写的第一份MRC——7步。白又新执行——第三步卡住。"这一步写的是'确保你的环境是正常的'。什么叫正常？"周栖野："就是——Python装好了，pip能跑..."白又新："我的Python装好了，pip能跑。但报错——因为我的Python版本是3.9。你的MRC没说需要3.11。"
  3. 引出方法：MRC的写作原则——(a) 每一步都是机器可执行的命令 (b) 不依赖"常识" (c) 有明确的验证方式——"如果这一步正确完成，你应该看到..."
  4. 项目落地：周栖野重写MRC——从7步变成13步。增加了Python版本检查、venv创建、依赖安装、配置文件的生成。白又新独立执行——全部通过。没有问周栖野一个问题。

### 第38章：固核层

- **核心对象层**：骨→器（固核层——xirang-core——"稳定下来的，值得维护的"）
- **核心相与失守**：（建设章——固核的定义是"值得长期维护"——这是背契的疫苗）
- **工程锚点**：稳定层（stable layer / core）的治理原则——有MRC、有测试、有依赖锁、有类型标注。从试法到固核的晋升标准不是"够好"——是"够稳定，能被后来者独立使用"。
- **张力曲线**：建设型（定义固核层的晋升标准→第一批脚本申请晋升→大部分被退回——不是因为不好，是因为"够好"和"够稳定"之间的差距被曝光）

- **六拍骨架**：
  1. 问题先出：周栖野定义固核层的标准——"每个模块必须：MRC通过、pytest覆盖率>80%、mypy无警告、uv.lock完备、README包含所有前提。"

  5. 多方复盘：宋既明——"固核不是奖杯——是承诺。每个进入固核的模块都在对后来者说：'你可以依赖我。如果我不行了——会有测试告诉你，有文档帮你迁移。'这不是苛刻。这是契约的代价。"
  6. 高层收束：固核层的标准确立了——不是因为有人想当警察。是因为在沼泽里——任何标准都会被抱怨太严。但那些抱怨的人——三年后不会在场。三年后在场的人——需要标准。
