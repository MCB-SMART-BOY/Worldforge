# 卷九「新手」Ch 81-90：后来者独立

## Section 总览

- **章段**：Ch 81-90
- **叙事主题**：后来者（乔落）的独立——从"按手册做"到"手册没写的情况——自己判断了"。不是她变成了高手——是她学会了"在不确定中做判断——并把判断写下来给下一个不确定的人"。postmortem文化建立——runbook从"傅远洲写的"进化到"乔落补充的"。

### 第81章：新手接住

- **核心对象层**：人→人（凌晨——传讯牌响——洪峰（traffic spike）。不是OOM——是外部流量突然飙升——`data-aggregator`服务数据库连接池耗尽。乔落on-call——接牌——独立诊断——找到根因——扩容连接池——恢复。这是她第一次完全独立处理事故——没有傅远洲在传讯牌另一端。）
- **核心相与失守**：流 → 乱流（连接池耗尽——不是内存不够——是连接数用完了。每一个新请求都在等连接——请求堆积——超时——失败的请求又重试——更多的请求——"洪峰不是外部的——是内部的——每一个超时重试——都是新的洪峰。"）
- **工程锚点**：数据库连接池（database/sql connection pool）——Go的`database/sql`包的内置连接池。`SetMaxOpenConns`/`SetMaxIdleConns`/`SetConnMaxLifetime`——不是设了就没事——是"需要多少连接——取决于洪峰时的并发请求数"。默认值是0（无限制）——如果不设——洪峰时连接数会膨胀到数据库的极限——然后数据库拒绝——然后应用超时——然后重试——死亡螺旋。
- **张力曲线**：攀升型（凌晨——传讯牌响——乔落接——"什么服务？""data-aggregator——连接池耗尽——请求超时率37%。""连接池配置——最大连接数？""......没有设——用的是默认值——无限制——但数据库端有限制——先到了数据库端——被拒绝——请求堆积——在应用端超时。"她连到数据库——查看连接数——"当前连接数：151——数据库最大连接数：150——刚好超过——每一个新请求——都在等那第151个连接——永远等不到。"她调整了连接池——设了MaxOpenConns=100——限制应用端连接数——给数据库留50个连接余量——"限制应用——不是限制自己——是保护数据库不被饿死。"）
- **角色焦点**：乔落（独立诊断——从三视图找到根因——调整配置——验证恢复——写事故记录。整个过程——她没有呼叫傅远洲。）
- **六拍骨架**：
  1. 问题先出：凌晨洪峰——data-aggregator连接池耗尽——请求超时率37%
  2. 为什么痛：连接池没设上限——应用在洪峰时会抢光所有数据库连接——数据库拒绝——应用超时——重试——更多连接请求——死亡螺旋
  3. 引出方法：连接池的三参数——MaxOpenConns（上限）、MaxIdleConns（空闲保持）、ConnMaxLifetime（连接寿命）——"不是设了就安全——是'设多少——取决于数据库能承受多少'。"
  4. 项目落地：乔落设MaxOpenConns=100——给数据库留50个连接余量——洪峰时应用端排队——而不是数据库被冲垮
  5. 多方复盘：傅远洲天亮看到事故记录——"她设了100——为什么不是150？""因为数据库最大150——如果应用拿满——数据库本身也需要连接做维护——留50是给数据库呼吸的。""你怎么知道的？""Ch43——秦望秋的goroutine泄漏——教会我看'余量'。设限制不是限制自己——是留余地。"
  6. 高层收束：新手接住了——不是因为她背了手册——是因为她理解"限制不是削弱——是保护"。洪峰不可预知——但连接池的限制——让洪峰不至于不可控。

- **并发/观测/简洁/部署**：连接池耗尽=并发瓶颈/三视图定位/database/sql=默认值再审计/on-call独立处理

### 第82章：手册上的注

- **核心对象层**：史→史（从Ch77延续——乔落的那行注——"峰值高于上月约百分之十五"——在驿河传播后——被追踪到四个人——现在被用于本卷Ch81的事故。她的注——不是让她自己下次知道——是让"下次接传讯牌的人"知道。）
- **工程锚点**：runbook注的生命周期——注不是写完就完了——是"被使用→被验证→被补充→被合并"。乔落的注经过：(1) 写入——凌晨Ch68 (2) 验证——Ch77四个人接力补充 (3) 使用——本卷Ch81新人参考了她的注 (4) 进化——被合并进正式手册的"洪峰处理"章节。
- **张力曲线**：沉静型（乔落看到自己的注被引用——"我写了'待补'——有人补了——现在被新人用来处理洪峰。我那行注——变成了手册的一部分。不是傅远洲写的——是我写的——'待补'两个字——变成了一个完整的章节。"）
- **六拍骨架**：
  1. 问题先出：乔落看到手册的"洪峰处理"章节——引用了她的注——旁边有四个人的补充——现在又加了她的Ch81处理记录
  2. 为什么痛：不是她的注被"认可"——是她的注被"使用、验证、补充"——变成了活的——不是死的文字
  3. 引出方法：runbook的生命力——不是"写完整"——是"被使用→被验证→被补充→再被使用"
  4. 项目落地：手册的"洪峰处理"章节——签名栏：傅远洲（初版）→乔落（Ch68补充）→四人接力（Ch77验证）→乔落（Ch81更新）
  5. 多方复盘："我看手册时——总觉得那是'傅远洲的'。现在我写的东西——在手册里——后来者看到——会想'这是乔落写的'——就像我看傅远洲写的。我不是傅远洲——但手册上有我的名字——也有后来者的名字。"
  6. 高层收束：手册上的签名——不是权力的标志——是责任的接力棒。"我写了——所以我负责让它是正确的——直到下一个人来修正它。"

### 第83章：数据库连接池

- **核心对象层**：流→流（数据库连接池深入——Ch81是单个服务的连接池耗尽——但驿河有51个服务——每个服务都有自己的连接池——连接到同一个数据库集群。51个连接池——各自独立——但最终都连到同一个数据库。总连接数=所有服务连接池之和——没有人算过总和。）
- **核心相与失守**：流 → 乱流（"每个服务设了自己的连接池——合理——但加起来——总和超过了数据库的限制。每个团队只看到自己的池——看不到别人的池。数据库是所有池的终点——不是无底洞。"）
- **工程锚点**：全平台连接池审计——不只审计每个服务的连接池配置——审计"所有服务连接池的总和——相对于数据库的总容量"。数据库的最大连接数——必须大于所有服务MaxOpenConns之和——还要留余量。"连接池不是服务的边界——是数据库的共享资源——共享资源需要全局视图。"
- **张力曲线**：发现型（乔落Ch81处理完事故——发现连接池配置分散在51个服务中——没有全局视图——"如果再有三个服务同时设了无限制——数据库会在洪峰时被51个服务同时淹没。"她发起了全平台连接池审计。）
- **六拍骨架**：
  1. 问题先出：乔落Ch81之后——检查其他服务的连接池配置——发现各服务独立设置——没有全局协调
  2. 为什么痛：数据库是所有服务的共享资源——但各服务的连接池配置是独立决策——没有人计算过总和
  3. 引出方法：连接池的全局审计——(a) 列出所有服务的MaxOpenConns (b) 加总 (c) 对比数据库的max_connections (d) 留至少20%余量
  4. 项目落地：审计发现——51个服务连接池总和超出数据库限制——"数据库默认max_connections=151——我们51个服务如果都用默认——或者大部分不设——小部分设了上限——总和仍然可以超过。"
  5. 多方复盘："不是单个服务的错——是没有全局视图。每个服务做好自己的事——但加起来——做了太多。"
  6. 高层收束：共享资源——需要共享视图。不是"每个服务管好自己的连接"——是"所有服务一起——管好数据库的连接"。"共享——意味着没有人能独自安全。"

### 第84章：迁移与事务

- **核心对象层**：文→史（一次数据库迁移（schema migration）——`settlement-engine`服务需要加一个字段——写了一个迁移脚本——执行——迁移在一半失败了——因为有个约束（constraint）在新的schema下不成立——但迁移没有用事务包裹——一半的变更已经写入了——数据库现在处于一个"半迁移"状态。回滚策略救了命——但回滚也需要手动。迁移没有事务——等于"没有办法干净地回到迁移前的状态"。）
- **核心相与失守**：流 → 乱流 + 史 → 断史（迁移没有事务——等于历史上出现了一个"无法描述的状态"——"迁移前"和"迁移后"之间——出现了一个"半迁移"——没人知道哪些数据变了——哪些没变。）
- **工程锚点**：数据库迁移（database migration）与事务（transaction）——迁移必须在事务中执行——全部成功或全部回滚。迁移文件版本化——每个迁移有up（前进）和down（回退）——迁移记录表（migration history table）追踪每次迁移的状态。"没有事务的迁移——不是迁移——是随机的修改。"
- **张力曲线**：悬崖型（迁移执行——一半失败——屏幕上显示"ERROR: constraint violation"——"回滚——快回滚。""回滚脚本在哪？""......没有写。"——Ch63的回滚锚点救了命——因为部署系统记录了迁移前的版本——手动恢复到迁移前的schema——但数据的"半迁移"状态——需要手动修复。）
- **六拍骨架**：
  1. 问题先出：数据库迁移在一半失败——没有事务包裹——schema处于"半迁移"状态
  2. 为什么痛：迁移没有事务——等于"不能回到迁移前"——因为不知道哪些变更已经执行了
  3. 引出方法：迁移的四个铁律——(a) 每个迁移必须在事务中执行 (b) 每个迁移必须有up和down (c) 迁移在执行前必须在staging环境验证 (d) 任何迁移在执行前必须备份
  4. 项目落地：傅远洲在记录板上加"迁移铁律"——与变更五问并列。"迁移是变更的一种——但它改写的是历史——比代码变更更严重——因为代码可以回滚到上一个版本——数据回滚——你需要知道'中间发生了什么'。"
  5. 多方复盘："代码回滚是一行命令——数据回滚是考古。如果没有迁移记录和事务——你在一个没有地图的洞里考古。"
  6. 高层收束：数据库迁移不是"改表结构"——是"改历史的记录方式"。每一次迁移——都在改写后来者看到的历史。改写历史——必须有"撤销"的能力。

### 第85章：乔落的判断

- **核心对象层**：人→人（**乔落弧线的高峰**——凌晨——传讯牌响——`data-aggregator`再次出问题——但这次不是连接池——是"手册上没写的情况"。一个第三方数据源返回了意外的格式——解析失败——数据丢失——对账开始不一致。手册上写了"如果解析失败——重试三次——仍失败则告警"。但乔落看了数据——发现格式变化是"有序的"——不是随机的错误——是数据源升级了格式——增加了新字段。手册没说这种情况——"重试三次——仍失败则告警"——但这不会解决问题——因为格式是永久改变的——不是临时故障。）
- **核心相与失守**：（正向——判断力的诞生。"手册告诉我重试三次——然后告警——等天亮。但我知道天亮后再告警——对账已经错过——结算受影响。手册是对的——在它写的时候。但现在——手册没有覆盖'数据源格式永久改变'这种情况。不是手册错了——是情况变了。")
- **工程锚点**：判断力（judgment）——不是"按手册做"——是"理解手册为什么这样写——然后判断'现在的情况——是不是手册假设的情况'"。乔落的判断过程：(1) 手册说"重试三次后告警"——为什么这样写？——因为假设错误是临时的 (2) 现在的情况——格式改变是永久的——重试不会有用 (3) 判断——需要改解析逻辑——不是重试。"手册是地图——但地图是之前画的——地形变了——地图需要更新。"
- **张力曲线**：紧张型（凌晨——只有她——没有傅远洲——"如果我改了解析——可能引入新问题——但不改——对账会错——结算受影响。手册说'重试三次后告警'——但手册没说'如果格式是永久改变——重试三次后告警——然后结算受影响'。""我判断了。我改了。——如果错了——是我的责任——不是手册的。"）
- **角色焦点**：乔落（不是"我懂了"——是"我在不懂的情况下——做出了判断——并为判断负责"。她改了解析逻辑——验证——对账恢复——写了新的事故记录——更新了手册的数据源格式处理章节——"原手册假设格式变化是临时的。经本次事故确认——数据源可能永久改变格式。处理流程更新如下。"）
- **六拍骨架**：
  1. 问题先出：数据源格式永久改变——手册的应对是"重试三次后告警"——但这是为临时故障设计的
  2. 为什么痛：手册假设错误是临时的——但格式变化是永久的——"重试"不会有用——"按手册做"会让对账错过
  3. 引出方法：手册是地图——地图假设"地形不变"。但地形会变——当时的地图需要当时的人判断"地形变了没有"
  4. 项目落地：乔落判断——格式是永久的——改解析——恢复——更新手册。她的判断被证明是正确的——天亮后傅远洲确认——数据源确实升级了格式——没有通知
  5. 多方复盘：傅远洲——"你为什么没有按手册做？""因为手册的假设不成立。手册假设错误是临时的——它说重试三次。但错误是永久的——重试没有用。""你怎么知道是永久的？""因为三次重试的错误完全相同——不是随机的——是同一个错误——三次同样的错误——意味着格式是固定的——不是间歇性的。"——"她不只是按手册做。她读了手册——理解了手册的假设——判断假设不成立——做了不一样的事。这不是违反手册——是升级手册。"
  6. 高层收束：新手能接住——不是因为会按手册做——是因为能判断——"手册的假设——现在——还成立吗？"手册不是圣经——是前辈在特定假设下的最佳判断。假设会变——后来者需要能判断"假设变了没有"。

- **跨卷锚点**：乔落"手册的假设还成立吗"——与化形卷纪承钧的"runbook在另一个世界炸了"形成跨卷回响。纪承钧的runbook炸了——因为他写了完整步骤但没写"为什么"——使用者不知道"假设变了没有"。乔落学会了——看手册时——先看假设——再判断假设是否还成立。

### 第86章：事故复盘

- **核心对象层**：史→史（postmortem文化正式建立——不是追责——是"让后来者不要再踩同一个坑"。但不是为了"让人感到安全"——是为了"把事故的代价——转化成后来者的地板"。）
- **核心相与失守**：（正向——继承文化建立。"每一个事故都是一堂课——不是给犯错的人的——是给所有后来者的。"）
- **工程锚点**：postmortem（事后复盘）——Google SRE的"blameless postmortem"——不是"没有人有错"——是"不追责——但追根因"。postmortem的四个核心问题：(1) 发生了什么——时间线 (2) 为什么发生——根因 (3) 怎么发现的——检测 (4) 怎么防止再次发生——行动项。
- **张力曲线**：文化建立型（傅远洲主持第一次正式postmortem——Ch85的事故。他明确说："这不是'谁错了'——是'什么错了'。找出'什么错了'——然后修它——让下一次的人不需要再找一次。"）
- **六拍骨架**：
  1. 问题先出：第一次正式postmortem——Ch85的数据源格式变化事故
  2. 为什么痛：不追责——追根因。不是因为"对人好"——是因为"追责会让人隐藏错误——隐藏错误会让同一种错误再次发生"
  3. 引出方法：postmortem的四个问题+时间线——从事故发现到恢复的每一步——公开记录——不匿名——但也不指责
  4. 项目落地：第一次postmortem记录贴在记录板上——"根因：数据源升级格式——未通知——解析失败——手册假设临时故障——判断该假设不成立——改解析——恢复。行动项：(1) 数据源格式变更需提前通知——已联系第三方 (2) 手册增加'判断假设是否成立'的步骤 (3) 解析器增加格式版本检测。"
  5. 多方复盘："postmortem不是让人安心——是让人不再需要——为同一个原因——在凌晨接传讯牌。"
  6. 高层收束：每一个事故——都是文明的代价。承认代价——记录代价——让后来者不付同样的代价——这就是继承。

### 第87章：runbook的进化

- **核心对象层**：史→史（runbook从"傅远洲写的"到"乔落补充的"到"所有接传讯牌的人共同维护的"。进化不是"越来越完整"——是"越来越多的人在上面签了名"。）
- **工程锚点**：runbook的社会进化——初版=解决已知问题（傅远洲写）→补充=覆盖新情况（乔落补充）→验证=被他人使用和确认（四人接力）→重构=从"步骤"到"判断框架"（从"做什么"到"为什么这样做"再到"这个为什么什么时候不成立"）。
- **张力曲线**：进化型（傅远洲翻看手册——看到"乔落"的签名出现在七个章节——每次出现都是事故后。"不是她写了七章——是她处理了七个事故——每个事故——手册之前都没有覆盖到。手册在成长——和乔落一起。")
- **六拍骨架**：
  1. 问题先出：手册有了多个签名——傅远洲、乔落、四个补充者的名字
  2. 为什么痛：手册不再是"傅远洲的知识"——是"驿河的集体记忆"——"傅远洲不来——手册在——比傅远洲更完整——因为不止他一个人在上面写了"
  3. 引出方法：runbook的生命力——不来自"写得完整"——来自"被补充过"——每一次补充证明手册是活的
  4. 项目落地：手册增加版本记录——每次更新记录：谁、什么事故后、改了什么——"不是审计——是让后来者看到——这本手册是很多人凌晨的代价。"
  5. 多方复盘："傅远洲不在——驿河不会死——因为手册在——手册上有乔落的名字——有其他人的名字——他们凌晨接传讯牌——他们写了手册——他们就是驿河。"
  6. 高层收束：最好的手册——不是"完整"——是"被补充过"。每一个补充——都是一个凌晨的故事。

### 第88章：不是一个人的平台

- **核心对象层**：人→人→史（手册更新签名不再只有傅远洲。传讯牌不再只等傅远洲醒来。决策不再只等傅远洲点头。"不是傅远洲不重要了——是驿河不再只有他一个'知道该怎么办的人'。"）
- **核心相与失守**：（正向——去中心化。"一个平台——如果只有一个人在凌晨知道怎么办——那不是平台——是那个人的延伸。"）
- **工程锚点**：制度去中心化——on-call轮值、postmortem、runbook协作、变更声明——所有这些制度的目标不是"让傅远洲管理更好"——是"让傅远洲不在时——驿河能自己运转"。
- **张力曲线**：成就感型（傅远洲看着记录板——"服务所有权——不再只有我的名字。传讯牌轮值——乔落这周。手册——七个签名。变更声明——团队自己写——自己审核。""我还在——但我不再是驿河全部的地板。")
- **六拍骨架**：
  1. 问题先出：傅远洲发现——他已经连续三个星期没有在凌晨被传讯牌叫醒
  2. 为什么痛：不是他变懒了——是"驿河有了自己的免疫系统——凌晨接传讯牌的人在手册上写了——下一个接的人就会了——不需要他"
  3. 引出方法：平台不是一个人的——是所有人的凌晨和所有人的手册签名
  4. 项目落地：记录板上——服务所有权表——每个服务后的签名——来自整个团队——不只是"傅远洲"
  5. 多方复盘："当我不在时——驿河还在运行。不是因为我建得好——是因为手册上有他们的签名——他们凌晨学了——他们写了——他们变成了后来者的地板。"
  6. 高层收束：一个人建的平台——是"那个人+51个服务"。所有人的平台——是51个服务+23个人+手册上无数签名。"平台——不是代码——是人。"

### 第89章：新手之后

- **核心对象层**：人→人（乔落能接住了——但制度够不够让所有后来者都能接住？"不是每个新手都是乔落。不是每个凌晨接传讯牌的人——都有勇气写'待补'——都有能力判断'手册的假设还成立吗'。"）
- **工程锚点**：制度与人的关系——制度给地板——但判断力是天花板。不是每个后来者都会在凌晨做正确判断——但制度至少让他们不至于掉到底——让判断正确的人能站到天花板上——把学到的写进手册——让判断力变成下一个人的地板。
- **张力曲线**：反思型（傅远洲——"乔落是特例——不是所有新手都像她。但制度——就是为'不是特例'的人设计的。制度不假设每个人都会在手册上多写一行——制度只保证——即使你不写——你也不会掉到地底下。"）
- **六拍骨架**：
  1. 问题先出：傅远洲反思——"乔落做到了——但下一个凌晨接传讯牌的新人——能做到吗？"
  2. 为什么痛：不能假设每个新手都是乔落——但制度应该让"不是乔落"的人——也至少有地板可站
  3. 引出方法：制度的合理预期——制度不能培养判断力——但制度能给判断力留空间——手册上的"待补"——是邀请——不是要求
  4. 项目落地：手册加了"假设"章节——"此手册的每一步——基于以下假设。如果你的情况不符合这些假设——此步可能不适用——你需要判断。"
  5. 多方复盘："最好的制度——不是告诉人每一步怎么走——是告诉人'我假设了什么'——然后说'如果你的路和我的假设不一样——你需要自己判断'。"
  6. 高层收束：制度是地板。判断是天花板。不是每个人都能到天花板——但每个人都不该掉到地板下面。地板让人站着——天花板等人来建。

### 第90章：平台之前

- **核心对象层**：人→阵（过渡章——一个人（傅远洲）到一群人（驿河团队）——但一群人需要什么？"一群人不是各做各的——是共享判断、共享告警、共享凌晨——但不共享混乱。"——这是卷十的命题：共同体治理。）
- **核心相与失守**：（过渡。）
- **工程锚点**：从个人领导到平台治理——个人领导靠"傅远洲判断"——平台治理靠"共享的制度+共享的价值观+共享的自反意识"。"一群人——不是一个人的延伸——是一群各自在凌晨接过传讯牌的人——共同维护'后来者的地板'。"
- **张力曲线**：过渡型（傅远洲在记录板前——"我建的——都在。所有权——on-call——观测——契约——行序——删模版——runbook。但这些都是'工具'——工具能让一群人协作了——但'协作'不等于'共同治理'。共同治理是——每一个人都觉得——'这个平台是我的——不是傅远洲的'。"）
- **六拍骨架**：
  1. 问题先出：驿河有了所有制度——但"制度是傅远洲建的"——还是"傅远洲的驿河"
  2. 为什么痛：人去中心化——但"归属感"没有去中心化——团队还在"执行傅远洲的规则"——不是"我们的规则"
  3. 引出方法：从"执行制度"到"共同治理"——需要让团队参与制度的制定和修订——不只是"按手册做"
  4. 项目落地：向卷十过渡——"SLO/SLI——服务目录——feature flag——零停机——这些需要整个团队一起决定——不是傅远洲一个人写了就成。"
  5. 多方复盘："最好的平台——是'我们的平台'——不是'他的平台'。制度是地板——但地板是谁铺的——决定了谁会觉得'这是我的地板'。"
  6. 高层收束：一个人建的是平台。一群人共同维护的——是共同体。向卷十——共同体治理——过渡。

> 📝 卷尾。乔落完成从"按手册做"到"判断手册的假设还成立吗"的成长。postmortem文化建立。runbook从个人知识变成集体记忆。手册签名去中心化。向卷十（平台——共同体治理——SLO/SLI——远古告警加速）过渡。
