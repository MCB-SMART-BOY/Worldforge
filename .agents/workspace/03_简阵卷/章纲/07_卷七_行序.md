# 卷七「行序」Ch 61-70：变更影响与跨卷入侵

## Section 总览

- **章段**：Ch 61-70
- **叙事主题**：变更不是"改代码"——是"改运行中的系统的行为顺序"。驿河的51个服务像多米诺骨牌——推倒一块，后面全倒。本卷揭示行序（变更顺序与影响传播）的核心命题：契约管"什么"，行序管"什么时候"和"影响谁"。
- **核心冲突**：跨卷模块进入共享平台——白又新将`seasonal-settlement-validator`带到驿河试运行。接入表沿用温故来维护的512MB平台默认预算，未做十一集群全量负载验证；叠加共享池余量不足与既有泄漏，凌晨一点十四分OOM Killer终止进程，乔落接传讯牌。
- **工具链阶段**：变更影响声明 / 回滚设计 / 部署窗口 / 默认值审计 / postmortem雏形
- **对象层**：门→史（从服务边界到变更的历史——每一次变更都在写后来的历史）
- **主相→蚀**：流 → 乱流（OOM——十一集群全量批次约需2.3GB，超出接入表沿用的512MB模板预算；与既有泄漏、共享池余量不足共同形成压力，512MB不是模块在息壤测出的上限，也不能单独解释进程为何被杀。）
- **主角状态**：傅远洲从边界治理进入时序治理——发现"顺序"本身就是一种契约。乔落第一次独立面对跨卷事故——在回滚手册上多写了一行注。
- **跨卷锚点**：**Ch65-68 被入侵（化形卷→简阵卷）**——白又新携息壤模块到驿河，目标负载和平台默认预算没有在接入前核清。**Ch69 修补者谱系锚点**——驿河接入模板的512MB默认值由温故来维护，选择依据稍后在旧版手册中找到。
- **卷尾落点**：事故处理了——默认值的来源与依据也已追到：温故来维护了接入模板，计算草图夹在旧版手册里。下一步是把分离的依据放回默认值审计，让后来者就近复核。

### 第61章：不是越快越好

- **核心对象层**：门→史（一个内部优化——改了一个服务的内部实现——接口没变、契约没变——但在改之前运行的三个服务更快——它们比改之前提前200ms到达下游——下游的限流逻辑被触发——连锁拒绝。不是快不好——是"越快"改变了调用链的时序——而时序本身是一种隐式契约。）
- **核心相与失守**：流 → 乱流（变更改变了调用时序——时序在契约之外——但时序炸了——因为"什么时候"和"什么"一样重要）
- **工程锚点**：变更影响分析（change impact analysis）——不是"改了会不会炸自己"——是"改了会不会炸依赖你的人"。四层影响：(1) 接口层——改了API (2) 行为层——改了逻辑 (3) 时序层——改了速度 (4) 资源层——改了消耗。大多数变更管理只管(1)和(4)——(2)和(3)在盲区。
- **张力曲线**：倒钩型（优化成功——响应时间从1,200ms降到800ms——团队庆祝——三十分钟后——下游限流器被触发——因为请求到达更快了——限流窗口内的请求数超过了阈值——"我们让它变快了——它因为太快而炸了。"）
- **角色焦点**：傅远洲（"快不是总好。快改变了时序——时序是另一种契约。不是签在proto文件里的契约——是签在'运行中的相对速度'里的契约。"）
- **六拍骨架**：
  1. 问题先出：一个工程师优化了`rate-limiter`的内部逻辑——响应时间从1,200ms降到800ms——部署上线。接口没变，契约没变，编译通过，测试通过。
  2. 为什么痛：下游`settlement-engine`的限流逻辑开始拒绝请求——因为请求到达更快了——在相同的限流窗口内到达了更多请求——"rate-limiter"现在每秒发送更多请求——下游不知道上游变快了。
  3. 引出方法：时序是隐式契约——不在proto里——在调用链的相对速度里。变更影响分析必须包括时序维度。"不是你改了啥——是你改了之后——上下游的相对速度变了没有。"
  4. 项目落地：傅远洲在变更流程中加了第四项检查——"时序影响声明"——任何改变响应时间的变更——必须声明"我的速度变了——从X到Y——以下服务可能受影响。"
  5. 多方复盘："这不是bug。优化是正确的。但'正确'不等于'安全'。安全=正确+不影响依赖者的时序假设。"
  6. 高层收束：不是越快越好——是"快之前——先告诉所有依赖你的人——我要变快了——你们准备好了吗"。

- **并发/观测/简洁/部署**：时序竞争/观测到"快了→炸了"的完整链路/gRPC调用链时序→可见/Ch57 deploy/rollback框架内

### 第62章：变更影响声明

- **核心对象层**：门→门（从"改了再说"到"先说会影响到谁"——变更影响声明（change impact statement）成为驿河的强制流程。不是限制变更——是让变更的代价被提前看见。）
- **核心相与失守**：契 → 背契（没有声明就是背契——不是背了API契约——是背了"我会告诉你我变了"这个公共承诺）
- **工程锚点**：变更影响声明（change impact statement / RFC / change advisory board）——变更不是个人的事——是公共事件。声明格式：(1) 变更了什么 (2) 为什么变 (3) 影响谁 (4) 怎么验证 (5) 回滚路径。
- **张力曲线**：对峙型（"写这个声明要半个小时——比写代码还长。""对。因为代码只影响你自己——声明影响所有依赖你的人。改代码是五分钟——但不告诉别人你改了——别人可能要花五个小时排查。"）
- **六拍骨架**：
  1. 问题先出：Ch61的事故让傅远洲意识到——没有变更声明流程——每次变更都是对依赖者的突袭
  2. 为什么痛：优化者出发点是好的——但没有告诉下游"我要变快了"——下游在不知情的情况下被突袭
  3. 引出方法：变更影响声明——不是审批——是公告。"不需要我批准你改——但我需要你告诉我你要改——这样我能检查我的假设是否还成立。"
  4. 项目落地：傅远洲在记录板上写下变更五问——每个变更必须回答——回答贴在变更记录板上——所有依赖者订阅
  5. 多方复盘："公告不是负担。是让依赖你的人——不至于在你改完之后——凌晨接传讯牌。"
  6. 高层收束：变更是公共行为。代码可以私有——但变更的代价是公共的。

### 第63章：回滚有路

- **核心对象层**：史→史（回滚不是"退回去"——是"知道退到哪里"。大多数回滚失败不是因为"回不去"——是因为"不知道上一个好的版本是哪个"。）
- **核心相与失守**：史 → 断史（没有回滚路径的变更——等于没有退路的行军。如果不知道上一个好的版本在哪——每一次变更都是单程票。）
- **工程锚点**：回滚设计（rollback design）——不是"部署系统支持回滚"就够——是"每次变更前——先确定回滚目标版本——先验证回滚路径——先确保回滚比部署更快"。回滚窗口应该比部署窗口更短——因为回滚是紧急情况——紧急情况下人不该等。
- **张力曲线**：反思型（傅远洲检查驿河的回滚记录——发现过去三个月有11次部署——3次需要回滚——只有1次回滚成功——另外2次回滚失败是因为"不知道滚回哪里"——上一个版本已经被覆盖了。）
- **六拍骨架**：
  1. 问题先出：回溯三个月部署纪录——11次部署——3次回滚——2次失败。失败原因：不知道回滚目标版本。
  2. 为什么痛：每次部署覆盖了上一个版本——没有保留"上一个好的"——回滚变成了"往前猜"——不是"往回退"
  3. 引出方法：回滚不是部署的反向——是独立的操作。部署前必须标记"当前版本=已知好的版本"——标记持久化到部署记录——不被后续部署覆盖
  4. 项目落地：傅远洲在部署系统中加了"回滚锚点"——每次部署前自动记录当前版本号+部署时间+部署人——回滚时从锚点列表中选择
  5. 多方复盘："回滚能成功——不是因为回滚工具好——是因为回滚之前——你知道上一个好的版本在哪里。"
  6. 高层收束：回滚不是选择——是部署的一部分。没有回滚路径的部署——不是部署——是赌博。

### 第64章：部署窗口

- **核心对象层**：流→流（部署窗口（deploy window）——不是"什么时候能部署"——是"什么时候部署不会杀人"。凌晨对账时间——绝对不能部署。月末结算——绝对不能部署。不是限制自由——是保护"不影响别人"的边界。）
- **核心相与失守**：流 → 乱流（没有部署窗口——任何时候都可能被变更打断——"随时可以部署"意味着"随时可能被别人的部署炸到"）
- **工程锚点**：部署窗口（deployment window / change freeze）——关键业务时段禁止变更——不是官僚——是对运行时稳定性负责。三类时段：(1) 自由窗口——随时部署 (2) 受控窗口——需要额外声明 (3) 冻结窗口——禁止任何非紧急变更。
- **张力曲线**：对峙型（"为什么我不能下午部署？""因为下午四点是结算高峰——你的部署如果出问题——影响的不是你的服务——是所有依赖结算的服务。你可以部署——但在晚上八点之后。"）
- **六拍骨架**：
  1. 问题先出：一个工程师下午四点部署——出问题——影响了正在进行的对账——对账中断——影响到结算——影响到商户——连锁
  2. 为什么痛：不是他故意的——是没有部署窗口——他不知道"什么时候不能部署"
  3. 引出方法：部署窗口——不是限制——是告知。"在哪些时段——你的变更可能会伤害别人。"
  4. 项目落地：驿河设立三类时段——基于对账周期、结算周期、峰值时段——全平台公开
  5. 多方复盘："部署窗口不是'你不能'。是'如果你在这个时段部署——你要额外小心——因为很多人依赖现在的稳定性。'"
  6. 高层收束：自由有边界——边界不是压制自由——是让自由不妨碍别人的自由。

### 第65章：模块接入

- **核心对象层**：门→门→阵（**跨卷入侵章——被入侵**。白又新从化形卷过来——将息壤的`seasonal-settlement-validator`模块部署到驿河。这个模块在化形卷Ch85构建——用于验证季节性结算数据——现在需要驿河的计算资源。）
- **核心相与失守**：流 → 乱流（跨卷模块接入暴露出不同平台的资源假设；息壤测试与驿河长期服务并非同一场景，接入表中的512MB来自驿河旧模板。）
- **工程锚点**：跨平台模块部署——对照模块在息壤的单机、手动、小批量观察与驿河的共享、长期运行条件；接入表预填的512MB是平台默认预算，不是模块实测的安全上限。部署前要核对目标负载、共享资源竞争和依赖服务可用性。
- **张力曲线**：悬疑型（傅远洲在申请上看到512MB，追问它来自模块还是平台模板；白又新拿出MRC与息壤的测试观察，却无法证明驿河的全量负载。两人发现同一个数字并不意味着同一份资源声明。）
- **角色焦点**：白又新（跨卷人物——从化形卷过来的"被入侵者"——他在做正确的事——让模块在更多平台可用——但"正确"在另一个平台可能变成"危险"）。傅远洲（"不是你的模块有问题——是它假设的世界——和驿河不一样。"）
- **六拍骨架**：
  1. 问题先出：白又新携带息壤模块`seasonal-settlement-validator`来到驿河——模块在息壤验证通过——请求部署
  2. 为什么痛：息壤的手动小批量测试不能证明驿河长期服务安全；驿河模板预填512MB预算，但没有十一集群全量批次的目标负载数据。
  3. 引出方法：跨平台部署的三检查——(a) 默认值审计——默认值在新环境中是否合理 (b) 资源竞争模型——新环境中资源如何分配 (c) 依赖可用性——依赖的服务在新环境中是否可用、SLA是否相同
  4. 项目落地：傅远洲和白又新共同审计——三栏都有记录，却没有目标负载测量；把未知项标成“首轮运行后复核”，允许短时试运行。检查表没有规定未知项必须阻止上线，埋下Ch67事故的流程缺口
  5. 多方复盘：跨卷模块接入——不是"能跑就接入"——是"验证它的假设在新环境中是否成立"。"模块是可移植的——但模块的假设不是。"
  6. 高层收束：一个模块从一个世界到另一个世界——它的代码没变——但它运行的世界变了。代码可移植——但假设不可移植。

- **跨卷锚点**：此行径化形卷Ch85-88（模块构建→发布→在不同环境运行）。白又新从化形卷到简阵卷——"被入侵"的入侵者视角。

### 第66章：512MB的默认值

- **核心对象层**：史→史（512MB是沿用的模板预算。当前配置没有写明适用负载，傅远洲先追查来源，再把这项审计扩展到全平台默认值；Ch74会找到分离在旧版手册中的计算依据。）
- **核心相与失守**：史 → 断史（现行配置、部署记录和接入文档只留有默认值，暂时没有附带选择依据；Ch74才从旧版部署手册找到笔记和草图。依据曾被保存，却与模板配置分离，无法就近复核。）
- **工程锚点**：默认值审计（default value audit）——数字需要连同环境、负载和选择依据一起传递。温故来曾留下计算草图，但它夹在旧手册里，与接入模板配置分离；现行记录不便复核，因此傅远洲要把依据与默认值放回同一处。
- **张力曲线**：考古型（傅远洲确认512MB来自旧版驿河服务接入模板，维护者为温故来；现行资料里没有选择理由，他继续翻找旧手册，不把“没找到”写成“从未留下”。）
- **角色焦点**：傅远洲（先从现行材料中追查温故来与512MB的关系；他只确认依据暂时未附在配置旁，不把“没找到”写成“从未留下”。）
- **六拍骨架**：
  1. 问题先出：驿河接入表预填的512MB默认预算让傅远洲警觉——全平台还有多少默认值需要按新负载重新核对
  2. 为什么痛：当前可查资料没有显示选择依据；默认值自身未必错误，但后人无法复核它成立的环境与计算。
  3. 引出方法：默认值审计的四个问题——(a) 谁设的 (b) 什么时候设的 (c) 当时的环境是什么（多少服务/多少资源）(d) 为什么是这个数字——不是其他数字
  4. 项目落地：傅远洲启动全平台默认值审计——发现至少23个默认值"理由不可追溯"——包括512MB
  5. 多方复盘：先记录当前缺口，继续寻找旧版部署手册；暂不判断当年的选择是否合理。
  6. 高层收束：默认值不是数字——是历史决策。历史决策的"为什么"——必须和数字一起传递。否则——后人看到的只是一个随机的数字。

### 第67章：OOM

- **核心对象层**：流→流（凌晨一点十四分，驿河共享资源池余量耗尽，OOM Killer终止`seasonal-settlement-validator`；传讯牌响，乔落接班排查。）
- **核心相与失守**：流 → 乱流（OOM——共享资源余量耗尽。不是突然的——从Ch43的goroutine泄漏到Ch65的模块接入，累积压力在凌晨找到出口。驿河模板沿用的512MB默认预算没有说明十一集群全量批次的需求；该批次需求约2.3GB，资源池余量不足时进程被内核终止。）
- **工程锚点**：OOM Killer——Linux内核在系统内存不足时的处理机制之一，会终止进程以释放资源。模块`seasonal-settlement-validator`因全量批次占用高而被选中；512MB是沿用的默认配置，不是这次峰值负载的测量结果。正文不把它写成通用硬上限，也不把进程被杀归结为单一服务的道德过错。
- **张力曲线**：崩塌型（十一集群全量负载与既有共享池压力叠加→资源余量见底→OOM Killer终止模块→三个下游服务超时。乔落用迹、脉、势核对事件、断点和资源曲线，发现模块是最后一项变更，却不是唯一压力来源。）
- **角色焦点**：乔落（第二次凌晨接传讯牌——但这次不是"刚好醒着"——这次是on-call。她通过三视图将内存曲线、下游trace断点和模块处理日志对上；看到的是资源余量耗尽与影响链，不声称三视图能单独证明所有历史负载。）
- **六拍骨架**：
  1. 问题先出：凌晨一点十四分——共享资源余量耗尽——OOM Killer杀死`seasonal-settlement-validator`
  2. 为什么痛：接入表沿用的512MB平台默认值没有十一集群全量批次约2.3GB的依据；资源池余量与既有泄漏共同构成压力，模块是触发变更，不是唯一来源。
  3. 引出方法：OOM的根因不是内存不够——是没有人审计过"每个服务到底需要多少内存"——默认值替代了真实测量
  4. 项目落地：乔落按Ch63的已知版本回滚锚点恢复服务；她不把512MB直接改成未经验证的新上限，也记录跨平台回滚手册的缺项。
  5. 多方复盘：追查默认预算的来源和跨平台接入缺少的资源复核；OOM不是单个模块的过错，而是全量负载、共享池余量、既有泄漏和未完成的检查共同作用。
  6. 高层收束：OOM不是内存问题——是"默认值替代了理解"的问题。当每个人都在用默认值——没有人知道"真正需要多少"。

- **并发/观测/简洁/部署**：goroutine泄漏累积/三视图核对OOM时刻/把平台默认值误当资源声明/按Ch63已知版本锚点回滚

### 第68章：回滚路径标注"待补"

- **核心对象层**：史→史（**乔落的继承者时刻**。模块回滚成功了——但回滚手册上的路径不完全——有些步骤只写了"参照标准流程"——但标准流程里没有"跨平台模块回滚"的特殊处理。乔落在回滚完成后——在手册上多写了一行："以下步骤默认模块来自驿河内部。跨平台模块——需额外检查第4、第7步。待补。"）
- **核心相与失守**：（继承——正向。不是修补缺陷——是让后来者不会在同一个坑里踩第二次。）
- **工程锚点**：runbook的持续进化——不是一次写完——是每次事故后由处理者补充。乔落的那行注——不是代替傅远洲的工作——是在傅远洲写的基础上——加了她在凌晨一点学到的。"runbook的签名——从'傅远洲'——变成'傅远洲、乔落'。"
- **张力曲线**：沉静型（事故过后——凌晨三点——乔落在回滚手册上写字——旁边是冷却的传讯牌。窗外是驿河的深夜——傅远洲在赶来的路上——但她已经处理完了——"手册上说'参照标准流程'——但标准流程没有这一步。我补了一行。"）
- **角色焦点**：乔落（她的成长弧线的高光——从Ch13"凌晨两点接传讯牌不知道该怎么办"到"独立处理——并在手册上为后来者留下标注"。不是"我会了"——是"后来者不需要再学一次我学到的"。）
- **六拍骨架**：
  1. 问题先出：回滚成功——但手册上的跨平台回滚步骤不完整
  2. 为什么痛：如果下一个接传讯牌的人遇到同样的情况——手册不能告诉他"多出来的步骤"——他需要重复乔落凌晨的摸索
  3. 引出方法：runbook不是固定文档——是活的——每次事故后由处理者补充"之前没说清楚"或"之前没覆盖"的部分
  4. 项目落地：乔落写了那行注——"待补"——她知道不完整——但承认不完整比假装完整更重要。"后来者看到'待补'——会知道这里需要注意——会小心——会比完全空白好。"
  5. 多方复盘：傅远洲看到那行注——"你写了'待补'。""因为我不确定下一步是什么——但我知道这里有坑——我标注了——后来者至少不会一脚踩进去。"
  6. 高层收束：最好的继承——不是在手册写满所有答案——是标注"这里还有问题——我还没解决——你注意"。标注不完整——比假装完整——更诚实——更有用。

- **跨卷锚点**：乔落的注——与化形卷纪承钧的runbook形成跨卷对照。纪承钧的runbook炸在息壤（化形卷Ch55-58）——因为他写了完整的步骤但没写"为什么"。乔落的注——承认不完整——但标注了"注意"。"完整的地图可能让人走错——因为地图上的路——不等于现在的路。标注'待补'——至少后来者知道——这不是完整地图。"

### 第69章：追踪512MB

- **核心对象层**：史→史（**修补者谱系锚点**。傅远洲追到温故来维护过驿河接入模板；现有配置只能确认维护者，尚不能证明谁具体选择了512MB。选择依据仍待继续追查。）
- **核心相与失守**：史 → 断史（傅远洲先在服务接入模板、配置和版本记录里找不到512MB的选择依据，暂时无法判断理由是否曾被保存。Ch74翻到旧版部署手册里的笔记和草图，才确认温故来曾按11个服务、8GB机器和约2.4GB余量计算；问题不是毫无记录，而是依据与配置分开，后来者一时无法复核。"）
- **工程锚点**：默认值的历史语境——数字要连同当时的资源、负载和假设一起复核。服务数从11增至51提示需要重算，但不能单凭规模断言512MB当年正确或如今必然失效；Ch74找到草图后，仍须按当前全量负载与共享池条件验证。
- **张力曲线**：考古揭示型（傅远洲从Ch66开始追查，先在正式配置中找不到依据，后在旧版部署手册里找到温故来的笔记——'先看负载模式再设'及11个服务的内存草图。谜底从'没有留下'改为'留下了，但没有和默认值放在一起'。"）
- **角色焦点**：傅远洲（找到旧版部署手册中的计算草图，意识到依据曾被保存，只是没有和配置放在一起；需要把“判断+前提+计算”写到后来者能就近复核的位置。）
- **六拍骨架**：
  1. 问题先出：傅远洲追查512MB的来源——通过文档、部署记录、老员工的回忆——追溯到三年前的温故来
  2. 为什么痛：模板只留下512MB，草图藏在旧版部署手册里；判断和依据分开存放，让后人起初无法就近复核。
  3. 引出方法：默认值文档化的双层标准——(a) 默认值本身 (b) 默认值的选择依据——包括当时的负载模式、资源约束、假设。双层必须同时传递——否则(1)没有(2)就是定时炸弹
  4. 项目落地：傅远洲在默认值审计规则中加了第五条——"每一个默认值必须附带选择依据——依据包括当时的资源环境、服务数量、负载模式。"
  5. 多方复盘：温故来按当时负载作了计算，也留了草图；修补者教的“先看负载模式再设”传了下来，但依据没有附在模板旁边。
  6. 高层收束：判断的依据也要和判断一同传给后来者；如果存放位置分离，后人就可能只见数字，不见它成立的条件。

- **修补者谱系锚点**：温故来是修补者的学生，曾维护驿河接入模板。512MB由该模板带入；Ch74找到与它相关的计算草图，但材料不足以证明维护者就是设值者，也不足以证明预算在所有当时负载下都安全。草图与配置分开保存，后来者难以就近复核。修补者关于“前提也要传递”的自我修正，将在卷十一成为主题回响。

### 第70章：行序之后

- **核心对象层**：史→史（事故处理了——模块回滚了——默认值审计启动——乔落在手册上写了注。傅远洲追到512MB的来源，也找到分开存放的计算依据；后续要把各类默认值的适用前提就近记录。）
- **工程锚点**：变更文化从"行序技术问题"到"行序文化问题"——不是工具不够——是"做判断的依据——需要和判断一起传递"。这个文化转变不是一卷能完成的——它指向卷八（删模版——为什么某些东西必须留下）、卷十一（修补者的承认——"我没有教完"）。
- **张力曲线**：收束型（傅远洲站在记录板前——上面新加了：回滚锚点、部署窗口、变更五问、默认值审计五条。乔落在旁边——她的那行注已经被合并进正式手册。"行序有了——但行序的代价——是乔落凌晨一点十四的传讯牌。所有制度——都是某个人的凌晨。"）
- **角色焦点**：傅远洲（"制度能防止很多事——但制度是建立在别人的凌晨上的。乔落凌晨一点十四接牌——我们才有了'跨平台模块部署三检查'。制度不是凭空想出来的——是在事故中——被接传讯牌的人——用代价换来的。"）
- **六拍骨架**：
  1. 问题先出：OOM事故复盘——行序体系的缺口被系统性地填补
  2. 为什么痛：不是因为缺制度——是因为每一次制度都是"出了事才写"——而"出事"意味着有人在凌晨接了传讯牌
  3. 引出方法：行序体系——变更声明+回滚锚点+部署窗口+默认值审计——不是结束了——是开始了。"这些制度——下一卷要面对新问题：模板太多——制度太多——哪些是真的必要的？"
  4. 项目落地：行序体系建成——但傅远洲知道——"这些制度——有多少是'因为出过事所以有了'——有多少是'因为真的需要所以有了'？我们会不会在另一个方向上走太远——制度太多——和模板太多——是同一种病？"
  5. 多方复盘：卷七的终结——向卷八（删模版）过渡——"我们现在有了制度——但制度本身需要被删减。43条传讯牌变成有意义的告警——但制度——也需要从43条变成4条。"
  6. 高层收束：行序让变更有了顺序。但顺序只是手段——不是终点。终点是——"让后来者——即使在没有你的凌晨——也知道往哪走。"

> 📝 卷尾。行序体系建成——但512MB的默认值指向更深的问题：修补者的教育有空白。向卷八（删模版——极简主义+制度vs空白对话）过渡。Ch65-68完成跨卷入侵（被入侵：化形卷模块在驿河OOM）。Ch69锚定修补者谱系（温故来=修补者的学生）。乔落在Ch68写下"待补"——继承者成长的关键时刻。
