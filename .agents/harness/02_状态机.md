# 02 · 状态机

> 定义各类产出物的生命周期。下图展示常见状态关系与任务闭环；章纲、正文设计、正文和审阅记录分别维护状态，不要求每章都创建每类产物，也不代表所有任务必须线性经过每一项。

## 一、核心状态

各类产出物各自维护状态；项目任务按本次目标闭环，不要求每项产出都存在：

```
章纲：待建 → 已完成       正文设计：待建 → 已完成       人物卡/资料：按各自用途更新

正文：待写 → 草稿 → 待审 → 审阅中 → 已审 → 完成
                           审阅发现问题：审阅中 → 修改中 → 审阅中

任务：明确范围 → 执行 → 复核 → 记录结果与续接点
```

## 二、状态定义

### 2.1 章纲（Chapter Outline）

| 状态 | 含义 | 如何判断 |
|------|------|---------|
| `待建` | 有明确章纲需求，但尚无可供执行的内容 | 按目标章纲索引和正文规划核对 |
| `已完成` | 设计足以支持当前任务；适用时包含工程冲突、人物选择和前后衔接 | 按内容和目标判断，不用文件行数推断 |

**状态格式示例（非当前项目状态）**：
```
驭器卷 Ch51: 章纲 ✅ (已完成) — 2026-06-13
驭器卷 Ch52: 章纲 ✅ (已完成) — 2026-06-13
```

### 2.2 正文设计（Body Design）

| 状态 | 含义 | 如何判断 |
|------|------|---------|
| `待建` | 未开始或仅有占位 | 文件不存在或只有标题 |
| `已完成` | 本章的正文设计文档就绪（读导、样场、入口设计等） | 正文设计文件存在且有实质内容 |

**注意**：不是每章都需要独立的正文设计文件。`正文设计/` 目录通常包含的是卷级设计文档和样场。章级设计由 `design-chapter` 产出，整合在写作流程中。

### 2.3 正文（Prose）

| 状态 | 含义 | 如何判断 |
|------|------|---------|
| `待写` | 章纲已完成，正文未开始 | 文件不存在 |
| `草稿` | 正文已起草，尚未完成作者自查 | 正文存在；结合作者记录确认 |
| `待审` | 作者已完成适用的 Prose Gate，自查后可交审 | 作者自查记录或明确的任务交接 |
| `审阅中` | 正在执行 `review-chapter`、范围审计或人工审阅 | 本次任务已有审阅范围和审阅者 |
| `修改中` | 根据审阅意见修订；修订后需回到审阅 | 正文与待处理意见可对应 |
| `已审` | 指定范围已形成审阅结论；未解决项已修复或明确记录为遗留/待决 | 可追溯的审阅记录，结论与遗留项清楚；不得只凭“审过”字样判断 |
| `完成` | 本次任务约定的审阅/修订已完成，回读过相关上下文且记录已更新 | 目标清单、正文和相关账本/索引相符；不代表全卷或作品永久定稿 |

**状态流转规则**：
- `待写 → 草稿`：正文起草完成
- `草稿 → 待审`：作者完成适用的 Prose Gate 自查
- `待审 → 审阅中`：按目标范围开始专项或人工审阅
- `审阅中 → 修改中`：审阅发现需处理的问题
- `修改中 → 审阅中`：修订后回查受影响问题
- `审阅中 → 已审`：本次范围的问题已处理，或明确记录为遗留、待决及后续动作
- `已审 → 完成`：约定的修订已回读，相关索引/账本已更新；遗留项有明确状态。是否提交由作者另行决定

### 2.4 人物卡（Character Card）

| 状态 | 含义 | 如何判断 |
|------|------|---------|
| `待建` | 角色已命名但卡未写 | 文件不存在 |
| `骨架` | 人物卡已有基本定位，仍缺重要动机、代价或关系信息 | 结合人物卡用途和明确未决项判断 |
| `已完成` | 本次任务所需的人物信息已交代，未决内容标出证据状态 | 不以固定 section 数或无“待补”字样代替核验 |

### 2.5 资料（Research/Reference）

| 状态 | 含义 |
|------|------|
| `待建` | 资料条目已知，未收集 |
| `初稿` | 资料已收集，未整理 |
| `已完成` | 资料整理完毕，可作为写作参考 |

## 三、全卷状态汇总格式

### 3.1 卷级状态表（仅在工作区索引或章纲确有此表时维护）

这里的 `00_卷索引.md` 指 `.agents/workspace/XX_卷/00_卷索引.md`，用于工作资料导航和可选状态汇总；它不是正文的正式阅读顺序。正文顺序与稿件类别以卷根目录 `00_正文索引.md` 为准（仅部分卷当前有该索引）。

```markdown
## 📊 进度状态

| 卷段 | 章范围 | 章纲 | 正文设计 | 正文 | 审阅 | 备注 |
|------|--------|------|---------|------|------|------|
| 示例分组 | 按已确认的卷内范围填写 | … | … | … | … | 示例格式，不代表当前项目映射 |
```

### 3.2 进度编码

| 编码 | 含义 |
|------|------|
| `✅` | 全部完成 |
| `N/总数` | 在已确认范围内 N 项完成；总数由对应索引/任务定义 |
| `—` | 不适用（如正文设计不是章级产物） |
| `🔴` | 有阻塞问题 |
| `🟡` | 进行中 |
| `⚪` | 未开始 |

## 四、状态变更触发条件

### 4.1 章纲：待建 → 已完成

**触发条件**：
- 目标章纲已有足够材料支撑当前设计或写作；如采用六拍结构，各拍信息具体而非占位
- 工程主题与涉及术语能准确说明；不按术语数量设门槛
- 与本章功能相关的张力、揭示和人物代价已考虑；不强制统一曲线
- 场景涉及世界观/人物责任时，能指出适用的三问或说明不适用原因

### 4.2 正文：待写 → 草稿

**触发条件**：
- 正文文件已创建
- 正文已形成可供回读的连续稿件；项目没有统一的硬性字数门槛
- 稿件类别和路径符合该卷现行正文索引（若有）

### 4.3 正文：草稿 → 待审

**触发条件**：
- 作者已完成与本章相称的 Prose Gate 自查
- 目标范围、必要上下文和未决事实已标明，便于审阅

### 4.4 正文：待审 → 审阅中 → 已审

**触发条件**：
- 已按用户目标进行专项或人工审阅；对本次范围中适用的问题作出处理或明确留项
- 不把模板项全勾视为质量结论；涉及正典、工程事实或跨卷映射的断言须有可核证据
- 六拍、三问等结构工具按对应写作规则和场景实际使用，不以形式缺项自动判为失败

### 4.5 正文：已审 → 完成

**触发条件**：
- Review Gate 中的硬约束已满足；建议项和待决项已说明，不把未解决的阻断问题标为完成
- 修改已回读，实时账本与受影响索引已更新
- 是否提交由作者另行决定，不影响审校状态

## 五、全局状态追踪

`.agents/workspace/正文全卷审校进度.md` 是当前全项目正文审校状态的唯一实时来源；旧状态快照已归档于 `.agents/docs/audits/2026-06-21-progress-panel.md`，不代表当前状态。每完成一批审校，更新：

1. 实时账本 `.agents/workspace/正文全卷审校进度.md`
2. 受影响卷的 `00_卷索引.md` 或章纲状态表（确有对应记录时）

### 更新流程

```
完成一章
    │
    ├── 更新实时审校账本
    │   └── 记录已读范围、修改、未决项和续接位置
    │
    └── 仅在卷索引/章纲确有对应状态栏时同步更新
```

## 六、状态查询

### 6.1 快速查询："现在做到哪了？"

1. 读 `.agents/workspace/正文全卷审校进度.md` → 查与当前任务有关的最近记录
2. 按用户目标和账本中的未决项确定工作对象，不从历史快照推断顺序
3. 读对应索引、章纲、正文和前后文 → 开始工作

### 6.2 精确查询："第X卷第Y章是什么状态？"

1. 若存在，读 `.agents/workspace/XX_卷/00_卷索引.md` 中对应状态表；它没有该表时不自行补造映射
2. 读正文文件（如存在）→ 确认实际状态

### 6.3 批量查询："哪些章需要审阅？"

1. 读实时审校账本及相关卷索引
2. 按任务范围识别未完成审阅或待核实事项
3. 遵循账本证据和用户给定的优先级确定顺序

## 七、状态机反模式

| 反模式 | 为什么错 | 修正方式 |
|--------|---------|---------|
| 正文写了但实时账本没更新 | 下次会话不知道实际进展，可能重复或漏审 | 任务结束或暂停时记录已完成范围、待决项和续接点 |
| 把专项审阅当成作者自查 | Prose Gate 与 Review Gate 职责混淆 | 作者先完成适用的 Prose Gate，再按目标范围审阅 |
| 跳过自查直接标记"完成" | 质量门被绕过——问题留在正文里 | 先完成与本次任务相称的自查和复核 |
| "已完成"后偷偷修改正文 | 修改可能使原审阅结论失效 | 重开受影响状态，并重过相应质量门 |
| 状态只在提交时更新 | 实时账本应记录当前工作状态，不依赖是否创建提交 | 按任务进展更新，不以提交作为触发条件 |
