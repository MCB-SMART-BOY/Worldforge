# 03 · 质量门

> 每个流水线阶段的复核框架。先满足用户明确目标和项目硬约束，再用与章节相称的检查项复核；不是为了清单打勾而制造固定篇幅或结构。

## 质量门全景

## 一、Prep Gate（准备门）

**位置**：Phase 1 结束时
**目的**：确认有足够的信息开始设计

| # | 检查项 | 判定标准 | 不通过时的动作 |
|---|--------|---------|--------------|
| P1 | 章纲已读取 | 已读目标章的章纲文件 | 去读章纲 |
| P2 | 前后衔接已核对 | 能说明相关前情和后续约束；卷首、卷尾或无后章时说明不适用 | 读相关正文/章纲；缺失时记录边界 |
| P3 | 工程主题已确认 | 若本章涉及工程内容，能说明相关概念及其事实来源 | 回看章纲、正文和卷设定 |
| P4 | 核心相已确认 | 若本章涉及四相/四蚀，能说明其对应关系；不适用时不强加 | 回看相关 canon |
| P5 | 卷级约束已知 | 能找到本次任务相关的卷级约束；只读适用资料 | 读目标卷对应的现行设定与索引 |

**Prep Gate 通过标准**：已有足够资料支撑本次任务；不适用项说明原因，缺失且会影响判断的资料列为阻断项。不得以 5/5 勾选代替判断。

## 二、Design Gate（设计门）

**位置**：Phase 2 结束时
**目的**：确认设计蓝图足够具体，可以直接进入写作

### 2.1 结构完整性

| # | 检查项 | 判定标准 | 参考 |
|---|--------|---------|------|
| D1 | 章节结构可写 | 核心行动、人物选择和后果形成可写的因果线；若采用六拍，应具体到场景而非占位语 | .agents/canon/15 |
| D2 | 工程主题明确 | 本章所需的工程事实与术语已经确认；不按词数设门槛 | .agents/canon/24 |
| D3 | 术语准确 | 已确认涉及术语的含义、英译及使用语境 | .agents/canon/24 |
| D4 | 世界观表达自然 | 涉及世界观表达时，读者能从场景理解它与工程事实的关系 | .agents/canon/15 |

### 2.2 张力设计

| # | 检查项 | 判定标准 |
|---|--------|---------|
| D5 | 张力形态适配 | 若本章需要显著张力变化，说明其形态；不要求从固定菜单选择 |
| D6 | 关键变化可定位 | 若存在悬念或转折，能指出其发生与作用；不设段落位置 |
| D7 | 节奏可读 | 需要时安排停顿或情绪回落；静场无需人为增加冲突 |
| D8 | 结尾适配 | 结尾按章节功能选择推进、余韵或平静收束，不强制钩子 |

### 2.3 揭示设计

| # | 检查项 | 判定标准 |
|---|--------|---------|
| D9 | 信息边界清楚 | 重要信息的来源、持有人与揭示时机可理解（如适用） |
| D10 | 信息差有意图 | 若依赖悬念或反讽，读者与角色的信息差符合叙事意图 |

### 2.4 预检

| # | 检查项 | 判定标准 |
|---|--------|---------|
| D11 | 三问预检适用 | 🩻 😣 🛤️ 对承担相应功能的章节/场景可预判；不适用时说明 |
| D12 | 入门可及性 | 读者能较早定位场景与核心问题；新概念有语境支撑 |
| D13 | 前后衔接有因果 | 本章结尾与后续发展存在可理解的关系；不要求固定悬念句式 |

**Design Gate 通过标准**：设计能支撑本章写作，工程因果、人物选择、读者信息边界和前后衔接已明确。未适用项注明原因；不按术语数量或勾选比例机械判定。

## 三、Prose Gate（写作门）

**位置**：Phase 3 结束时
**目的**：确认正文质量达到审阅标准

### 3.1 三总裁定（硬约束按适用范围检查）

| # | 检查项 | 判定标准 |
|---|--------|---------|
| W1 | 先工程后修辞 | 若本章涉及工程问题，读者能说清正在处理什么；修辞不掩盖工程因果。纯关系、过渡或余韵段可标不适用。 |
| W2 | 因果规则有边界 | 若设定推动事件或改变世界运行，检查其适用范围、触发条件与失效后果；普通名词、道具、意象和人物假说可标不适用。 |
| W3 | 成长=责任升级 | 若本章推进人物成长，检查选择、责任、关系或代价是否具体；未推进成长时标不适用。 |

### 3.2 六拍结构诊断（按本章适用）

| # | 检查项 | 判定标准 |
|---|--------|---------|
| W4 | 问题先出 | 本章以问题、行动、意象或人物关系进入；开场方式服务场景。 |
| W5 | 代价可感 | 关键问题落到具体角色、工作或关系，不停留在抽象系统名词。 |
| W6 | 工程准确 | 涉及工程方法时保留准确的现实术语，不以世界观隐喻替代它。 |
| W7 | 场景落地 | 工程问题在具体项目与使用情境中成立；玄枢/息壤/驿河/青炉仅为第一阶段示例。 |
| W8 | 视角适配 | 需要展示协作或继承时，纳入相关人物视角；不为满足“多视角”而添角色。 |
| W9 | 主题回响 | 主题可由行动、意象、选择或判断自然浮现，不要求章末格言。 |

### 3.3 张力实际呈现

| # | 检查项 | 判定标准 |
|---|--------|---------|
| W10 | 张力曲线可感知 | 若本章需要明显的张力变化，检查节奏是否读得出来；静场、转场、余韵或平静收束不必人为制造高低起伏。 |
| W11 | 节奏有呼吸 | 高压场景之间有适合本章的停顿、转场或情绪变化，不规定篇幅。 |
| W12 | 结尾有余韵或推进力 | 结尾留下适合本章功能的情感、判断或行动方向；不强制制造悬崖式钩子。 |
| W13 | 代价具体 | 关键选择的后果能落到人、工作或关系上；是否不可逆由事件决定，不人为夸大。 |
| W14 | 人物有温度 | 检查情绪是否完全被分析语言覆盖；冷静可以是人物状态，不能抹去具体处境。 |
| W15 | 因果链清晰 | 每个重要事件有"因为"在前面。没有"太巧"的事件。 |

### 3.4 术语铁律

| # | 检查项 | 判定标准 |
|---|--------|---------|
| W16 | 真实术语保留 | 全文未用世界观术语替换真实工程术语（Cargo 还是 Cargo） |
| W17 | 中文术语注英文 | 章节首次引入中文工程术语时标准确英文；明确复指可省略，跨章重引或歧义时再标（见 canon15/24） |
| W18 | 世界表达可理解 | 读者需要理解其工程含义时，可从场景或上下文看出对应关系；不要求给每个文学意象逐词加注 |
| W19 | 新概念自足 | 新术语在此卷内有够用解释（不假设读者读过别卷） |

### 3.5 入门友好度

| # | 检查项 | 判定标准 |
|---|--------|---------|
| W20 | 读者定位 | 读者在适当位置能辨认场景、视角和当下问题；不设固定字数 |
| W21 | 新术语负荷 | 新术语数量作为预警信号，结合解释密度、章节长度和目标读者判断，不机械截断 |

### 3.6 三问落地

| # | 检查项 | 判定标准 |
|---|--------|---------|
| W22 | 三问按需使用 | 仅对承担病理、代价与后续选择的场景使用 🩻 😣 🛤️；其他场景可标不适用，不要求逐场景作答。 |

**Prose Gate 通过标准**：正文达到用户约定的目标；硬性正典/工程事实没有被修辞覆盖；人物行为有因果和代价；术语遵循现行 canon。其他结构项按题材、叙事视角和本章功能判断，指出的问题要有文本证据与可执行修法，不用得分替代判断。

## 四、Review Gate（审阅门）

**位置**：Phase 4 审阅完成后
**目的**：确认审阅完成且问题已解决

| # | 检查项 | 判定标准 |
|---|--------|---------|
| R1 | 高优问题处理 | 阻断性与高优问题已修复，或明确记录为待决及其影响；建议项不要求全改 |
| R2 | 命名规范正确 | 系列名「万构界」、卷名「《万构界·X卷》」、无 `xx百炼成仙` 残留 |
| R3 | 跨卷引用自足 | 如有跨卷引用，本章内给了够用解释（不假设读者读过别卷） |
| R4 | 跨卷叙述独立 | 共享事件从本卷主角的代价和病理重新叙述 |
| R5 | 文学-工程对照 | 重要表达的含义在读者需要时可从场景或上下文理解；必要时核实工程原型 |
| R6 | 章节间衔接 | 若有连续章节，核对因果、时间与人物状态；跳时或独立篇章说明即可 |
| R7 | 批量一致性 | 如果同批写了多章，章节间无矛盾（人物、术语、时间线一致） |

**Review Gate 通过标准**：本次范围内的高优问题已修复或记录为明确待决；正文、索引和实时账本之间没有被悄悄抹平的事实冲突。其余检查项结合范围和风险使用。

## 五、Commit Gate（提交门）

**位置**：git commit 前
**目的**：确认提交本身符合项目规范

| # | 检查项 | 判定标准 |
|---|--------|---------|
| C1 | 文件名正确 | 符合目标卷正文索引、项目当前命名规则和稿件类别；不因附篇/来源稿套用正式章节名 |
| C2 | 文件位置正确 | 在 `XX_YY卷/` 下 |
| C3 | 无 AI 署名 | 若作者要求提交，commit message 不添加任何 AI 或 agent 共同署名（项目规则：`AGENTS.md`） |
| C4 | Commit message 清晰 | 简洁描述实际修改；除非作者另行规定，不要求套固定卷名或蓝图章号格式 |
| C5 | 无意外文件 | 只包含目标章节和关联的状态更新文件 |
| C6 | 实时账本已更新 | 本次提交涉及的工作范围已记录在实时审校账本 |

**Commit Gate 通过标准**：作者明确要求提交后，提交内容与目标匹配、必要记录已更新、无违反根 `AGENTS.md` 的 AI 署名规则。其他格式项按实际仓库约定执行；不自动 amend。

## 六、按任务使用质量门

### 规则
1. **适用才执行**：完整章节创作通常按 `01_流水线.md` 的准备、设计、写作、审阅顺序推进；局部审校、索引维护和结构迁移只执行与目标相关的检查，不强行经过创作阶段。
2. **有证据地复核**：对当前任务适用的门写出证据和结论；不适用项说明原因，不为走流程而制造打勾步骤。
3. **修改后回查**：后续改动触及已检查的事实、因果、结构或引用时，重新检查受影响的项目；不按固定改动百分比推断是否要复审。

### 重新过门的触发条件

| 后续修改 | 需要重新过的门 |
|---------|--------------|
| 修改了工程主题 | Design Gate |
| 修改影响正文表达或叙事效果 | Prose Gate 中受影响的项目 |
| 修改了跨卷引用 | Review Gate |
| 修改了文件路径或稿件类别 | 重新核对卷内正文索引与相关链接；若提交，再过 Commit Gate |

## 七、质量门反模式

| 反模式 | 为什么错 | 正确做法 |
|--------|---------|---------|
| "差不多就行" | 质量门形同虚设 | 关键判断须给出文本证据与结论；允许标注不适用、待核或证据不足，不以符号打勾代替分析 |
| 审阅者代替作者过 Prose Gate | Prose Gate 是作者的自我检查，审阅是第二道 | 作者先过 Prose Gate，审阅者过 Review Gate |
| 批量过门 | 多章共用一次 Prose Gate → 单章问题可能遗漏 | 每章单独过 Prose Gate；按章纲分组、任务范围与风险安排 Review Gate，不设固定篇数 |
| 门过了但问题还在 | "形式上"打勾但没有实际检查 | 每项检查必须有具体证据（引正文行、引术语清单等） |
