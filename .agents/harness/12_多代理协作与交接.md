# 12 · 多代理协作与交接

> 定义可跨 Codex、Omarchy OMP、DeepSeek Harness 使用的协作逻辑。各运行环境自行选择启动、等待和消息工具；本文件规定任务边界、证据和验收，不假设存在统一命令。

## 一、适用条件

适合拆分：至少两个任务可以并行完成、输入材料已明确、文件写入范围可互相隔离，且最终需要一次主审整合。

不适合拆分：任务依赖前一项结论、多个代理必须同时改同一文件、核心问题尚未界定，或工作量小到交接成本大于并行收益。此时由主审串行推进。

## 二、分工协议

开始并行工作前，主审为每项任务写清：

| 字段 | 要求 |
|---|---|
| 目标 | 交付什么结果，服务于哪个用户目标 |
| 范围 | 负责读取/修改的路径，列出明确排除项 |
| 证据 | 必须查阅的索引、canon、正文或状态账本 |
| 输出 | 报告、改动或待裁定问题应放在哪里 |
| 验收 | 如何证明覆盖完整、链接正确、事实未越界 |
| 共享状态 | 是否与其他代理共用文件；如共用，指定唯一写入者 |

默认采用“一个文件/目录范围只有一个写入者”。多个代理可并行只读同一份 canon；对同一个索引、账本或 TSV 的分区写入，应指定行/区段并回读合并结果。

## 三、执行循环

```text
拆分独立任务
  → 分配范围和输出
  → 代理核证据、执行、报告
  → 主审检查报告与实际改动
  → 解决冲突、补缺口、统一口径
  → 运行适用的静态核对
  → 更新账本/覆盖清单和下一步
  → 若验收项仍未满足，继续下一轮
```

并行完成只表示子任务返回，不表示整个目标完成。主审必须检查：

1. 代理是否实际阅读和修改了约定文件；被截断的输出、文件名列表或 `rg` 命中不能充当全文审读。
2. 报告是否区分正文已证事实、历史蓝图、人物解释、作者方案与未知项。
3. 改动是否越出分配范围；若共同文件发生修改，是否有清晰的合并者。
4. 下游引用、索引、工作流和实时账本是否需要同步。
5. 仍待核事项是否保留为待核，未被摘要改写成既定事实。

## 四、跨会话交接

任务较长、需要换代理或新会话续接时，更新 `.agents/workspace/正文全卷审校进度.md` 或适用的项目维护记录，写明：

- 当前目标与已完成的具体范围；
- 证据文件、关键判断和反证；
- 代理正在执行的范围、输出文件与未完成状态；
- 已修改文件及尚未回读的下游引用；
- 下一项可直接执行的动作和验收条件。

不要只写“继续审计”或“还有很多”，也不要把代理的计划写成已完成成果。

## 五、并行安全与文件保护

- 修改前检查 Git 状态，并保留作者和其他任务已有的工作。
- 迁移、重命名、删改唯一资料前，先找到引用和替代路径；在用户要求保留资料时，不做不可逆删除。
- 若两个改动依赖同一事实裁定，先由主审决定共享证据边界，再让各代理按同一结论修改。
- 需要用户决定的内容先整理成证据、选项和影响；不因并行任务卡住而自行编造正典。
- 提交或外部发布仍遵循作者明确指示；并行结束本身不授权提交。

## 六、完成条件

满足本次任务的验收清单、全部改动由主审回读、冲突和未决项有记录、覆盖清单与实际文件一致、必要的链接/结构核对通过后，才可标记该轮完成。若目标是全目录审计，任何“待读”项目都意味着审计目标尚未完成。
