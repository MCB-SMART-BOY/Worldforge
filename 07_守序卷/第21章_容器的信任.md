# 守序卷 · 第21章 · 容器的信任

Spring 容器替应用创建 Bean、装配依赖、执行生命周期回调，也能通过代理提供事务和缓存等增强。言知非一直把这些工作交给容器，直到常安为升级 Spring Boot 补运行时验证时，测试报告里出现一条红线：一条标注了 `@Transactional` 的结算路径没有开启事务。

最初，团队怀疑 Boot 3 改了默认代理方式。核对配置和版本记录后，他们发现生产环境在升级前后一直使用 CGLIB 代理，默认设置并没有发生这次事故所说的变化。真正的问题在一段早已存在的代码：`SettlementService` 的公开结算方法被声明为 `final`。CGLIB 通过子类代理增强方法，无法覆盖这个方法，因此事务拦截器始终进不去。新测试是在升级准备期间才补上的；升级让旧问题浮出水面，却不是它的起因。

“那之前为什么没人发现？”测试负责人翻着旧报告，“我们测了结算结果，没测事务边界。数据刚好写成功，不能证明事务按预期工作。”

团队移除不必要的 `final` 修饰符后，重新运行事务集成测试：调用方法时事务确实开启；抛出异常后，相关写入按预期回滚。另一个测试专门验证自调用路径，确保结算方法经由容器代理进入，而不是同一个对象内部绕过代理直接调用。

容器的行为依赖代理类型、方法可见性、调用路径和实际配置。Spring AOP 使用 JDK 动态代理或 CGLIB；CGLIB 不能增强 `final`、`private` 等无法被覆盖的方法。只看到注解存在，不足以证明增强生效；只看到版本升级，也不足以证明框架变更就是根因。

言知非把这次测试写进升级清单：关键事务要验证事务是否开启、异常如何回滚、调用是否经过代理。缓存测试要检查实际命中和失效，依赖注入测试要核对最终 Bean 类型与来源。测试不需要覆盖每个注解的每个组合，却应覆盖系统赖以成立的容器行为。

升级前的红线没有证明 Spring 不可信。它提醒团队，容器只会按当前版本与配置执行；团队必须说明自己期待它做什么，并用运行结果验证这份期待。
