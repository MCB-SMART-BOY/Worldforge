# 守序卷 · 第16章 · 连接池的配置

常安的 `application.properties` 里有五行连接池配置：

```properties
spring.datasource.hikari.maximum-pool-size=47
spring.datasource.hikari.minimum-idle=12
spring.datasource.hikari.connection-timeout=15000
spring.datasource.hikari.idle-timeout=300000
spring.datasource.hikari.max-lifetime=600000
```

它们至少七年没被系统复核过。几次交接里，维护者都留下相似的话：“不要动，生产验证过。”言知非把这句话写在纸上，下面添了几个空格：在哪种负载下？谁验证的？验证了什么？结果在哪里？

`maximum-pool-size=47` 的提交说明只有“增加连接池大小，解决偶尔的连接超时”。旧服务器有十六个 CPU 核，硬盘是 SSD。有人拿一个粗略的 CPU 与磁盘公式算出三十三，便把四十七标成“多了约四成”。可连接池大小不能只靠核心数和磁盘类型定案；HikariCP也要求结合执行环境与数据库承载能力来判断。三十三只能作为一次估算，不能证明四十七错误。团队还得看查询耗时、并发占用、数据库连接预算和等待队列。

而且，四十七是每个进程的上限。若四个应用实例都使用这组配置，理论上应用侧最多可能打开一百八十八条连接；其他服务和数据库保留额度还没有算进去。言知非把这个乘法写进核查单，旁边注明“上限，不是当前使用量”。

`connection-timeout=15000` 表示请求从池中获取连接时，最多等待十五秒。它不限制 SQL 执行多久。最初那场慢查询事故里，正是查询占着连接，其他工作线程等不到空闲连接，最终触发获取超时。十五秒该不该缩短，要结合请求时限、等待队列、数据库恢复速度和上层重试策略决定；仅凭“连接建立通常很快”无法回答。

`idle-timeout=300000` 表示连接空闲达到五分钟后可被回收，但只有池内空闲数高于 `minimum-idle=12` 时才会生效。池会尽力保留至少十二条空闲连接。`max-lifetime=600000` 则限制池中连接的最长生命周期；连接仍在使用时不会被强行关闭，而会在归还后退出池。它是否合适，需要对照数据库或网络设施的连接时限。

团队没有在当天改任何数字。他们先调出活跃连接、空闲连接、等待线程和获取超时记录，准备在可复现的峰值负载下比较不同配置。言知非在每个参数旁添上当前的验证问题：数据库能承受多少连接？连接通常被占用多久？空闲数是否经常触及下限？最长生命周期是否短于基础设施的断连阈值？

配置不会因为年头久就自动变错，也不会因为曾经跑过生产就永远正确。它们只有连同环境、证据和复核时间一起记录，才算一项仍然有效的决定。
