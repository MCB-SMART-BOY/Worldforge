# 守序卷 · 第5章 · 旧的为什么

言知非把依赖树、启动条件报告和配置文件摊在一起，顺着那次超时往下追。事故起点已经清楚：`settlement-db-starter` 的 3.4.3 改短了连接池等待时间；生产数据让查询占用连接更久；六十四个工作线程挤在四十七条连接后面。可为什么连接池最大值恰好是四十七，仍没人说得出来。

Git 历史显示，十二年前，有人把 `maximumPoolSize` 从二十改成四十七。提交说明只有一句：“fix: 增加连接池大小，解决偶发连接超时。”没有负载数据，没有数据库连接上限，也没有说明问题究竟出在池太小、查询太慢，还是别的应用占用了数据库会话。那个改动或许救过急；留下的数字却活得比理由久。

另一个值是 `defaultTxTimeout = 120` 秒。它来自十七年前的一次提交，说明只有“增强事务配置”。言知非暂时没有动它：它是应用自己的事务超时，不是这次触发的十五秒连接池等待。把两个同叫“超时”的数字混作一个原因，只会让下一次排查更难。

他把全局配置、环境变量、部署脚本和自动配置逐一比对，列出二十三项找不到充分依据的数值。只有四项能找到说明：为何取这个值、依赖什么前提、谁负责在前提变化时复核。其余数值散在配置文件、注解和环境变量中；有几项的来历，甚至只在公司内网迁移前的一份个人 Wiki 里出现过。

“旧的为什么”并不总能被找回来。Git 提交可以告诉后来者谁改过、何时改过，却未必记录当时的压力和选择。多年后从结果反推理由，最多得到一个待验证的假说，不能冒充原作者的答案。

言知非决定先不改那些尚未查明的参数。他为每项配置补上当前有效值、来源链、已有证据、未知处、责任人和复核触发条件；已经确认危险的十五秒单独走修复流程，连接池规模则等测量完成后再评估。追溯不是冻结系统，而是避免把猜测伪装成授权。

夜深时，他把第一张追溯表放到 `applyChunk` 的代码旁。表上没有替常安补出所有失去的记忆，只写清哪几件事已经查明，哪几件还不知道。

**沉默的秩序需要被翻译成可追问的声明。**
