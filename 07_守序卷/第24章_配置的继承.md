# 守序卷 · 第24章 · 配置的继承

容器启动问题处理完，言知非在生产核查单上看到两个数据库地址。`application-prod.properties` 写着 `db-prod-01`，运行中的服务却连接 `db-prod-02`。这一次，Bean 创建顺序没有问题，真正被覆盖的是配置值。

Kubernetes 的 ConfigMap 里有环境变量 `SPRING_DATASOURCE_URL`，它在应用启动时覆盖了文件中的 `spring.datasource.url`。三年前迁移数据库时，DBA只改了集群配置，没有同步仓库里的环境文件。后来每次查文件的人都看到旧地址，只有查看容器实际环境和 Spring `Environment` 的属性来源，才能还原生效值。

言知非把团队内部的“配置层”图重新画了一遍：打包在应用里的默认文件、外部配置文件、环境变量、`SPRING_APPLICATION_JSON` 和命令行参数都可能提供同一属性。Spring Boot 按属性源优先级解析，较高优先级的值覆盖较低优先级的值。`@Value` 与 `@ConfigurationProperties` 是读取和绑定这些解析结果的方式，不是额外的覆盖层。

为避免再靠记忆排查，平台组给常用非敏感配置增加来源核对：启动时记录最终连接主机、活动 profile、对应的属性源和部署版本。用户名、密码、令牌等敏感值只记录“来自哪个来源”，不落明文；完整属性来源诊断限制在受控环境和授权人员范围内。应用自身的日志不再把整份 Environment 原样写出。

这份记录还得和部署变更相连。ConfigMap 的修改由部署仓库追踪，应用配置文件由代码仓库追踪；迁移工单同时引用两处变更。遇到不同环境值时，值、来源、更新时间和负责人都能沿记录找回。

配置覆盖不是容器临时起意。它按优先级执行了声明过的规则，只是团队过去没有把覆盖关系与部署变更放在同一条证据链里。言知非在核查单上补完 `db-prod-02` 的来源，又把报告里的密钥字段检查了一遍，才把结果交给值班负责人。
