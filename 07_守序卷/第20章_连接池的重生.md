# 守序卷 · 第20章 · 连接池的重生

连接池参数的复核没有产出一组新的“标准答案”。它先让常安看见自己不知道什么：四十七条连接的历史理由未明，十五秒等待从配置生效后几乎没有复盘，外部服务等待曾占住事务，数据库连接预算也没有按实例总数核算。

言知非和维护组把做法定成四步。第一，记录每个参数的来源、适用环境、最近一次验证证据、责任团队和复核信号。对 `maximum-pool-size=47`，他们把“十六核按旧公式得出三十三”记为待核的历史估算，而非推荐值；下一次测试要比较数据库连接预算、查询耗时、工作线程并发和池等待情况。

第二，观察池的真实状态。面板同时显示活跃、空闲、总连接数、等待连接的线程以及获取超时次数，并按实例和数据库端核对。等待线程持续出现值得调查，但一个瞬时尖峰不能单独证明池太小；高连接使用率也可能来自慢查询、长事务、锁等待或外部调用。

第三，把泄漏检测作为辅助信号。`leakDetectionThreshold` 的告警会带上借出位置，却可能只是合法连接持有时间超过阈值。值班手册要求检查连接后来是否归还、对应事务做了什么，并与 SQL 和请求追踪对齐。代码评审也会查看事务中是否夹着远端调用或长时间计算。

第四，在隔离的负载环境里验证候选配置。团队重放有代表性的查询和峰值并发，比较三十三、四十七以及其他候选值下的等待、超时、数据库负载和响应时间；如果瓶颈来自慢查询或锁等待，就先处理查询路径，而不是用更多连接把压力转给数据库。任何变更还要经过灰度观察与回退准备。

这套流程没有保证每个参数永远正确。它让每次调整都能回答：环境变了吗？证据是什么？影响范围多大？出现什么信号就回退？言知非把“经过生产验证”改成了带时间、负载和结果的记录。

连接池终于从一组被反复叮嘱“别动”的数字，变成团队能解释、能观察、也能重新验证的运行规则。可这些数字并非凭空存在：它们由 Spring 容器装配，由数据源 Bean 承接。下一步，言知非要查清容器究竟按什么条件把配置变成了运行中的对象。
