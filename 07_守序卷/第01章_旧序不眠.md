# 守序卷 · 第1章 · 旧序不眠

凌晨两点十一分，常安的结算任务停在半途。

这套 Java 系统已经运行了二十一年。它每天清晨前汇总上一日的跨平台交易，再把结果交给各方账本。今晚，任务先处理完一批记录，随后几名工作线程迟迟借不到数据库连接。日志里刷出同一句错误：`Connection is not available, request timed out after 15000ms`。

两周前的一次例行升级，把应用内部的 `settlement-db-starter` 从 3.4.2 升到了 3.4.3。版本号只升了一个补丁位，团队便把它归进低风险的安全修补。没人留意发行说明里还有一处默认值变化：连接池取连接的等待上限，从三十秒缩短到了十五秒。

那并不是 SQL 查询的执行时限。真正把连接池压满的，是生产数据。数据库已有二十一年历史，缺少索引的月末查询有时要跑十八秒；而结算任务会同时派出六十四个工作线程，争用最多四十七条连接。查询慢时，连接迟迟不归还，排在后面的线程等满十五秒便拿到超时异常。

事故复盘时，言知非把批次流程画在白板上：调度器负责分发任务，每个分块由独立的 `SettlementChunkService` 事务提交；全部分块结束后，编排任务才会写入批次汇总日志。前面已提交的分块不会因为后续线程取连接失败而一并回滚。于是结算明细已经前进，批次汇总却仍停在“处理中”——两份记录各自都是真的，放在一起却说不通。

凌晨两点三十二分，言知非被电话叫醒。新任架构师入职三个月，前任离开时只留下一句：“常安运行二十多年了，很稳定。你主要看着就好。”

他听懂了“看着”的另一层意思：别动。系统仍在运行，但没人能说清它为什么还能运行。

言知非顺着异常往回查，先查连接池，再查启动配置、依赖树和最近的升级记录。每一层都给出一个答案，却没有一层能独自解释整场事故。他在复盘页首写下第一条审计问题：**这个十五秒，究竟是谁决定的？**

旧序没有醒来。它只是用一次中断提醒所有人：有些规则并未消失，只是已经没人记得它们藏在哪里。
