# 守序卷 · 第17章 · JDBC的旧约

连接池的参数有了核查单，言知非接着打开数据库连接 URL。那一行落在 `application.properties` 里：

```text
jdbc:mysql://db-prod-01:3306/changan?useSSL=false&useUnicode=true&characterEncoding=UTF-8&serverTimezone=Asia/Shanghai&autoReconnect=true&useLegacyDatetimeCode=false
```

问号后有六个参数。提交记录显示，它们来自不同年份的事故和升级；URL旁边没有留下各自的理由。言知非先不碰配置，而是查应用实际加载的 Connector/J 版本、TLS设置、数据库字符集和时区，再把结果与每次加入参数的记录对上。

`useSSL=false` 会禁用连接加密。它曾在团队尚未准备证书时被紧急加入；后来内网部署了 TLS，参数却一直留着。证书部署并不能单独证明删掉它就安全：还要确认驱动版本的默认行为、证书校验方式、服务端要求，以及生产连接实际协商出的加密状态。若取消禁用项，必须在预发布环境验证连接和证书校验，再安排生产变更。

`autoReconnect=true` 更让维护者停下了鼠标。MySQL Connector/J 文档不建议依靠驱动静默重连，因为连接断开后，事务状态、临时表和会话变量等上下文可能已经丢失；应用需要知道连接失败，再决定如何恢复。常安已经使用连接池，团队要确认该参数在当前驱动版本中的处理方式，并查明是否仍有代码依赖它。这个旧选项不能被当作安全重试机制。

`characterEncoding=UTF-8` 也不能只凭 Java 运行时的默认字符集就判为冗余。数据库和连接驱动各自有字符集设置，明确指定可能是在保护兼容行为。`useUnicode`、`useLegacyDatetimeCode` 和 `serverTimezone` 是否仍有意义，则要看 Connector/J 版本及实际日期、字符转换结果。言知非将它们标为“待版本核验”，没有把未知写成废弃。

六个参数现在有了六条待验证记录：来源、当前驱动解释、线上有效配置、依赖它的业务路径、移除或调整时的风险、验证负责人。对于 `autoReconnect`，首要问题是确认没有人把它当成事务补救；对于 TLS，则要先证明加密与证书验证已经按预期生效。

URL不是一块永远不能碰的古碑。它是多次决定叠在一起的结果。若只删除看起来陈旧的参数，可能拆掉仍在生效的兼容约束；若让所有参数永久留存，旧约又会掩住真正的风险。言知非把版本号和运行证据补到清单里，决定逐项复核，而不是整串照搬或一次清空。
