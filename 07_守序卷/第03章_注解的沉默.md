# 守序卷 · 第3章 · 注解的沉默

言知非回到结算代码，找到了事故路径上的 `@Transactional`。它标在 `applyChunk` 方法上，声明了事务传播方式，却没有显式填写事务超时。

他先在白板上划开两条线：一条是 Spring 事务的生命周期，另一条是 HikariCP 从连接池借出连接时的等待时间。事故中的十五秒发生在后一条线上——工作线程还没取得连接，SQL 尚未开始执行。事务注解没有设定这个连接池等待值；改变它的是升级后的配置默认值。

这并不意味着注解无关紧要。`@Transactional` 还有超时、隔离级别、只读和回滚规则等属性；没有写出的部分，会交由 Spring 的事务管理器和底层数据库按各自默认规则处理。默认值不是一个统一答案：传播行为由框架决定，隔离级别通常委托给数据库，连接获取超时则属于连接池。几种规则叠在一起，才构成生产里真正发生的行为。

他抽查了五十个事务注解：百分之七十三没有显式事务超时，百分之六十一没有写回滚规则，绝大多数沿用默认传播和隔离设置。这些数字本身不能说明配置错了；它们说明，维护者很难仅凭注解判断运行时究竟采用了什么值。

注解像写在代码里的便签。它能告诉读者“这里需要事务”，却未必能告诉后来者：事务超时由谁提供，隔离级别落到数据库后是什么，代理是否真的拦截了这次调用，异常又会触发怎样的回滚。答案散在注解、Spring 配置、代理机制、连接池和数据库版本之间。

“我不是要把默认值全改成显式配置。”言知非在调查会上说，“有些默认值本来就合适。我要知道的是：当前生效的是什么，值从哪里来，前提变了以后谁会发现。”

他新建了一张注解行为追溯表，先记录抽样的方法、有效参数、配置来源和待确认项。表格第一行正是 `applyChunk`。十五秒被圈在连接池一栏，事务注解旁边则留了一个问题：**这次调用真的经过了 Spring 代理吗？**

答案不在注解表面。言知非转去查常安的容器启动记录。
