# 守序卷 · 第28章 · 消息队列的旧约

五条 JMS 通道里，最老的是 `settlement.notification.queue`。它在十六年前创建，用来把结算完成通知送到其他系统。最初的 XML 消息格式写在一份 DTD 里；文件在十年前迁移应用服务器时遗失，眼下只剩消费者代码和队列管理配置。

消费者已经历多次改造，解析逻辑逐渐学会容忍可选字段、旧名称和不同版本的消息。有人把这种宽容称为“兼容”。言知非翻开失败消息和生产样本后发现，其中一部分兼容分支已无人能说出对应哪个生产者；还有些异常只是因为命名空间 URI 或元素名称不同。XML 前缀本身可以变化，只要它指向同一个命名空间；真正需要核对的是命名空间和结构，不是前缀拼写。

队列配置也藏着旧决定：并发消费者为三，失败重试七次，超过次数后进入死信队列，必须人工处置。为什么是三而不是五，为什么重试七次，历史记录都没有答案。团队先查当前 broker、生产者数量、处理时长、失败类型和死信回放流程；在找到证据前，这些值只代表现状，不代表最佳值。

消息通道负责传递数据，不会替两端维护完整契约。生产者可以增加字段，消费者也可以逐步演进，但每一项变化都要按双方解析方式验证：字段缺失时如何处理，未知字段是忽略还是拒绝，重复消息如何去重，失败进入死信后由谁决定是否重放。死信重放尤其不能只看 XML 能否解析，还要防止重复执行结算副作用。

言知非为这条队列建起契约档案：样例消息、字段和命名空间、生产者与消费者名单、兼容规则、重试与死信策略、回放责任人。之后每次生产者或消费者发布，都用已登记的样例和双方契约测试验证变化；新增的兼容分支必须附上仍在使用它的生产者证据。

那份遗失的 DTD 不会靠猜测补回来。眼前能做的是把当前实际交换的消息记录下来，邀请两端共同确认，再让下一次格式变化有一条可复查的路。
