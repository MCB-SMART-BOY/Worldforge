# 守序卷 · 第18章 · ORM的映射

URL清单提醒言知非：配置写着什么，不等于运行时一定做了什么。这个问题在 ORM 映射里更明显。

常安用 Hibernate 将实体映射到关系表。`SettlementEntity` 上标着 `@Table` 与 `@Column`，账户关联则声明为 `@ManyToOne(fetch = FetchType.LAZY)`。注解短短几行，真正发出的 SQL 却要看查询方式、持久化上下文、Hibernate版本和关联是否被访问。

报表任务一次查出一千笔结算记录，随后逐条读取 `settlement.getAccount()`。若这一千笔记录关联了一千个不同账户，且账户尚未载入上下文，延迟访问可能再触发约一千次查询；若多笔记录指向同一账户，持久化上下文可能复用已载入实体，查询数会少一些。言知非让团队打开 SQL 统计，在测试数据和实际报表路径上确认查询次数，不再把“N+1”当作仅凭注解就能断定的结果。

这条报表确实需要账户摘要，于是仓储方法为这一种读取场景显式写了抓取查询：

```java
@Query("SELECT s FROM SettlementEntity s JOIN FETCH s.account WHERE s.date = :date")
List<SettlementEntity> findByDateWithAccount(Date date);
```

这让该查询在读取结算记录时一并取回账户。实体映射仍保持延迟加载，让其他只需要结算信息的路径不必一律加载关联。团队还记录了抓取查询可能带来的行数膨胀，并检查它是否与分页或其他集合关联组合使用。

`LAZY` 也不是脱离上下文就能随处访问的承诺。实体离开持久化上下文后，未加载的关联可能无法再取；不同映射和提供方对延迟加载的实现也有边界。服务层要么在事务范围内明确完成所需读取，要么将结果映射成包含必要字段的 DTO，避免把未加载实体带到更外层才触发隐式查询。

言知非把一条规则贴进代码评审清单：看 ORM 代码时，同时看生成的 SQL、查询次数和数据形状。对象映射减少重复 CRUD，却没有替团队决定抓取计划。凌晨的告警不会显示一行 `findAll()` 背后究竟跑了几条 SQL；这些行为需要在代码旁边留下可复现的查询和测量结果。
