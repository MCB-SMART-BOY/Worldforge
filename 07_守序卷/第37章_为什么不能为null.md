# 守序卷 · 第37章 · 为什么不能为null

在 `SettlementEntity` 里，`channelType` 是 `String`；数据库列定义为 `VARCHAR(32) NOT NULL`，JPA 映射也标了 `@Column(nullable = false)`。创建结算对象的代码都会给它赋值，维护者只记得一句话：“它不能是 null。”

言知非翻出一份2010年的事故报告。那年，一段批量导入脚本把渠道字段留空。SQL 按 `channelType` 分组时，数据库把这些记录放进一个 `NULL` 分组；报表组只渲染已登记的渠道，漏掉了这个分组里的金额，导致渠道合计与总计不一致。故障花了三天才查明。之后，团队在应用和数据库两层禁止空值，却没有把事故理由留在约束旁边。

“数据库不是把这些行随机分错了。”言知非在报告页边写道，“它们被正确地分到 NULL 这一组，是报表漏处理了这组数据。”这句话保留了事故真正的因果，也让后来的人看见约束保护的是哪一项业务不变量：每笔结算都必须能归入已定义的渠道类别。

团队核对当前历史数据、导入脚本和报表逻辑，确认这个不变量仍然成立。记录中于是补上两层信息：非空约束是业务要求；若将来要允许未知渠道，必须定义未知渠道如何展示和汇总，补齐数据迁移与报表测试后再调整。注解和数据库约束仍然保留，理由随代码与迁移脚本一起维护。

言知非继续抽查其他 `nullable = false` 字段。有些来自业务事实，有些只是为了避免技术路径上的空指针，还有几项仅能追到旧事故。表面相同的数据库标记，背后的理由并不相同；每一项都需要回到使用它的查询、报表和写入流程中确认。
