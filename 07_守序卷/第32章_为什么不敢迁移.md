# 守序卷 · 第32章 · 为什么不敢迁移

常安上一次大型 Java 迁移发生在七年前：从 Java 7 转向 Java 8，耗时十八个月，期间记录了四起生产事故。言知非把事故时间线铺在会议桌上。故障不是部署当天同时爆发，而是在第二周、第三周和第七周，随着特定流量、批处理窗口和数据组合逐渐出现。

团队复盘后发现，测试集覆盖了常见路径，却没有触及那些后来才浮现的条件。某些日期边界让旧解析逻辑多保留一天；一次重试让批处理重复执行；另一个旧模块依赖了框架默认提供的空值行为。每次故障都能在事后找到线索，迁移前却没有把线索写成验证场景。

“我不是怕改代码。”一位资深维护者说，“我怕改完之后，过了一个月才发现没人记得的那条路已经变了。”

言知非在白板上写下这句话。恐惧不是拒绝进步，而是风险尚不可见时积累下来的经验。说“迁移后一定会炸”过于绝对；但过去几次事故确实说明，绿灯测试没有覆盖所有真实负载和业务周期。

新的计划不要求先把所有未知消灭。团队先把已知事故模式变成回归场景：日期边界、重复执行、空值映射、连接等待和外部接口兼容。每项场景都标注触发条件、旧版本观察结果、迁移后的允许差异和监控信号。覆盖不了的边界仍保留为风险，由负责团队决定是否接受或延后迁移。

信心不会因为会上有人说“这次肯定没问题”就长出来。它来自可解释的差异、能提前触发的测试，以及出现问题时能及时回退的准备。言知非把复盘中最迟才暴露的那起事故放到计划首位，要求团队先证明自己能在测试环境重现它。
