# 守序卷 · 第19章 · 连接的泄漏

三年前，常安遇到过一次连接池耗尽。值班日志里反复出现 `Cannot get connection from pool`，最初的处置是把连接池上限调大。请求暂时恢复，几周后数据库连接数逼近服务端上限，其他应用也开始报错。

言知非回放当时的一条慢请求。`ReportService` 在事务方法中先查数据库，随后调用一个外部 HTTP 服务。远端有时需要三十秒才超时；这段等待期间，数据库连接仍然由当前事务持有。高峰时，许多请求一起停在 HTTP 调用上，四十七条连接很快被占满。池并没有凭空丢失连接；它们只是被业务流程占得太久。

连接泄漏有更严格的含义：代码借出连接，却没有按预期归还。连接长时间处于借出状态会导致相似的池耗尽症状，但原因和修复办法未必相同。诊断时要看连接是否最终归还、持有时间、事务边界和调用链，不能把所有“池里没空闲连接”都叫泄漏。

团队在复现环境里把 HTTP 延迟注入到报表流程，观察池的活跃连接与等待线程。追踪结果证实，连接在外部调用开始前已经取出，并在事务结束后才归还。将外部请求移出持有数据库连接的区段、缩短事务，以及为 HTTP 调用设置合理超时，分别进入修复方案评审；具体改法还要保障业务读取的一致性，不能简单把注解删掉。

HikariCP 的 `leakDetectionThreshold` 可以在连接借出超过阈值时记录“疑似泄漏”警告和借出时的堆栈。它是定位线索，不是裁决：长查询、外部等待或较大的合法事务也可能超过阈值；连接随后归还时，日志仍需结合时间线判断。阈值应高于常见的合法持有时间，并在观察期内评估误报与漏报。

事故复盘把“连接池扩容”从根因栏移走，改成一次暂时缓解。真正要追踪的是连接从何时借出、被哪段工作占用、何时归还，以及数据库和外部服务之间的等待如何叠加。连接有限，事务却可以把它带进不该久留的地方。
