# 守序卷 · 第8章 · AOP的背面

`accountService.getAccount(accountId)` 看起来只是一行普通调用。可在常安，它可能先经过权限检查，再进入缓存拦截器；缓存未命中时，才继续调用目标方法。事务、审计和指标记录也可能由代理或切面加入。究竟经过哪些环节，不能单靠这行源码判断。

言知非让值班组追踪同一请求的两条路径。外部服务持有 Spring 容器注入的代理，调用会进入拦截链；而 `AccountService` 内部一个方法用 `this.getAccount(id)` 调用另一个带注解的方法，直接落在当前对象上，绕过代理。那条内部调用没有触发预期的缓存和审计记录。

“我在方法上看见注解，以为每次调用都会经过它。”负责这段代码的工程师盯着两条追踪记录，“原来调用从哪里来，也决定了注解能不能生效。”

另一个问题藏在切面顺序里。权限、缓存、事务和审计都拦截同一方法时，谁先执行、缓存命中后哪些环节仍会运行，取决于实际注册的拦截器、切面顺序和具体缓存结果。Spring 允许为适用的 advisor/aspect 声明顺序；没有明示的交叉顺序，就不能凭源码排列想当然地下结论。

常安以前只有 Bean 清单，没有逐方法的代理链记录。言知非和维护团队做了一个启动报告：它读取运行时 Bean 的代理与 advisor 列表，登记可确认的顺序，并和上次启动结果比较。报告不会替他们判断顺序是否正确，但能让新增切面、条件变化和代理缺失进入审查视野。

他们随后把 `this.getAccount(id)` 拆成独立的查询组件，由 Spring 注入代理后的 Bean；测试分别验证外部调用、缓存命中、缓存未命中和内部业务路径。四种路径得到四份记录，差异第一次有了名字。

AOP 的背面不是“看不见的魔法都危险”，而是源代码只展示了目标方法，运行时还可能有代理和拦截器。**读得见声明，仍要查得到它如何落地。**
