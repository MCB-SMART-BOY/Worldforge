# 守序卷 · 第10章 · 注解的考古

言知非从常安最老的代码里挑出十处注解，和维护者一起追查它们的参数、来源与前提。十处并不多，却足以看见同一种时间差：代码仍在表达旧决定，系统早已搬到了新的环境。

第一处是 `ReportService.generateReport()` 上的 `@Transactional(timeout = 300)`。十五年前，它负责读取一座外部旧库；数据量大，查询经常超过三分钟，所以事务超时设为五分钟。十年前旧库迁走，查询缩短到约五秒，五分钟的设置却留了下来。

这并不意味着任何卡住的 SQL 都必然占住连接整整五分钟。事务管理器会把期限交给它管理的资源；实际能否中止正在执行的语句，要看事务管理器、数据访问层和数据库驱动如何配合。可旧值仍可能让某些等待拖得过长。团队先检查运行日志和数据源行为，再决定是否缩短，而不是只因“现代服务不该有五分钟超时”便改掉它。

另一处是 `SettlementService` 注入的 `LegacyProcessor`。源码里只有一个字段，容器里却有旧、新两个实现。当前选择由 `@Primary` 指定；一年前，新实现被标成优先项时，这个注入点便换了目标。Spring 的解析规则有据可查，真正缺失的是变更记录：为什么切换、哪些路径受影响、是否验证过新旧行为。

若候选 Bean 不止一个、又没有 `@Primary`、`@Qualifier` 或可用的名称匹配，容器通常会报无法确定的错误，并非总会悄悄选一个。言知非把这一条也写进考古笔记：不要把所有意外都归咎于框架“偷偷做了决定”，先查实际候选和解析条件。

十处注解里，有的前提仍然成立，有的已经改变，还有几处只能确认“理由已失传”。团队没有把后一类补写成推测，而是标注待证、指定复核人，并在高风险路径上先做行为测试。考古的目标不是清空旧注解，是分清哪些旧约仍在保护人，哪些已经不合时宜。

收工时，言知非把十份记录放进审计册。最醒目的不是结论，而是每条结论旁边的证据来源和未知项。

旧序开始有了可读的边界。下一步，他们要面对更难的问题：当一条旧规则曾经保护过所有人，它什么时候会变成束缚？
