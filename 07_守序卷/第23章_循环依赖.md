# 守序卷 · 第23章 · 循环依赖

启动审计报告里还有一项旧配置：`spring.main.allow-circular-references=true`。它让常安两个服务之间的字段注入循环继续运行。移除这个开关试跑时，容器立即报告无法创建 Bean，启动停在 `OrderService` 与 `SettlementService` 的相互依赖上。

支付完成后，`OrderService` 调用 `SettlementService` 结算；后者又回头向 `OrderService` 查询订单状态。两边都在处理业务判断，彼此需要对方才能完成工作。过去，这个循环靠字段注入和提前暴露的 Bean 引用绕过了启动错误；Boot 2.6 起，循环引用默认不再自动放行，常安显式打开的兼容开关把问题留到了今天。

Spring 在特定的单例、属性注入场景中可以借助提前引用处理循环，但这依赖 Bean 的创建方式和代理状态；构造器注入的循环无法通过“先给出未完成实例”解决。提前引用也不等于两个服务已经有了清晰边界。若代理、初始化回调或 Bean 后处理器参与其中，问题还需要按具体创建路径验证。

团队没有把开关删掉后便宣布修复。他们先画出两项职责：订单服务负责订单状态与承诺，结算服务负责支付与资金记录。双方共同需要的只是一条订单状态查询。于是他们提取只读查询接口，由订单查询组件持有，结算与编排流程分别依赖清晰的入口；支付完成后的状态推进由应用服务按明确顺序组织。

迁移分两步进行。先增加新接口和行为测试，确认支付成功、失败、重复回调时状态一致；再逐个替换循环引用并在预发布环境移除 `allow-circular-references`。启动失败不再被当作配置问题压过去，而成为职责边界没有整理完成的证据。

容器偶尔能用提前引用让循环依赖继续工作，是否允许这种兼容行为要看版本和配置。即使启动成功，双方仍然耦合在一起。真正的代价会在修改时出现：一个状态规则变更，两个服务都要跟着调整，测试也必须跨过两边的初始化和事务边界。
