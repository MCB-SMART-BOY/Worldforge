# 守序卷 · 第9章 · 注解不是文档

常安有二百四十七处 `@Deprecated`。其中一百八十三处没有 `forRemoval` 属性；一部分标记写于 Java 9 之前，那时这个属性尚不存在，后来补上的标记也未必说明团队是否真的准备删除。旧注解告诉编译器和读者“这里不再推荐使用”，却没有留下原因或替代入口。

十年后接手的人只好猜：这是为了兼容某个旧客户，还是已经有更安全的替代方法？原作者也许只是希望调用方迁移，也许当年确实计划删除。标记仍在，决定的语气却已失传。

事务注解也有同样的缺口。言知非在一处审计方法上看到 `propagation = REQUIRES_NEW`。这让审计记录可以在外层业务事务回滚后独立提交。代码能告诉机器采用了什么传播方式，却没有说明为何必须让这条记录活过外层失败。

仓库历史里有答案：2019 年的一次生产事故中，外层事务回滚连带抹掉了结算审计记录，团队因此改用独立事务。这个决定在当时有明确代价——审计记录可能先于业务结果落库——也有明确收益：即使结算失败，调查仍能还原发生过什么。数年后，相关业务流程已改变，是否还需要相同边界，必须重新核对。

注解负责声明行为，提交记录、事故报告和设计说明负责保存理由。两者应当互相引用，而不是把长篇历史塞进代码注释里。言知非给追溯规范补了一项：每个非默认的关键属性，都要能找到采用理由、证据来源、责任人和复核条件；找不到的，明确标为“理由待考”，不可伪造一个听起来合理的故事。

他在 `REQUIRES_NEW` 旁边挂上 `INC-2019-042`，又新建了一条复核任务。那不是判定旧选择仍然正确，只是让后来的读者知道，为什么这条线当初没有和别的线一起断掉。

注解不是文档。**它告诉机器该怎样做，理由要留给人来追问。**
