# 守序卷 · 第27章 · SOAP的幽灵

`SettlementInquiryService` 的 WSDL 把 `InquiryRequest` 描述为三个字段：`settlementId`、`transactionDate` 和 `channelType`。服务端当前的 Java 请求类却多了一个 `includeArchivedRecords`，这是七年前为了查询归档结算记录而增加的。

这并不意味着每个 SOAP 客户端都能发送这个字段。按旧 WSDL 生成的客户端甚至不知道它存在；手写 XML 是否会被接受，则取决于服务端绑定和校验设置。言知非让团队把旧 WSDL、当前服务类和两种客户端请求分别放进兼容测试，确认哪些请求能解析、缺省值是什么、归档查询到底由谁在使用。

测试显示，WSDL 已不能准确说明服务端现在接受的请求形状。有人曾从 Java 类生成 WSDL，却没留下生成工具、版本和发布流程。后来 Java 类继续演化，WSDL 留在旧目录里；调用方成功与否各自依赖客户端代码和线上配置，没人能指着那份文件说“这就是当前唯一真实的契约”。

SOAP 的问题不在 XML 天生笨重，也不在 WSDL 不够正式。问题是团队把一次生成出来的描述当成永久契约，却没有同步、兼容和发布流程。WSDL 仍然有用，但应从受版本控制的接口定义生成，或由自动化测试证明它与实际端点保持一致；手改 DTO 后也要检查生成描述的差异。

旧描述同样不能随意覆盖。已经按旧 WSDL 生成的客户端，可能把字段集合和类型固定在自己的代码里。团队先保存旧版文件及校验和，核对调用方使用的版本，再决定是否发布新端点、兼容字段或迁移指南。任何变化都要用旧客户端和新客户端做请求级验证。

言知非把这份 WSDL 从“接口真相”改标为“待验证的历史副本”。它还可以帮助寻找调用方和理解旧行为，却不能单独证明线上服务当前接受什么。下一张清单写着五条 JMS 通道，那里没有 WSDL，也没有一份仍然完整的消息说明。
