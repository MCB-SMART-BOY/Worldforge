# 守序卷 · 第31章 · 迁移的考古学

常安准备从 Java 17 迁到 Java 21，从 Spring Boot 2.7 迁到 3.2，并把 Hibernate 5 升到 6。三个核心组件同时跨越大版本，依赖和运行时行为都会改变。项目负责人把它叫作升级，言知非却先在计划里加了一行：先确认旧版本实际上做了什么。

“我们不能只按迁移指南改到能编译。”他在评审会上说，“代码表达的是意图，生产行为还经过容器代理、ORM抓取、JDBC驱动、数据库版本和JVM运行时。别人依赖的，可能是这些层共同形成的结果。”

上一轮大迁移花了十八个月，期间出了四次生产事故。复盘发现，问题并非集中在某一个组件，而是一些很少触发的边界条件：特定查询返回空值时的映射、定时任务重复运行时的幂等性、峰值下的连接等待，以及旧接口对缺省字段的处理。它们在日常样本里不明显，却被某些业务周期稳定触发。

团队把旧版本当成待观察的系统，而不是一份写在文档里的理想实现。他们先从生产指标、请求样本、失败记录、数据库查询和接口契约中建立行为基线，并把已知缺陷单独标注：哪些行为必须保持，哪些问题趁迁移修复，哪些还没有足够证据。

随后，言知非把依赖层列在迁移图上：语言与JVM、Spring容器与代理、Hibernate映射、JDBC驱动、数据库执行计划、消息生产与消费。每一层都有自己的变更说明；真正要检验的，是这些变化组合后是否改写了常安当前的行为，以及是否影响调用方依赖的承诺。

迁移不是复制旧系统的每一处缺陷，也不是只追逐新版本。它要让团队知道什么在保持、什么将改变、为什么改变。要做到这一点，得先明白大家为什么会害怕再次动它。
