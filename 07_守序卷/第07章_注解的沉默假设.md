# 守序卷 · 第7章 · 注解的沉默假设

注解行为追溯表刚铺开，言知非就在缓存事故报告里看见一个熟悉的名字：`@Cacheable`。

七年前，常安的 `AccountService` 用 Ehcache 缓存账户资料。管理器配置了每项最多保留三十分钟；后来团队把后端迁到 Redis，代码里的注解仍然是 `@Cacheable(value = "accounts", key = "#accountId")`。迁移脚本复制了缓存名称和键格式，却漏掉了逐项过期策略。注解一直没变，管理器已经换了。

Redis 中的账户键因此越积越多。实例运行在有内存上限的容器里，缓存进程最终被系统以内存耗尽为由终止。事故保护逻辑把缓存不可用当作缓存未命中，流量随即全部落到数据库；账户查询排队，结算服务也被拖慢。那晚没有任何一个 `@Cacheable` 标记报错，沉默的是标记背后那份已经丢失的配置约定。

小组复盘时，有人提议给所有缓存注解旁边都写上过期时间。言知非摇头：`@Cacheable` 负责声明缓存语义，本身并不设置 TTL；过期策略取决于实际的缓存管理器和后端配置。把 TTL 写进注释，若它和 Redis 的真实设置脱节，只会再造一份过期文档。

他们改为登记缓存策略的责任链：缓存名、键空间、容量和过期规则由哪份配置提供，后端不可用时如何降级，最近一次负载验证何时进行。每条策略绑定对应的注解与配置项；从 Ehcache 迁往 Redis、从本地缓存改为共享缓存时，迁移单必须逐项核对这些前提。

“注解不用为七年前的配置负责。”一位维护者说。

“对。”言知非回答，“但迁移的人得知道，自己接过来的不只是一个键名。”

他把“缓存管理器变更”加进注解追溯表的复核触发项。下一步要查的，已经不只是注解写了什么，而是一个方法在运行时究竟经过了谁的手。
