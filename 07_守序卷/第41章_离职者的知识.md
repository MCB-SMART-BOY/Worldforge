# 守序卷 · 第41章 · 离职者的知识

代码评审（code review）进行到一半，言知非停在结算计算器的一行代码前。

```java
result = amount * 0.997;
```

计算没有错，测试也全绿。可没人说得清这个系数为什么是0.997，而不是别的数。Git blame显示，这行代码由赵谦在十五年前提交。提交说明只有五个字：“调整结算系数。”赵谦十二年前离开常安，此后没人改过它。

言知非叫来结算负责人。对方知道这意味着每笔交易扣除千分之三，却不知道费率依据。他们查了需求文档、审批记录和旧版本仓库，没有找到答案。最后，财务档案管理员翻出一份扫描件，标题被水渍遮住，只能辨认出“平台费率”几个字和赵谦的签名。

“代码一直跑得好好的。”有人说。

“它跑得好，只能说明输入和环境一直没逼它解释自己。”言知非说。

这行数值没有注释，没有对应的提交讨论，也没有文档链接。赵谦当年可能在会议里解释过，也可能是按一份已经遗失的审批单实现。如今谁都无法确认。代码留下了决定的结果，却没留下作出决定的人所依据的理由。

常安的开发史里，至少有四十名工程师参与过结算系统，其中三十二人已经离职。每个人离开时都带走了一部分经验。大多数时候，经验的消失并不会立刻造成事故：程序照常运行，账目也对得上。直到有人要改一行旧代码，才发现自己无法判断那条规则保护了什么。

团队给0.997加上“待考”标记，没有贸然改动。言知非把赵谦的提交、财务档案和仍未找到的审批依据登记进调查清单。

“我们要找的是赵谦吗？”新同事问。

“如果还能找到他，可以问。但不能把制度建立在他必须回来上。”言知非说，“先把能找到的证据留住。”

那天之后，他开始在评审中追问：这个值从哪里来？它依赖什么条件？条件改变时，谁会发现？问题不在某个离职者忘了交代，而在常安一直把“有人记得”当成记录的一种。
