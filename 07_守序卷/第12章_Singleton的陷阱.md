# 守序卷 · 第12章 · Singleton的陷阱

数据库里偶尔出现事务主键冲突。重试通常能让请求通过，于是告警被归进“偶发故障”；可同一类冲突每隔几天就回来一次。言知非把失败记录按时间排开，发现它们大多落在流量上升的时段。

他找到生成器 `TransactionIdGenerator`。十年前，常安只有一台应用服务器。生成器用当前毫秒时间和进程内的序列号拼出事务 ID；字段声明为 `volatile` 的双重检查锁，保证同一个 JVM 只初始化一个生成器实例。那时，这个方案一直工作正常。

三年前，服务改成四个 JVM 实例。每个实例都有自己的生成器和本地序列号。同一毫秒里，如果两个 JVM 走到相同的序列位置，就可能产出相同的 ID。数据库的唯一约束能抓住冲突，却只能在写入时揭示问题：插入失败，当前事务回滚，业务请求中断。重试有时换到了新的时间窗口，有时又碰上同一类冲突，于是它看起来时好时坏。

故障不在于“用了 Singleton”，而在于团队把局部唯一误当成全局唯一。Java 类的静态实例通常以类加载器和 JVM 为边界；Spring 的 `singleton` 作用域表示一个容器中一个 Bean 实例。四个独立进程各有自己的容器，也各有一个实例。它们不会因为类名相同就共享内存。

“那 Singleton 在分布式系统里都不能用？”有人问。

“不是。”言知非把生成器的调用图调出来，“如果它只保存进程内的不可变配置，或者管理本地资源，容器内单例仍然有用。问题在于这里的 ID 必须跨实例唯一，而生成器只掌握本地状态。”

他在故障单上列了两个候选方向：由数据库或专门的 ID 服务分配序列；或者给每个实例分配不会冲突的节点标识，再与时间和本地序列组合。前者要评估集中分配的吞吐和可用性，后者要管理节点号、时钟回拨和重启行为。选哪条路都不能只换一段算法，还得用并发和故障场景验证唯一性。

“单例”这个名字容易让人想象一个系统级的唯一对象。可模式只保证它声明范围里的唯一：边界是一个进程、一个容器，还是整个部署，必须由需求和实现共同说明。常安的代码没有突然变坏；变化的是部署边界，而旧假设一直留在原处。

言知非把事故标签从“偶发主键冲突”改成“多实例下的 ID 唯一性缺口”。再往下，他要判断的不是哪种模式更高级，而是当初为抽象付出的成本，究竟买到了什么。
