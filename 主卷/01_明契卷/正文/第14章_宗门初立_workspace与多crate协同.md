# 明契卷 · 第十四章 · 宗门初立，workspace 与多 crate 协同

北岭二号守门房东偏屋里，段迟舟把三份薄册平码在木板上。

前一夜，北院让他先替门外试一试新加的 `dry-run` 说明。他照旧法，只抄了门口那一份青炉回去。

结果石镜很快给了他一行冷字：

`error: failed to load manifest for dependency 'qinglu-core'`

他又按回报去借做事那一份、管前提那一份。三份薄册摊开，名字都写着青炉，彼此却像不是同一座炉里长出来的骨。

段迟舟没再硬试，只把三份册子一捆，天亮就送回北院。

· · ·

他进门后只说了一句话：

“若门外替你们接手时，还得先自己猜哪几份东西原本属于同一座炉，那这口炉还是没真立起来。”

第十三章把青炉的门口、骨头和前提分了层，北院众人原以为，总算能安稳几日。

结果真正的麻烦，偏偏就长在“终于能多人一起动手”这件事上。

那天，长案上摆了三份几乎一模一样的青炉目录。

第一份，是季循改过的。他把 `dry-run` 真正落进了 `qinglu-core`，让试跑时能多给出一段“为什么这次会这样走”的解释。

第二份，是程知序改过的。她站在使用者一侧，把 `qinglu-cli` 里那些过于像行内黑话的提示，全改成了人能直接看懂的话。

第三份，是闻衡改过的。她盯的不是门口，而是 `qinglu-config`，把那几条最容易长歪的默认值又压了一遍，要求凡是会影响正式判断的前提，都得写明出处。

三人各改各的时，石镜里都能过。

可等到沈见微把三份改动往一处一合，镜面当场裂出两行冷字：

`error: no field 'advice' on type DiagnosisReport`

`error: failed to load manifest for dependency 'qinglu-core'`

· · ·

屋里一时没人说话。

第一行，说明程知序那边的 `qinglu-cli`，已经在等季循刚加上的新字段。

第二行，说明它去找 `qinglu-core` 时，找的还是另一处旧位置。

两行字摆在一起，几乎像是把这三天所有“我以为你知道”的空缺一口气照了出来。

苏野平先啧了一声。

“不是都分骨了吗，怎么还会撞成这样？”

“因为我们只是把骨分开了，还没把工地合起来。”闻衡说。

她把三份目录并排摊开，让所有人都能看见最外层那几页 `Cargo.toml`。

页上都写着青炉的名字。

可细看下去，差别已经出来了。

季循这份里，`qinglu-cli` 指向 `qinglu-core` 的位置还是旧写法。

程知序那份里，新字段已经加到了门口的输出说明里。

闻衡这份里，又把共用的一味外来材料升了半版。

每一份改动单看都说得通。

一旦真要合炉，问题立刻就出来了。

闻衡在白纸上先写下第一句解释：

能单独编、单独说明、也能单独被别人拿去用的一小份项目，叫 crate（crate）

又写第二句：

把几份相关的小项目放进同一座总工地里一起管，叫工作区（workspace）

她写到这里，抬头看向季循。

“第十三章以前，青炉还只像一间屋子。现在屋里已经分出三块骨，还是各自带着自己的小账本。只要多人同时改，迟早会互相撞车。”

季循盯着那句“总工地”，一下就听懂了。

前几章他们一直在做拆分。

把入口拆出来，把配置拆出来，把真正做事的部分拆出来。

可拆到今天，新的问题也随之长出来了：

若每一块骨都只顾自己那本账，谁来保证它们真还属于同一座青炉？

贺时进走近石镜，直接问得更实：

“说白了，到底卡在哪？”

沈见微把问题拆成三条，写在镜面上。

第一条，路径不一。

也就是去找隔壁那块骨时，每个人机器里写的目录位置并不完全一样。

第二条，版本不一。

也就是有人已经按新写法改了，有人还在照旧版等。

第三条，依赖不一。

要借来一起用的外来材料，叫依赖（dependency）。如今三块骨各记各的依赖，谁先换、谁后换，全靠记性。

“这不是代码谁写得更好。”沈见微说，“这是项目已经从一人能记住的大小，长到了必须先把总工地立起来的大小。”

韩砺年一直站在门边，直到这时才慢慢开口。

“我先前一直怕你们拆得太快，拆成三四包各管各的私货。”他说，“若是那样，青炉就只是把一口旧黑锅拆成三口新小锅。”

他顿了顿，目光落在那三页 `Cargo.toml` 上。

“可今天这撞法反倒把事撞明白了。不是不能分骨，是分骨以后，得有人先把整座工地的总图钉在最外层。”

这话一落，连苏野平都没立刻反驳。

因为他也看出来了。

如今最危险的，不再是所有东西都塞在一扇门里。

而是每块骨都开始各自长自己的小规矩，最后让“分层”重新变成“分家”。

沈见微没有再往下讲大道理。

他直接抽出一张新纸，写下一个最外层的总账页：

```toml
[workspace]
members = ["qinglu-cli", "qinglu-core", "qinglu-config"]
resolver = "2"
```

季循盯着这几行字，有些愣。

沈见微便在旁边补了一句人话：

“从今天起，青炉最外层先承认一件事：这三块骨不是三份散项目，它们同属一座总工地。”

闻衡立刻接上第二步。

她又写下一句解释：

几块骨都要一起借的外来材料，尽量在总工地统一写清，不再各自偷偷改口

然后她把三份原先分散的依赖一项项往外层收。

能共用的，就放到一起。

必须单独算的，才留在各自那块骨里。

程知序看着那张总账页，终于把自己这三天最别扭的地方说了出来。

“我不是怕分骨。”她说，“我怕的是我明明改的是给人看的门口，结果一抬头，才发现门后的骨已经不是我以为的那一根。”

“所以才要共史。”闻衡说。

她在纸边又补了第三句：

大家沿同一份总目录、同一套依赖、同一次整体验证往前走，这就叫共史

季循低声问：

“那共约呢？”

沈见微拿起笔。

“共约，就是几个人一起做事时都得守的同一套做法。”

他直接定下第十四章最重的三条：

改公共接口，要同时改代码、说明、调用处。

改共用依赖，要先说清为什么改，再让整座工地一起过一遍。

改某一块骨，不许只在自己那份副本里偷偷跑通。

他说完，又在最下边补了一行最短的话：

> 先合工地，再合改动。

这句话一落，屋里反而安静了。

因为所有人都知道，这看上去只是规矩，实际上是在挡一种很自然、也很危险的冲动：

反正我这里已经能跑，就先这么交出去。

可青炉若真这么长，迟早还会回到卷首那夜的老病。

纸上看似都对。

真合到一起，就没人知道现在到底该信哪一份。

苏野平盯着那三条共约，看了很久，最后先挑最刺的一句问：

“整座工地一起过一遍，怎么过？”

沈见微把石镜转向最外层新立的那张总账页。

“以后先站在最外层跑。”他说，“不是只跑 `qinglu-cli`，也不是只跑你手上那一块骨。是让整个工作区一起过一遍检查（`cargo check --workspace`），先看这座工地今天还能不能完整站住。”

季循听着这句，心里忽然一松。

第十章教他沿结构看项目。

第十三章教他沿边界分入口。

到第十四章，他才第一次真正明白，多人一起做事时，最外层那张总图为什么比“我这一块已经写好了”更重要。

因为从这一步开始，青炉已经不只是“谁会写”，而是“谁改动时能不把别人拖进暗处”。

韩砺年这时终于往前走了两步，把手里一直压着的旧窗名录放到了长案中央。

“我原先不肯这么早交。”他说，“怕你们今天一拆，明天一改，后天又换一整套说法。那我把旧窗对应关系交出来，等于又交进一口看不懂的新锅里。”

他抬起头，看向那张最外层的 `workspace` 总账页。

“可现在不一样了。如今我看见的，不是三个人各抱一包自己的活。是同一座工地先把谁跟谁同炉、谁该跟谁一起过检查，写在了最外头。”

这已经是韩砺年极重的让步。

程知序没有说话，只把自己的那份 `qinglu-cli` 改动往总工地里重接了一遍。

季循也把 `qinglu-core` 新增的说明字段重新对上调用处。

闻衡则守着最外层，把共用依赖和路径一条条压平。

等到石镜里那道长长的检查光流终于顺到底部，最后只剩下一行稳稳的字：

`workspace check passed`

这一次，屋里没有人立刻松气。

因为他们都知道，真正过的不是一条命令。

而是青炉第一次从“几块分开的骨”长成了“能让多人沿同一张总图协作的一座炉”。

沈见微把新的最外层总账页压进文契第九层，又在旁边补上一句给后来者看的话：

> 先认同一座工地，再谈各自那一块本事

季循看着那句话，忽然觉得第十四章的名字并不只是写给青炉。

它也像是在写这间北院小室里的几个人。

从今天起，他们不再只是围着同一张长案的人。

他们开始像一个真正的宗门那样，按骨分工，各守其责，却沿着同一份史、同一套约、同一座炉往前走。
