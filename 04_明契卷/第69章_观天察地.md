# 明契卷 · 第69章 · 观天察地

青炉需要诊断——日志、追踪、指标。不是"加上 tracing"——是让生产中的错误能被追溯到源码中的具体行。

Rust 的 `tracing` crate 提供结构化事件和 span 上下文——事件字段、时间戳和 trace ID 是否写进输出，要由订阅器及相应的格式化、分布式追踪配置决定。不是只写 `println!`——而是写 `info!(request_id = id, "processing started")`，并在服务入口创建 span、把请求标识沿调用链传下去。生产环境中一个请求失败了——如果各服务已接好同一套追踪上下文，凌晨的人就能用 trace ID 串起它经过的 span 和事件，定位到具体模块与步骤。单有一条 `info!` 事件，不会自动生成完整的分布式调用链。

"诊断不是'记录一切'——是'记录后来者需要知道的'。他们需要知道——什么请求、哪个 span、在哪一步出错、当时的上下文是什么。把 tracing 的事件、span 和输出配置接好，生产状态才变得可查询。错误在生产中是沉默的——除非日志让它们发出声音。而日志发出声音的条件不是'日志多'——是关键事件带有一致的请求上下文，能被凌晨的人反向拼接成故障路径。"
