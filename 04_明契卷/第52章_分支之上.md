# 明契卷 · 第52章 · 分支之上

分支让提交可以沿不同方向推进，再选择何时汇合；它不会自动隔离共享工作目录，也不能保证两条改动互不影响。青炉决定采用 feature branch → PR → review → merge 的协作流程：每条 branch 是一组待检验的改动，合并前要检查它与当前主干及团队约定是否相容。

沈见微建起青炉的 `main` 分支。季循改配置，苏野平写扫描脚本，程知序修复使用入口上的问题，各自在分支上提交，再通过 PR 汇合。分支让每个人看见自己提交的边界，却不替他们保证“互不干扰”；一旦相邻改动碰到同一处，review 和合并就得把差异摊开。冲突若在发布前被发现，团队仍有时间一起判断。

"旧的工具链没有共同的提交记录——人们传着各自的文件副本，常常要先问谁手里那份更新。"沈见微说，"分支不会替我们避免冲突，但至少能把各自做过的改动留下来。汇合时有记录可比，我们就知道该讨论哪一处。"
