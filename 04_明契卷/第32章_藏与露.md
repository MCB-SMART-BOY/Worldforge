# 明契卷 · 第32章 · 藏与露

沈见微开始审计青炉核心 crate 候选接口里的 `pub` 关键字。此前对外发布的只有命令器，`qinglu-core` 还没有作为公共库依赖发布；这次检查是在决定哪些接口将来值得公开。Rust 中 `pub` 控制可见性，但单独一个 `pub` 还不等于对外承诺：项必须能从 crate 的公开路径到达，而兼容责任也与它是否成为已发布、被调用方依赖的 API 有关。

他逐行检查核心 crate 的候选接口，撤掉二十六处当前没有必要的 `pub`。审计先确认这些声明在本 crate 中实际可达的位置、内部调用方式和预定用途；数字说的是本次改动数量，不代表二十六项都曾成为已发布 API 或被外部用户依赖。它们中有些只是早期原型沿用的可见性，有些尚无跨 crate 使用需求。

"二十六处——不是二十六份已经许下的承诺，而是二十六处要重新核对的可见性。青炉核心库还没发布，外部调用方也没有依赖它们的证据。现在收回多余的可见面，是为了先把边界缩到团队确实打算维护的范围。等库发布、调用方依赖某个可达接口后，随意改签名可能让他们编译失败；即使仍能编译，行为变化也可能破坏约定。Rust 编译器会按可见性规则检查代码，却不会替团队决定哪些接口值得长期维护。"

承诺不是越多越好——是越少，每个承诺越可靠。不是隐藏——是保护。保护使用者不被一个随时可能变的接口伤害，也保护维护者的修改不炸掉别人的代码。尚未公开的内部实现仍须谨慎维护；但在库 crate 发布前，团队还能调整候选接口，而不必先迁移外部依赖者。
