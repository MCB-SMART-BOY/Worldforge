# 第32章《藏与露》



沈见微开始审计青炉核心 crate 候选接口里的 `pub` 关键字。青炉目前只有一份内部命令器原型，尚未对外发布；`qinglu-core` 也没有作为公共库发布。这次检查是在决定哪些接口将来值得公开。Rust 中 `pub` 控制可见性，但单独一个 `pub` 还不等于对外承诺：项必须能从 crate 的公开路径到达，而兼容责任也与它是否成为已发布、被调用方依赖的 API 有关。

他逐行检查核心 crate 的候选接口，撤掉二十六处当前没有必要的 `pub`。审计先确认这些声明在本 crate 中实际可达的位置、内部调用方式和预定用途；数字说的是本次改动数量，不代表二十六项都曾成为已发布 API 或被外部用户依赖。它们中有些只是早期原型沿用的可见性，有些尚无跨 crate 使用需求。

沈见微在审计页上圈起“二十六”，对桌边的人说：“这不是二十六份已经许下的承诺，而是二十六处需要重新核对的可见性。核心库还没发布，也没有证据表明外部调用方依赖这些接口。现在收窄边界，是为了只留下团队确实打算维护的入口。库发布后，调用方依赖某个可达接口，随意改签名可能让他们编译失败；行为变化也可能破坏约定。编译器能检查可见性，却不能替我们决定哪些接口值得长期维护。”

他在清单末补了一句：收窄可见性不是为了藏起实现，而是避免把尚未稳定的候选接口误写成长期契约。承诺少一些，每一项才更容易守住。内部实现仍须谨慎维护；等外部调用方真正依赖这些入口，修改就要承担相应的兼容责任。
