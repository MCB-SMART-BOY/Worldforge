# 明契卷 · 第71章 · 程知序的凌晨

第二天，程知序把昨夜追查到的根因和迁移过程整理出来——问题不在他的代码，而是青炉一项六个版本前改过的 trait bound 没有写进 changelog。

他把追查过程写成了 issue——不是抱怨，是"这是错误发生的时间、这是受影响的项目、这是缺失的 changelog 条目、这是建议的修复方式"。这份 issue 比一句"坏了"更完整——它还指出"这里应该有一个声明，但它不在"。他在凌晨没有愤怒——他写了一个模板，这样以后类似的问题可以被更快地定位。

"你的 crate 的每一个 breaking change——都是我的凌晨。不是'我不会再改'——是'改之前——先告诉我——给我的代码一个编译的机会而不是突然打断它。'使用者的凌晨是 API 设计中最真实的反馈——比任何 review 都更诚实。闻衡的尺能看到接口的不完整，程知序的 issue 能看到接口在真实世界中如何断裂。两个维度互相补充。"
