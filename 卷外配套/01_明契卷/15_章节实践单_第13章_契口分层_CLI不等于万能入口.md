## 二、本单定位

### 1. 本章工程问题

- 哪些能力应该被做成可复用核心，哪些只该停留在入口壳

### 2. 本章要立起的判断尺

- 分骨不是为了优雅，而是为了不让未来协作继续压成一团直觉

### 3. 本单不负责的内容

- 不讨论完整插件系统
- 不要求一口气拆完所有骨
- 不把分层当成功能扩张的借口

## 四、故事映照

- 本章对应的主要事件：贺时进要把新需求继续塞回 CLI，主角拒绝万能壳
- 本章是谁在承担代价：主角承担拆骨的短期复杂度，继承者获得第一次可接的边界
- 这一章为什么必须用这个工程动作来照出剧情：核心与外壳一旦不分，未来所有协作都会重新锁回入口层

## 五、本章最小实践

### 1. 核心概念

- core
- shell
- 公共 API

### 2. 最小项目动作

- 把 `check` 的核心规则从命令入口里抽进 `lib.rs` 或独立核心层

### 3. 推荐工具 / 命令 / 观察点

- 工具：`cargo check`
- 命令：`cargo check`
- 观察点：核心逻辑是否还能在不依赖 CLI 的情况下被调用

### 4. 必做练习

- 练习目标：让同一份规则既能被 CLI 调用，也能被后续测试或其他入口复用
- 输入：当前 `qinglu` 原型
- 输出：一个最小公共函数或公共类型边界
- 完成标准：入口层只负责收参数和展示结果，核心层负责规则判断，并且接口名称能说明责任

### 5. 可选延伸

- 补一页“哪些东西仍然故意留在壳层”，训练自己说明不抽离的理由

## 七、常见误区

- 误区一：
  - 表现：一看到“核心层”就把所有代码都往里塞
  - 为什么不对：这样只会把另一个层变成新的万能壳
- 误区二：
  - 表现：只因为未来“可能复用”就先抽出一堆公共接口
  - 为什么不对：没有稳定责任的复用，只会提前冻结错误边界
