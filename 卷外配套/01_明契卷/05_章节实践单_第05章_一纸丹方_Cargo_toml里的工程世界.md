## 二、本单定位

### 1. 本章工程问题

- 为什么 `Cargo.toml` 不是随手填的配置桶，而是项目向别人公开的第一份誓约

### 2. 本章要立起的判断尺

- manifest 的每一行都应该能解释“它在承诺什么”

### 3. 本单不负责的内容

- 不讲 crates.io 发布细节
- 不讨论复杂 feature matrix
- 不替代后续版本策略

## 五、本章最小实践

### 1. 核心概念

- Cargo.toml
- 版本承诺
- feature 边界

### 2. 最小项目动作

- 为 `qinglu` 写一份有意义的 `Cargo.toml`，并为每个关键字段补一句责任说明

建议把本节控制在一个可在 `20–40` 分钟内完成的范围。

### 3. 推荐工具 / 命令 / 观察点

- 工具：文本编辑器、`cargo`
- 命令：`cargo check`
- 观察点：你能不能解释自己为什么要这个字段，而不是“大家都这么写”

### 4. 必做练习

- 练习目标：让 `qinglu` 的 manifest 看起来像誓约，而不是杂项表
- 输入：当前 `qinglu` 仓库
- 输出：补全后的 `Cargo.toml` 和一份 `docs/manifest-notes.md`
- 完成标准：至少解释 `name`、`version`、`edition`、一个 `feature`，并说明它们分别对维护者、使用者和后来者意味着什么

### 5. 可选延伸

- 尝试删掉一个你解释不清的字段，观察项目是否反而更诚实

## 七、常见误区

- 误区一：
  - 表现：把 `Cargo.toml` 当成只要编译通过就行的元数据文件
  - 为什么不对：字段一旦公开，就会被别人当成行为预期的一部分
- 误区二：
  - 表现：先把想得到的依赖都加进去，之后再慢慢删
  - 为什么不对：每个依赖都在扩张你未来要解释和承担的边界
