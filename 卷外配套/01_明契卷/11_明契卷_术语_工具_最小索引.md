# 《万构界·明契卷》术语 / 工具最小索引

## 一、文档定位

本索引服务于《明契卷》卷一到卷十的四批配套实例。

它不是百科，也不是 Rust 手册。

它只负责让读者在不打断正文节奏的前提下，先查清最常妨碍理解的高频词。

## 三、工程术语索引

| 术语 / 工具 | 最小解释 | 为什么此卷必须懂 | 常见误解 | 对应实践单 |
|---|---|---|---|---|
| scope | 本版本明确要解决的问题边界 | 没有它，项目会重新长成万金油幻觉 | 觉得 scope 就是保守 | 第02章 |
| 非目标 | 当前版本故意不承诺的事 | 它在防止对别人撒谎 | 以为只是“暂时懒得做” | 第02章 |
| rustup | 管理 Rust 工具链的入口 | 它决定别人能否从干净环境重起 | 以为装一次就再也不用管 | 第04章 |
| toolchain | 编译器和配套工具的具体组合 | 它本身就是项目秩序的一部分 | 以为只是安装步骤 | 第04章 |
| cargo | Rust 的项目与构建工具入口 | 它把构建、检查、运行、测试拉进同一条公开路径 | 以为只是包管理器 | 第04章、第24章 |
| Cargo.toml | 项目的 manifest 文件 | 它是第一份外显之约 | 以为只是配置杂项表 | 第05章 |
| manifest | 项目的公开元信息与依赖说明 | 让别人知道这器是什么、不是什么 | 以为写了就等于理解了 | 第05章 |
| ownership | 值和资源由谁负责 | 它直接回应卷首事故里的责任空区 | 以为只是借用检查器的麻烦 | 第06章 |
| borrow | 在不转移拥有权时临时使用值 | 它让“读”与“拿走”被区分开 | 以为借用就天然免费 | 第06章 |
| drop | 值离开作用域时的释放语义 | 它提醒资源的退出也属于责任 | 以为只跟底层内存有关 | 第06章 |
| module | 把职责写进结构边界的基本单位 | 让后来者第一次有读入入口 | 以为拆文件就等于有结构 | 第07章 |
| Option | 表示“可能没有值” | 让缺失被正名，而不是被硬造默认值 | 以为所有失败都该用它 | 第08章 |
| Result | 表示“可能成功也可能失败” | 让失败变成公开语义 | 以为写了 Result 就算错误处理完成 | 第08章 |
| panic | 程序无法继续的硬停 | 帮你分清普通失败和致命失守 | 以为所有错误都该 panic | 第08章 |
| dry-run | 不真正执行破坏性动作，只先检查路径是否成立 | 它是诚实小器常见的第一能力 | 以为 dry-run 可以代替真实校验 | 第09章 |
| README | 对人类公开的最小入口说明 | 它经常是后来者遇见项目的第一张脸 | 以为写一段介绍就够了 | 第02章、第26章 |
| config | 决定程序行为前提的公开输入层 | 它是“只在我机器能跑”能否被治的关键 | 以为多写几个默认值就算配置设计 | 第11章、第25章 |
| workspace | 管理多 crate 协同的根骨架 | 它决定多人是否能在同一炉里共修 | 以为只是把仓库拆得更细 | 第14章 |
| crate | Rust 项目的独立编译与边界单元 | 它让职责与依赖关系第一次可被明确书写 | 以为 crate 越多越高级 | 第10章、第24章 |
| trait | 把已成立的行为边界写成接口的方式 | 它是抽象节制的正面工具，也可能成为新壳 | 以为一有重复就该上 trait | 第15章 |
| 泛型 | 在边界清楚时复用逻辑的方式 | 它帮助减少重复，但也最容易提前冻结不确定 | 以为泛型越多越通用 | 第15章 |
| Git | 项目内史的公共入口 | 它让“为什么这样改”第一次可以被复查 | 以为只是备份工具 | 第16章 |
| commit | 一次清楚、可复查的变化单位 | 它决定历史是否可读 | 以为把所有改动塞一起更省事 | 第16章 |
| branch | 暂时分出一条变化线 | 它保护试改不直接污染共路 | 以为分支只对大型团队有用 | 第16章 |
| tag | 给某个历史节点打公开记号 | 它让共同体能指认一个稳定点 | 以为只是版本美化 | 第16章、第25章 |
| issue | 公共提问与记录问题的入口 | 它让使用者和维护者共享问题上下文 | 以为群里问一下就够了 | 第17章 |
| pull request | 公共提出改动与讨论改动的入口 | 它把理由链、评审和史连在一起 | 以为只是点一个合并按钮 | 第17章 |
| review | 共同体对边界、错误、文档与历史的复核 | 它是交解释权的动作 | 以为只是挑代码风格 | 第18章 |
| CI | 把最低公共验证写成可重复执行的检查 | 它让门规第一次能自动守住底线 | 以为有测试就等于有 CI | 第18章 |
| CONTRIBUTING | 给新贡献者的公开入门契约 | 它让新人第一次能沿规则进门 | 以为写了文件就自然有人能用 | 第18章 |
| 生命周期 | 某段数据在多长时间内仍然有效 | 它决定“谁死了、谁还能碰”是否清楚 | 以为只是编译器绕口令 | 第21章 |
| 内存安全 | 一类资源边界错误被系统性提前拦住 | 它把最难复盘的错从运气问题改成设计问题 | 以为等于程序永不出错 | 第21章 |
| `Send` | 值可以安全移交到另一线程 | 它帮助判断哪些任务能并行分发 | 以为只要能编译就代表设计合理 | 第22章 |
| `Sync` | 值可以被多线程安全共享引用 | 它直接对应共享状态代价 | 以为共享就一定更省事 | 第22章 |
| 锁 | 保护共享可变状态的协调机制 | 它是代价，不是免费便利 | 以为加锁就等于并发问题解决 | 第22章 |
| `unsafe` | 需要程序员自己额外证明安全前提的边界 | 它是责任增加，不是性能捷径标签 | 以为看到 `unsafe` 就一定不该用 | 第23章 |
| FFI | 跨语言或跨运行边界调用外部能力 | 它是旧桥进入青炉的主入口之一 | 以为接通了就算边界成立 | 第23章 |
| 单元测试 | 针对局部逻辑的最小验证 | 它把核心规则先钉牢 | 以为只测函数就够了 | 第24章 |
| 集成测试 | 验证多个部件一起工作是否成立 | 它让契口与配置组合被真实检查 | 以为和端到端是一回事 | 第24章 |
| 契约测试 | 验证边界承诺是否持续成立 | 它特别适合桥接与插件层 | 以为只是换个名字的集成测试 | 第24章 |
| 端到端 | 沿真实入口跑完整条关键链 | 它证明使用者路径是否真的可走 | 以为所有验证都该写成长链 | 第24章 |
| semver | 用版本号表达兼容语义的规则 | 它帮助门外之人判断升级风险 | 以为只是编号格式 | 第25章 |
| changelog | 记录版本变化和影响的公开说明 | 它是外史的一部分 | 以为只是发版宣传摘要 | 第25章 |
| release | 对外发布一个可指认版本的动作 | 它本身就是立契 | 以为代码合并完就算发布完成 | 第25章 |
| deprecation | 对即将退场的能力给出公开提醒 | 它让拆桥开始有路可走 | 以为只是“以后可能会删” | 第25章、第29章 |
| 二进制交付 | 以可安装可执行形态交付给用户 | 它决定用户第一眼遇见的是真门还是谜语 | 以为只要能编译出文件就够了 | 第26章 |
| process | 一次程序执行实例 | 它是运行态讨论的起点 | 以为和命令本身没有区别 | 第27章 |
| service | 持续为外部提供能力的运行方式 | 它会放大权限、锁和环境问题 | 以为只是把命令常驻 | 第27章 |
| daemon | 脱离交互终端长期运行的进程 | 它让“程序真的活着”变成额外责任 | 以为只要一直跑着就行 | 第27章 |
| log | 记录运行中发生了什么 | 它是最小可诊断入口 | 以为写越多越好 | 第28章 |
| trace | 把同一轮执行中的关键步骤串起来 | 它帮助跨环境追踪一次真实运行 | 以为等于日志换名字 | 第28章 |
| metric | 对运行态做聚合观察的数据 | 它帮助看趋势，不替代诊断 | 以为有图表就等于可观测 | 第28章 |
| 迁移说明 | 告诉使用者如何从旧路径走到新路径 | 它是拆桥时对门外负责的文档 | 以为内部自己知道就够了 | 第29章 |
| 兼容层 | 为不断流而保留的过渡结构 | 它是桥，不是新核心 | 以为留着没坏处 | 第29章 |
| 技术债 | 过去为了现实窗口借来的未来代价 | 它会随时间沉积并反咬演进 | 以为只是代码不够漂亮 | 第29章 |
| 显式代价 | 现在就把失败、限制与前提写清所要付出的即时成本 | 它帮助判断“重”到底值不值 | 以为只是形式主义 | 第30章 |
| 不变量 | 无论谁来改、何时运行都不能被悄悄破坏的底线约束 | 它帮助项目识别哪些桥绝不能偷渡 | 以为只是数学词 | 第30章 |
| 工程适配 | 工具、语言与项目问题之间是否合适的判断 | 它防止整卷滑向语言信仰 | 以为只是个人偏好 | 第31章 |
| handoff drill | 模拟原作者不在场时的交接与修补演练 | 它是卷尾继承能否成立的最低验证 | 以为有 README 就算做过交接 | 第32章 |
| patch release | 针对已发布版本的小范围修补发布 | 它帮助共同体验证自己能否在作者缺席时继续守火 | 以为只是把版本号加一小位 | 第32章 |

## 四、命令 / 动作最小索引

| 命令 / 动作 | 用在什么场景 | 期望看到什么 | 出错时先检查什么 |
|---|---|---|---|
| `env` | 识别隐性环境前提 | 看见当前环境变量集合 | 哪些前提其实没被文档写下 |
| `which bash` | 确认命令入口来自哪里 | 知道实际执行的是哪份程序 | PATH 是否和文档假设一致 |
| `rustup show active-toolchain` | 确认当前工具链 | 看见当前生效的 toolchain 名称 | rustup 是否安装、默认工具链是否正确 |
| `rustc --version` | 确认编译器版本 | 明确当前编译器版本 | 当前 shell 是否真的走到想要的编译器 |
| `cargo --version` | 确认 cargo 入口 | 明确当前 cargo 版本 | cargo 是否来自预期工具链 |
| `cargo new qinglu --bin` | 初始化项目骨架 | 得到一个最小可起炉的仓库 | 当前目录是否干净、命名是否合适 |
| `cargo check` | 快速验证代码能否通过编译检查 | 看到构建检查通过 | manifest、模块路径、函数签名是否不一致 |
| `cargo check --workspace` | 验证多 crate 是否仍沿同一套共约协同 | workspace 检查通过 | crate 边界、依赖关系、公共接口是否不一致 |
| `cargo run -- check ./sample-release.toml` | 运行最小校验入口 | 成功时得到通过信息，失败时得到具名错误 | 样例配置是否存在、错误是否被清楚返回 |
| `cargo test` | 验证最小行为是否被重复检查 | 测试通过且输出清楚 | 是否只写了演示，没有真正做可重复验证 |
| `cargo test --lib` | 只先验证核心逻辑 | 看到核心规则层通过 | 失败是否被压在更长链条里看不清 |
| `cargo test --test release_rehearsal` | 演练关键用户路径 | 看见真实入口链能被重复走通 | 测试是否仍然依赖维护者私货环境 |
| `git init` | 建立项目内史入口 | 仓库开始拥有公共历史根 | 是否在正确目录初始化 |
| `git log --oneline` | 快速回看历史线 | 历史节点清楚可读 | 提交信息是否仍然含糊 |
| `git tag <name>` | 给稳定节点打记号 | 某个共识点被公开标识 | 是否在错误提交上打标 |
| `cargo fmt --check` | 守住最小格式底线 | 格式检查通过 | 是否存在未整理代码 |
| `cargo clippy` | 守住一批静态检查底线 | 看见关键 lint 信息 | 是否把 lint 当成噪音完全忽略 |
| `cargo publish --dry-run` | 在真正发布前先演练发布链 | 看到交付面和打包动作基本成立 | 元信息、文档、忽略文件是否还没准备好 |
| `cargo install --path .` | 模拟用户从本地安装项目 | 能用接近用户视角的方式得到可执行入口 | 安装说明、二进制名、帮助信息是否自洽 |
| `qinglu doctor --once` | 一次性运行诊断动作 | 看见本次检查清楚结束 | 运行模式是否仍依赖交互式前提 |
| `qinglu doctor --watch` | 验证守夜模式设想 | 看见长驻模式的最小入口 | 锁、退出条件和日志位置是否写清 |
| `RUST_LOG=info cargo run -- doctor ./sample-release.toml` | 观察一次带日志的执行 | 看见步骤、上下文和失败链 | 日志是否只有碎片化文本，没有关键标识 |

## 五、最易混淆概念对

| 概念 A | 概念 B | 关键区别 | 在本卷里为什么重要 |
|---|---|---|---|
| 文档存在 | 契约成立 | 前者只说明“有文字”，后者说明“文字与行为一致” | 卷首事故正是文档存在却仍然失信 |
| 命令成功 | 行为可信 | 前者是本次执行结果，后者是公共可依赖性 | 明契卷第一把尺就立在这里 |
| scope | 功能愿望单 | 前者会砍掉做不到的承诺，后者只会扩张幻觉 | 第二章的立约核心 |
| 所有权 | 默认共享 | 前者明确谁负责，后者常常让责任消失 | 第六章直接回应旧缓存和全局状态问题 |
| Option | Result | 前者处理“有无”，后者处理“成败” | 第八章要防止把失败继续模糊化 |
| 可用小器 | 全能大壳 | 前者先保证真实可信，后者常靠隐藏代价维持 | 第九章的最小可用版本判断 |
| README | 注释 | 前者面向进入项目的人，后者面向读局部代码的人 | 第十二章开始把项目记忆分层 |
| module | crate | 前者是代码结构层级，后者是编译与边界单元 | 第十章与第十四章会先后用到 |
| 抽象节制 | 过早统一 | 前者是知道何时停手，后者是用漂亮结构冻住未成熟关系 | 第十五章的中段真相就立在这里 |
| 协作入口 | 私下传代码 | 前者能留下公共史，后者只能继续喂养熟人默契 | 第十七章的门外之问核心 |
