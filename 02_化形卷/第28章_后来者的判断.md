# 化形卷 · 第28章 · 后来者的判断

周栖野把三份材料的收尾文字并排放在石镜上：旧石镜里的shell脚本、林过川的Python工具、那份C命令行程序。它们的形式不同——一条TODO、一段README、一行代码注释——他想比较的是各自停步时留下了什么。

三份记录的字面内容不同，周栖野读到的相似处，是它们都留下了尚未完成的判断。

C工具注释原文："此函数依赖内部API。该API已废弃。无法完成。"

Shell脚本的原始TODO：`TODO: handle the case when pip is not installed`

林过川的README原文："这个工具本身不能被自动化交接。因为它依赖的 Python 版本在下一代息壤已经不兼容。放弃。"

相似的意思——从不同的措辞、时代和语言中读出来——落在三位从未见过彼此的人身上；这先是周栖野的归纳，不是材料已经证明的共同意图。

**后来者应该自己判断。**这是周栖野从三种不同停步记录中归纳出的读法，不是任何一份原文里的完整句子，更不是三位作者共同写下的指令。

· · ·

这些措辞相近，但不足以证明三人互相传承了同一种信仰。周栖野把它们并排看时，先想到的是一种可能：他们也许都不愿替后来者决定该怎么走。这个解释暂时说得通，却还只是他的解释。

shell脚本的作者面对的是pip行为的不确定性。周栖野推想，依赖检查脚本本身也受环境约束——pip的版本会变，包名会变，甚至pip本身可能被更好的工具替代；但TODO只写到“处理未安装pip的情形”，没有留下这段推理。

林过川面对的是交接工具本身不能被交接的悖论。他写了自动扫描依赖的工具。代码几乎完整。测试也写了。然后他发现——这个工具依赖的Python版本在下一代息壤已经不兼容。交接工具本身需要交接。而他没有制度来声明"在我的前提下，这是对的"。所以他写了一句"放弃"。不是技术失败。是发现了一个他一个人无法解决的递归困境。

C工具的作者面对的是内部API被废弃。他依赖了一个在组织内部被弃用的接口。那个接口没有做弃用声明（`deprecation notice`）。有一天就默默地没了。代码还在那里——关键函数变成了一个洞。他留下了依赖失效和函数未完成的记录，却没能留下可继续执行的实现。

三个人在不同的时代停下。现有材料能分别说明：shell脚本依赖当时环境中的pip行为；林过川的README写明工具依赖的Python版本在下一代息壤不兼容；C工具依赖的内部API已被废弃。周栖野还推想，林过川或许担心下一代Python的import规则变化会让扫描结果失真；但README没有留下这层担忧，无法确认这是不是林过川当时的判断。它们不是同一个技术原因，也没有证据证明三人出于同一信念而停笔。相似的是，他们留下的说明都把一部分判断交给了后来者，却没有足够的可复核前提让后来者接着做。

· · ·

周栖野把这三份材料的收尾文字放在一起之后，忽然想起了什么。他翻开自己的记录本——在某一页的边缘标注，是从驭器卷传来的。纪承钧在玄枢最底层的断史库里发现的那一行残码。

`[RESERVED FOR INHERITANCE COVENANT — PENDING RATIFICATION]`

周栖野觉得这也许与玄枢的PENDING残码、驿河那一万多次未回应的告警有关：不同世界都留下了未完成或未回应的痕迹。但这些材料尚不能证明它们出自同一信念，也不能确认背后是同一种恐惧。它们只能作为待比较的线索。

不是同一个人教出来的，这一点目前没有证据；是否是同一种困境，也仍待核实。

"这可能是他们对后来者的信任，也可能只是各自停下时留下的说法。"叶藏拙说，"我们知道空白把判断留给了后来者，却还不知道他们当时为什么这样写。"

· · ·

周栖野在林过川的README旁边，加了一行标注。

"林过川。你的工具没有完成交接。我还不知道你留下那句话时，是在信任后来者，还是已经没有条件继续。你的README至少让我知道这里停过。玄枢有人用前提声明、公共记录板和伤痕记录留下尝试过程；那是他们的回应，不足以证明你们共享同一种信念。我先把已知的原因和仍然未知的部分并排记下。后来者不必把我的解释当成你的原意。"

他放下笔。三份材料的收尾文字仍然在石镜上并排亮着。不是同一句原文，也未必来自同一种信念；它们只是让周栖野看见，前提和未完成处没有被充分交给下一代查验。
