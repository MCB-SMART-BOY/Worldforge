# 化形卷 · 第80章 · 分层之后

三层的速度图挂上墙后，周栖野回看一份刚通过晋升审核的 core 模块。MRC、类型和测试都在；轮到检查测试如何准备数据时，他停在一行 import 上。

core 的测试直接引用了 lab 里的一个共享 fixture。它只负责准备测试数据，不是对外能力，也没有申请晋升。可如果有人调整这份试验层代码，core 的测试就可能跟着变；若另一个干净环境没有那条路径，测试也无法照原样运行。

周栖野把测试文件和规则一起带到宋既明面前：“我们写了 lab 到 core 的晋升门槛，却没有说测试夹具该放在哪一层。这算不算越级？”

宋既明看过那行 import：“它不是产品代码。按现有清单，它不需要作为模块晋升。可 core 的测试已经依赖它，按‘谁会依赖这个东西’来算，它也不再只是 lab 里的私人试验。”

两人没有马上把 fixture 挪进 core。那样会把“测试需要共享”直接变成“它应该属于固核”，仍然是在替规则猜答案。周栖野先把情况画在板上：依赖已经跨层，归属规则却只写了正式模块；这是规则没有覆盖的灰区，不是某个人漏做了已有步骤。

叶藏拙读完记录，翻开账本最后一页：“规则也会老。你要怎么知道这只是一个漏项，还是三层还有别的盲处？”

“像模块一样，给制度留检查入口。”周栖野在板上写下“每六个月公开审视一次三层规则”。第一次审视定在六个月后；任何人都可以提出需要检查的边界，审视结果和修改理由都记下来。“今天先把这个 fixture 的依赖标清楚，列为待定规则；不假装标准已经回答了它。”

宋既明补上“谁依赖、如何验证、变更会影响哪层”三项，作为这次审视的记录入口。叶藏拙在账本上写下日期，周栖野则把审视周期贴到三层规则旁。具体规则仍待讨论，但这次遗漏已经有了负责人、问题记录和回来的时间。

“三层不是永远正确的。”周栖野说，“它只是目前最好的边界。边界遇到新情况，就得把情况写进去；要是写不进去，也得公开承认。”

叶藏拙合上账本：“这样后来者能知道，规则不是从来就完整。也能知道什么时候可以质疑它。”

周栖野看着板上的三层图。快与慢各有了空间，但空间之间仍会长出新的依赖；今天那行 import 就是提醒。制度不因为有了名字和目录就完成了，它得持续被检查、补充，也得允许后来者指出遗漏。六个月后，他们会回来审视这些边界；在那之前，这条灰线不会再被当成没有问题。
