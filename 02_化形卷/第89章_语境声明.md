# 化形卷 · 第89章 · 语境声明

周栖野先把傅远洲的问题写进跨域部署检查表：资源声明改为必填，至少列出峰值负载、批次大小、内存上限与 CPU 亲和性。没有证据的字段不能照抄默认值，必须标为“未知，待目标环境验证”。

随后，他把这次事故的复核单单独抽出来，标题写上 `seasonal-settlement-validator`，将每一项都填回证据里。

**息壤已验证：**季晚禾人工逐个集群处理，通常约占用 200MB；已有测试中内存未超过 500MB。  
**驿河已观测：**季度全量批次一次加载十一个集群，内存需求约 2.3GB；接入表沿用的驿河平台模板默认预算为 512MB，无法承载这次负载，进程被杀，三条结算管道同时超时。  
**仍未知：**在驿河长期运行时的内存曲线、可安全承诺的批次上限，以及 CPU 亲和性要求。一次事故记录能说明这次负载越过了默认值，不能替未来负载给出上限。

他在末尾补了一行：“512MB 是驿河接入模板沿用的默认预算，不是息壤测试得出的资源上限，也不是驿河已验证的安全上限。息壤的单集群手动处理，不等于驿河共享资源池中的长期服务。重新部署前，须由接收方按目标环境和实际批次重新验证；验证范围之外，保持未知。”

这是一条第一阶段的资源声明规则。附在规则后的单模块记录只适用于这次事故里的模块，还不是所有文档通用的语境模板。它只写得出这次确实见过的条件，也把尚未验证的部分留空。周栖野把它附在跨域部署复核单后，没有把 2.3GB 改写成新的保证。

他看着那张纸，明白“资源声明必填”仍只是起点。填上一个数字，仍可能把局部经验伪装成普遍上限。下一步要解决的，是让每一项承诺都说清：它在哪种场景里成立，场景之外还要查什么。后来，这条要求才会从跨域部署检查扩展为 MRC、API 契约与入职文档的通用语境声明。
