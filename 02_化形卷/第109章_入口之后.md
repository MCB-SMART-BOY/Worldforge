# 化形卷 · 第109章 · 入口之后

周栖野把“如何加入息壤”那份入职文档放在桌上，又新开了一页，标题写着：**如果维护者离开。**他没有准备离开；他想知道，哪天自己不在，后来者能不能从入口继续走下去。

文档刚写到“当前维护者”一栏，他就停住了。白又新和季晚禾已经各自走通入职路径，这份文档也给后来者标出了从哪里开始；但模块名可以从目录里列出来，谁负责回答问题、谁能确认迁移完成，却不能只从提交记录里推断。他在 `field-mapper` 旁写下自己的名字，又在尚未确认的职责后标注“待确认”，没有把“最后改过代码的人”伪装成正式接手人。

叶藏拙拿起笔，检查他列出的内容：“你把环境步骤和测试写了。你脑子里那些还没写下来的判断呢？”

周栖野翻到语境声明，补上已验证范围和未验证边界；又把 MRC、`uv.lock`、Dockerfile、测试入口以及入职文档各自的位置列进知识地图。离开的人要指出哪些内容已经写清楚，哪些仍只存在于自己的经验里。空着的地方不准写“大家都知道”，只能写“待补”并指定下一步检查。

季晚禾拿起这份初稿，从入职文档的第一步开始走。她在“权限与维护者交接”处停下：“如果交接已经发生，这里要写谁能批准变更；如果还没发生，就不能让我猜一个名字。”她把这条标成待补，并在旁边写下自己无法继续的原因。

周栖野接过她的标记。入职文档原本回答“你来了，第一步怎么做”；现在这份交接协议要回答“我走了，谁接什么，怎样确认接手完成”。两边需要相同的入口、相同的验证方式，但出口还多出一层责任转移：模块维护者、知识所在位置、尚未写进文档的判断，以及离开前必须完成的确认。

他把流程写成四项：维护者清单；文档与依赖的知识地图；未文档化知识声明；逐项执行并确认的交接检查。实际离开时再填写日期和接手人。没有已确认的人名，就保持待定；没有验证过的步骤，就不能标成完成。

“你这是准备走？”季晚禾问。

“不是今天。”周栖野说，“是我不在的那天不能变成事故。”他把自己负责的步骤先按清单走一遍，发现有一处说明仍只写着“按默认配置运行”。他将它标成未完成，链接到刚加上的语境声明，而不是替未来接手的人猜默认值。

叶藏拙从旧石镜记录里抽出那三段残码。C 工具的原注释说，依赖的内部 API 已经废弃，关键函数无法完成；shell 脚本只留下处理未安装 `pip` 的 TODO，不能据此判断作者是否预见了其他机器上的行为；林过川的 README 则写明，工具依赖的 Python 版本在下一代息壤已不兼容。

"他们留下的不是同一条指令，但这些断点都把未解决的问题留给了后来者。"周栖野说，"我们现在至少能给判断的材料、验证的方法和责任的去处。"

季晚禾把初稿还给他：“我愿意再照它走一次。没写清楚的地方，我会继续标出来。”

周栖野在页首加上：“这是首版交接协议；未确认项不代表已完成。”他没有宣布所有人都已有接手人，也没有假装离开从此没有风险。但入口和出口终于对上了：来的人能验证自己如何进入，走的人必须说明留下什么、谁接手，以及还有哪些空白。

下一步，他们要把可以带出息壤的能力清单整理出来。那份清单也必须带着边界，不能因为另一边愿意接收，就把本地验证说成跨域保证。
