# 化形卷 · 第56章 · 第三步失败

周栖野把纪承钧的 runbook 逐行对照息壤现有流程。十七步里，有十一步目前无法按原流程完成或核验。不是因为写错了，而是息壤缺少其中依赖的系统（`infrastructure`）；“待确认”仍表示需要核实，不等于已经证明每一步都绝对不可行。

核心问题在第三步。"确认所有下游依赖方已全部迁移。"

在玄枢——每座桥都有渡桥司的依赖注册表（`dependency registry`）。依赖方在登记时就声明了自己依赖什么接口、什么版本。确认依赖方迁移只需要查注册表——一个查询，三秒。在息壤——依赖在import链里。在人的记忆里。在叶藏拙的账本里——那是人工记录，不是系统。唯独不在机器可查询的注册表里。

要确认"所有下游依赖方已迁移"——在息壤意味着什么？人工审计每一个import语句。每一个脚本。每一个notebook。每一个cron任务。每一座桥——约两到三个时辰。

第八步——构建系统验证。玄枢有统一的构建与迁移校验流程。息壤的 Python 代码当然可以由解释器执行、也可以编译语法；缺少的是统一的构建和集成验证，无法仅凭一条命令确认所有使用者迁移后的导入、接口和行为。替代方案是逐台手动运行迁移验证，成本难以扩展。

第十一步——渡桥司退场审批。玄枢有专门管桥的机构。息壤——只有顾迁舟一个人。

· · ·

顾迁舟在runbook旁边贴了一张对照表。十七步。每步对应玄枢的前提——息壤是否有对应系统——如果没有，替代方案的成本。第三步——依赖注册表——息壤无——替代方案：人工审计所有import——每桥约两到三个时辰。第八步——构建系统验证——息壤无——替代方案：人工跑验证——不可扩展。第十一步——渡桥司退场审批——息壤无此机构——替代方案：顾迁舟一个人。

"这份runbook的价值不在它写了什么——在它暴露了什么。它暴露了息壤最脆弱的地方——我们不管理依赖。我们猜测依赖。玄枢不猜测——他们注册依赖。这是根基性的不同。不是修一两个工具能解决的。"

runbook的失败不是事故。是镜像。它照出了两个世界的架构鸿沟。
