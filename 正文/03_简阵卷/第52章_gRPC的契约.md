# 简阵卷 · 第52章 · gRPC 的契约

傅远洲把驿河内部服务间调用从 REST 加 JSON 迁移到 gRPC 加 protobuf。不是 REST 不好——是 REST 的契约不是机器可验证的。JSON schema 在人的脑子里——你知道这个字段是 string，他知道吗？你知道这个字段不能为 null，他知道吗？gRPC 的 schema 在 proto 文件里——机器会验证。proto 文件是 API 的唯一真相来源——服务端的接口、客户端的 stub 全部从同一个 proto 生成。

第一个迁移的服务间调用——`data-aggregator` 到 `stats-calculator`。改 proto 就是改契约——改契约就会有版本号——有版本号就有迁移指南。proto 定义不允许拼错字段名——编译期就爆。之前服务 A 调用服务 B，字段名拼错了——传到 B，B 用默认值处理，结果静默错误。凌晨追了几个时辰才发现是一个拼写错误。现在 proto 在编译时就说"这个字段不存在"。

不是不用 REST——是内部服务之间需要更强的契约。REST 适合开放给外部的简单接口，gRPC 适合内部高频调用需要严格类型和性能的地方。两者不是敌人——是不同的契约等级。外部接口用 REST 加 OpenAPI，内部服务间用 gRPC 加 protobuf。契约的强度取决于依赖的深度——被越多人依赖的东西需要越强的契约。不是所有接口都要 gRPC，但被五十一个服务间接依赖的核心调用链需要。
