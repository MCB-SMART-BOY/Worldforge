# 简阵卷 · 第32章 · context 的旅程

傅远洲审查Ch21失明事故中的调用链，发现一个问题：没有一个服务在调用下游时传了`context.Context`。Go的context不只是传参数——是传因果链。取消信号——上游不关心了，下游应该停止。截止时间——超时后不再等待。trace ID——让请求在全链路中可被追踪。

没有context，每个服务都向虚空发了请求然后永远在等。上游取消了请求——下游不知道，继续跑着浪费资源。没有trace ID，跨服务的请求无法被追踪。秦望秋的观测面板只能看到每个服务单独的日志，但拼不出一条请求的完整路径。

"context不是在传参数——是在传责任。你在请求下游时说：这是谁在等这个结果，多久之后可以不等的。下游知道这些之后才能做出正确决定——超时要不要重试、取消要不要回滚、日志里写什么。"

傅远洲给`data-aggregator`的调用链加入了context传播——从上游到四个下游。每个HTTP调用传context，context包含超时，下游检查context是否被取消，trace ID追踪全程。第一次，一个请求的完整路径可以被追踪——每一步的延迟、状态、日志都挂在同一个trace ID下。凌晨接传讯牌的人不再需要猜——跟随trace ID就能看到全过程。
