# 简阵卷 · 第32章 · context 的旅程

傅远洲审查 Ch21 失明事故中的调用链，发现一个问题：没有一个服务在调用下游时传了 `context.Context`。Go 的 context 不只是传参数——是传因果链。取消信号——上游不关心了，下游应该停止。截止时间——超时后不再等待。trace ID——让请求在全链路中可被追踪。

没有 context，每个服务都向虚空发了请求然后永远在等。上游取消了请求——下游不知道，继续跑着浪费资源。没有 trace ID，跨服务的请求无法被追踪。秦望秋的观测面板只能看到每个服务单独的日志，但拼不出一条请求的完整路径。

"context 不是在传参数——是在传责任。你在请求下游时说：'这是谁在等这个结果，多久之后可以不等的。'下游知道这些之后才能做出正确的决定——超时要不要重试、取消要不要回滚、日志里写什么。"

傅远洲给 `data-aggregator` 的调用链加入了 context 传播——从上游到四个下游。每个 HTTP 调用必须传 context，context 必须包含超时，下游必须检查 context 是否被取消，trace ID 用于追踪全程。第一次，一个请求的完整路径可以被追踪——从进入第一个服务到离开最后一个，每一步的延迟、状态、日志都挂在同一个 trace ID 下。

"现在如果一个请求在第七层超时——能看到它从第一层开始，经过了哪里，在哪一层卡住了。之前只能看到第七层自己超时了——不知道是谁让它超时的。context 传播不是 Go 的语法特性——是因果律。让每一个请求从出生到结束的路径可见。凌晨接传讯牌的人不再需要猜——跟随 trace ID 就能看到全过程。"
