# 驭器卷 · 第73章 · FFI 的地狱

unsafe 地图完成后的第二天——一次外部调用失败了。

不是大爆炸——是协阵扩域的一个旧子阵——在调用玄枢的信号码查询接口时——返回了乱码。正确数据——在 C++ 侧——是对的——`std::string`——标准字符串对象——内容正确——编码正确——长度正确。经过一层 C 绑定——`extern "C"`——变成 `const char*`——字符指针——不带长度信息——以 null 结尾。经过第二层——Fortran 的接口层——变成 `CHARACTER*(*)`——Fortran 的字符串类型——固定长度——不足时——空白填充。最后——到达那个旧子阵——子阵的接收端——是一位 Java 服务——通过 JNI（Java Native Interface）——把 Fortran 的字符数组——转回 Java 的 `String`。

Java 服务收到的——是乱码。不是全部——是——字符串末尾——多了几个不可打印字符——看起来——像是——"未初始化内存"。

陆踏痕花了整个上午——追这条调用链。从 Java 端——逆向往回追——JNI → Fortran → C → C++。每一步——数据在变——不是内容变——是——表示方式变。C++ 的 `std::string`——有 `.size()` 方法——可以精确知道字符串的长度。但当它被转为 `const char*` 时——长度信息——丢了。C 层——只知道——这是一个字符指针——不知道它多长——它会在 null 字节处停止——但如果字符串本身——没有 null——或者——在分配的内存块里——null 不在字符串末尾——而在——字符串——之前或之后——C 的函数——读到的——可能是——超过字符串真实长度的——内存区域。

"Fortran 那层——`CHARACTER*(*)`——继承了 C 层的长度不确定。Fortran 的字符串——是固定长度的——如果 C 传过来的不是一个精确固定长度的字符串——Fortran 会用空白填充——直到固定长度。然后 Java 那层——JNI——接收 Fortran 的字符数组——转成 Java `String`。——但——JNI——假设 Fortran 传过来的是一个 C 风格的 null-terminated string——而 Fortran 的 `CHARACTER`——不以 null 结尾——它以空白填充。——所以——Java 收到的——是——Fortran 传来的字符——加上——填充的空白——加上——可能在字符串末尾——额外的一块未初始化的内存——然后——JNI 调用 `strlen`——超过应读范围——直到遇到一个随机的 null 字节。——显示的——就是乱码。"

"每一步——都是对的——在自己的那一层——是对的。C++——对。C——对。Fortran——对。JNI——对。但每层之间——信息——丢了。——C++ 到 C——丢了长度。C 到 Fortran——丢了格式。Fortran 到 JNI——丢了编码约定。四个'对'——拼在一起——变成了——一个——'乱码'。"

"ABI 兼容——不是同一种语言——是——它们——能编译成——可以被链接器放在一起——的二进制。但链接器不保证——你的字符串——在另一侧——还是你的字符串。链接器只保证——符号找得到。——保证语言级别的安全——是程序员的责任——但——当你的 FFI——跨了三种语言——和四种字符串表示——的边界——程序员——几乎不可能——理解——所有隐式假设。——地狱——不是某一步错了——是——每一步——都是对的——但——'对'——是——每个人——在自己的语境里——定义——而语境——不传过边界。"

· · ·

下午。陆踏痕画出这条 FFI 的完整调用链——跨了五个编译单元——三个语言——两个操作系统——从 C++17 的 `std::string`——到 Java 8 的 `String`——中间——是——C ABI——Fortran 77 的固定字符串——和——JNI。

"这不是最复杂的。"他说。"玄枢里——还有更深的——Fortran 到汇编——汇编到——硬件寄存器。——但这条——是——最具代表性的——因为——每一层——都是常见的技术——C ABI——是'通用接口'——几乎每种语言——都能调用 C 的函数——但'通用'——意味着——它不保证——任何语言特定的行为。——内存布局——是谁的责任——C++ 说——'我给了一个指针——你——在 C 那边——自己管。'——C 说——'我收到了一个指针——我不知道它指向的内存——是谁分配的——谁负责释放——它的生命周期——有多长。'——Fortran 说——'我收到了一个字符串——我需要它是固定长度的——如果不是——我填充——填充物——是什么——取决于编译器。——然后——Java 的 JNI——说——'我假设——你给我的——是一个 C 风格的 null-terminated string。——不是——Fortran 的——空白填充——固定长度——的字符数组。——这个假设——写在了 JNI 的文档里——但——在这条调用链上——它被——违反了。——没有报错——因为——JNI——在大多数情况下——能正确读到 null。——只是在——字符串长度恰好是 256 的倍数时——null 不在预期位置——读到空白。'"

"这个 bug——不是一次引入的——是——一层一层——'对'——叠出来的。——地狱——不是某一个人做错了——是——文明——在跨语言边界——的——承诺——和——实际——之间——留了——无人负责的——空白。——那个空白——在——C ABI 的'通用'——和——每种语言的'特定'——之间。"

· · ·

钟守玄看到了陆踏痕的画——那条跨了三个语言边界的 FFI 调用链。他把这张图——贴在了 unsafe 地图上——在最深的那一层。

"这就是为什么旧桥那么多。"他说。"不是我们喜欢搭桥——是 FFI 地狱——逼出来的。搭桥——是一种——隔离——把地狱的一侧——和另一侧——隔开——让桥——承担——隐式转换——和——假设——让桥两侧的人——不需要理解——对方语言里——字符串——是什么样的。——桥——是地狱里的路。——不是好路——但——在没有其他方法——跨过语言边界之前——桥——是唯一的路。"

"但桥——本身——也是在 FFI 地狱里搭的。每座桥——也都跨了语言边界。所以桥——也是纸做的。——和你刚才画的那条链——本质上——是同一件事——只是——桥——把它叫做——'适配层'——而不是——'FFI 调用'。——纸墙——是不管叫什么名字——都是纸的。"

· · ·

傍晚。纪承钧在 unsafe 地图上——FFI 边界的地方——加了一行说明。

"FFI——不是邪法——是——'自负额外证明之责。'——越过语言边界的人——必须自己证明——安全。——编译器——在边界两端——各自保证安全——但边界本身——是无人之地。——在无人之地——调用约定（calling convention）、内存布局（memory layout）、字符串编码（string encoding）、错误处理（error handling）——没有一项——是自动兼容的。——每一项——都需要——被显式——被验证——被文档化。——以前——这项责任——被'刚好能跑'——掩盖了。——观测——和——sanitizer——让——没有被履行的证明——重新——变得可见。——纪承钧。——前提——此图——基于玄枢当前的 FFI 调用链。——后来者——在你越过语言边界时——请——在此处——标注——'已验证——什么——用什么方法——在什么前提下。'——不是——'我觉得可以'。——是——'我证明——在这个前提成立时——安全。——前提如下。——请后来者验证——前提是否仍然成立。——前提可能不成立。'"
