# 驭器卷 · 第32章 · CMake 地狱

纪承钧试图修改玄枢的构建系统，是从一行 include 开始的。

include 本身很简单——就是把一个构建模块的路径从旧的位置改到新的位置。旧的位置已经废弃了两年，代码早就迁走了，只剩一个空目录。他以为这只是一次清扫——把不再被引用的路径从 CMakeLists.txt（`构建配置文件`）里删掉。像收拾旧机柜——把不用的东西清出去。

他改了一行。

然后玄枢编译失败了。

不是在改了 include 的那个模块失败。是在三个完全无关的地方。一个和旧适配层相关的构建目标爆了未定义引用（`undefined reference`）。一个外部接口的包装层找不到它的依赖头文件（`header file`）。还有一个——最诡异——在链接阶段（`link stage`）出了一个他从未见过的错误：重复符号定义（`duplicate symbol`），但两个符号——在不同的目标文件里——不应该同时出现。

"我只改了一行 include。"他盯着石镜上那串编译错误。

钟守玄路过他身后。看了一眼错误。没有停。

"CMake 地狱。"他说。像在说一个老朋友的名字。

· · ·

三个时辰后，陆踏痕拿着一个旧笔记本走进来。

那个本子是他在旧构建区最底层翻到的——不是卫千枢的，不是钟守玄的。封面上没有名字，只有一个日期——七年前。里面记的不是代码。是问号。几十条问号——每一条都是一个人对着玄枢的 CMake 构建树发问的记录。"为什么这里的 include 路径要用变量？——变量在哪定义的？" "这个条件判断——在什么平台上为真？" "此处的目标依赖是否还在使用？"——每条问号旁边有一个日期和一个名字的首字母。有些问号旁边被人用红笔写了回答。有些没有人回答。

"这个本子——是一个前辈的。他在试图追踪 CMake 隐式依赖（`implicit dependency`）的时候疯了。"

"不是疯了。"纪承钧接过那个本子。"是发现——你追踪的每一个变量——都有可能——在某一个你从未见过的 .cmake 文件里——被悄悄地改了。"

他把本子翻到最后一页。那一页只有一行字。字迹比前面都深——像是写的人在最后一刻决定放弃描述，只写结论：

"在玄枢追 CMake 变量——就像在旧河里捞一条你没有线索引的鱼。你永远不知道——你搜不到的变量——不在源码里。在环境里。——佚名"

· · ·

那天深夜，陆踏痕发现了那个幽灵变量。

他花了三个时辰——从那个"不应该出现的重复符号"开始，一步一步往上游追溯。先是链接器的详细日志（`verbose linker log`）——找出两个符号的真正来源。然后是两个符号对应的编译单元——发现它们都应该被一个条件编译排除——但条件编译没有生效。然后是条件编译的判断变量——在那个 CMakeLists.txt 中是一个 `if(DEFINED LEGACY_COMPAT)`——但 `LEGACY_COMPAT` 在整个源码库里搜不到定义。

不在代码里。不在 CMake 文件里。不在任何 .cmake 模块里。

"那它在哪？"

陆踏痕回到旧构建区。翻开他之前收集的所有旧构建日志。在其中一台最老的旧构建机器的日志里——那台机器的启动脚本（`shell profile`）的第 47 行——有一行：

`export LEGACY_COMPAT=1  # 不要动这个值——不知道为什么但是动了会坏。——然后是一年前的日期`

那行注释是一年前加的。但 `LEGACY_COMPAT=1` 这个值——可能已经存在了更久。不是被显式加的。可能是在某一个已经不可考的凌晨，某一个人为了临时解决一个环境差异，在启动脚本里加了这一行 export（`导出环境变量`）。然后所有机器从这台机器克隆了配置。然后这个环境变量——通过克隆——传播到了玄枢的每一台机器上。然后——几十几年后——变成了构建系统里一个"刚好存在"的前提——没有人定义它——没有人知道它为什么是 1——但它必须是 1。因为如果它不是 1——条件编译会走另一条路——那条路——在很久以前——可能可以编译——但现在——已经不能了。

"这不是构建系统的 bug。"陆踏痕说。"这是文明在特定时间、特定机器上——做的一个特定决定——通过克隆——变成了永久的前提——然后那个决定的人——已经不在了。——留下了一个在启动脚本第 47 行的幽灵——维持着整个构建系统的正确分支——而没有人知道——他现在是不是还在。是不是记得——那个凌晨——他打了这行 export。"

· · ·

沈照痕是在第二天上午看到这个发现的。他正在整理观测日志，被纪承钧叫来看那个幽灵变量。他看了很久。然后说了六个字。

"工具升级了。方式没有。"

纪承钧看着他。

"CMake——是一个现代化的构建系统。它支持模块化、支持条件编译、支持变量作用域——如果你从一开始就用 CMake 的方式——'谁需要这个变量，谁定义它'——那这个变量——会定义在离它的使用最近的地方。但玄枢——不是一开始就用 CMake 的。玄枢最开始——是 shell 脚本。后来——是 Makefile。再后来——才是 CMake。每一次工具升级——都只是把旧的用法翻译成新的语法——没有重新设计。所以玄枢的 CMake——不是 CMake。是一个穿着 CMake 外衣的——Makefile 的——shell 脚本的——凌晨 export 的——活化石。"

"所以改一行 include——会炸。"

"会炸。因为那一行 include——不是一行。是十几年CMake 翻译链上的一个结。你解开它——整条链松了。那些你不知道的隐式依赖——在链上的其他地方——断了。你只看到你解的那一结。但整个网络——在动。"

纪承钧看着石镜上那串编译错误。不修了。不是放弃。是承认——修一行 include——需要的不是一行修改。是理解整个网络的每一个结。而那个网络——在任何人脑子里——都是不完整的。不是一个人能完成的工作。

他拿起笔——在玄枢依赖图上——在构建系统的那一区——标注了一行：

"CMake 地狱——发现：构建系统不是设计的，是沉积的。每一层工具升级都是翻译而非重构。隐式变量通过环境继承传播——源头不可考。变更前提：需要完整的构建变量追踪。目前不可行。——前提：以上分析基于一次失败的 include 修改。可能还有其他隐式依赖未被触发。——后来者——如果你试图修改 CMakeLists.txt——先在启动脚本第 47 行——找幽灵。"
