# 明契卷 · 第63章 · unsafe 的契约

青炉需要调用一个 C 库来做特殊格式的解析——解析北岭设备集群发来的旧协议帧。这不是 Rust 能直接做的事——C 库是几十年前写的，接口是裸指针和手工内存管理。这是 FFI（Foreign Function Interface）——跨过 Rust 编译器保护边界——必须用 `unsafe`。

Rust 的 `unsafe` 不是"关闭编译器检查"——是"我在此处自负其责"。`unsafe` 块内的代码仍然受 Rust 的大部分安全检查约束——但编译器允许你在里面做四件安全 Rust 不能做的事：解引用裸指针、调用 unsafe 函数、修改可变静态变量、实现 unsafe trait。编译器不会替你验证这些操作的安全性——但它信任你在 unsafe 块外的承诺。

沈见微在 unsafe 块旁边写了安全论证（safety comment）——不是随口说"这是安全的"，是一份有逻辑推导的文档。他用 `/// # Safety` 文档注释格式——这是 Rust 社区约定——每一段 unsafe 代码的文档必须包含 Safety 段落。

"`/// # Safety`——调用者必须保证传入的指针 `ptr` 是非空的、正确对齐的、指向至少 `len` 字节的有效内存。此函数不接管指针的所有权——调用者负责在函数返回后释放内存。"

"C 库的生命周期——谁分配内存——C 侧通过 `malloc` 分配，Rust 侧通过 `libc::free` 释放——在 `Drop` 实现中调用——确保在 Rust 侧的所有权结束时内存被释放。参数类型——C 侧 `const uint8_t*` 对应 Rust 侧 `*const u8`——已验证在 x86_64 和 aarch64 上字节布局一致。并发安全性——该 C 函数在源码中声明为可重入（reentrant）——不访问全局状态——可以跨线程调用。失败模式——如果 C 库返回 null——Rust 侧转换为 `Option` 并返回 `None`——调用方必须处理 None 情况。"

"unsafe 不是禁区——是签字画押。你越过编译器保护边界——必须自己留下承诺和论证。不是'我认为它安全'——是'以下是基于什么验证它是安全的——在这个前提下——此论证成立。后来者——如果前提变了——例如 C 库升级了、目标平台变了、并发模式变了——请重新论证。——前提可能不成立。"
