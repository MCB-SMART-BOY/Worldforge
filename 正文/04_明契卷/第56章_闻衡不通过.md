# 明契卷 · 第56章 · 闻衡不通过

一个 PR 被闻衡打回——不是因为代码错了，是因为没写清。

"你的代码是好的——但你的描述——'修了一个 bug'——我不接受。修了什么 bug？谁报告的？在什么场景下出现？为什么之前的测试没抓到？修了之后——怎么确保这个 bug 不会再出现？我需要的不是'你修了'——是'后来者读你的 PR 知道这个 bug 的完整故事'。"

闻衡不是在找 bug——他在找"没写清楚的地方"。代码的 bug 编译器能找到——但文档的 bug 只有人能找。而文档的 bug 在生产环境中不会让代码报错——只有凌晨接传讯牌的人能找到。"可能你写的修复非常正确——但如果后来者不知道这个 bug 曾经存在过、什么时候被修了、为什么被修、在什么条件下可能再次出现——他们会在两年后重新引入同一个 bug，或者错误的修改被再次触发。你的 fix 不应该只是一个 diff——它应该是一个故事，告诉后来者：这里曾经坏过，这是它坏的原因，这是修复的逻辑，这是防止再次坏的测试。"
