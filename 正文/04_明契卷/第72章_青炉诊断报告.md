# 明契卷 · 第72章 · 青炉诊断报告

沈见微用 `cargo-audit` 和静态分析工具对青炉的对外接口做了一次全量审计。每一个对外暴露的 pub 函数都被检查——调用统计来自青炉侧的数据：哪些接口在最近三十天内被外部 crate 调用、调用多少次、在什么版本上。工具自动标注了调用次数为零的接口——标记为"可安全废弃"。

他生成了一份诊断报告 v0.3.1。报告的格式是他自己定的——每个标注了接口名称、cargo-audit 的发现、青炉侧调用统计、风险等级、推荐替代方案（如果有的话）。扉页写了："以下分析基于青炉侧可见的依赖关系图。未知依赖（unknown dependencies）不在检查范围内。——请在使用此报告的任何建议前——在你那边——确认你的依赖关系。——沈见微。——前提：本报告是工具输出，不是权威判断。工具——可能错。语境——可能不同。"

"报告本身是正确的——基于青炉侧的调用统计。"闻衡看了报告——审契者的尺扫过每一个标注。"这些接口——在 Rust 生态中——确实没有外部 crate 在调用它们。但 Rust 的依赖关系是编译期确定的——Cargo.toml 里写的才是依赖。在玄枢——C++ 的世界——依赖不在任何声明文件里——在 Makefile 注释里——在 shell 脚本的 `curl` 命令里——在凌晨三点的 hotfix 里。我不知道这些——我的工具也不知道。我不知道的——不在报告里——但它们在玄枢——在运行。"

他把报告发了出去。发给了玄枢、息壤、驿河——所有可能依赖青炉的世界。报告做了所有对的事——正确的工具、正确的分析、正确的免责声明。每一个标注都有依据，每一个风险等级都有计算，扉页的声明写得诚恳——"工具可能错——语境可能不同。"但它的正确有一个边界——在边界之外的世界上它可能炸。这个边界——不在任何工具的检查范围内——不在他见过的任何工程方法论的覆盖范围内。

这份报告在驭器卷被纪承钧收到。卷八那一夜，玄枢因为删掉了 `legacy-report-gateway` 而断火——就是这个报告中的"可安全废弃"接口——青炉侧——调用为零——三十六个月。玄枢侧——调用为零——三年。但北岭的备份服务器在每夜丑时通过一条 Unix domain socket 静默调用它——那条 socket 不在任何注册表、不在任何网络采集点——在 Makefile 的注释里——在六年前一个离职者的 shell 脚本中。

此刻沈见微还不知道。报告刚发出去——和每一份"对的事"一样——在不知道的语境里，正在路上。

程知序路过记录板时扫了一眼报告的扉页。他是青炉的第一个外部使用者——在凌晨翻过源码的人。"你的免责声明——写得很好。但读的人——在凌晨——面对你的报告——不知道'未知依赖'意味着什么。他不知道你的'未知'有多大。你也不知道。——这不是你写得不够好——是'未知'不能被写下来。只能被炸出来。"
