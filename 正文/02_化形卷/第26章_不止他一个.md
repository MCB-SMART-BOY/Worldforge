# 化形卷 · 第26章 · 不止他一个

旧石镜里的三段代码，周栖野开始逐段深入研究。不是研究它们的代码质量——是研究它们为什么停下来。

第一段，shell 脚本。作者不知道是谁，比林过川早，可能比叶藏拙还早。脚本逻辑是清楚的：遍历目录，提取每个脚本的 import，检查包是否存在。但在"检查包是否存在"这个函数里，它直接调用了系统上的 `pip` 命令。而 `pip` 的行为在不同 Python 版本、不同操作系统、甚至同一个系统不同虚拟环境之间都不同。作者发现这个函数在另一台机器上跑不动——不是逻辑问题，是环境依赖问题。脚本自己依赖了它试图检查的东西。最后一行注释："TODO: handle the case when pip is not installed."然后停了。

第二段，林过川的 Python 工具。几乎完成了——提取 import、生成 requirements.txt、验证依赖。但他写了 README："这个工具本身不能被自动化交接。放弃。"不是代码没写完，是代码写完了他发现了更深的矛盾。交接工具自己也需要交接。他这次可以提取所有 import，但如果 import 的推断规则在下一版 Python 中变了，他的工具会静默产生错误的依赖列表。后来者不知道规则变了——以为工具是对的，照着结果做——直到某个脚本在丑时报错。

第三段，C 语言的命令行工具。作者更早——可能比息壤还早。代码注释很详细，但关键函数里有一个大洞——被删了。"此函数依赖内部 API。该 API 已废弃。无法完成。"不是写不完，是依赖的东西不在了。

三个人，三种语言，同一个目标。都失败了。失败的原因结构相同：工具本身依赖了某种前提，而那种前提在未来的世界里不再成立。不是哪个人的错——是任何一个人都无法独立解决的循环。交接工具需要能跨时间自我维持——这在没有制度的时代是不可能的。

"交接工具自己也需要被交接。工具本身依赖的前提会变——pip 的行为会变，Python 的 import 规则会变，内部 API 会废弃。每一代人写的工具，只在自己那一代的前提成立时有效。到了下一代，前提变了，工具就无效了。这就像给一个文件打补丁——补丁本身会过时。需要的不是更好的补丁，是一套制度——让每一代人在工具过时的时候能发现它过时了，然后更新它，同时标注更新的前提。前提声明。留白。接手的你也写。"

三个人没有制度。所以他们只能失败。
