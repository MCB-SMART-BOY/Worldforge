# 化形卷 · 第22章 · 不止一个 final

周栖野按时间戳重新排列了林过川所有标记为 `final` 的脚本。七个。不是七个不同功能的最终版——是同一段逻辑，写了七次。

最早的比林过川离开早两年，最晚的是离开前一周。他把七个文件全部打开，并排放在屏幕上，逐行对比。不是修复 bug——是需求变更。每次 `final` 之间的差异，不是一个 bug 被修了两次，而是一个需求被改了又改。结算格式从 CSV 变成 JSON，又从 JSON 变回 CSV——因为外部调用方换了又换。信号码映射表从十六位改到八位，又从八位改回十六位——因为协阵那边的协议版本在来回迁移。不是他在迭代——是他在被不同的外部需求推着走，每次推到终点时他以为自己到了，然后新的需求从另一个方向把他推回去。

没有 Git，没有版本控制。每个版本是独立的文件，文件名是他的版本号。`final` 不是一个状态，是一个愿望。每次他说"这次是最后一次"时，他不是在撒谎——他是真心相信。但愿望无法被兑现，因为在"先让它跑"的文化里，需求是流动的，而文档是需要成本的。林过川选择了把有限的成本投入在代码上，而不是文件名上。后果是后人面对七个 `final`，不知道哪个是真的 final，或者全都是，或者全都不是。

同一段逻辑在七个文件中有五种不同的实现方式。每一次需求变更拉着它改，但旧版本没有被保留——删了，覆盖了，或者以一个无可辨认的文件名藏在某个角落。不是林过川不认真——他每次 `final` 的时候都是认真的。问题是 `final` 在一个没有版本管理的世界里，真正的意思是"此刻不想再改了"，不是"这个版本是对的"。

叶藏拙在旁边说了一段话，不是批评，是理解。

"他每次命名 `final` 都是真诚的。他只是没有工具——没有 Git，没有版本控制，没有石录。所以他把状态写在了文件名上。文件名是他的 commit message。但他的 commit message 只有两个字。没有为什么，没有前提，没有他当时在什么条件下做了这个决定。后来者面对七个 `final`，不是在做选择——是在考古。"

周栖野在七个 `final` 后面的空白处写了他的第一条考古标记："林过川。七年，七个 `final`，五种实现。同一段逻辑。没有版本管理，没有 commit message。从文件名推测——每次新需求打破旧前提。此记录供后来者参考。——周栖野。"

不是解决了问题。是让问题被看见了。看见本身，是对沼泽的第一铲。
