# 化形卷 · 第52章 · 弃用声明

第二条桥的弃用声明（deprecation notice）发出时，群聊炸了。

`xirang-excel-adapter`——十一个使用者，比第一条多。弃用声明贴在公共记录板上：版本号、退场日期、迁移路径、联系人。模板来自顾迁舟的桥账，但这次的使用者群体更大，反应也更激烈。

"你在给我的月度结算加 deadline。"有人回复。"我的脚本全靠这个——你告诉我三个月后它不能用了？"

顾迁舟的回应没有被群聊的激烈带偏。"不是它不好——是它已经完成了使命。它是一座桥。桥的使命是让人通过。所有人都通过了，桥就成了障碍物。你是通过了的人——你现在站在对岸，回头看着桥。你觉得它一直在那里——但如果你一直在对岸，不需要回来，桥就可以拆了。如果你还在桥上——告诉我。我帮你下来。"

弃用声明不是惩罚——是尊重。在息壤的历史上，"这个接口变了"从来没有被提前通知过。使用者在某个早上打开脚本，发现它报错了，然后花半天追查，发现是上游改了接口，没有告诉任何人。弃用声明把"突然坏了"变成了"计划中的变更"——这两者之间的区别，就是后来者能不能安全地走在路上的区别。

弃用声明的三个层级被制度化。代码级——`warnings.warn("deprecated", DeprecationWarning)`，运行时提醒。文档级——在 CHANGELOG 和 README 中标注版本号和退场日期。沟通级——给每个已知使用者发通知："你依赖的东西即将变更。这是变更方式。这是联系人。"

弃用声明让人知道什么时候需要迁移，让人可以做计划。之前最可怕的不是接口变了——是某天早上打开脚本发现它不跑了，没人提前告诉任何人。弃用声明把突然坏了变成有计划的变更。不需要欢迎变更——但至少需要知道变更什么时候来。
