# 化形卷 · 第55章 · 收到 runbook

桥拆除进行到一半，顾迁舟收到一份来自驭器卷的包裹。纪承钧写的迁移 runbook——"为息壤桥退场准备的迁移流程，共十七步，基于驭器卷渡桥司的桥治理标准。供参考。"

周栖野打开。前两步是术语翻译——"桥 = adapter，退场 = sunset。"第三步——"确认所有下游依赖方已全部迁移。"这一行下面没有验证步骤，没有脚本，没有命令，没有工具。因为在玄枢，每座桥都有渡桥司的依赖注册表，所有依赖方在搭建时就声明了自己依赖什么。确认依赖方迁移就是查注册表——一行命令的事。在息壤，依赖注册表根本不存在。

季晚禾尝试按 runbook 执行。到第三步——"确认所有下游依赖方已全部迁移。如果无法确认，标记为'待确认'，继续下一步。"她标记了"待确认"。第四步也需要依赖注册表——又标记了"待确认"。第七步需要构建系统验证——息壤没有统一的构建系统。第十一步需要渡桥司退场审批——息壤没有渡桥司。第十五步——她在那行旁边写："我不知道该怎么做。没有标准。"十一个"待确认"。整个 runbook 在她的世界里无法执行。

每一行都是善意的，每一行都写得很清楚——但每一行都依赖了息壤不存在的系统。不是写错了，是前提不同。玄枢的桥治理建立在依赖注册表、构建系统、渡桥司这三个基础设施上。息壤的桥治理建立在 import 链、叶藏拙的账本、顾迁舟一个人的桥账上。

"这不是谁的错。但有一个很重要的认知——你在你世界里的'理所当然'，在另一个世界里可能是不存在的基础设施。你的 runbook 在玄枢是最有效的流程——在息壤，它是一份'我们缺了什么'的清单。那份清单的价值比 runbook 本身更大。它告诉我们：我们需要依赖注册表。我们需要统一的构建验证。我们需要正式的桥治理机构。你的 runbook 用失败的方式帮我们画了一张地图。"

他写了一封回信。不是抱怨——是解释每一步的前提在息壤是否成立。"这是最重要的一课——你的方法建立在什么前提之上？那些前提——在别人的世界里成立吗？如果你跨过了道的边界去发一份 runbook，请带上前提清单。不是为了保护你——是为了让收到的人能判断。我不知道你的世界的形状。你不告诉我你脚下的地基长什么样，我就不知道你的路能不能接上我的路。"
