# 化形卷 · 第34章 · poetry / uv

周栖野的 `requirements.txt` 里有 `pandas>=1.3`。宋既明问了一个问题："你装的是 pandas 的哪个确切版本？"

"最新的。"

"明天，最新的可能就变了。明天后来者装的 pandas 不是你今天用的 pandas。"

`requirements.txt` 的 `>=` 语法是承诺的漏洞。它说"我需要至少 1.3 版本"，但它不承诺"我用的是 1.5.3"。今天和明天装的 pandas 可能不一样。大多数时候不一样没关系——直到有一天 pandas 的某个小版本改了一个函数的行为，而那个行为恰好在 `field_mapper.py` 里被依赖。

更深的漏洞在依赖的依赖。pandas 依赖 numpy。numpy 依赖 libc、libgfortran、libopenblas——这些是系统级库，不同于 Python 包，它们在 macOS 上的行为和 Linux 上的行为不同。`pip install pandas` 成功，但在 macOS 上装的 numpy 和在 Linux 上装的 numpy 可能是用完全不同的编译方式生成的。它们的行为可能在边界条件上有差异。

lock file 的哲学不是"锁定"——是"诚实"。`uv lock` 生成一个文件，精确记录每一个依赖包的版本哈希（hash），包括间接依赖。总共有八十多个包——远比 `requirements.txt` 里的十九个多。那些多出来的六十一个包，周栖野从来没有 `import` 过，但它们在他的代码运行时被加载了。它们一直在——他从来没有声明过。

"conda 试图回答'非 Python 依赖怎么办'。pip 试图回答'怎么装'。poetry 试图回答'怎么锁'。uv 试图回答'怎么快且怎么锁对'。它们都不是终极答案，但 uv 是目前最诚实的——它让依赖的依赖不再是隐形的。后来者不需要知道 pip 的历史，他们只需要知道 `uv.lock` 里的哈希值是对的。代码和需求的真正距离在被诚实声明的那一刻变得可见。"

lock file 不只是锁定了版本——它是依赖链的完整地图。后来者拿到这份地图，知道每一个字节从哪里来。地图不能阻止前提改变，但地图让改变发生的时候你能追索——是哪一环变了，影响从哪开始，往哪里传播。依赖的依赖也是依赖。诚实不是完美——是知道自己在依赖什么。
