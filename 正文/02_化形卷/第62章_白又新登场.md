# 化形卷 · 第62章 · 白又新登场

周栖野把第一份火种——`auto_field_mapper`——的 MRC 和测试交给白又新。

"三天后告诉我结果。不要问任何人。你只用自己的环境、这份 MRC、和这份测试。如果走不通，不是你的问题——是 MRC 不够好，或者火种不够格。你的失败是 MRC 的失败。"

白又新的角色不是学生，是验证者。继承者测试（successor test）——用完全独立的人验证知识的可传递性。不需要背景知识，不需要口传，不需要"前提在作者脑子里"——只需要入口和可执行的步骤。他是息壤的"第一个人"——如果他走不通，后来者更走不通。

他消失了三天。没有人知道他去了哪里。第三天，他出现在周栖野桌前。

"跑通了。但你的 MRC 第三步少了一个前提。你的 `uv sync` 需要 Python 3.11 以上。我是 3.9——第一步就失败了。我自己装了 3.11，然后跑通了。但如果你问的是'只按 MRC 能不能跑'——不能。在第三步你漏了 Python 版本。"

周栖野在 MRC 的第三步加了 `python --version` 检查。然后看着白又新："你花了多长时间发现是 Python 版本的问题？"

"两个时辰。"

"你不需要花这两个时辰。我应该检查的。"

"我知道。但现在 MRC 对了——后来者不需要花这两个时辰了。这就是你让我做的，对吗？"

继承者完成了第一次独立走通。但过程暴露了 MRC 的一个缺陷——Python 版本的前提被漏了。这不是白又新的失败——是入口的胜利。他发现了缺陷并反馈了回来。继承的第一次完整循环：建立、测试、发现缺陷、修正、更完整。入口被验证并修复了——后来者不会再卡在同一个地方。继承者测试的价值不在证明 MRC 是对的，在发现 MRC 在哪里漏了一行前提。
