# 化形卷 · 第28章 · 同一行原因

周栖野把三段代码的最后一行并排放在石镜上。不是比较代码——是比较它们在停下之前写的最后一个注释。旧石镜的shell脚本。林过川的Python工具。C命令行的作者。

同一句话，以三种不同的方式，跨越了漫长的时间。

C工具的最后一行："此函数依赖内部API。该API已废弃。无法完成。后来者如果需要此功能——应该自己重新实现。"

Shell脚本的最后一行："TODO: handle the case when pip is not installed. 如果后来者试图完成此脚本——请注意——pip的行为在不同环境中不同。我无法预测你的环境。你自己判断。"

林过川的README最后一行："这个工具本身不能被自动化交接。放弃。后来者应该自己重新判断需求。"

同一句话——用不同的措辞，在不同的时代，在不同的语言里——被三个从未见过彼此的人独立写出。

**后来者应该自己判断。**

· · ·

不是巧合。不是同一个师门传承。

shell脚本的作者面对的是pip行为的不确定性。他知道依赖检查脚本本身的依赖会变——pip的版本会变，包名会变，甚至pip本身可能被更好的工具替代。他怎么写一个永不过期的交接工具？他写不了。所以他在TODO旁边留了警告："你自己判断。"

林过川面对的是交接工具本身不能被交接的悖论。他写了自动扫描依赖的工具。代码几乎完整。测试也写了。然后他发现——这个工具依赖的Python版本在下一代息壤已经不兼容。交接工具本身需要交接。而他没有制度来声明"在我的前提下，这是对的"。所以他写了一句"放弃"。不是技术失败。是发现了一个他一个人无法解决的递归困境。

C工具的作者面对的是内部API被废弃。他依赖了一个在组织内部被弃用的接口。那个接口没有做弃用声明（`deprecation notice`）。有一天就默默地没了。代码还在那里——关键函数变成了一个洞。他留下的注释是最完整的——他解释了为什么停下、后来者应该怎么做——但他没办法写出那个缺失的函数。

三个人在不同的时代停下。但停下的理由完全相同：他们信不过自己写的东西在下一代人的手上仍然成立。不是做不到——是不敢传。因为前提会变。而他们没有制度来声明"在我的前提下，这是对的"。所以只能选择沉默。

· · ·

周栖野把这三段最后一行放在一起之后，忽然想起了什么。他翻开自己的记录本——在某一页的边缘标注，是从驭器卷传来的。纪承钧在玄枢最底层的断史库里发现的那一行残码。

`[RESERVED FOR INHERITANCE COVENANT — PENDING RATIFICATION]`

同一个困境。在不同的世界。用不同的语言。玄枢的创始者留下PENDING，不敢写完。化形的三代人各自写到关键处停下，不敢传。驿河的远古告警发了一万多次，没有人回应。同一种恐惧："我传下去的东西，会不会在后来者的世界里变成墙？"

不是同一个人教出来的。是同一种困境在不同世界里被不同的人独立发现。文明级的免疫反应。

"他们每个人都是对的。"叶藏拙说，"他们怕写下来的东西变成墙——所以选择沉默。但沉默也是墙。只是墙的形状是空的。"

· · ·

周栖野在林过川的README旁边，加了一行标注。

"林过川。你的工具本身不能被自动化交接——是因为交接需要的不是工具。是制度。我读到了你的README。在玄枢，有人发现了同样的困境——他们用了不同的方法来回应。他们建了前提声明制度。他们建了公共记录板。他们建了伤痕制度——不让凌晨传讯的代价被遗忘。制度让后来者不需要重新发现你的困境。你的README是第一步——但你不应该是最后一步。我不是来完成你的工具的。我是来继续你的思路——用制度，而不是代码。"

他放下笔。三段代码的最后一行仍然在石镜上并排亮着。同一句话。三个时代。三种语言。一个困境——终于被看见了。
