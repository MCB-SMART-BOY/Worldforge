# 化形卷 · 第96章 · 四项必填

傅远洲展开每一条必填项背后的故事。制度不是凭空设计的——是事故驱动的。

内存上限。两年前驿河一个服务 OOM 之后连锁杀掉了同一个节点上的七个服务。运维在凌晨四点盯着监控屏，看着服务一个一个变红。根因是一个模块没有声明峰值负载——和息壤 Ch87 一模一样的模式。事后驿河把"内存上限"写进了必填项——每块部署到驿河的模块必须标注在什么场景下、多少并发下、内存峰值是多少。

并发上限。一个 goroutine 泄漏把整个集群的连接池耗光了。不是内存问题——是并发问题。修复后把 goroutine 泄漏堵住了——但规则加了一条：并发上限必须标注。不是不能高并发——是在哪个点之后会出现竞争。

健康检查端点。一个服务在"正常运行"——所有监控全绿——但实际上所有 handler 都在返回 timeout。健康检查只检查了进程是否存活——没有检查 handler 是否在工作。事后把健康检查从"检查进程"改成了"检查功能"——必须有一个端点真实执行业务逻辑并返回结果。

优雅关闭超时。运维在凌晨三点杀服务时丢了一整天的数据——进程被 SIGTERM 后立即被 SIGKILL 了，还没来得及把内存中的数据写回磁盘。优雅关闭超时让进程在被强制杀死之前有时间保存状态和清理连接池。

"每一条必填都是一个后来者的半夜。制度不是聪明人想出来的——是被刺痛的人在伤疤上刻的字。后来者遵守制度——他们在不知不觉中避免了前人用血换来的教训。他们不需要知道这些——遵守就够了。但当他们想知道为什么的时候，每一条都有源头，源头是一个人在凌晨四点被叫醒。"
