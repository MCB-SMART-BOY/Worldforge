# 容断卷 · 第49章 · 排队论

"容量——不是感觉——是排队论（queue theory）——可以估算，也必须验证。"

柯守打开了一份分析——某项服务的平均处理时间（service time）约30毫秒，请求到达率（arrival rate）约每秒200个。按平均值估算，系统每秒要完成约6秒的工作量，也就是平均同时有6个请求在处理。

"六个并发——不是六个worker就够了。假设每个worker都能独立处理请求，单个worker的平均服务率约为每秒33.3个；六个worker合计的理论处理能力约每秒200个，利用率已经是100%，没有留给突发、长尾和调度开销的余量。若目标利用率是70%，这个简化假设下至少需要九个worker；这只是估算起点，实际容量还要由负载测试确认。"

"请求不会均匀到达——一批请求可能几乎同时涌来，比泊松到达更突发。服务时间也不是常数——有的请求只需5毫秒，有的需要300毫秒——分布（service time distribution）有长尾。平均处理时间告诉我们平均要多少并发，不能单独告诉我们尾延迟和队列会长成什么样。"

他在白板上画了一条曲线——横轴是单服务台利用率（utilization，ρ=λ/μ；λ为到达率，μ为单服务台的服务率）——纵轴是系统内平均请求数，包含正在处理和排队的请求。

"在理想M/M/1模型下，ρ=0.5时，系统内平均请求数L=ρ/(1−ρ)=1；ρ=0.8时是4；ρ=0.9时是9；ρ=0.95时是19；ρ=0.99时是99。若只算等待队列，平均值是Lq=ρ²/(1−ρ)。这些数字只描述一个服务台、泊松到达和指数服务时间等理想条件下的趋势。刚才那六个并行worker不是M/M/1；多服务台要用相应模型，或用实测来判断。CPU利用率也不等于服务台利用率。真实流量有突发、服务时间有长尾时，等待还可能比理想模型更差。"

"排队论告诉容断工程师三件事。一——容量管理要在满载之前开始；二——队列变长可能来自到达量增加，也可能来自服务时间变长，要先查瓶颈，再决定扩容或减载；三——队列不能无限长。队列耗尽后，请求会超时或被拒绝；提前按优先级给出429，比任由等待堆满更可控。"

排队论在磐的应用——不是学术——是容断的前提设计。"每项服务都要声明处理能力、服务时间分布、队列深度上限、并发worker数和目标利用率。"例如，支付服务的平均处理时间是20毫秒，99分位延迟（p99 latency）是150毫秒；队列深度50、目标利用率0.7开始背压、0.85开始减载，可以先列为候选值，但不能从M/M/1曲线直接推出。它们要结合worker数和服务时间分布，在该服务的多worker负载测试中验证。

"排队论的另一课——小请求不能无限优先。如果简单查询和复杂分析共用一个先进先出队列（FIFO），一个慢请求就可能挡住后面的快请求，这叫队头阻塞（head-of-line blocking）。可以按优先级分队列、分处理池，让核心请求有自己的处理能力，复杂分析在自己的池里慢慢做。"

"排队论——不是容断的附加课——是容断的数学基础。单服务台模型帮助我们理解接近满载时等待如何上升；多worker服务的阈值和队列上限——要结合worker数、服务时间分布和负载测试来定。可计算——可验证——可演练。容断——也需要式——也需要被量化。"
