# 共构机制、工程映射与冲突规则

## 一、共构定义

**共构**是不同道统围绕同一器、阵或门，在不同层级承担不同构筑责任的状态。

它不是语言拼盘，而是职责分工、边界协商与代价转移的总和。

---

## 二、基础共构模式

### 1. 化形—明契
- 先让念成形，再把能长久留下的部分固核
- 典型现实感：Python → Rust

### 2. 驭器—明契
- 古器在下，新界在上
- 典型现实感：C++ → Rust

### 3. 驭器—简阵
- 重核在底，多器在外，阵面必须替古器承担治理压力
- 典型现实感：native core → service platform

### 4. 化形—简阵
- 试法先行，随后进入多人协作与稳定部署
- 典型现实感：脚本工具 → 平台服务 / 工作流系统

### 5. 简阵—容断
- 大阵协作 + 不断裂活性
- 典型现实感：Go ↔ Erlang/Elixir

### 6. 通界—覆约
- 先接通边界，再在内部补约
- 典型现实感：JavaScript → TypeScript

### 7. 守序—求式
- 制度平台之中，引入更高形式表达
- 典型现实感：Java/C# 平台 ↔ Scala/F#/高形式路线

### 8. 造言—诸道
- 当既有器具不足时，直接改造造器之法
- 典型现实感：DSL、宏系统、元语言、配置语言重塑

## 三、失守、故障与韧性

### 1. 错误
错误是**仍在契约表达范围内的失守**。
它能被说清、被传递、被处理。

### 2. panic
panic 是**当前上下文已经无法继续守住其基本承诺的断裂**。

### 3. 故障
故障是四相之一或数相失守后，在真实世界中的显象。

### 4. 韧性
韧性不是第五相，而是四相协调之后，系统在局部失守时不致于立刻全局崩塌的整体品格。

### 5. 分析顺序
排障时应优先采用：

**象 → 因 → 相**

也就是：
1. 先看表象
2. 再找原因
3. 最后判断是哪一相失守

## 四、架构与拓展结构

### 1. 架构
**架构以式为骨，以契为界，以史为后果。**

### 2. workspace
**workspace 是多骨同炉、共约、共史的组织方式。**

### 3. 服务
服务是在某域中长期开放契口、等待他域来访的器。
一旦越域，默认前提就会显著减少。

### 4. 插件系统
插件系统是通过契口实现的受约束扩展。
它不是“任意开门”，而是对未来变化的克制安排。

### 5. 插件系统的主要熵蚀风险
- 契口过大，导致失式
- 契口含糊，导致背契
- 对内部细节依赖过深，导致断史
- 运行边界混乱，导致乱流

---

## 五、冲突来源

后续剧情冲突优先从下面这些源头生成：

### 1. 失式冲突
边界不清、模块侵入、架构失骨。

### 2. 乱流冲突
资源关系失控、状态难追踪、并发反噬、代价被低估。

### 3. 背契冲突
文档失真、测试不足、承诺与现实不一致。

### 4. 断史冲突
版本失信、改动不可追溯、历史厚重到无人敢动。

### 5. 黑箱化冲突
器还在跑，但越来越没人能说清。

### 6. 继承失能冲突
世界表面没坏，但后来者已经接不住。

### 7. 断桥潮冲突
过渡结构长期滞留、兼容成本被转嫁、迁移节奏无人负责。

## 七、写作规则

1. 世界观术语解释本质，现实术语负责落地。
2. 不要为了风格强行替换所有现代技术术语。
3. 新设定必须说明：
   - 它是什么
   - 它坏了会怎样
   - 它归哪一相
   - 它作用于哪一层级
   - 它把代价推给了谁
4. 每卷至少要推进三条线：
   - 一个器 / 阵 / 门的成长线
   - 一种道统的命题线
   - 一层文明病理的揭示线
