# 对象层级、机构、域与宿域

## 一、对象层级链

万构界中的构世对象，不宜混写。
后续设计剧情与工程主题时，建议严格使用以下层级。

### 正式层级链
**念 → 约 → 图 → 文 → 骨 → 器 → 阵 → 门 → 史**

### 1. 念
对某个病灶或可能性的最初意识。
对应现实中的问题意识、灵感、痛感来源。

### 2. 约
项目最早写下的誓约、边界与非目标。
对应：
- MVP 边界
- scope
- 不做什么
- 为什么做

### 3. 图
设计图景与构想轮廓。
对应：
- 架构草图
- 模块关系
- 技术路线
- 目标结构

### 4. 文
具体实现之文。
对应代码本身。

### 5. 骨
项目内部已成形的结构分支。
对应：
- crate
- module
- workspace 成员
- 子系统骨架

### 6. 器
已经能独立工作的单个造物。
对应：
- 一个库
- 一个 CLI
- 一个守护进程
- 一个服务组件

### 7. 阵
多个器与骨按照秩序协同形成的系统。
对应：
- 多 crate 系统
- 多服务系统
- 插件化体系
- 复杂架构群

### 8. 门
围绕某个器或阵，在时间中持续守护其契与史的共同体形式。
对应：
- 团队
- 维护者共同体
- 开源项目共同体
- 组织化工程群体

### 9. 史
所有前述对象进入时间秩序、留下痕迹、可被继承后的总状态。

### 使用规范
- 同一场景尽量只把一个层级写成主对象，其他层级作为环境或后果
- “层级链中的史”是对象完成演化后的状态；“四相中的史”是所有对象都必须面对的时间维度
- 若一个冲突无法判断主对象层级，多半说明叙事焦点仍然过散

## 二、观象三层

这是链接中较早出现、但仍然有用的一组观察框架。
它不替代层级链，而是帮助写作者从不同尺度观察同一问题。

### 1. 天道层
- 看四相、熵蚀、黑箱化、继承失能这类顶层法则
- 负责回答“这个世界为什么会这样坏、又为什么必须这样修”

### 2. 人间层
- 看门、机构、宿域、共同体、道统关系
- 负责回答“谁在守、谁在争、谁在承担现实代价”

### 3. 炉火层
- 看一个具体项目如何从念到史，如何在章节里一步步起炉、成器、成阵
- 负责回答“这一卷这一章到底在推进什么对象”

### 使用原则
- 写世界观大判断时先看天道层
- 写组织与人物冲突时先看人间层
- 写卷纲、章纲与主项目时先看炉火层

## 三、核心机构

这些机构更接近“文明功能位”，不必理解成世界上只有一座建筑。
一门可自设其司，多门也可共认其制。

### 1. 万库阁
公共器藏与索引秩序之所。

#### 对应现实
- 包管理生态
- registry
- crates.io / npm / Maven / PyPI 等公共库藏

#### 它负责
- 器物来源
- 版本谱系
- 生态流通
- 公共信任

### 2. 石录
项目共同承认的历史主脉。

#### 对应现实
- Git 仓库
- commit 历史
- branch / merge 轨迹
- tag 记录

### 3. 问心台
并入主脉前的一切守契之关。

#### 对应现实
- review
- test
- CI
- lint
- 格式检查
- 规则校验

### 4. 观象司
器入世后的观测、理解、归因与诊断机构。

#### 内部三分
- **迹**：日志、报错、崩溃痕迹
- **脉**：链路、上下文、tracing
- **势**：趋势、负载、延迟、吞吐、指标

### 5. 渡桥司
专司兼容、迁移、适配与过渡秩序的机构。
当旧约未能立刻废除、新约又必须到来时，渡桥司负责决定桥怎么搭、何时拆。

### 6. 古器院
专门看守重器、旧核、古接口与口传秘义的机构。
它既是文明财富，也是黑箱化最容易沉积之所。

### 7. 共构坊
处理不同道统围绕同一器、阵、门协作建造的中枢场所。
多语言工程、跨域集成、适配层与共同治理都常在此发生。

### 8. 断史库
保存失败迁移、废弃桥梁、旧版说明与事故复盘的场所。
它不是垃圾堆，而是文明避免重复犯错的冷史之地。

### 9. 诸宿议会
跨宿域协调大型系统边界、公共契约与迁移节奏的高层机制。
它不写代码，但常决定谁必须向谁让渡成本。

## 四、契与史的接口概念

### 1. 言契
被说清的承诺。
对应文档、README、API 说明、设计文档、迁移说明。

### 2. 证契
被证明的承诺。
对应测试、示例、CI、运行检查、契约验证。

### 3. 审契
对契是否成立所作的人类裁定过程。
对应 review、triage、设计审查、发布前核验。

### 4. 内史
项目内部如何变化。
对应 commit、branch、merge、变更理由与过程说明。

### 5. 外史
项目向外界如何立名与被承认。
对应 version、release、changelog、兼容策略、弃用说明、迁移路径。

### 6. 契口
系统为外界接入而主动开放的、有边界的接入面。
对应插件接口、服务 API、hook、配置契约、扩展点。

### 7. 渡桥
当旧约未能立刻废除、新约又必须到来时，为平稳过渡而搭建的临时结构。
对应 compatibility layer、adapter、shim、deprecated transitional API。

### 8. 门规
共同体为守住边界、节制负担、保护守门者而立下的规则。
对应贡献指南、支持策略、提交流程、评审规范、发布政策、scope 约束。

## 五、域

### 定义
**域**是能共享某些默认前提、能以较低成本互相成立假设的运行边界。

### 对应现实
- 进程内
- 单机
- 局域服务群
- 远程服务
- 多地域网络
- 设备侧与云侧

### 越域意味着
- 信息不全
- 时延存在
- 状态不完全可见
- 局部失守常态化
- 契口与观象的重要性上升

### 越域四代价
- 解释成本上升
- 重试与补偿成本上升
- 默认前提减少
- 观测需求暴涨

## 六、宿域

### 定义
**宿域**是某一道或某几道长期寄居、繁衍、扩展、共同演化的大平台世界。

域偏运行期，宿域偏文明生态。

### 五属性
1. 载体
2. 史积
3. 库势
4. 制力
5. 门气

### 1. 原生重器宿域
- 直抵底层
- 古器极多
- 黑箱厚重
- 对个人能力要求极高

### 2. 守制平台宿域
- 共同体大
- 制度强
- 平台化明显
- 长寿命工业秩序集中

### 3. 化形试法宿域
- 试法快
- 原型多
- 生长快
- 易成脚本林与试法遗迹

### 4. 通界前沿宿域
- 前沿变化极快
- 人器边界压力强
- 生态风暴多
- 工程秩序追着变化跑

### 5. 容断并行宿域
- 越域常态
- 局部失守常态
- 活性优先
- 继续活比局部完美更重要

### 6. 协阵扩域宿域
- 多器成阵是常态
- 团队理解成本极其重要
- 部署频、变更快、协作压力大
- 最容易把复杂度偷偷推给未来

### 7. 求式高地宿域
- 思想密度高
- 形式力量强
- 门槛高
- 易成高峰孤岭

---

## 七、道统与宿域关系速览

- 驭器之道根植于原生重器宿域
- 守序之道根植于守制平台宿域
- 化形之道根植于化形试法宿域
- 通界之道与覆约支根植于通界前沿宿域
- 容断之道根植于容断并行宿域
- 简阵之道根植于协阵扩域宿域
- 求式之道常驻求式高地宿域
- 造言之道跨寄于求式高地、化形试法与通界前沿之间
- 明契之道是跨宿返照之道，常在多宿交界、黑箱最厚处起炉

---

## 八、宿域旁例与未来支脉留位

这一节不用于重写正式道统，只用于给未来扩卷留稳定接口。

### 1. 守制平台宿域的旁例
- Java 是守序之道的主显
- Kotlin 更像守序宿域内部的现代化更新支
- Scala、Clojure 虽与 Java 同宿，但道心并不等同于守序

### 2. .NET 侧的旁例
- C# 更接近守序平台的工业主脉
- F# 与 C# 同宿，但血脉更近求式高地
- 因此同宿不等于同道，这一侧最适合用来写平台制力

### 3. 容断并行宿域的旁例
- Erlang 是容断之道的古主脉
- Elixir 是其后生文火，更重表达与社区可近性
- 二者可共卷，不宜过早拆成两本

### 4. 通界前沿宿域的旁例
- JavaScript 先接通变化边界
- TypeScript 在其上补写更强之约
- 因此 TypeScript 更适合作为覆约支，而不是脱离通界单独立卷

### 5. 原生与平台交界的旁例
- Swift 兼受原生重器宿域与平台制力影响
- 若未来要写它，重点应落在宿域交界的代价，而不是简单并入明契或守序

### 6. 统计与算学旁支留位
- R 更适合留作未来的“学图卷”或“算学卷”旁支
- 这一方向偏统计、图形、学术传统与数据文明
- 它不是当前四大主卷的优先对象，但可以保留接口
