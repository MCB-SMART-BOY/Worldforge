# 驭器卷 · 第99章 · 阶梯之上

交钥验证推进到这时，陆踏痕独立处理了一次复现的边界故障。此前也有过类似场景——北岭调用延迟升高，deep-bridge 协议解码层异常。但这次更复杂：异常不是间歇的，是持续的，而且观测面板上的指标互相矛盾——内存正常，文件描述符正常，但延迟在涨，同时错误率也在涨，但错误不是网络超时，是协议解码返回了格式错误。

这种模式，钟守玄的守门者 runbook 里没有。不是钟守玄没遇到过——是他遇到过太多次，但每次的原因都不一样，他没办法总结成一条规则。他在 runbook 里写了："此类型故障需要同时观察三个指标并依赖经验判断。无法写成规则。来问我，趁我还在。"

陆踏痕没有去找钟守玄。不是因为不愿意，是因为凌晨三点，钟守玄在睡觉——他第一次敢让钟守玄在事故期间继续睡觉。他自己打开观测面板，从迹开始追，定位到协议解码层的一个条件分支。异常集中在超过512字节、含高位字节的输入上。最近的系统升级是时间线索，却不是根因：源码显示旧分支把可能为负的 `char` 直接传给 `std::tolower`，违反了它的参数约束，行为未定义。新旧镜像回放同一输入后，问题稳定复现；修正字符转换并复测后，格式错误消失。不是 glibc 的 bug，也不能由一次升级的先后关系推出因果。

他把发现写进了 runbook 空白页。不是简单地写"修复了系统升级后出现的解码异常"。他写了四段。

第一段："故障现象——延迟和错误率同时升高，内存和文件描述符正常。在钟师的守门者 runbook 中属于'无法写成规则'类型。"

第二段："追查路径——迹→定位到协议解码层→回溯最近变更→复现一条超过512字节、含高位字节的信号码→源码检查发现旧分支把可能为负的 `char` 直接传给 `std::tolower`。这超出函数允许的参数范围，属于未定义行为；新构建环境让问题显现，但不能据此说是 glibc 的缺陷。用旧、新镜像回放同一输入，并检查字符分类代码，确认触发条件。"

第三段："判断——runbook 中的'三个指标观察法'适用，但还要问：'最近什么变了？'延迟和错误率同时升高、资源指标正常时，先比对发布、配置、输入格式和环境变更，再回到代码和复现验证。变更时间与故障相邻只能提供线索；符号表也不能证明行为变化。"

第四段："建议——在钟师的守门者 runbook 中'无法写成规则'条目下加一条：'若近期有环境或版本变更，记录变更与故障的时间关系；用代表性输入复现，检查相关源码和配置。只有确认接口或符号版本不匹配时，才用符号版本工具辅助判断。参见 ABI 兼容性评估记录。'——陆踏痕。前提：此补充基于一次高位字节触发的字符分类缺陷；其他变更需要各自的证据链。"

写完，他把笔放下。然后去泡了一杯茶。

钟守玄早上读到这段补充时，看了很久。不是看技术内容——是看那个动作本身。陆踏痕没有完全按照 runbook 做，因为 runbook 中的一步在他面对的具体情境下不成立。他自己判断了，然后修改了 runbook。不是"照着 runbook 做"——是"理解 runbook 为什么那样写，然后判断自己的情境是否适用"。这是继承的最高形态——不是复制，是理解后的再创造。

"这就是我一直在等的。"钟守玄把 runbook 合上。"不是有人能照着我做——是有人能在我做的基础上，做出我没想到的判断，然后写下来，让下一个后来者继续。我花了三十几年，从'不写'走到'写'。他花了不到一年，从'照着写'走到'自己判断，然后补充写'。比我快。不是因为比我聪明——是因为他站在阶梯上。阶梯让他不需要重复我三十年的'不写'，直接就能走到我花了三十年才走到的位置，然后继续往前走。阶梯的意义不是让人更快到达顶点——是让人从更高的起点开始走。每一代人都从前一代人停下的地方起步，而不是从零。"

陆踏痕的"后来者补充"页上，终于有人写了。不是纪承钧，不是钟守玄，不是沈照痕——是那个初到玄枢时带着空白记录本，后来学会独立观测，又帮钟守玄给 runbook 写后来者注的人。现在他写的不是注，是补充。不是"这里我不懂"——是"这里 runbook 不够，我扩展了"。

阶梯之上——不是"后来者独立了"的终点。是"后来者开始为下一个后来者铺路"的起点。
