# 驭器卷 · 第32章 · CMake 地狱

纪承钧试图修改玄枢的构建系统，是从一行 include 开始的。

include 本身很简单——就是把一个构建模块的路径从旧的位置改到新的位置。旧的位置已经废弃了两年，代码早就迁走了，只剩一个空目录。他以为这只是一次清扫——把不再被引用的路径从 CMakeLists.txt（`构建配置文件`）里删掉。像收拾旧机柜——把不用的东西清出去。

他改了一行。

然后玄枢编译失败了。

不是在改了 include 的那个模块失败。是在三个完全无关的地方。一个和旧适配层相关的构建目标爆了未定义引用（`undefined reference`）。一个外部接口的包装层找不到它的依赖头文件（`header file`）。还有一个——最诡异——在链接阶段（`link stage`）出了一个他从未见过的错误：重复符号定义（`duplicate symbol`），但两个符号——在不同的目标文件里——不应该同时出现。

"我只改了一行 include。"他盯着石镜上那串编译错误。

钟守玄路过他身后。看了一眼错误。没有停。

"CMake 地狱。"他说。像在说一个老朋友的名字。

· · ·

三个时辰后，陆踏痕拿着一个旧笔记本走进来。

那个本子是他在旧构建区最底层翻到的——不是卫千枢的，不是钟守玄的。封面上没有名字，只有一个日期——七年前。里面记的不是代码。是问号。几十条问号——每一条都是一个人对着玄枢的 CMake 构建树发问的记录。"为什么这里的 include 路径要用变量？——变量在哪定义的？" "这个条件判断——在什么平台上为真？" "此处的目标依赖是否还在使用？"——每条问号旁边有一个日期和一个名字的首字母。有些问号旁边被人用红笔写了回答。有些没有人回答。

"这个本子——是一个前辈的。他在试图追踪 CMake 隐式依赖（`implicit dependency`）的时候疯了。"

"不是疯了。"纪承钧接过那个本子。"是发现——你追踪的每一个变量——都有可能——在某一个你从未见过的 .cmake 文件里——被悄悄地改了。"

他把本子翻到最后一页。那一页只有一行字。字迹比前面都深——像是写的人在最后一刻决定放弃描述，只写结论：

"在玄枢追 CMake 变量——就像在旧河里捞一条你没有线索引的鱼。你永远不知道——你搜不到的变量——不在源码里。在环境里。——佚名"

· · ·

那天深夜，陆踏痕发现了那个幽灵变量。

他花了三个时辰——从那个"不应该出现的重复符号"开始，一步一步往上游追溯。先是链接器的详细日志（`verbose linker log`）——找出两个符号的真正来源。然后是两个符号对应的编译单元——发现它们都应该被一个条件分支排除——但分支没有生效。CMakeLists.txt 里写着 `if("$ENV{LEGACY_COMPAT}" STREQUAL "1")`，读取的是构建进程的环境值；`LEGACY_COMPAT` 的设置却在整个源码库里都搜不到。

不在代码里。不在 CMake 文件里。不在任何 .cmake 模块里。

"那它在哪？"

陆踏痕回到旧构建区。翻开他之前收集的所有旧构建日志。在其中一台最老的旧构建机器的日志里——那台机器的启动脚本（`shell profile`）的第 47 行——有一行：

`export LEGACY_COMPAT=1  # 不要动这个值——不知道为什么但是动了会坏。——然后是一年前的日期`

那行注释是一年前加的。但 `LEGACY_COMPAT=1` 这个值——可能已经存在了更久。某个已不可考的凌晨，有人为了临时解决环境差异，在启动脚本里加了这一行 export（`导出环境变量`）。之后，构建主机从这台机器的镜像复制而来，连登录环境也一并继承。再往后，这个环境变量成了构建系统里一个"刚好存在"的前提：没人知道它最初为何设为 1，却知道去掉它会走向另一条条件分支，而那条分支如今已经无法正常编译。

"这不只是构建系统的 bug。"陆踏痕说。"这是某个人在特定时间、特定机器上做的决定，后来经由镜像复制，变成了构建的前提。做决定的人已经不在了，只留下启动脚本第 47 行的幽灵，替构建选中那条能工作的分支。没人知道最初写下它的人，还记不记得那个凌晨。"

· · ·

沈照痕是在第二天上午看到这个发现的。他正在整理观测日志，被纪承钧叫来看那个幽灵变量。他看了很久。然后说了六个字。

"工具升级了。方式没有。"

纪承钧看着他。

"CMake 支持模块化、条件判断和变量作用域。如果从一开始就按它的方式组织构建，谁需要变量，谁就在清楚的作用域里定义它。可玄枢最初用 shell 脚本，后来换成 Makefile，再后来才迁到 CMake。每次升级都只把旧用法翻译成新语法，没有重新梳理来源。所以玄枢的 CMake 像穿着 CMake 外衣的 Makefile、shell 脚本，甚至是凌晨写下的 export——一层层沉积成的活化石。"

"所以改一行 include——会炸。"

"会炸。因为那一行 include——不只是一行。它可能还带进了旧变量和目标定义，是十几年迁移链上的一个结。你解开它，别处依赖的东西就可能消失。你只看见自己解开的这一结，整张网却都在动。"

纪承钧看着石镜上那串编译错误。不修了。不是放弃。是承认——修一行 include——需要的不是一行修改。是理解整个网络的每一个结。而那个网络——在任何人脑子里——都是不完整的。不是一个人能完成的工作。

他拿起笔——在玄枢依赖图上——在构建系统的那一区——标注了一行：

"CMake 地狱——发现：构建系统不是一次设计出来的，而是在迁移中层层沉积。旧变量通过构建主机的环境继承，源头不可考。变更前提：先追踪受影响的变量、目标和 include 路径。——前提：以上分析基于一次失败的 include 修改，尚不能代表所有构建入口。——后来者——如果你试图修改 CMakeLists.txt，先查清启动脚本第 47 行的幽灵。"
